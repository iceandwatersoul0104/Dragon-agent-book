# 第 35 章 成本与性能优化

## 一、本章要解决的问题

月底账单出来，是预算的三倍。运营拿着账单来问"钱花在哪了"，工程师加了一行统计才发现：一个客服 Agent 的平均任务走 12 步，每一步都把完整历史、检索结果和上一轮工具返回重新发给模型。第 1 步的输入是 900 token，第 12 步的输入是 1.4 万 token。总量不是线性增长的，是步数的平方。

同一天，延迟从 8 秒涨到 40 秒。原因是 Agent 为了查一个订单，串行调了三个接口：查用户、查订单、查物流，每个 2~10 秒，其中前两个其实互不依赖。

这两件事的共同点：**在 Agent 系统里，成本和延迟不是"用得省一点"的优化项，而是和模型选型同层级的架构决策。** 它们不进需求文档，却决定这套系统能不能长期跑下去——账单按月翻倍，而用户对 40 秒的等待耐心是有限的。

本章要建立三样东西：一套能算清钱花在哪的成本模型；五个可操作的手段（提示缓存、模型路由、结果复用、上下文裁剪、延迟优化）各自的原理、收益与副作用；以及它们之间的冲突——省钱与降延迟不是同一件事，有时候还互相打架。

## 二、原理：机制拆解

### 2.1 成本模型：一次任务的钱花在哪

一次任务的 token 流向是这样的：

```
  系统提示 + 工具定义 + few-shot  ──┐  ← 每轮重发，可被缓存
                                    │
  历史对话（逐轮增长）              ├──► 输入 token ──┐
  检索结果                          │                │
  上一轮工具返回                    ┘                ├──► 费用
                                                      │
  模型输出（决定下一步）  ──────────────────────────► 输出 token
                                                      │
  工具参数 ──► 工具执行 ──► 工具返回（进下一轮输入） ─┘
                                    ▲
                                    └──► 工具往返：结果要进下一轮输入，等于再计一次输入
```

四条要记住的：

1. **输入是 O(n²)**。n 步任务每步重发全部历史，输入总量随步数平方增长。10 步就是 100 倍于单步。这条决定了后面所有优化的方向。
2. **工具往返要计两次**。工具输出既产生了一次工具执行，又作为下一轮的输入被重新计费。工具返回体越大、轮次越多，这笔账越贵。
3. **系统提示和工具定义是"固定开销"**。它们在每一轮都重发，步数越多累计越贵，但内容不变——所以它是缓存收益最高的部分。
4. **输出的单价并不比输入低。** 团队常以为成本堆在长 prompt 上，其实输出 token 单价更高，而"让模型少说话"往往直接掉质量。

总费用 = 输入 token × 输入单价 + 输出 token × 输出单价（缓存命中的部分按更低的缓存价计）。因此只有三个杠杆：**减少 token 数、提高缓存命中率、降低单价**。

### 2.2 提示缓存（prompt caching）

**原理。** 主流模型服务都提供前缀缓存：服务端保存一段"前缀"的 KV 缓存或等价物，当后续请求的 token 前缀与已存前缀逐 token 相同时，命中部分按更低的缓存价计费。触发方式分两种：显式标记（Anthropic 用 `cache_control` 标出稳定前缀的末尾）与自动触发（OpenAI 在前缀超过 1024 token 时自动缓存）。

**计费口径。** 以各家公开的价目为例：Anthropic 写缓存按普通输入价的 1.25 倍（5 分钟 TTL）或 2 倍（1 小时 TTL）计，命中按 0.1 倍计；OpenAI 的自动缓存没有写入成本，命中按 5 折计，默认 TTL 约 1 小时（随模型而异）。**倍数与 TTL 会随模型和时间调整，接入前以当期官方价目为准。**

**什么时候缓存划算。** 按 1.25 倍写入、0.1 倍读取算，读两次才追平不缓存的 2 倍——也就是说**一次写入至少要摊到 1.5 次读取才不亏**。写完没人读，等于白付 25% 的溢价。调用间隔一旦超过 TTL，命中率会塌掉，你付了写入溢价却没拿到读取折扣。

**前缀稳定性设计。** 缓存按前缀匹配，所以内容顺序必须是"稳定的东西在前，变化的东西在后"：

| 位置 | 内容 | 是否稳定 |
|---|---|---|
| 1 | 系统提示 | 稳定 |
| 2 | 工具定义（顺序固定） | 稳定 |
| 3 | few-shot 示例 | 稳定 |
| 4 | 历史对话 | 每轮追加，前缀仍稳定 |
| 5 | 本轮问题与检索结果 | 每轮变化 |

**不要把动态内容放进前缀**：当前时间戳、用户名、会话 ID、随机数、动态拼装的检索结果。一旦这些混进系统提示，第 1 个 token 之后全部失效，缓存命中率直接归零。正确做法是把它们移到末尾，或者做成"稳定占位符 + 末尾注入"。

**命中率怎么测。** 服务端返回里会分别给出缓存读与缓存写的 token 数：Anthropic 是 `cache_creation_input_tokens` 与 `cache_read_input_tokens`，OpenAI 是 `usage.cached_tokens`。命中率 = 缓存读 / (缓存读 + 缓存写)。要按模型、按会话、按调用点分别看——整体命中率高，可能只是某一个长系统提示在撑。

**失效陷阱**：前缀被改一个字符就全段失效；TTL 过期；工具定义新增一个工具，等于改了前缀；把每轮变化的字段写进了系统提示；多 Agent 场景下不同 Agent 的前缀拼接顺序不一致。

### 2.3 模型路由（model routing）

**按难度分级。** 意图分类、字段抽取、格式转换这类任务，小模型就够用；多步推理、长文综合、复杂代码修改，值得上大模型。

**级联（cascading）。** 让小模型先试，用一个便宜的判据决定是否升级：

- 格式与 schema 校验失败 → 升级；
- 置信度低或自检不通过 → 升级；
- 输出长度异常、包含"不确定"标记 → 升级；
- 关键事实缺失（像第 34 章那样用关键事实清单检查）→ 升级。

级联把大部分常规流量压到小模型，同时把难题交给大模型。但它的代价是**尾部延迟和尾部成本**：升级的那批任务，要付两次钱、等两次。

**质量-成本帕累托。** 把模型画到"质量 × 单价"的平面上，你会得到一条帕累托前沿（同等质量下最便宜的组合）。路由的目标不是选最便宜的那个点，而是在前沿上按任务难度取不同的点：简单任务取左下角，难题取右上角。

### 2.4 结果复用与语义缓存（semantic cache）

**精确缓存**：输入、环境状态、模型版本、提示词版本、工具版本、知识库版本完全一致时，直接复用上次结果。key 必须包含所有这些版本号，否则一改提示词还在发旧答案。

**语义缓存**：把问题向量化，相似度超阈值就复用旧答案。它省得更多，但风险大得多，因为"相似"不等于"等价"。

**适用边界**（四条同时成立才可用）：

1. 只读、不产生副作用；
2. 幂等，重复执行结果一致；
3. 不依赖会话历史或用户身份；
4. 时效性不敏感，或有明确的 TTL。

**风险**：

- **上下文依赖**：同一个问题在不同会话、不同用户权限下，答案不同。语义缓存看不见这个差异。
- **过期**：知识库更新了，缓存还在发旧答案。
- **错误固化**：一次错误答案被缓存后，后面所有相似问题都错，而且更难发现——因为它看起来是"命中缓存"而不是"模型答错"。
- **污染面扩大**：把有副作用的动作（写库、发消息）缓存下来，等于把一次副作用重放成多次。

所以：**写操作永远不要进语义缓存**；有副作用的工具要在 key 里带上副作用标识（谁、什么对象、什么状态），或者干脆不缓存。

### 2.5 延迟优化

延迟有两个成分：**首 token 延迟（TTFT）** 和 **总时长**。用户对两者的感知完全不同——界面上的骨架屏能掩盖 TTFT，但掩盖不了总时长。

- **流式（streaming）**：不省 token，只改善感知延迟，让用户先看到字。适合对话，不适合批量任务（流式反而增加开销）。
- **并行工具调用**：互不依赖的工具一次并发发出，延迟从"求和"变成"取最大值"。前提是确认无依赖、无副作用冲突；并行会产生竞态，写操作要串行。
- **并行子任务**：把可以拆开的子问题并发跑，代价是 token 总量上升（每个子任务都要带自己的上下文）。
- **投机解码（speculative decoding）**：用小模型起草若干 token，大模型并行验证，输出分布与直接用大模型等价，是"无损加速"。它省的是时间不是 token，而且要求两个模型架构与词表兼容，通用性有限。
- **异步化**：把"等用户回复"、"等长任务跑完"从请求链路里摘出去，改成事件驱动——Agent 结束这一轮，等外部事件触发下一轮。请求不再被挂住。
- **提示缓存同时降延迟**：命中缓存省掉了重复处理前缀的计算。

```
串行（模型 1.2s，工具 a/b/c 各 2s，工具间无依赖）：
  [模型 1.2s][工具 a 2s][模型 0.8s][工具 b 2s][工具 c 2s][模型 1s]  → 9s

并行（a/b/c 同时发）：
  [模型 1.2s][a/b/c 并行 2s][模型 1s]                            → 4.2s
```

## 三、为什么这样设计：取舍与失效条件

1. **不要为了省钱把质量底线一起砍掉。** 分类、抽取、改写用小模型没问题；复杂推理用小模型是埋雷——它省下的钱会在错误后果里加倍还回来。先定质量底线，再谈路由。
2. **级联会拉长尾延迟。** 需要升级的那批任务，成本和延迟都是双倍。如果你的场景对延迟敏感（P95 有 SLA），级联的适用性要重新算。
3. **语义缓存在对话式 Agent 上极易出错。** "我上次问过这个"的语境里，同一问题的答案往往依赖上文。**对话场景默认不要开语义缓存**，精确缓存都更值得先做。
4. **前缀稳定设计会让提示词变难写。** 把时间、用户名从系统提示挪到末尾，提示词组织上更别扭，个性化质量也可能受损。这是真实成本，要算进账。
5. **并行工具调用在有依赖时会引入竞态。** "先查订单再查物流"看着能并行，实际并行后拿到的是过期或半成品数据。副作用操作尤其不能并发。
6. **投机解码不是通用方案。** 需要草稿模型与目标模型兼容，批量场景收益也不明显。它是特定部署形态下的优化，不该写进通用架构。
7. **流式不省 token，只改善感知。** 用流式掩盖真实变慢是自欺——用户等待的是答案，不是动画。
8. **别用"每次调用成本"做考核。** 多绕圈的系统单次调用更便宜，但每次成功任务成本更高。口径必须是"每次成功任务成本"（见第 33 章）。
9. **高缓存命中率也可能没用。** 命中率被一段没人看的长系统提示撑起来，实际短前缀部分仍然全价。命中率要配合"缓存 token 占总输入的比例"一起看。

## 四、动手：最小可实现

参考实现 `code/ch35-cost-performance/`，纯标准库，不需要 API Key 就能跑通。它是一个"成本-延迟实验室"，把上面每一条变成可测量的开关：

1. **成本模型**：把一次任务拆成输入 / 输出 / 缓存读 / 缓存写 / 工具往返五项，用本地示意价目表算出钱；
2. **提示缓存模拟器**：按前缀哈希匹配 + TTL，测命中率，并演示"动态内容混进前缀 → 命中率归零"；
3. **模型路由**：按难度分级 + 级联（校验失败升级），统计各级占比与成本；
4. **语义缓存**：纯标准库实现的字符 bag-of-words 余弦相似度，演示"近似命中"与"上下文指纹不同则不命中"；
5. **延迟模型**：流式只改善 TTFT、工具并行把求和变取最大值；
6. **对照实验**：同一批任务跑"基线"与"优化后"，输出成本与延迟对比。

```python
# 上下文裁剪把输入从 O(n^2) 拉回 O(n)（节选自 simulate_once，全文见 code/ch35-cost-performance/main.py）
# --- 历史：不裁剪时随步数线性增长，叠加后是平方级 ---
history_tokens = (step + 1) * HISTORY_PER_STEP
if cfg.trim:
    history_tokens = SUMMARY_TOKENS + min(history_tokens, TRIM_TURNS * HISTORY_PER_STEP)
usage.input_tokens += history_tokens
```

## 五、开源实现对照

本章没有"一个框架解决全部问题"的开源实现，成本优化是各家 SDK 里的零散能力。值得对照的是这些项目提供了什么：

- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python ）：模型、工具、交接、护栏与追踪拼装轻量多 Agent 工作流；它的追踪能直接回答"这次任务花了多少 token、几步、哪个工具最贵"，是成本优化的观测前提。
- **Langfuse**（MIT Expat，`ee/` 等目录按 `ee/LICENSE` 另计，https://github.com/langfuse/langfuse ）：按 trace / observation 统计 token 与成本，能把"最贵的十个任务"排出来。
- **OpenLLMetry**（Apache-2.0，https://github.com/traceloop/openllmetry ）：把 LLM 调用转成 OpenTelemetry span，token 与延迟进时序库后可以做成本看板。
- **LangSmith SDK**（MIT，https://github.com/langchain-ai/langsmith-python ）：追踪与数据集一体，成本指标可以按数据集切分。

对照的重点不是"用哪个框架省钱"，而是**先能看见成本，再谈优化**。没有逐任务的 token 与延迟分解，你只能整体降配，而整体降配会同时伤害质量。

## 六、坑与检查清单

**成本可见性**

- [ ] 每次任务都有 token 分解：输入 / 输出 / 缓存读 / 缓存写 / 工具往返
- [ ] 成本口径是"每次成功任务成本"，不是"每次调用成本"
- [ ] 能排出"最贵的十个任务"，并下钻到具体是哪一步、哪个工具
- [ ] 输入 token 随步数的增长曲线可查（看是不是在平方增长）

**提示缓存**

- [ ] 系统提示、工具定义、few-shot 排在最前，动态内容一律靠后
- [ ] 前缀里没有时间戳、用户名、会话 ID、随机数
- [ ] 工具定义顺序固定，新增工具等于改前缀，要重测命中率
- [ ] 缓存命中率与"缓存 token 占比"一起看，不只看命中率
- [ ] 知道 TTL 是多少，长会话会中途失效

**模型路由**

- [ ] 小模型只用在有明确判据的任务类型上
- [ ] 升级判据是可验证的（schema 校验、关键事实缺失、置信度）
- [ ] 单独统计升级任务的占比与它们贡献的成本
- [ ] 质量基线在小模型上也测过，没有靠感觉

**结果复用**

- [ ] 缓存 key 包含模型、提示词、工具、知识库版本
- [ ] 语义缓存只用在只读、幂等、无上下文依赖的任务上
- [ ] 写操作与有副作用的动作不进任何缓存
- [ ] 缓存有 TTL 与一键清空（发现错误答案时能立刻止血）

**延迟**

- [ ] 同时看 TTFT 与总时长，不只看其中一个
- [ ] 无依赖的工具并发执行，有依赖的串行
- [ ] 副作用操作不并发（避免竞态与重复写）
- [ ] 长等待走异步/事件驱动，不占着请求不放
- [ ] 批量任务不开流式（只增加开销不改善体验）

## 七、小结与延伸阅读

1. **先建成本模型，再谈优化**：输入是 O(n²)、工具往返计两次、输出单价更高，这三条决定了钱花在哪。
2. **三个杠杆**：减少 token、提高缓存命中、降低单价。缓存靠前缀稳定性，不靠运气。
3. **路由是帕累托取点，不是降配**：简单任务用小模型，难题留给大模型，级联的尾延迟要算进账。
4. **缓存的边界是只读、幂等、无上下文依赖**：对话场景默认别开语义缓存，写操作永远别缓存。
5. **延迟和成本会互相打架**：并行与投机解码花时间换时间，流式只改善感知。并行工具与裁剪常常同时改善两者，是优先做的两项。
