# 第 34 章 评测体系：基准、任务集、LLM-as-Judge 与回归测试

## 一、本章要解决的问题

上个季度换了模型、动了两版提示词、给工具加了两个参数。线上客服 Agent 的用户投诉变多了，但没人能说清到底哪里变差——"感觉不太行"、"是不是新模型话术太油"、"上周不是这样的"。三个人的主观印象互相矛盾，最后的决策依据是一张点赞率截图。

这类争论的根源不是没人关心质量，而是没有一把能当尺子的东西。评测要回答三个具体问题：

1. **这次改动让哪些任务变好了、哪些变坏了？** 不是平均分掉了半分，而是"退款咨询类从 18/20 掉到 15/20，新增的三个失败全是多轮追问场景"。
2. **换模型值不值？** 质量提升多少、成本涨多少、延迟代价多大，三者放一起比。
3. **现在能不能上线？** 上一个版本的回归有没有被打破。

公开榜单一个都回答不了，它只能回答第四个问题：在别人写的任务上，平均比另一个系统高多少。

评测体系要自己建，代价也不小：要有任务集、判定器、可复现的运行环境，还要有人持续维护。本章讲清楚这三样怎么搭、坑在哪、哪些环节可以省。

## 二、原理：机制拆解

### 2.1 评测的三段式结构

```
   ┌────────────────┐    任务描述     ┌────────────────┐   轨迹 + 产物   ┌────────────────┐
   │   任务集       │ ─────────────► │   被测 Agent    │ ─────────────► │    判定器      │
   │ 环境 + 黄金答案 │                 │ 模型/提示词/工具 │                │ 断言 / rubric  │
   └────────────────┘                 └────────────────┘                └───────┬────────┘
                                                                                 │
              通过率 / 分层通过率 / 步数 / 成本 / 失败分布 ◄──────────────────────┘
                                          │
                                          └──► 基线对比 ──► CI 门禁 / 放行决策
```

三个环节必须**彼此独立**：任务集是刺激物（环境、任务描述、黄金答案），被测系统是被试（模型 + 提示词 + 工具 + 上下文策略），判定器是裁判（程序化断言最强，规则匹配次之，LLM Judge 再次，人工最贵但最准）。

最常见的架构错误是**把判定器塞进被测系统**——让 Agent 自己判断"我做对了吗"。它会给自己打高分，而且高分不携带任何信息。

判定器强度直接决定评测有效性：能用断言判的绝不用模型判（代码是否通过、数据库状态是否正确、订单号是否出现在结果里），只有开放式表达才交给 LLM Judge。

### 2.2 主流基准逐个剖析

公开基准不是没用，但必须知道它们各自测的是哪一段能力。

| 基准 | 测什么 | 不测什么 |
|---|---|---|
| **SWE-bench** | 真实 GitHub issue 的修复成功率 | 需求模糊性、PR 评审、部署、非代码任务 |
| **GAIA** | 工具增强型通用助理的多级问答，含多模态 | 长时程、真实副作用、业务系统集成 |
| **WebArena** | 可复现网站副本上的浏览、下单等自主任务 | 视觉定位精度、生产数据、真实商业站点 |
| **BFCL** | 函数与工具调用准确性、多轮 agentic | 任务完成度、业务价值、跨系统副作用 |
| **tau-bench** | 模拟用户 + 领域规则下的多轮客服 | 真实用户情绪、跨域知识、开放式沟通 |
| **OSWorld** | 真实桌面环境的多模态 GUI 操作 | 长程规划、跨应用一致性、生产环境 |
| **MCP-Bench** | 同模型同配置下对比 MCP 服务器质量 | 跨模型泛化、端到端业务价值 |
| **AgentBench** | 数据库、OS、知识图谱、家务、网购等多环境交互 | 当下工具链与真实业务形态 |

读表的正确姿势：**"测什么"决定它能不能当方向性体检，"不测什么"决定它不能用来证明什么。** SWE-bench 能告诉你改代码能力行不行，不能告诉你理解业务行不行；BFCL 能告诉你工具协议接对没有，不能告诉你任务有没有完成。

另有三点值得单说：SWE-bench Verified 是经人工校验的 500 条子集，比混着歧义 issue 的全集更适合横向比较；GAIA 受限分发是社区对污染的对冲——评测集一旦全网公开，训练语料里大概率已有它；tau-bench 提出的 pass^k（k 次独立试验全部成功的比例）衡量可靠性——按各次独立的假设，单次成功率八成的系统连续三次全对只有五成出头。MCP-Bench 的横向对比只在同模型同配置下成立。

### 2.3 基准饱和、污染与"分数 ≠ 能力"

三个问题叠在一起：

**饱和。** 头部系统在几百条任务的集合上分差往往只有几个百分点，而任务本身有随机性——同一个 Agent 跑两遍可能不同（工具超时、检索顺序、采样）。这个量级的差距落在噪声里，榜单排序基本不可信。

**污染。** 评测集公开在 GitHub 和 HuggingFace 上，训练语料几乎必然扫过。污染的后果不是分数虚高，而是**分数不再有区分度**：所有系统都在同一批"见过题的题"上刷分。

**更根本的是三层差距**：**任务分布**不同（你的工单有历史、有上下文、有话术规范，基准的是虚构的）；**工具**不同（你的工具是内部 API，有自己的错误码与幂等性，基准工具是理想化的）；**成功定义**不同（基准的成功是终局状态判定，你的成功可能是"用户没再追问第二次"）。

所以公开榜单的正确用法是**方向性体检**：判断"我们在通用助理能力上是不是差得离谱"；**上线判据必须来自自建任务集**。
### 2.4 自建任务集：四个设计维度

**规模。** 起步 100~300 条：少于 100 条噪声压不住，多于 500 条维护成本先压垮你。关键路径每类至少 20 条，才谈得上"这一类稳不稳定"。

**覆盖矩阵。** 按维度铺格子，而不是随手攒题：

- 任务类型：单轮、多轮追问、工具调用、检索、创作、拒绝类；
- 环境状态：空数据 / 脏数据 / 依赖不可用 / 权限不足；
- 难度分层：易 / 中 / 难 / 对抗；
- **失败模式**：曾经出错的问题类型、触发过事故的请求、用户最常投诉的场景。

最后一行最值钱也最容易被漏。正常任务谁都会写，把"模型以前栽过的地方"固化成用例，才是评测集的护城河。

**难度分层要有判据**，不能靠拍脑袋：

| 层级 | 判据示例 |
|---|---|
| 易 | 单轮、单一工具、答案在上下文里 |
| 中 | 多轮、需要 2 个以上工具或检索、答案需要合并 |
| 难 | 信息分散在多处、有干扰信息、需遵循业务规则 |
| 对抗 | 表述有歧义或带诱导、要求与常识冲突、工具返回误导性内容 |

**黄金答案怎么构造**。不要标"标准答案字符串"，要标**验收条件**：可执行任务用断言（退出码、数据库最终状态、产物结构、关键字段值）；开放式任务用 rubric（维度 + 权重）加关键事实清单。一条任务的标准答案应该长这样：*"必须包含订单号；必须说明退款到账时间；不得承诺具体到账日期"*。

**维护比构造更难**。黄金答案会过期：页面改了、接口参数变了、话术规范更新了。每条任务要带"环境版本"与"最后验证时间"，定期重跑，失效的要么重标要么删。**过期的黄金答案比没有更糟**——它会把好系统判成错。评测集也要版本化，改动留 diff。

### 2.5 LLM-as-Judge 的偏差与缓解

LLM Judge 便宜、可扩展，但它的判断有系统性偏差，方向是稳定的：

| 偏差 | 表现 | 缓解 |
|---|---|---|
| **位置偏差** | 同一对答案调换顺序，结论就变 | 交换位置各判一次取一致；不一致的送人工 |
| **长度偏好** | 更长、更结构化的答案更容易得高分，哪怕信息没多 | rubric 明确"长度不加分"；做长度匹配对照 |
| **自偏好** | judge 与被评系统同源时倾向给高分 | 用不同厂商/系列的模型当 judge |
| **格式偏好** | Markdown、列表、客套话被当成"更专业" | rubric 把格式排除在评分维度外 |
| **尺度漂移** | 打 1~10 分时整体偏松或偏紧 | 用二元/少档位判定替代连续打分 |

还有两个更"工程"的坑：**判据漂移**（judge 自己理解 rubric 与你不同）和**奖励 hacking**（被测系统学会迎合 judge，比如多写客套话、多列要点）。

缓解手段按性价比排序：

1. **判据先行**：rubric 先写死，judge 只负责套用，不许自由发挥；
2. **二元判定优于 1~10 分**：少档位、少尺度，稳定性更好；
3. **位置交换 + 取一致**：贵一倍，但能直接量化 judge 的不稳定率；
4. **多 judge 投票 + 人工校准**：三个模型各判一次取多数，分歧样本进人工；再定期抽 100~200 条人工标注算一致率，低于阈值就改 rubric。

诚实边界：**judge 只能替代一部分人工**，上线放行、安全相关这类决策必须保留人工抽检。

### 2.6 把评测接进 CI

三层结构，触发时机与预算都不同：

| 层级 | 内容 | 触发 | 耗时量级 |
|---|---|---|---|
| **确定性检查** | 输出格式校验、工具 schema 校验、提示词契约、结构化输出快照、断言级单元用例 | 每次提交 | 秒级 |
| **抽样回归** | 固定随机种子上跑 30~50 条固定任务，看关键 SLI 是否回归 | 每次合并/发版 | 分钟级 |
| **全量评测** | 全部任务、多次采样、judge 全开 | nightly 或发版前 | 小时级、烧钱 |

**版本化与基线对比（baseline diff）**是回归测试的核心。每次评测产出一个快照：模型版本、提示词版本、任务集版本、judge 版本、通过率、步数分布、成本、失败用例清单。和基线比的时候，不要只看平均分，要看**具体哪些任务从通过变成不通过**——那才是能直接派活的清单。每个指标设回归阈值，由业务容忍度定；基线要能复现，四个版本号缺一不可。

**门禁的作用是拦住回归，不是评价团队**；太严会让人去改评测集而不是改系统，评测集一旦被"改到能过"就彻底失效了。

## 三、为什么这样设计：取舍与失效条件

1. **公开基准是体检，不是判决。** 把榜单当上线依据是最贵的错误——上线判据只能来自自建任务集。
2. **任务集不要一上来就做大。** 300 条维护得动的任务集，比 3000 条烂尾的任务集有用得多。烂尾的集合会持续给出错误信号，比没有集合更糟。
3. **黄金答案不要写成标准答案字符串。** 开放题写标准句子等于把评测变成字符串匹配，既测不出能力，也会逼着系统去背句子。
4. **judge 只能是"部分替代人工"。** 它不能替代"这条要不要放行"的决策；把 judge 当权威，是把不稳定的判断规模化。
5. **位置交换让成本翻倍，多 judge 投票也不便宜。** 前者对高频短任务的评测值得，对跑一次要几小时的工作流不划算；后者意味着三倍推理成本。对高频评测做位置交换，对边界分数的样本才启用多 judge。
6. **门禁不是越严越好。** 严到让团队难受，就会出现"改评测集"和"跳过 CI"两种绕过。阈值要卡在"真的会影响用户"那一档。
7. **评测集会过拟合。** 针对评测集调优的任务集，线上不一定涨——尤其是 judge 可被迎合时。必须留一部分**不参与调优的隐藏集**定期跑。
8. **不要把评测分数当 KPI 考核团队。** 一旦分数进了绩效，人会优化分数而不是优化系统。评测分应该触发行动，不该触发奖惩。

## 四、动手：最小可实现

参考实现 `code/ch34-evaluation/`，纯标准库，不需要 API Key 就能跑通。它包含一个能真正演示"评测怎么用"的最小实现：

1. **任务集**：6 条任务，覆盖三个难度层，每条带环境、断言式黄金答案、关键事实清单、标签；
2. **被测系统**：mock Agent 会按任务难度给出不同质量的答案；`--live` 用真实 API 作答；
3. **判定器**：程序化断言（关键事实覆盖）+ 一个**可控偏差的 mock Judge**，能开关位置偏差、长度偏好、自偏好；
4. **偏差演示**：同一答案交换顺序判两次，统计 judge 的不稳定率，再演示"位置交换取一致"如何压低它；
5. **CI 门禁**：与 `baseline.json` 对比，通过率跌幅超阈值则退出码非 0，并列出回归的任务清单。

```python
# 关键事实判定（节选，全文见 code/ch34-evaluation/main.py）
def fact_coverage(answer: str, key_facts: List[str]) -> Tuple[List[str], List[str]]:
    """黄金答案不写成标准句子，而是"必须包含的信息点"清单。"""
    low = answer.lower()
    hit = [f for f in key_facts if f.lower() in low]
    missing = [f for f in key_facts if f.lower() not in low]
    return hit, missing


# 位置偏差演示：同一份答案，换个顺序判分可能不同
def judge_with_swap(judge: MockJudge, task: Task, answer: str) -> Dict[str, Any]:
    first = judge.score(task, answer)
    second = judge.score(task, answer, swapped=True)
    stable = first["pass"] == second["pass"]
    return {
        "first": first,
        "second": second,
        "stable": stable,
        # 缓解手段：位置交换后取严（两次都通过才算通过）
        "strict_pass": first["pass"] and second["pass"],
    }
```

## 六、坑与检查清单

**任务集**

- [ ] 任务来自真实工单/真实日志，不是拍脑袋写的
- [ ] 覆盖矩阵包含"失败模式"维度：历史事故与投诉已成任务
- [ ] 每个难度层有明确判据，不是靠感觉分
- [ ] 黄金答案写成验收条件与关键事实，不是标准答案句子
- [ ] 每条任务带环境版本与最后验证时间
- [ ] 任务集有版本号，改动留 diff
- [ ] 留了一部分隐藏集，不参与调优
- [ ] 判定器独立于被测系统

**判定器**

- [ ] 能用断言判的没有交给 LLM Judge
- [ ] rubric 先写死，judge 只负责套用
- [ ] 用二元/少档位判定，不打 1~10 分
- [ ] 开启位置交换，统计并跟踪 judge 不稳定率
- [ ] judge 与被测系统不同源，或已评估自偏好影响
- [ ] 有 100~200 条人工标注做定期校准，一致率有记录
- [ ] 判分时去掉了系统名称与模型标识

**CI 接入**

- [ ] 提交级跑确定性检查（格式、schema、快照）
- [ ] 发版前跑固定任务集的抽样回归
- [ ] 评测结果快照包含模型/提示词/任务集/judge 四个版本
- [ ] 基线对比能列出具体回归的任务，不只是平均分
- [ ] 每个指标有明确的回归阈值
- [ ] 评测预算可控，不会因为烧钱被跳过

**治理**

- [ ] 评测分不直接进绩效
- [ ] 有人负责维护任务集，过期条目有清理流程
- [ ] 上线前的高风险判定保留人工抽检
- [ ] judge 被 hack 过（答案变长、变客套）的迹象有检查
## 七、小结与延伸阅读

1. **评测回答四个问题**：哪些任务变好了、换模型值不值、能不能上线、是不是系统性短板。公开榜单只答得上最后一个。
2. **任务集是核心资产**，黄金答案要写成验收条件，判据先行，隐藏集防过拟合。
3. **judge 有系统性偏差**（位置、长度、自偏好、格式、尺度），用判据固化 + 位置交换 + 多 judge + 人工校准压下去，但压不到零。
4. **CI 分三层**：提交级确定性检查、发版前抽样回归、nightly 全量；基线对比要列出具体回归任务，而不是只给平均分。
5. **评测集本身是代码**：要版本化、要测试、要有人维护。评测失效的常见原因不是没人跑，是跑不动了。
