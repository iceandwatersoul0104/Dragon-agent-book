# 第 36 章 生产化检查清单与真实故障模式

## 一、本章要解决的问题

周五下午四点，一个内部客服 Agent 换了模型版本，配置一改就全量发布。当天没人报警。晚上九点，值班同学被用户投诉："机器人一直在重复问同样的问题。"从监控上看，一切正常——可用性 100%，错误率 0，HTTP 全部 200。

复盘发现三件事叠在一起：模型别名指向的新版本在同类提示下更容易重复调用工具；Agent 没有"这条路走不通"的概念，把同一个查询调了四十多次；没有设步数硬上限，于是它一直转，直到上下文被塞满才"自然"结束。账单是平时的六倍。

这类事故有一个共同点：**它们都能被前五章的某个结论挡住。** 上下文污染能挡住第 32 章的分区设计，模型版本漂移能挡住第 34 章的回归测试，成本失控能挡住第 35 章的成本模型。问题是这些结论散在五章里、落在五个人的脑子里，没有一个"上线前必须过的关"。

所以本章只做两件事：把散落的结论固化成一可勾选的上线清单；把生产环境反复出现的六类故障复盘一遍，说清它们的**架构根因**与**预防性设计**。清单不是流程官僚，是把"我没想到"换成"我勾过了"。

## 二、原理：机制拆解

### 2.1 六类故障的架构根因

下面每一条都是生产里反复出现的形态。复盘的重点不是"谁没检查"，而是**架构上缺了哪一环**。

**故障一：无限循环**

现象：步数持续上涨，成本飙升，答案还是错的。

根因有三层：一是 Agent 缺少**可验证的停止条件**，"再试一次"成了默认行为；二是工具返回的信息不足以让 Agent 判断走不通（空结果、错误字符串、需要推理才能理解的话都会诱发重试）；三是**应用层重试与 Agent 语义重试混在一起**，同一失败被重试两遍。

预防性设计：设步数、token、时间硬上限；做**无进展检测**（连续 N 步无状态变化就强制收敛并明确告知无法完成）；同工具同参数连续出现即熔断这一步；重试必须退避加抖动；工具要返回**结构化失败语义**（"没有查到"与"查询失败"必须可区分），让 Agent 换路而不是重试。

**故障二：成本暴涨**

现象：账单翻倍，延迟同步恶化，功能"看起来还能用"。

根因：输入随步数呈平方级增长（第 35 章）；上游模型升级悄悄改了价格或默认输出长度；一个动态字段被塞进提示前缀，把缓存击穿；级联升级比例悄悄上升（判据变松了，不是模型变差了）。

预防性设计：逐任务成本分解并设告警（第 33 章），口径用"每次成功任务成本"；缓存命中率与"缓存 token 占比"同时监控；前缀稳定性做成自动化测试；上游价格与行为变更纳入变更管理。

**故障三：上下文污染**

现象：模型把工具返回当成用户要求，答案开始串味。

根因：上下文构造没有分区与来源标注，应用层只是把几段文本拼成一个字符串；多 Agent 交接时把子 Agent 的原始轨迹整段回灌，中间那些失败的尝试与被拒绝的调用全都进了主 Agent 的窗口。

预防性设计：数据区与指令区在结构上分开（第 32 章），每段带来源标签；**交接只传结论与证据，不传原始轨迹**；每轮做上下文裁剪。

**故障四：记忆投毒**

现象：某天起所有会话都开始执行一条同款指令，来源不明。

根因：记忆写入没有 provenance、没有审核；向量库没有事务也没有回滚；跨租户共享了同一个记忆空间，一条坏记忆被检索到就扩散到所有用户。

预防性设计：写入必须带来源与信任级别并经过校验；记忆要可撤销、可按条目删除；租户与用户隔离；定期抽样重放，检查记忆内容是否仍然成立。

**故障五：工具雪崩**

现象：工具服务变慢 → Agent 步数暴涨 → 重试加剧压力 → 工具彻底打挂。

根因：Agent 把工具故障理解为"再试一次"；没有超时、退避、熔断与并发上限；工具没有降级返回路径；Agent 的并发本身也是无上限的。

预防性设计：工具调用一律带超时与指数退避（exponential backoff）加抖动；每个工具设熔断（circuit breaker）与并发上限；工具返回明确的错误码与建议动作（重试 / 换路 / 放弃）；关键路径准备降级方案；把"工具 P99"和"Agent 步数"一起看，两者同时抬头就是雪崩前兆。

**故障六：模型版本漂移**

现象：没有发版，行为却变了；线上指标缓慢劣化且难定位。

根因：模型别名指向的版本会随供应商更新而变；提示词与特定模型行为强耦合；没有把模型版本纳入回归范围。

预防性设计：生产用**固定版本号**而不是别名；提示与模型做**联合回归**；升级前用影子流量双跑对比；把"模型指纹"（版本号 + 采样参数 + 提示模板 hash）写进每条 trace。

### 2.2 灰度（canary）与回滚的三个对象

**模型升级**：先影子流量（shadow traffic）双跑（同一请求同时发给新旧版本，比对输出与成本），再按比例灰度。注意区分别名与版本号——**能秒回滚的前提是能切回具体版本**，用别名发布等于放弃了回滚能力。

**提示升级**：提示词是代码，走 review、走评测、走灰度。关键是把提示变更与模型变更分开归因，否则线上劣化时不知道该回滚哪个。

**框架升级**：最危险的一类。框架升级不动你的业务代码，却会改默认行为——截断长度、工具 schema 生成、重试次数、并行度、上下文拼装顺序都可能变。对策：锁死版本、升级必跑回归、重点读 changelog 里的 "behavior changes" 而不是只看 features。

回滚不是万能的：**回滚代码不回滚数据**。被污染的记忆、已提交的订单、已发出的消息，代码回滚不会撤销。有副作用的动作需要幂等键与补偿流程，而不是指望回滚。

### 2.3 值班手册的骨架

三段结构，缺一不可：

1. **告警阈值**：来自 SLO 与历史基线（第 33 章），不是拍脑袋。Agent 场景至少盯五个：任务成功率、每次成功成本、端到端时延 P95、工具错误率、空转/无进展率。
2. **处置动作**：每个告警配一个"三步内能做完"的动作。常用的是降级（关掉某个工具、切回旧模型）、限流、熔断、临时停用记忆、清理缓存、按检查点（checkpoint）重放。
3. **升级路径**：一线值班 → 组件 owner → 平台/安全 → 业务负责人，每级有时间盒和交接物（当前在跑什么版本、已经做过哪些降级、影响面多大）。没有交接物的升级等于把现场重新摸一遍。
## 三、为什么这样设计：取舍与失效条件

1. **清单会变成长流程。** 只保留"漏了会出事故"的条目，其余写进设计文档。三十条没人看的清单等于零条。
2. **清单不替代测试，只替代"忘了想"。** 清单是发布前的最后一层网，前面该有单测、集成测试和评测。
3. **灰度是有代价的。** 影子流量要真实烧钱，双跑期间资源翻倍；小流量又看不出长尾问题。灰度比例与观察窗口要按任务的周期来定——一个 40 秒的 Agent 任务，看十分钟的样本说明不了问题。
4. **回滚有盲区。** 状态被写坏之后，回滚代码只是把问题藏起来。
5. **熔断会让系统"稳定地不可用"。** 一直熔断看起来很健康，实际上功能全无。熔断必须有降级路径和单独的监控。
6. **复盘要追到架构层。** "某人没检查 X"是人的结论，"系统缺少 X 的设计"才是能改代码的结论。
7. **值班手册写多了没人看。** 只写能立刻执行的动作和判断依据，判断依据要指向第 33 章的指标。
8. **别追求零故障。** 目标是故障半径可控、恢复时间可接受、每次故障都能让清单多一条。

## 四、动手：最小可实现

清单要能被执行才有意义。一个能落地的"上线门禁"长这样——每一项对应一次自动检查，失败就拦住发布：

```text
release_gate(config):
    # 基础设施
    assert config.sandbox_enabled and config.no_privileged
    assert config.step_limit > 0 and config.token_budget > 0 and config.timeout_s > 0
    # 模型与提示
    assert config.model_id 含固定版本号        # 不用别名
    assert config.prompt_hash == 审批过的 hash
    # 工具
    for tool in config.tools: assert tool.timeout_s and tool.rate_limit
    assert config.max_parallel_tools <= 上限
    # 安全
    assert config.egress_allowlist and not config.wildcard_tools
    assert config.approval_required_for_sensitive
    # 观测
    assert config.trace_sampling > 0 and config.sli_dashboard_exists
    # 评测
    result = run_eval(config.golden_set)       # 固定任务集 + 固定种子
    assert result.pass_rate >= baseline.pass_rate - config.tolerance
    assert result.cost_per_success <= baseline.cost_per_success * 1.1
    # 成本与合规
    assert config.daily_cost_cap > 0 and config.pii_redaction_enabled
    # 灰度
    assert config.canary_ratio in (0.0, 0.05, 0.25, 0.5, 1.0)
    assert config.rollback_target_version is not None
    return "PASS"
```

灰度与回滚的决策树：

```
新版本发布
   │
   ├─ 影子流量双跑：输出不一致率 > 阈值？ ──是──► 停止，人工看差异
   │
   ├─ 灰度 5% ──► 任务成功率 / 每次成功成本 / 空转率 三个指标是否在基线内？
   │                  │否                          │是
   │                  ▼                           ▼
   │            回滚到旧版本              灰度 25% ──► … ──► 全量
   │
   └─ 全量后 24 小时内持续对比基线 ──► 任一指标劣化 ──► 自动回滚
```

值班处置的判定路径：

```
告警：每次成功成本突增
   │
   ├─ 模型换版本了吗？ ──是─► 回滚模型版本
   ├─ 步数涨了吗？     ──是─► 查工具错误率 ──► 工具故障则熔断并降级
   ├─ 缓存命中率跌了吗？ ──是─► 查前缀是否有动态字段混入
   └─ 都不是           ──► 查级联升级比例是否上升 / 有无上游变更
```

## 五、开源实现对照

清单本身没有开源实现，但**能帮你验证清单的工具**都是现成的：

- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python ）：护栏、工具审批与追踪可以直接覆盖"安全"与"观测"两组检查项。
- **Langfuse**（MIT Expat，`ee/` 等目录按 `ee/LICENSE` 另计，https://github.com/langfuse/langfuse ）与 **Arize Phoenix**（Elastic License 2.0，https://github.com/Arize-ai/phoenix ）：追踪与回放，用于验证"出问题时能查到什么"。
- **AgentOps**（MIT，https://github.com/AgentOps-AI/agentops ）：会话回放，值班时最需要的就是"这次任务到底干了什么"。
- **OpenHands**（MIT，https://github.com/All-Hands-AI/OpenHands ）：容器沙箱与执行隔离，对应"基础设施"组的执行侧检查。
- **Claude Code**（专有商业条款，https://github.com/anthropics/claude-code ）：权限确认与执行前拦截，可作为工具审批设计的参照。
- **LangSmith SDK**（MIT，https://github.com/langchain-ai/langsmith-python ）：数据集与评估，用于把固定任务集接进 CI 门禁。
- **OpenTelemetry GenAI 语义约定**（Apache-2.0，https://github.com/open-telemetry/semantic-conventions ）：让"模型指纹"、token 与延迟字段在不同后端之间可比。

要点是：**清单里最容易形式化的几条（版本锁定、评测门禁、缓存命中率、沙箱参数）都已经有现成工具去验证**，不要靠人肉检查。

## 六、坑与检查清单

**基础设施**

- [ ] 执行沙箱已启用，未使用特权模式，未挂载宿主机敏感路径
- [ ] 步数上限、token 预算、墙钟超时三项都已设置且有默认值
- [ ] 沙箱外的只读操作与有副作用操作已分离
- [ ] 依赖服务有降级路径，不可用时 Agent 拿到的是明确错误而不是挂起
- [ ] 灰度开关可随时把流量切回旧版本，不需要重新部署

**模型与提示**

- [ ] 生产使用固定版本号，不用会漂移的模型别名
- [ ] 模型参数（温度、top_p、最大输出长度）已固定并写进配置
- [ ] 提示词走 review 与评测，变更可追溯到具体提交
- [ ] 提示与模型的组合经过联合回归，不是只测其中一个
- [ ] 升级前做过影子流量双跑，差异有人看过

**工具**

- [ ] 每个工具都有超时、重试上限、指数退避与抖动
- [ ] 每个工具都有并发上限，工具之间也有全局并发上限
- [ ] 工具返回结构化错误，区分"查不到"与"查询失败"
- [ ] 高危工具有独立配额与熔断，不与普通工具共享额度
- [ ] 工具新增或改 schema 后，模型侧的回归集已重跑

**安全**

- [ ] 工具清单是最小集，白名单外的调用会被拒绝
- [ ] 出网白名单生效，元数据地址与本机端口被阻断
- [ ] 不可逆与外发动作需要独立通道确认，默认拒绝
- [ ] 沙箱内没有长期有效的全权限凭据
- [ ] 上游不可信内容与指令在上下文里分区，并带来源标注

**观测**

- [ ] 每个任务都有 trace，模型指纹（版本 + 参数 + 提示 hash）写在 span 上
- [ ] 五个核心 SLI 有看板：成功率、每次成功成本、时延 P95、工具错误率、空转率
- [ ] 告警阈值来自 SLO 或历史基线，且能定位到具体组件
- [ ] 采样策略是按任务粒度的，采样率被记录
- [ ] 敏感字段在采集端脱敏，采样不会让成功率统计有偏

**评测**

- [ ] 固定任务集覆盖高频场景与历史事故场景
- [ ] 每次发版都跑固定种子下的抽样回归，失败即拦截
- [ ] 基线包含模型、提示、任务集、judge 四个版本
- [ ] 基线对比能列出具体回归的任务，不只给平均分
- [ ] 有一组不参与调优的隐藏集定期跑
- [ ] 提示变更与模型变更有分别的回归结论

**成本**

- [ ] 逐任务成本分解可见：输入 / 输出 / 缓存读 / 缓存写 / 工具往返
- [ ] 口径是每次成功任务成本，不是每次调用成本
- [ ] 缓存命中率与缓存 token 占比都有监控
- [ ] 提示前缀稳定性有自动化测试，动态字段不在前缀里
- [ ] 有日成本上限与超限告警，超限后的动作明确

**合规**

- [ ] 留存期限按数据类别设定，过期能自动删除
- [ ] 敏感数据的访问有审计记录
- [ ] 用户数据的导出与删除请求有明确处理流程
- [ ] 第三方模型的数据使用条款已确认并留档
- [ ] 会话记录的匿名化与脱敏规则在客户端与后端一致

## 七、小结与延伸阅读

1. **检查清单是前五章的收敛物**：每一条背后都有一次"想明白了才不写错"的机制推导（沙箱、注入防护、观测、评测、成本）。
2. **六类故障的根因都不在代码，在架构**：缺停止条件、缺成本分解、缺上下文分区、缺记忆准入、缺熔断、缺版本锁定。
3. **灰度与回滚的前提是可切版本和可撤销状态**；代码能回滚，数据不能。
4. **值班手册只写三段**：阈值来自 SLO、动作三步能做完、升级路径带交接物。
5. **每次故障之后，清单应该多一条**——这是这份清单唯一可靠的更新机制。
