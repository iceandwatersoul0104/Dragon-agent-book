# 第 16 章 PydanticAI、Agno 与 smolagents：类型驱动与轻量路线

## 一、本章要解决的问题

一个内部工具团队的 Agent 项目，用当时最重的那套框架写了三周：单文件三百行、全局变量、模型输出靠正则解析、测试必须把 HTTP 全 mock 掉才能跑。项目本身只是想"查一下订单状态，回答一句"。

换了轻量框架之后发现一件更值得说的事：**这三个框架不是"大框架的简化版"，是三种不同的赌注。**

- PydanticAI 赌的是"产出必须是结构化的"，代价是你得先把类型写出来，回报是下游不用解析、不用防御、模型给错了能被打回重做；
- Agno 赌的是"上手速度比控制力重要"，构造函数短到一行，代价是产出是自由文本、内部行为基本看不见；
- smolagents 赌的是"代码比 JSON 更适合当动作"，一次模型回复就能写循环、调多个工具、做计算，代价是代码执行的安全边界得你自己划。

本章把这三条路线拆开看，最后给选型判据。先说清楚一件事：它们都不提供第 12 章那种状态图级编排，多步流程要么自己写循环，要么用 Agno 的 Workflow——这是轻量路线的共同天花板。

## 二、原理：机制拆解

### 2.1 PydanticAI：把类型当契约

四个机制，环环相扣。

**依赖注入（deps_type / RunContext）**：不属于提示词、但工具需要的东西——数据库连接、HTTP 客户端、当前租户——按次运行传进去。模块级只建一个 Agent，就能服务所有请求，不会因为"当前用户是谁"把状态漏到全局变量里。

**输出类型契约（output_type）**：产出不是一个字符串，是一个数据类。字段名、类型、缺一不可。模型给错了，框架把错误信息**喂回模型**让它重做（`ModelRetry`），而不是抛个异常让调用方擦屁股。

**模型无关**：`model` 参数接受一个模型对象或一个字符串，换供应商只改这一处，Agent 代码一行不动。

**测试友好**：工具 schema 从函数签名生成、产出有类型、模型可替换——这三件事叠起来，整个 Agent 才能离线跑。

```
  依赖（deps）──┐
                ├──→ RunContext ──→ 工具函数
  模型 ─────────┘         │
                          ▼
                    output_type 契约
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
          合格 → 返回            不合格 → ModelRetry（带理由）
                                          │
                                          └──→ 模型重做
```

**模型无关**这条最容易被低估。`model` 参数接受一个模型对象或一个字符串，换供应商只改这一处，Agent 代码一行不动。而这条抽象最好的证明是**测试替身**：因为模型是一个协议，测试里把它换成脚本化的替身，整个 Agent 就能离线跑——不用 API Key，不用把 HTTP 一层层 mock 掉，也不担心每次跑测试都烧一点额度。

配套代码里那次实测很说明问题：模型先交了一份 `top_amount` 是字符串的产出，被类型检查打回；改完又交了 `total` 和各状态数量之和对不上的产出，被语义校验打回；第三次才合格。**类型查形状，校验器查语义**——后者类型系统管不了，只能自己写。

### 2.2 Agno：把复杂度藏进框架

Agno 曾名 Phidata。它的主张很直接：Agent 应该是个配置对象，不该是个类。

```python
agent = Agent(
    name="订单助手",
    model=model,
    instructions="你是订单助手",
    tools=[fetch_orders],
    knowledge=kb,          # 知识层
    db=storage,            # 会话/记忆
)
resp = agent.run("订单 A-91 到哪了？")
```

五个概念：**Agent**（上面这一坨）、**Team**（一组 Agent 加路由规则，哪条任务给谁）、**Workflow**（步骤化流程，状态在步骤之间传）、**Knowledge**（知识层）、**AgentOS**（把 Agent、Team、Workflow 装起来持久运行）。

其中**知识层是 Agno 相对其他轻量框架最突出的地方**：文档切块、建索引、检索，命中就自动拼进上下文——你不用自己写一遍检索和拼接。配套代码里知识库命中"订单状态说明"，它就自动出现在提示里了。

代价很直接：`resp.content` 是什么类型？取决于模型答了什么。下游要用，就得自己解析、自己防御、自己处理"模型这次没按格式答"的情况。

### 2.3 smolagents：让模型写代码

两条路径，同一个基类。

**工具调用智能体（ToolCallingAgent）**：模型发 JSON 工具调用，框架执行，把结果喂回去。一个工具一次调用。

**代码智能体（CodeAgent）**：模型写一段 Python，框架执行，把输出喂回去。关键差别在**一次回复里能写的东西**：循环、条件、多个工具调用、计算，全都在一段代码里。

smolagents 还有个约定值得记住：代码里 `print("Final Answer: ...")` 的输出**直接就是最终答案**，框架不再让模型复述一遍。配套代码里同一个任务，CodeAgent 用了 **1 次**模型调用，ToolCallingAgent 用了 **2 次**——省下的那一次往返是实打实的。

**极小依赖面**是它另一个卖点：核心就两个类加几个现成工具类型，不拖一整套框架进来。这还有另一层含义——升级成本低，不会因为上游某个大版本改了 API 就把你锁死。代价是那些"框架本来该替你做"的事——持久化、观测、部署——一件都不包。

还有一条硬要求：**代码必须进沙箱**。第 9 章讲过代码执行的风险，在 smolagents 里这条从"可选"变成了"默认路径"——沙箱不再是加分项，是准入条件。配套代码用受限 builtins 白名单跑，够做算术和调工具，但**不足以当安全边界**，生产环境必须用容器。

### 2.4 可观测性、可扩展性、生产化的差距

| | PydanticAI | Agno | smolagents |
| --- | --- | --- | --- |
| 可观测性 | 有 trace 能力，可选接第三方 | AgentOS + 遥测开箱即用 | 弱，基本要自己接 |
| 可扩展性 | 工具集、动态指令、输出类型自由组合 | Agent / Team / Workflow 三层齐全 | 主要就是加工具 |
| 生产化 | 类型契约 + 依赖注入，最容易嵌进已有服务 | 持久运行、存储、知识层都现成 | 沙箱、部署、观测全要自己搞 |
| 编排能力 | 无状态图，复杂流程自己写 | Workflow 够用 | 最弱 |

诚实地说：三家在**编排**这一栏都很弱。要循环、检查点、中断、审批、回滚，得靠第 12 章。

差距最实在的地方在**出问题时你能不能看见**。类型驱动路线出错是一句"字段 top_amount 类型不对"，直接指向契约；极简路线出错只看到一段自由文本，得自己猜模型当时想说什么；代码路线能看到那段代码本身——这反而是代码路径的一个隐藏优势：出错的现场就是代码。

## 三、为什么这样设计：取舍与失效条件

三条路线各自的失败条件：

**PydanticAI 型不适合**：流程需要显式图和回滚（去第 12 章）；产出只是给人看一眼、不进任何下游（写个类型是白写）；团队不写 Python，类型契约反而成了阅读门槛。

**Agno 型不适合**：产出要被多个下游消费、接口必须稳定（自由文本迟早出事）；需要在失败时精确知道"它当时为什么那么答"（内部过程不可见）；要精确控制每一步。

**smolagents 型不适合**：环境里没有可用的隔离手段（模型生成的代码只能直接跑在宿主机上，绝对不要）；工具调用链需要严格的可观测性和审计；产出要强类型。

共同的失效条件：**需要状态图级编排**。

选型判据，三条路径：

1. **小项目 / 快速验证**：一条 Agent + 几个工具 → **Agno 型**。构造函数最短，知识层现成，跑不通就扔。
2. **类型安全优先**：产出是数据、要被下游消费、要能离线测 → **PydanticAI 型**。多写几行类型，省掉后面一堆解析和防御。
3. **代码智能体优先**：任务本质是"让模型写段代码算一算"，或者工具组合复杂（要循环、要条件判断） → **smolagents 型**。但先把沙箱准备好。

一条经验：**先用最简单的路线写，跑通之后再决定要不要往类型里加东西。** 反过来——一开始就上全套类型契约、图编排、多 Agent——会把项目直接拖死。

举个具体的：一个"查订单状态回客服"的内部工具，产出只是一句话给人看，不进任何下游——选极简型，一天能上线；同一个工具后来要接工单系统，产出必须变成字段对得上的结构——这时补类型契约，比推倒重来便宜。再往后，流程里出现了"要人审批才能退款"——三条路都该让位给状态图了。

## 四、动手：最小可实现

配套代码在 `code/ch16-light-frameworks/`，`main.py` 用 1120 行纯标准库把三条路线各写一遍放在同一个文件里，**不需要 API Key 就能跑通完整回路**，内置 mock 模型。

依赖：Python 3.9 及以上，零第三方包，不需要 `pip install`。

```bash
cd code/ch16-light-frameworks
python main.py                     # 跑全部场景
python main.py --demo pydanticai   # 只跑类型驱动路线
python main.py --demo agno         # 只跑极简路线
python main.py --demo smolagents   # 只跑代码优先路线
python main.py --demo compare      # 三条路线并排对比
```

三个场景跑**同一个任务**：统计订单各状态的数量，找出金额最大的一单。这样对比才有意义。

- **pydanticai**：模型交两次不合格的产出（一次类型错、一次语义错），两次都被打回重做，第三次合格。
- **agno**：知识库命中自动入上下文，产出是自由文本。
- **smolagents**：CodeAgent 一次模型调用写完代码并打印最终答案；ToolCallingAgent 两次调用。

几个关键机制在代码里长这样：

```python
# 1) 工具 schema 从签名长出来——不用手写
def schema_from_func(fn):
    props = {}          # 参数类型来自类型注解
    doc = (fn.__doc__ or "").strip().splitlines()
    return {"name": fn.__name__, "description": doc[0], "parameters": {...}}

# 2) 依赖按次注入，不进提示词
@agent.tool
def fetch_all_orders(ctx: RunContext) -> List[dict]:
    """按当前租户查订单列表。"""
    return ctx.deps.orders

# 3) 输出校验：先构造目标类型，再查字段类型，最后跑语义校验
def _validate_output(self, output):
    ...                                        # 缺字段/多字段 -> ModelRetry
    for name, want in get_type_hints(...):     # 类型不对 -> ModelRetry
    for v in self._validators: v(output)       # 语义不对 -> ModelRetry

# 4) 代码路径：Final Answer 约定，省一次模型往返
if "Final Answer:" in out:
    return out.split("Final Answer:", 1)[1].strip()
```

切真实模型加 `--live`，需要三个环境变量：

| 变量 | 必填 | 默认值 |
| --- | --- | --- |
| `LLM_API_KEY` | 是 | — |
| `LLM_BASE_URL` | 否 | `https://api.openai.com/v1` |
| `LLM_MODEL` | 否 | `gpt-4o-mini` |

live 模式下换成真模型的有三处（按契约发工具调用、直接回答、写 Python 代码），**依赖注入、输出契约、校验重试、知识检索、沙箱执行全部不变**——这正是要验证的：换个模型之后，框架那层的保证还在不在。

## 五、开源实现对照

- **PydanticAI**（MIT，https://github.com/pydantic/pydantic-ai）：本章路线一的参考实现。以 Pydantic 模型定义输入输出，类型安全地注入模型与依赖。它的输出契约和依赖注入是三家里最完整的。
- **Agno**（Apache-2.0，https://github.com/agno-agi/agno）：本章路线二的参考实现。以 Agent、Team、Workflow 组织多 Agent，AgentOS 承载持久运行。三家里功能面最宽的。
- **smolagents**（Apache-2.0，https://github.com/huggingface/smolagents）：本章路线三的参考实现。极简 Agent 库，让模型用 Python 代码块代替 JSON 工具调用。依赖面最小。
- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：对照组。当你的问题从"产出对不对"变成"流程怎么走、怎么回滚"时，轻量路线就该让位了。
- **LlamaIndex**（MIT，https://github.com/run-llama/llama_index）：对照组。当知识检索本身是主要工作量时，数据框架比"给 Agent 挂个知识层"更厚，第 13 章专门拆。

## 六、坑与检查清单

- [ ] 产出类型写清楚：字段名、类型、缺一不可，别用 `dict[str, Any]` 糊弄。
- [ ] 校验器查语义，类型系统查形状，两层都要有。
- [ ] 依赖走注入，别用全局变量存"当前用户"。
- [ ] 工具的 docstring 认真写——它就是模型看到的参数说明。
- [ ] 工具的返回类型也标好，模型据此决定怎么用。
- [ ] 校验失败要有重试预算，别无限重试烧钱。
- [ ] 测试用模型替身，别真调 API——离线测试才跑得进 CI。
- [ ] 产出解析失败要有兜底，别让一段脏文本打穿整条链路。
- [ ] 代码智能体的沙箱用容器，别用宿主机。
- [ ] 沙箱白名单每加一个内置函数都是安全边界松动，改动要评审。
- [ ] 代码智能体的最大步数要设上限。
- [ ] 知识库命中的内容别无限拼进上下文，先裁剪再注入。
- [ ] 团队路由要能观测：谁接了哪条任务、依据是什么。
- [ ] 需要检查点、中断、审批时，果断换到第 12 章的路线。

## 七、小结与延伸阅读

这三条路线不是功能多少的差别，是赌注的差别。PydanticAI 赌产出值得写进类型，Agno 赌上手速度值，smolagents 赌代码比 JSON 更适合当动作。选哪条，看你更怕什么：怕下游解析崩溃，选类型驱动；怕框架太重挡住迭代，选极简；怕工具组合表达不出来，选代码优先。

不管选哪条，有两件事是共同的：一是**产出类型决定了下游的负担**，能定契约就定；二是**能写进代码的判断就别交给模型**。

还有一条共同的短板：**它们都不管编排**。要循环、要检查点、要在中途停下来等人批——那是第 12 章的事。轻量路线的正确定位是：把流程的骨架用最省力的方式搭出来，把真正需要控制力的那部分，交给更重的那套框架，或者自己写状态机。
