# 第 13 章 LlamaIndex：数据驱动的 Agent 范式

## 一、本章要解决的问题

先看一个内部知识库问答系统的演进。

第一版很朴素：把十几篇文档全拼进提示词。文档到三十篇就塞不下了，而且大部分内容和问题无关，模型开始一本正经地引用根本没读到的段落。

第二版改成向量检索：切块、算 embedding、检索 top-3、拼进提示词。这版能用了，但很快冒出三个新问题：

- 用户问"1 加 2 等于几"，系统照样先跑一遍检索，把三段完全无关的运维手册塞进上下文——多花 token，还把模型带偏了；
- 想同时用向量和关键词检索，两套逻辑前后写了两遍，改一次召回参数要改两个地方；
- 检索之外还想加"先分类再查""查不到就追问"，这些逻辑只能硬塞进检索函数里，越写越长。

问题的根子在于：这套系统把**数据层当成 Agent 的一个副作用**，而不是底座。

LlamaIndex 的主张正相反：Agent 的输入主要不是用户问题，而是**从自己的数据里取回来的东西**。所以数据接入、切块、索引、检索这些在别的框架里算"工具"的东西，在这里是底座；Agent 和工作流架在底座之上。

本章拆三件事：数据层到底怎么和 Agent 耦合、事件驱动的工作流（Workflows）是什么、和上一章的状态图差在哪、什么时候该选它。

## 二、原理：机制拆解

### 2.1 数据层：索引是第一公民

检索增强生成（Retrieval-Augmented Generation, RAG）说的就是"先从自己的数据里检索，再把结果交给模型生成"这一套做法。LlamaIndex 把这半件事——检索那一半——做成了底座：它的数据链路是四层，一层套一层：

**文档（Document）与节点（Node）**。原始文档来自各种加载器（PDF、网页、数据库、飞书文档）。检索的最小单位不是文档而是**节点**——切块后的片段。切块要留重叠，否则答案正好被切在边界上，就成了"明明库里有却检索不到"。这种问题排查起来最费时间，因为召回率看着没问题。

**索引（Index）**。把节点组织成可检索的结构：向量索引、BM25 索引、关键词表、图索引。同一批节点可以建多种索引。

**检索器（Retriever）**。给一个查询，返回一批节点。

**查询引擎（Query Engine）**。检索 + 提示词 + 模型，封装成一个"给个问题出答案"的调用单元。

Agent 挂在这套底座上，方式有三种，这是本章的骨架：

```
        ┌─────────────────────────────────────────────┐
        │                  Agent 层                   │
        │      决定：查不查 / 查什么 / 怎么用结果        │
        └───────┬───────────────────────┬─────────────┘
                │ 作为工具               │ 作为内置能力
                ▼                       ▼
        ┌───────────────┐      ┌────────────────┐
        │ search 工具   │      │ 每次回答前强制  │
        │ 模型自己决定  │      │ 检索并注入上下文│
        └───────┬───────┘      └────────┬───────┘
                └───────────┬────────────┘
                            ▼
        ┌─────────────────────────────────────────────┐
        │                  检索层                     │
        │  VectorIndex   BM25Index   FusionRetriever │
        └───────┬─────────────────────────────────────┘
                ▼
        ┌─────────────────────────────────────────────┐
        │                  数据层                     │
        │  Reader → Document → chunk → Node → 索引    │
        └─────────────────────────────────────────────┘
```

第三种是前两者的封装：把整个查询引擎包成一个工具交给 Agent，Agent 只知道"有个能问答的东西"，不知道底下是向量库还是 BM25。

三种接法的差别不在检索质量，而在**谁来决定查不查**。这决定了成本曲线，也决定了模型有没有"忘了查"这个失败模式。

### 2.2 事件驱动的工作流（Workflows）

LlamaIndex 的编排层不画图，用**事件（Event）**。

- 事件是有类型的数据包；
- 步骤（step）是一个 async 函数，声明自己处理哪类事件；
- 步骤之间靠"发事件"通信，**不共享可变状态**；
- 汇聚靠 `collect_events` 等特定类型的事件到齐。

```
  StartEvent
      │  send_event
      ├──→ RetrieveEvent(vector) ──→ RetrievedEvent(vector) ──┐
      ├──→ RetrieveEvent(bm25)   ──→ RetrievedEvent(bm25)  ──┤
      └──→ CollectEvent ─────────── collect_events 等两路 ────┤
                                                             ▼
                                                    SynthesizeEvent
                                                             │
                                                             ▼
                                                        StopEvent
```

看上图和上一章的状态图对比，差别很清楚：**状态图靠"共享一份状态 + 归约"来协调，事件驱动靠"各走各的，靠事件汇合"来协调。** 前者的耦合点在数据，后者的耦合点在消息。

步进式执行带来的四个实际好处：

1. **每一步是独立单元**。可以单独测、单独重跑、单独看耗时，不用对着一个混合函数调参；
2. **链路天然是事件日志**。不需要另外埋点，回放就是重放事件序列；
3. **加分支不用改别人的代码**。新需求就是多发一个事件，不用去动现有步骤的签名；
4. **并行是自然的**。两个检索事件同时发出去，谁先回来谁先进队列，汇合点自己等齐。步骤本身是 async 函数，慢的一步不阻塞其他步骤——并行不是特例，是默认行为。

至于 Agent 抽象和 Workflows 的关系：**Workflows 是编排层，Agent 是编排层上的一个"会决定调工具"的角色**，两者不是二选一。Agent 可以作为一个步骤跑在工作流里，也可以它自己就是一个工作流。

### 2.3 多 Agent：路由 + 专家

LlamaIndex 把这种"路由 + 专家"的多 Agent 编排叫作 `AgentWorkflow`。它和 `Workflows` 是两层：`Workflows` 提供事件与步骤的机制，`AgentWorkflow` 是在这之上预置好的一种团队编排。

多 Agent 的常见形态是"路由 Agent 判断问题属于哪一类，交给对应专家"：

```
  StartEvent ──→ 路由步骤 ──→ HandoffEvent(target=runbook)
                                    │
                                    ▼
                          AgentThinkEvent ──→ AgentToolEvent ──→ AgentObserveEvent
                                    │                              │
                                    └──────── 回到 AgentThink ─────┘
```

这里有个容易被忽略的设计：**每个专家带自己那份索引**。运维手册的 Agent 不该看见报销制度——不是"不该"，是"看见也没用"，检索出来的是空的，还白花一次 embedding 和检索的延迟。专家的"想"这一步，判断"要不要查"用的也是**自己那份**索引的命中情况。

交接靠事件，专家之间不互相调用。加一个专家，就是加一份索引 + 加一个角色，**工作流本身一行不用改**。

还得留一个不带索引的"通用"出口：库里根本没有的问题，让它去检索只会得到一堆无关片段。一个诚实的"我不知道"，比一段编出来的答案有价值。

## 三、为什么这样设计：取舍与失效条件

框架换来了什么：完整的数据接入到检索链路（几十种加载器、解析、切块、索引、混合检索、重排），以及一条事件驱动的编排层。这些活儿自己写一遍是几周的工程量。

代价也很实在：依赖重、抽象层多；`Node` 对象会在 Agent 代码里到处传，数据层的抽象会渗透上去；索引是"活"的——文档改了要重建，schema 变了要重灌。还有一条容易低估的：索引是长期资产，文档一改就得重建。知识库天天变的团队，要先把重建策略想清楚，再决定要不要上这套东西。

下面是**不该选 LlamaIndex** 的几种情况，这些比优点值钱：

1. **难点在控制流，不在数据**。流程的核心是循环、回滚、审批、中断后恢复——那是上一章状态图的地盘。LlamaIndex 的事件流不提供检查点和时间旅行，硬要自己实现一遍。
2. **数据量小、来源单一**。就一个 API、两三个文档，建索引、切块、配 embedding 的成本回不来。写个关键词匹配就够了。
3. **需要长周期运行和人工介入**。任务跑三天，中间等人批、还要能回滚重放，状态图那套检查点机制更直接。
4. **一次性问答脚本**。索引是长期资产，脚本用完就扔，资产变负债。
5. **业务实体关系复杂**。订单、账户、库存之间有复杂关系时，图数据库或领域模型比向量检索合适。

反过来，**这些情况该选 LlamaIndex**：

1. **知识密集型任务**：答案必须来自私有数据，数据量大、来源杂；
2. **数据接入本身就是主要成本**：几十个来源要统一解析、清洗、入库；
3. **检索质量是核心竞争力**：需要混合召回、重排、多路融合，这些有现成实现；
4. **流程本身不复杂，重点在"查什么、怎么组织结果"**。

一句话：**控制流是难点就选状态图，数据是难点就选数据框架。**

## 四、动手：最小可实现

配套代码在 `code/ch13-llamaindex/`，`main.py` 用 1217 行纯标准库复刻上面这套语义，**不需要 API Key 就能跑通完整回路**，内置 mock 模型和一份 12 篇文档的知识库。

依赖：Python 3.9 及以上，零第三方包，不需要 `pip install`；事件驱动部分用标准库的 `asyncio`。

```bash
cd code/ch13-llamaindex
python main.py                    # 跑全部三个场景
python main.py --demo coupling    # 只跑耦合形态对比
python main.py --demo workflow    # 只跑事件驱动工作流
python main.py --demo agents      # 只跑多 Agent 交接
```

三个场景分别对应前面三节：

- **coupling**：同一个问题跑两遍——一遍检索作为内置能力（一定查），一遍检索作为工具（模型自己决定）。库外问题"1 加 2 等于几"上，内置形态白查一次、白塞 159 个 token、还答不出来；工具形态一次都不查，直接答 3。
- **workflow**：两路检索并行 → `collect_events` 汇聚 → 合成。打印完整事件流，能看到 7 个事件的先后顺序。
- **agents**：路由 → 交接 → 专家内部"想 → 调工具 → 看结果 → 再想"。三道题分别路由到运维、制度、通用三个专家。

几个关键机制在代码里长这样：

```python
# 1) 切块留重叠：避免答案被切在边界上
def chunk_document(doc, chunk_size=90, overlap=25): ...

# 2) 混合检索：RRF 只看名次，两种打分尺度不一致也能合
class FusionRetriever:
    def retrieve(self, query, top_k=3):
        scores[node_id] += 1.0 / (60 + rank + 1)   # 各路各算各的

# 3) 步骤只认事件类型，不共享状态
@wf.step(RetrieveEvent)
async def retrieve(ctx, ev):
    ctx.send_event(RetrievedEvent(source=ev.source, nodes=...))

# 4) 汇合点：等两路 RetrievedEvent 到齐
@wf.step(CollectEvent)
async def collect(ctx, ev):
    got = await ctx.collect_events(["retrieved", "retrieved"])

# 5) 专家用自己那份索引判断要不要查
def think(self, question, history):
    overlap = self.bm25.overlap(question) if self.bm25 else 0
    ...
```

切真实模型加 `--live`，需要三个环境变量：

| 变量 | 必填 | 默认值 |
| --- | --- | --- |
| `LLM_API_KEY` | 是 | — |
| `LLM_BASE_URL` | 否 | `https://api.openai.com/v1` |
| `LLM_MODEL` | 否 | `gpt-4o-mini` |

live 模式下只有三处换成真模型（分类、决定要不要检索、根据片段作答），**索引、检索、工作流、多 Agent 交接完全不变**——这正是要验证的：换了真模型之后，数据层和编排层的行为是不是还是可预期的。

## 五、开源实现对照

- **LlamaIndex**（MIT，https://github.com/run-llama/llama_index）：本章讲的范式的参考实现。以数据连接器与索引为中心，为 Agent 提供检索与工作流引擎，`Workflows`、`AgentWorkflow`、索引与检索组件都在这里。
- **Haystack**（Apache-2.0，https://github.com/deepset-ai/haystack）：另一种取向——把检索、生成与 Agent 拆成组件，用显式管道控制数据流向。管道式组件编排和批处理是它的主场，事件驱动的工作流不是它的主语；和 LlamaIndex 比，它更强调"显式控制检索与路由"。
- **LangChain**（MIT，https://github.com/langchain-ai/langchain）与 **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：上一章那条线。检索在这里是链上的一个组件或图里的一个节点，数据接入能力弱，编排（循环、检查点、中断）能力强。两条线的取舍正好相反。
- **Dify**（Apache-2.0 加附加条件，Dify Open Source License，https://github.com/langgenius/dify）：低代码平台，把 Agent 工作流与 RAG 管道做成可拖拽的界面。自建数据层时它省事，但编排逻辑被收进平台里，可编程性不如直接写代码。
- **Qwen-Agent**（Apache-2.0，https://github.com/QwenLM/Qwen-Agent）：工具调用 + RAG 一体化，围绕自家模型生态打通函数调用、MCP、代码解释与检索。适合已经锁定模型厂商的团队。

## 六、坑与检查清单

- [ ] 切块留重叠，块大小按文档类型定，别一套参数打天下。
- [ ] 检索结果里保留出处（文档标题、节点 ID），出问题时能回溯到原文。
- [ ] 别只看召回率，也看召回进来的是不是**真的相关**——不相关片段比没有片段更糟。
- [ ] 混合检索要各自调权重，别指望 RRF 替你调参。
- [ ] 索引更新策略想清楚：全量重建、增量更新，还是定时重灌。
- [ ] 检索器的耗时单独观测，别混在 Agent 的总耗时里。
- [ ] 提示词里的检索片段有数量和长度上限，别把 top-k 开成 top-50。
- [ ] 库外问题要能正常作答，不要强行检索一段无关内容硬凑答案。
- [ ] 领域划分别太细，专家之间互相不认索引的浪费是实打实的。
- [ ] 事件类型要少而明确，事件名一多就没人说得清链路在干嘛。
- [ ] 步骤保持单一职责，一个步骤干两件事就等于没有分步。
- [ ] `collect_events` 要设超时，别让一个等不到的事件把整个流程挂死。
- [ ] 数据层和编排层分开写：检索换实现时，Agent 代码一行都别动。

## 七、小结与延伸阅读

LlamaIndex 代表的是另一条主线：**先把数据层做厚，Agent 和工作流架在上面**。它和上一章的状态图不是替代关系，而是各自解决不同的问题——状态图解决控制流，数据框架解决检索。

理解了三个点就能选型：**索引是第一公民**（数据接入到检索是一条完整链路，不是零散工具）；**事件是唯一的协调方式**（步骤之间不共享状态，汇合靠等事件，加分支不用改别人）；**检索的耦合方式决定成本**（内置能力代价固定，工具形态代价可变，外加一个"模型会不会忘了查"的权衡）。

判断该不该用它，只问一句：**我这个 Agent 的难点，是在"怎么查"，还是在"怎么走"？** 是"怎么查"，选数据框架；是"怎么走"，回头看第 12 章的状态图。
