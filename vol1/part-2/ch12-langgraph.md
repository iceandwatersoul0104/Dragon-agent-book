# 第 12 章 LangChain 与 LangGraph：状态图式编排范式

## 一、本章要解决的问题

先看一个自己踩过的坑。

我们上线过一个运维助手 Agent，主体就一个 `while` 循环：模型输出工具调用就执行，输出最终答案就退出。头两个月跑得好好的，第三个月开始出事：

- 周四凌晨 3 点，调用监控服务的那个工具超时 30 秒，异常直接穿透 `while` 循环，进程退出。那条工单停在"已经拿到 12 条证据、还没生成方案"的状态，第二天没人知道它走到哪一步；
- 想加个审批环节，于是在循环里塞了个 `input()`。测试环境好好的，上了灰度才发现服务一重启，审批状态全丢，同一笔 8 万块的退款被提交了三次；
- 出事后想复盘，把当时的 prompt 日志捞出来一看，只有一坨拼接好的文本——没有"第几步、每步状态是什么、模型当时返回了什么"。

复盘会上有人说了句实话：**问题不是 while 循环写得不够聪明，是它没有状态快照。**

要人工介入、要回溯、要重放，就得先把"跑到哪儿了"变成一等公民，而不是散在几个局部变量里。

状态图式编排（State Graph Orchestration）就是为这件事设计的：把 Agent 的控制流从一串 `if`/`while` 改成一张显式的有向图，状态是一份可序列化的文档，每走一步存一份快照。

本章拆这套抽象的三个支点：归约（reducer）、检查点（checkpoint）、中断（interrupt）。以及它们各自的代价。

## 二、原理：机制拆解

### 2.1 四个零件

状态图（State Graph）由四个零件组成。

**状态 schema（State Schema）**：一组具名通道（channel），每个通道有自己的类型和归约函数。状态不是一个裸 dict，是一个**有合并规则的文档**。

**节点（node）**：一个普通函数，签名是 `fn(state) -> dict`。它读全量状态，返回**增量**——要写哪几个通道、往里写什么。节点返回增量而不是整份新状态，是为了让同一超步里的多个节点互不覆盖：它们各自返回要写的通道和值，合并规则统一由通道的归约函数决定。

**边（edge）**：静态边无条件跳转；条件边（conditional edge）配一个路由函数，读状态决定下一站。

**检查点（checkpointer）**：每执行完一个超步，把状态存一份。

超步（superstep）是理解全局的关键：一组可以并行执行的节点。同一超步里的节点读到的是**同一份输入状态**，各自返回增量，写入按通道的归约函数合并，合并结果才成为下一超步的输入。

```
                        ┌────────────────────────────────────────┐
                        │              状态 (State)             │
                        │  task      : str         ← 覆盖        │
                        │  messages  : list[dict]  ← add_messages│
                        │  evidence  : list[dict]  ← add        │
                        │  decision  : str         ← 覆盖        │
                        └────────────────────────────────────────┘
                           ▲                       │
              写入增量（带归约）                   │ 读取全量
                           │                       │
              ┌────────────┴──────┐      ┌────────┴─────────┐
              │   节点 collect     │      │   节点 draft     │
              │ 写 evidence 增量   │      │ 写 draft 增量    │
              └────────────┬──────┘      └────────┬─────────┘
                           │ 静态边                │ 静态边
                           ▼                       ▼
                    ┌─────────────┐         ┌──────────────┐
                    │ 节点 join   │         │ 节点 approval │◀── interrupt()
                    │ 读全部证据  │         │ 挂起等人工    │
                    └─────────────┘         └───────┬──────┘
                                                    │ 条件边
                                  ┌─────────────────┴────────────────┐
                                  ▼                                  ▼
                          ┌───────────────┐                  ┌───────────────┐
                          │ 节点 apply    │                  │ 节点 revise   │
                          │ 执行副作用    │                  │ 记录返工轮次  │
                          └───────────────┘                  └───────────────┘
```

### 2.2 归约：并发能不能用的分水岭

通道的归约函数（reducer）定义了"新写入怎么和旧值合并"。常见三种：

```python
def overwrite(old, new):        # 覆盖：后写的赢
    return new

def add(old, new):              # 累加：列表拼接
    return list(old) + list(new)

def add_messages(old, new):     # 消息：按 id 合并，同 id 就地替换
    merged, order = {}, []
    for m in list(old or []) + list(new or []):
        mid = m.get("id") or "__anon_%d" % len(order)
        if mid not in merged:
            order.append(mid)
        merged[mid] = m
    return [merged[k] for k in order]
```

为什么归约比覆盖更适合并发分支合并，看一个具体例子。假设两个并行分支同时取证：

```
超步 1:  metrics 分支 ──写 [m1]──┐
          logs 分支   ──写 [l1]──┤  两个分支读同一份输入状态
                                  ▼
超步 2:  join 节点读到的 evidence = ?
```

- 用覆盖语义：join 读到 **1 条**。后写的分支把先写的整个吃掉了，日志分支持有的证据凭空消失，而且没有任何报错；
- 用累加语义：join 读到 **2 条**，两个分支的产出都保住。

真实项目里这个坑的代价不是"少一条数据"，而是"少了一条关键的错误日志，排查方向整个跑偏"。

所以**状态写入是"增量 + 归约"，不是赋值**。这条决定了并行分支能不能用：通道的归约写在 schema 里，不写在节点里，换掉归约函数就换掉了并发语义，节点代码一行不用改。

`add_messages` 之所以特别常用，是因为它一次解决两个问题：并行写入不会互相覆盖，同一条消息被重写（节点重跑）时也不会变成两条。

### 2.3 检查点与时间旅行

每个超步结束后存一份检查点（checkpoint），内容是三样：状态全量、下一步要跑哪些节点、元数据（这步谁写了哪些通道、来源是正常循环还是人工修正）。

它撑起三件事：

1. **断点续跑**：进程崩了、机器重启了，从最后一个检查点恢复，不用从头再烧一遍 token；
2. **状态回溯（fork）**：挑一个历史检查点，从那儿重新跑。旧分支的记录还在，两条分支并存，互不覆盖；
3. **状态修正（update）**：人工在某个检查点上直接改状态值，生成一个新检查点，从那儿继续。

第三种最实用。Agent 算错了，运营在检查点上把 `decision` 从 `rejected` 改成 `approved`，再重放——后面所有节点看到的都是改过的状态，而原始那条执行轨迹一个字节没动。调试和审计都在。

检查点的元数据里记着它的**来源**：正常循环产生的、`interrupt` 挂起产生的、人工修正产生的，还有从历史分叉出来的。排查问题时先看来源列，就知道这一步是系统自己走的，还是被人推了一把；也方便把"人改过的那条轨迹"单独捞出来做审计。

### 2.4 中断：挂起、审批、恢复

中断（`interrupt()`）的真实语义有三条，这三条比 API 名字重要得多：

1. **挂起时，节点此前对状态的写入全部作废**。状态停在它执行之前，流程停在它身上；
2. **恢复时，节点从第一行重新执行**，`interrupt()` 这一次直接返回人工给的答复；
3. 因此 `interrupt()` 之前的副作用必须幂等。

```python
def node_approval(state):
    # 第一次进来抛中断；恢复时这里从头重跑，interrupt() 直接拿到答复
    answer = interrupt({"draft": state["draft"], "evidence_count": len(state["evidence"])})
    return {"decision": "approved" if answer == "approve" else "rejected"}
```

第 3 条直接划出了审批的可行边界：只读判断、改状态可以做；发短信、扣款、发工单不行——那些得挪到 `interrupt` 之后的节点里，让"人已经批了"这件事成为状态的一部分，而不是一次隐式的前置副作用。

挂起点由检查点记着，不在进程内存里。服务重启、换个进程来接、隔一天再批，都能接得上——这正是第一节那个 `while` 循环版本做不到的事。

## 三、为什么这样设计：取舍与失效条件

先说框架换来了什么、代价是什么。

| | 手写 `while` 状态机 | 状态图框架 |
| --- | --- | --- |
| 持久化 | 自己写，重启就没了 | 检查点自带，落库即可 |
| 人工介入 | `input()` / 回调，容易丢 | 中断有明确的挂起点和恢复语义 |
| 并行分支 | 自己搞线程和锁 | 超步原语 + 归约合并 |
| 复盘 | 拼 prompt 日志 | 逐步快照 + 历史分支 |
| 可读性 | 二十行以内很直观 | 图一复杂就得画出来看 |
| 调试 | 断点直接打 | 要顺着检查点链路看 |
| 依赖 | 零 | 一套框架 + 生态（LangChain、LangSmith 等） |

框架是把**重复劳动**（存状态、恢复、并行调度、可视化）一次性买断。代价是状态必须可序列化、调试链路多一层、升级节奏由别人定。

下面是**不该用**这个方案的几种情况，这部分比"优点"值钱：

1. **流程是直线，而且不超过三步**。用 LangChain 的 LCEL 拼一下，或者干脆写个函数。图带来的状态管理和序列化开销大于收益。
2. **状态装不进 JSON**。状态图要落检查点，状态就得可序列化。里面塞了数据库连接、文件句柄、编译好的 tokenizer、大模型对象，就得改成"存 ID、运行时再取回"。这类"状态很重"的系统，图的抽象会反过来拖住你。
3. **在线接口要求毫秒级延迟**。每步落一次检查点就是一次序列化和一次写库。能接受就接受，不能接受就换内存态检查点，但要清楚这意味着进程一挂就丢。
4. **图比状态还复杂**。条件边一多，图就变成一张谁也读不懂的网络。状态只有三个字段、条件分支却有十几个的时候，换成事件流或者带持久化的队列消费者更好。
5. **只要"多步 + 人工确认"**。一个带状态表的队列消费者就能干完，上图是杀鸡用牛刀。
6. **原型和一次性脚本**。`thread_id`、检查点清理、状态 schema 全是负担。
7. **团队没人熟悉这套心智模型**。超步、通道、归约不是免费的，上手成本要算进项目成本。
8. **状态 schema 还在天天改**。探索期每加一个字段，老检查点都可能读不出来。先把状态定型，再上持久化。

还有一条隐性成本容易漏算：**节点重跑语义**。中断恢复会让整个节点重跑，模型调用重跑就是真金白银，而且带温度采样时两次结果可能不一致。关键节点要么幂等，要么把不确定性收敛到状态里。

## 四、动手：最小可实现

配套代码在 `code/ch12-langgraph/`，`main.py` 用 1092 行纯标准库复刻上面这套语义，**不需要 API Key 就能跑通完整回路**，内置 mock 模型和 mock 工具。

依赖：Python 3.9 及以上，零第三方包，不需要 `pip install`。

```bash
cd code/ch12-langgraph
python main.py                    # 跑全部三个场景
python main.py --demo merge       # 只跑并行合并（归约 vs 覆盖）
python main.py --approver reject  # 审批人一律驳回，看返工与升级
python main.py --trace            # 打印每一步的节点与写入
```

三个场景分别对应前面三节：

- **triage**：事故分诊。`plan → collect → draft → approval → apply → report`，审批被驳回则走 `revise → draft` 返工，超过轮次上限升级给人。审批挂起时打印待审批内容，人工答复后从中断点恢复。
- **merge**：两个分支同时取证，**同一张图跑两遍**，一遍用累加归约、一遍用覆盖归约，输出 `证据条数 = 2` 对 `证据条数 = 1`。
- **fork**：跑完原始走向后，回滚到"第一次进审批之前"的检查点，人工改掉 draft 和 decision，生成一个新检查点再重放，得到另一条分支；两条分支的检查点共存。

核心机制在代码里长这样：

```python
# 1) 归约写在 schema 里，不在节点里
schema = State({
    "evidence": ch("evidence", add, factory=list),      # 并行分支要用累加
    "messages": ch("messages", add_messages, factory=list),
    "decision": ch("decision", overwrite, ""),
})

# 2) 节点只返回增量
def node_collect(state):
    return {"evidence": [...], "messages": [msg("tool", "采集到 2 条证据")]}

# 3) 中断：挂起 → 人工答复 → 节点从头重跑
def node_approval(state):
    answer = interrupt({"draft": state["draft"]})
    return {"decision": "approved" if answer == "approve" else "rejected"}

# 4) 检查点：每步一存，可回溯可修正
graph.compile(checkpointer=MemorySaver())
graph.get_state_history(config)                          # 历史分支
graph.update_state(config, {"decision": "approved"})     # 人工修正状态
graph.invoke(None, {"configurable": {"thread_id": "t1",
                                     "checkpoint_id": cp.id}}, resume="approve")
```

切真实模型加 `--live`，需要三个环境变量：

| 变量 | 必填 | 默认值 |
| --- | --- | --- |
| `LLM_API_KEY` | 是 | — |
| `LLM_BASE_URL` | 否 | `https://api.openai.com/v1` |
| `LLM_MODEL` | 否 | `gpt-4o-mini` |

live 模式下只有"生成计划 / 写草案 / 写总结"三处换成真模型，**编排逻辑、归约、检查点、中断语义完全不变**——这正是要验证的：换成真模型之后，流程还是不是按同样的状态在走。

读输出时盯三处：检查点历史里 `source=interrupt` 的那几行，是审批挂起的位置；`next` 列告诉你下一步该跑哪个节点；终态的 `decision` 和 `rounds` 能看出中间被驳回过几次。`--trace` 会把每个超步的节点和写入字段都打出来，对不上的时候先看它。

## 五、开源实现对照

- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：本章讲的机制的参考实现。用显式状态图与检查点编排可循环、可恢复的 Agent 工作流，状态 schema、归约通道、中断、检查点都在这里。
- **LangChain**（MIT，https://github.com/langchain-ai/langchain）：LangGraph 的下层积木。以 Runnable/LCEL 组合模型、提示、工具与检索，Agent 由链拼装——直线流程用它更省事，需要循环、检查点、人工介入时才上 LangGraph。
- **LangSmith SDK**（MIT，https://github.com/langchain-ai/langsmith-python）：追踪、数据集与评估。图编排让每一步可回放，追踪能把"这次跑成了什么样"落成可查询的数据，两者是一套的。
- **LangMem**（MIT，https://github.com/langchain-ai/langmem）：给 LangChain 提供自主写入与检索长期记忆的工具。图的状态是"这次任务的进度"，记忆是"跨任务的知识"，两者别混在一个通道里。
- **Haystack**（Apache-2.0，https://github.com/deepset-ai/haystack）：另一种取向——把检索、生成、Agent 拆成组件，用显式管道控制数据流向。组件级管道和批量处理是它的主场，状态图式的循环与时间旅行不是它的主语。
- **LlamaIndex**（MIT，https://github.com/run-llama/llama_index）：数据驱动的一条线，把 Agent 架在索引和检索之上，第 13 章单独拆。

## 六、坑与检查清单

- [ ] 每个通道都显式写了归约函数，不要依赖默认值——默认是覆盖，并行分支下会静默丢数据。
- [ ] 并行分支写入的通道一律用累加或消息归约。
- [ ] 状态里只放可序列化的东西，不可序列化的对象改成存 ID、运行时取回。
- [ ] 节点函数保持纯净：同样的输入给同样的输出，不要在里面读时钟或随机数。
- [ ] 条件边的路由函数是纯函数，不发请求、不写文件，否则图不可复现。
- [ ] `interrupt()` 之前的副作用全部做成幂等的。
- [ ] `thread_id` 有明确业务含义，别全塞 `default`。
- [ ] 检查点存储有清理策略，否则它会一直涨。
- [ ] 检查点里存了模型版本或 schema 版本；模型升级后老检查点还能不能读，要验证。
- [ ] 图超过 20 个节点就画出来看，别靠脑子记边。
- [ ] 终止条件写在图里，不要靠外层 `while True`。
- [ ] 并行分支里每个节点的耗时、失败、重试单独观测，不要只看整体成功率。
- [ ] 从检查点恢复前，确认模型版本和提示词版本没变。

## 七、小结与延伸阅读

状态图式编排的三个支点，各解决一件事。**归约**决定并发分支能不能共存——覆盖语义会让后写的分支吃掉先写的，而且不报错。**检查点**决定流程能不能被打断、回溯、重放——每步一份快照，状态回溯和人工修正都建立在它上面。**中断**决定人能不能真的插进流程中间——代价是节点会整个重跑，所以副作用必须幂等。

判断该不该用它，看三个问题：流程是不是真的需要循环和回溯？状态是不是可序列化的？每步落一次快照的延迟和存储能不能接受？三个都是"是"，就用；有一个是"不是"，先别上图。
