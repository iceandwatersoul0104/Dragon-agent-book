# 阅读路线图

全书 40 章分七卷，顺序是按"从概念到落地"排的，不是按重要性排。你完全可以跳着读——下面给三张表：一张总表看每章解决什么问题，一张是三条按读者角色分的路线，第三张是遇到具体症状时反查章节的索引。

先说一句实话：如果你时间只够读十章，别自己挑，按下面路线 A 走。

## 一、总表：40 章 / 7 卷

优先级是按"有 Python 或后端基础、准备自己动手造 Agent"这个默认读者给的：**必读**＝不读会在后面的章节里卡住或踩坑；**选读**＝有用但可以按需展开；**可跳**＝除非你的项目正好落在那个方向。

## 二、三条推荐路线

### 路线 A：第一次做 Agent 的工程师（10 章）

**第 1、2、3、4、8、10、11、5、9、34 章。**

排法说明：

1. **第 1 章** — 先把边界划出来。不划边界，你会把"一个带工具调用的脚本"当成 Agent，然后在它开始自主决策时措手不及。
2. **第 2 章** — 这是全书的坐标系，四回路和四个横切面。后面每一章都在用这套词汇，早读一次能省掉后面反复重述。
3. **第 3 章** — 理解单步成功率乘以步数会怎么塌陷。这决定了你的第一版要砍掉多少自由度。
4. **第 4 章** — 第一个能跑的循环。ReAct 是理解后面所有变体的母版，先看它原始形态，再看框架怎么改写它。
5. **第 8 章** — 工具契约放在提示之前。工具描述是提示词的一部分，但 schema、错误回灌、幂等是 API 工程问题；这一章决定了你的 Agent 是"看起来能用"还是"能上线"。
6. **第 10 章** — 上下文是预算。多数人第一次做 Agent 都会在这里翻车：上下文越来越长、越来越贵、答案越来越差。
7. **第 11 章** — 停止准则。Agent 不会自己停，这个不设上限的实现会在某次夜里烧掉额度。
8. **第 5 章** — 回到提示层。放在后面是有意的：先知道架构能做什么，再看提示技巧还能补多少，以及哪些问题提示解决不了。
9. **第 9 章** — 代码即行动。理解"让模型写代码执行"这条路线为什么常常比逐个调工具强。
10. **第 34 章** — 评测。学会怎么验证改动是让 Agent 变好了，而不是你觉得变好了。

**加餐**：上线前翻一遍第 36 章的清单；业务要做检索就加第 30 章；准备用现成框架就加第 19 章。

### 路线 B：已经能写 ReAct，想上生产的工程师（14 章）

**第 3、8、11、10、28、2、29、33、34、35、32、31、36、6 章。**

排法说明：

1. **第 3 章** — 重新算一遍可靠性账。你现在要决定步数上限和熔断阈值，这个数得自己算一遍。
2. **第 8 章** — 工具契约与幂等。生产事故的高发区就在这里：重试了不该重试的工具、执行顺序错了、错误回灌带偏了后续推理。
3. **第 11 章** — 停止准则、预算守卫、无进展检测。这是你在生产上唯一能兜住成本的东西。
4. **第 10 章** — 上下文工程。开始管预算，而不是等它爆。
5. **第 28 章** — 上下文窗口工程。第 10 章讲怎么组织，这一章讲压缩、淘汰和提示缓存的算法与参数，两章连着读。
6. **第 2 章** — 回来对一遍坐标系。做到这一步，你的实现里通常已经长出了几个没名字的回路，把它们对上名字，后面读状态管理才不迷路。
7. **第 29 章** — 检查点、回放、恢复语义。出问题时能退回去，比事后复盘重要一个数量级。
8. **第 33 章** — 可观测性。这是上生产的门槛：没有 Trace，后面所有问题都只能靠猜。
9. **第 34 章** — 评测体系。生产环境的迭代靠回归，不靠感觉。
10. **第 35 章** — 成本与性能。跑量起来之后，成本模型和提示缓存命中率直接决定这事儿能不能做。
11. **第 32 章** — 提示注入与越权。系统开始接触外部内容，这章的威胁模型必须建立。
12. **第 31 章** — 沙箱与执行隔离。只要有一步是执行代码或命令，这就是必读项。
13. **第 36 章** — 生产化检查清单。把前十四章压成一页验收表。
14. **第 6 章** — 反思与自纠错收尾。放在最后是因为它的收益最容易被高估：同一模型评审自己常常只是确认偏见，先学会识别这个陷阱，再决定要不要开反思回路。

**加餐**：打算用 LangGraph 就加第 12 章；要接外部知识库加第 27、30 章；要做多 Agent 再回来读第 20、23、25 章。

### 路线 C：做 Agent 平台 / 框架的架构师（16 章）

**第 2、3、12、14、16、13、19、20、23、24、25、29、33、34、35、39 章。**

排法说明：

1. **第 2 章** — 统一坐标系。平台层最容易出问题的原因，是每个框架的抽象都长得不一样；先用一套自己的词汇去描述它们。
2. **第 3 章** — 架构收益边界。平台最常见的错误是替用户做本该用户自己做的决定。
3. **第 12 章** — LangGraph 的状态图是编排范式本体：节点、边、归约、检查点、中断，这套词汇是其他框架的参照系。
4. **第 14 章** — AutoGen 与 OpenAI Agents SDK 两条路线的对照：会话式多 Agent 和"单 Agent + 交接 + 护栏"，平台要支持哪条路线，取决于你的用户群。
5. **第 16 章** — PydanticAI、Agno 与 smolagents。类型驱动路线在企业里很常见，代码优先路线在工具密集场景里很常见。
6. **第 13 章** — LlamaIndex。数据驱动是另一类用户，别用编排框架的思路去套检索型 Agent。
7. **第 19 章** — 选型决策树与十个反模式。这章可以直接改造成你自己的平台选型问卷。
8. **第 20 章** — 多 Agent 判据。平台层尤其要先想清楚"什么时候不该上多 Agent"，否则会把复杂度当成卖点推给用户。
9. **第 23 章** — 协作拓扑与调度。这是平台真正要抽象的东西，不是对话。
10. **第 24 章** — MCP 与 A2A 的职责边界，以及内部消息契约的设计。平台对外暴露什么接口，这章是前提。
11. **第 25 章** — 多 Agent 失效模式与成本治理。平台需要提供熔断与归因能力，而不是让每个用户自己踩坑。
12. **第 29 章** — 检查点、回放、共享状态。持久化语义是平台级的基础设施，跨 Agent 共享状态的取舍在这里。
13. **第 33 章** — 可观测性语义设计。Trace/Span 的字段规范一旦定错，迁移成本极高，值得一开始就照着做。
14. **第 34 章** — 评测。平台要能证明自己的版本比上一版好。
15. **第 35 章** — 成本与性能。平台要么提供成本归因，要么用户会自己来算账单然后来找你。
16. **第 39 章** — 协议生态全景。这是平台最容易被忽略、但生命周期最长的一层：协议会替你把生态接进来。

**加餐**：第 32 章安全基线、第 36 章上线清单要纳入平台自己的发布流程；做 GUI 方向加第 38 章；关注自举方向加第 40 章。

## 四、配套代码怎么用

### 目录结构

`code/` 下有 33 个与章节对应的目录，目录名就是 chapters.json 里各章的 `code_dir` 字段：

```
code/
├── run_all.py                  # 批量跑通全部示例
├── ch02-anatomy/               # 第 2 章：四回路架构
│   ├── main.py
│   └── README.md
├── ch04-react/                 # 第 4 章：ReAct
│   ├── main.py
│   └── README.md
├── ...
├── ch31-sandbox/               # 额外产出 audit.jsonl
├── ch33-observability/         # 额外产出 traces.jsonl
├── ch34-evaluation/            # 额外产出 baseline.json
└── ch37-coding-agents/
    └── demo_repo/              # 一个可以真实改动的示例仓库
```

每个目录里 `main.py` 是可运行版本，`README.md` 说明它演示了本章的哪个机制、以及输出该怎么读。

### 怎么跑

```powershell
# 批量跑通全部示例（默认 mock 模式，离线可用，不消耗任何额度）
python code/run_all.py

# 只跑其中一章的示例
python code/run_all.py --only ch04

# 单章直接跑
python code/ch04-react/main.py

# 跑真实 API（需要自行配置环境变量）
python code/ch04-react/main.py --live
```

几点说明：

- **默认是 mock 模式**，所有示例不联网、不需要 API Key，直接 `python code/<code_dir>/main.py` 就能跑。
- `--live` 会切到真实模型 API，需要自己把环境变量配好；`run_all.py` 永远不传这个参数，所以批量验收不会碰到你的额度。
- `run_all.py` 支持 `--only <子串>` 和 `--timeout <秒>` 两个参数。
- 每章第四节里嵌的是可以直接抄进自己项目的最小实现；`code/` 目录里是同一机制的完整可运行版本。两者可以对照着读。
- 运行会在示例目录下生成 `audit.jsonl`、`traces.jsonl`、`baseline.json` 这类产物文件，它们是给第 31、32、33、34 章的输出格式做参照的，不是残留垃圾。

## 五、一条建议

别按章号顺序从头读到尾。四十章从头读，读到第 20 章的时候你多半已经忘了第 8 章说过什么。

比较省时间的做法是：先花两小时读第 1、2 章，然后直接去你眼下要解决的问题那卷，用上面第三张表反查章节；读完一段，回来补第 3 章和第 36 章——这两章是全书唯一值得从头读到尾的。
