# 第 3 章 为什么需要架构：可靠性、复利与工程约束

## 一、本章要解决的问题

先看一个常见的翻车场景。

某团队做了个工单分类系统：800 字提示词 + 一次模型调用，输出七个类别之一。上线误分类率 18%，业务不满意。

于是他们做了教科书上正确的事：引入编排框架，流程拆成八个节点，加了状态机、检查点、重试和一个"复核 Agent"。三个月后，系统有 2400 行编排代码、四套提示词模板、一个自定义归约器，误分类率 16%。

三个月、三倍人力、两个百分点。真正的解法是另一件事：**先用确定性规则挡掉 70% 的明显样本，剩下的交给模型**。同样是那一次调用，误分类率掉到 5% 以下，代码不到 200 行。

这个案例同时否定了两种极端：一次调用不够用，但"上框架"也不等于解决问题。架构不是正确性保证，它只是让某些失败模式变得可见、可控。

本章要回答的不是"要不要上框架"，而是三个更精确的问题：架构在哪几件事上把"不可控"变成"可控"；一次调用和一套系统的差距能量化到什么程度；什么时候框架是纯负债。

## 二、原理：机制拆解

### 2.1 错误累积与可靠性天花板

设一次模型决策连同紧随其后的执行，整体成功率为 p。链式执行 n 步，端到端成功率是 pⁿ——每步都是一次独立的赌注。

p = 0.95 时的塌陷曲线（第四章的脚本会直接打印这张图）：

```
 步数   端到端成功率
   1       95.0%  #######################.
   4       81.5%  ####################....
   8       66.3%  ################........
  12       54.0%  #############...........
  16       44.0%  ###########.............
  20       35.8%  #########...............
  25       27.7%  #######.................
  30       21.5%  #####...................
```

12 步掉到 54%，30 步只剩 21%。这不是模型的错，是乘法的性质。

关键在于：**架构不提高单步的 p，它只做三件事。**

| 手段 | 做了什么 | 对成功率的影响 |
| --- | --- | --- |
| 缩短关键路径 | N 次决策压成 1 次 | pⁿ → p |
| 混入确定性步骤 | 校验、类型检查、代码分支，p = 1 | 加入不失败的项 |
| 把失败拦在早处 | 护栏、断言、测试提前拦住 | 缩短错误污染后续步 |

所以"可靠性天花板"不是模型能力的上限，而是**关键路径上模型决策次数**的上限。架构的作用就是把这个次数压到 1，第四章的实验给出具体数字。

### 2.2 上下文经济学

token 是三重硬约束：窗口上限、每次调用的钱、模型的注意力——上下文越长，对关键约束的召回越不可靠。

对一个 12 步的任务，两种执行方式的输入 token 差着数量级（按第四章脚本的参数：每轮 800 token 背景 + 60 token 观测）：

- 每步都让模型决策，上下文随步数增长：800 字背景 + 累积观测，12 步共 **13,560 token**
- 一次规划 + 确定性执行，只带摘要：共 **1,520 token**

九倍差距不是靠"少说点话"省下来的，靠架构里四个动作：

| 手段 | 省在哪 | 代价 |
| --- | --- | --- |
| 裁剪 | 只带摘要，原文落盘 | 摘要可能丢信息 |
| 状态化 | 结果存成字段，不重复推导 | 状态结构要设计 |
| 分层 | 不变背景进 system prompt | 背景变了要重建 |
| 确定性化 | 代码能算的别让模型算 | 得先判断哪些能算 |

其中**确定性化**收益最大，也最常被忽略。上一章的"一次推理 + 多次确定性执行"就是它：能用代码得到的中间结果，别让模型再推一遍。重复推理的代价不只是钱：模型每轮重读同样的背景，等于每轮重建对约束的理解，理解会漂移——第 5 轮和第 1 轮的模型已经不是同一个"读者"。

### 2.3 可测试性

LLM 的输出不确定，直接对它写断言会得到一堆随机失败的测试。架构的任务是**把不确定的部分圈起来，让绝大部分代码回到确定的世界**。

| 测试层 | 测什么 | 断言方式 | 覆盖目标 |
| --- | --- | --- | --- |
| 纯函数层 | 工具实现、参数解析、状态归约 | 精确断言 | 100% |
| 契约层 | 决策对象结构、护栏拒绝 | 结构 + 拒绝断言 | 全分支 |
| 行为层 | 端到端轨迹与结果 | 固定 mock 比对轨迹 | 关键场景 |

分层的依据是上一章的"三份账"：**离开状态机的东西是确定的，进上下文的东西是不确定的**。决策对象有 schema，工具参数有类型，护栏有明确的 allow / deny——这些都能精确断言。只有模型生成的自然语言不能，所以要"断言它做了什么"，不是"断言它说了什么"。

## 三、为什么这样设计：取舍与失效条件

### 3.1 框架真正替你解决的就三件事

诚实地列：主流编排框架相对手写循环，多出来的是**持久化与恢复、人在环、可视化调试**。这三件之外的——工具契约、护栏、评测、成本控制——框架都不解决，或者只解决一半。这份清单就是一条现成的选型判据。

### 3.2 边际收益递减：什么时候手写 300 行更好

先说"300 行"是什么：一个状态对象、一个循环、五个工具、检查点落盘、错误处理与重试，加起来约 300 行。用框架写等价的最小图，代码量差不多，但多一层抽象和一层调试跳转——出错时要在节点、边、状态、配置之间来回跳，手写版只有一个调用栈。

判据表：

| 你的情况 | 建议 | 理由 |
| --- | --- | --- |
| 单模型、步骤 ≤ 5、不需恢复 | 手写循环 | 三大能力都用不上 |
| 分支固定在 5 个以内 | 手写循环 | 图建模收益低于成本 |
| 中间必须有人审批 | 上框架 | 人在环是强项 |
| 崩了要从中间续跑 | 上框架 | 检查点是强项 |
| 多 Agent 分工协作 | 上框架 | 交接与路由是强项 |
| 要给非工程同学看过程 | 上框架 | 可视化是强项 |
| 多项目统一 Agent 写法 | 上框架 | 规范统一是强项 |

一句话判断：**如果你的系统用不到持久化恢复、人在环、可视化调试中的任何一项，框架带来的主要是抽象成本、依赖体积和调试跳转。**

### 3.3 三个过度工程化反例

**反例一：把"专家"拆成 Agent。**
一个 6 步任务拆成 4 个 Agent，每个都要重读一遍背景，token 直接翻倍。更糟的是交接处：上游说"我发现这个订单不存在"，在交接摘要里被压成"无结果"，下游当成"查到了但结果为空"，又走了三步才发现不对。**简化**：专家降级成一个工具，一次调用返回完整结论；只在真需要不同模型、权限或上下文时才拆。

**反例二：为了可观测性上框架。**
"我想看到每一步在干什么"，于是引入完整编排框架、自定义归约器和图编辑器。**简化**：先写 trace——每步的动作、参数、返回、耗时、token 落成 JSONL，九成的可观测需求够了；真需要接管或续跑时再上图。

**反例三：把业务流程建成 LLM 节点图。**
一个 5 个分支的退款流程被建成 12 个节点，每个分支一个 LLM 节点。分支条件明明是 `if`，为什么要花一次模型调用？**简化**：分支用代码 if/else，只在真需要语义判断的节点放 LLM。节点图留给"节点内部要做判断"，不用来表达控制流。

三个反例的共同点：架构被用在了它不产生价值的地方。**架构的价值密度在"不确定性密集"的地方最高，在确定性密集的地方最低。**

## 四、动手：最小可实现

下面这个脚本把本章的论点变成可运行的数字：同一个 12 步任务，三种策略各跑 2000 次模拟，比较端到端成功率、模型调用次数和累计输入 token，并打印塌陷曲线。把它保存成 `arch_lab.py` 即可运行。

**依赖**：Python 3.9+，纯标准库，无 API Key，无网络。

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""一次推理 + 多次确定性执行  vs  每步都推理：成本与可靠性对照实验。

纯标准库，无需 API Key。mock 模型按固定种子注入随机失败，对比三种执行策略的
端到端成功率、模型调用次数与累计输入 token，并画出成功率随步数塌陷的曲线。

运行：python arch_lab.py
"""
import random

STEPS = 12          # 一次工单处理需要走多少步
P_STEP = 0.95       # 单步（一次模型决策 + 一次执行）整体成功率
P_PLAN_RIGHT = 0.90  # 方案 B：一次规划就选对整条路径的概率
P_FIXED = 0.60      # 确定性规则能直接挡掉的比例
BASE_TOKENS = 800   # 每轮都要带的不变背景（工单正文、规则说明）
OBS_TOKENS = 60     # 每步新增的观测长度
TRIALS = 2000
SEED = 20261107


def tokens_replan_every_step(steps: int) -> int:
    """方案 A：每步都问模型，上下文随步数线性增长。"""
    return sum(BASE_TOKENS + i * OBS_TOKENS for i in range(steps))


def tokens_plan_once(steps: int) -> int:
    """方案 B：只规划一次，之后确定性执行，只带摘要不重发全量历史。"""
    return BASE_TOKENS + steps * OBS_TOKENS


def run_replan_every_step(rng: random.Random, steps: int):
    """方案 A：每步一次模型决策，任一步失败则整条链失败。"""
    for _ in range(steps):
        if rng.random() > P_STEP:
            return False, steps
    return True, steps


def run_plan_once(rng: random.Random, steps: int):
    """方案 B：一次规划，之后全确定性执行。规划调用失败、或规划选错路径，整条链都失败。"""
    if rng.random() > P_STEP:          # 这次模型调用本身失败
        return False, 1
    if rng.random() > P_PLAN_RIGHT:    # 规划选错了后续路径
        return False, 1
    return True, 1


def run_rules_first(rng: random.Random, steps: int):
    """方案 C：先用确定性规则挡掉一部分，剩下的才走方案 A。"""
    if rng.random() < P_FIXED:
        return True, 0
    ok, calls = run_replan_every_step(rng, steps)
    return ok, calls


def curve(p: float, max_steps: int = 30):
    """成功率随步数塌陷的曲线。"""
    rows = []
    for n in range(1, max_steps + 1):
        rows.append((n, p ** n))
    return rows


def bar(rate: float, width: int = 24) -> str:
    filled = int(round(rate * width))
    return "#" * filled + "." * (width - filled)


def main() -> int:
    print("=" * 66)
    print(f"一、成功率随步数塌陷（单步成功率 p = {P_STEP}）")
    print("=" * 66)
    print(f"{'步数':>4}  {'端到端成功率':>10}  曲线")
    for n, rate in curve(P_STEP):
        mark = "  <- 12 步" if n == STEPS else ""
        print(f"{n:>4}  {rate * 100:>9.1f}%  {bar(rate)}{mark}")

    print()
    print("=" * 66)
    print(f"二、三种执行策略对照（{STEPS} 步任务，{TRIALS} 次模拟）")
    print("=" * 66)
    rng = random.Random(SEED)
    rows = []
    for name, fn in (("A 每步都推理", run_replan_every_step),
                     ("B 一次规划+确定性执行", run_plan_once),
                     ("C 规则先挡+模型兜底", run_rules_first)):
        wins = 0
        calls = 0
        for _ in range(TRIALS):
            ok, c = fn(rng, STEPS)
            wins += ok
            calls += c
        rows.append((name, calls / TRIALS, wins / TRIALS))

    print(f"{'策略':<24}{'模型调用/任务':>12}{'端到端成功率':>12}{'平均输入 token':>14}")
    print("-" * 66)
    tok_a = tokens_replan_every_step(STEPS)
    tok_b = tokens_plan_once(STEPS)
    tok_c = tok_a * (1 - P_FIXED)
    for (name, c, s), tok in zip(rows, (tok_a, tok_b, tok_c)):
        print(f"{name:<24}{c:>12.1f}{s * 100:>11.1f}%{tok:>14,}")
    print("-" * 66)
    print("注：以上为本脚本按固定种子模拟得出，非任何真实评测。")
    print()
    print("=" * 66)
    print("三、方案 B 的敏感性：规划正确率下降时它还剩多少优势")
    print("=" * 66)
    print(f"{'规划正确率':>10}  {'端到端成功率':>12}  {'相对 A 的成功率':>14}")
    for q in (0.95, 0.90, 0.80, 0.70, 0.60):
        s = P_STEP * q
        print(f"{q * 100:>9.0f}%  {s * 100:>11.1f}%  {s / (P_STEP ** STEPS):>13.1f}x")
    print("-" * 66)
    print("结论：即使规划正确率降到 70%，方案 B 的成功率仍高于方案 A，")
    print("      而输入 token 只有方案 A 的约九分之一。")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

输出：

```
策略                           模型调用/任务      端到端成功率    平均输入 token
------------------------------------------------------------------
A 每步都推理                         12.0       54.6%        13,560
B 一次规划+确定性执行                     1.0       85.3%         1,520
C 规则先挡+模型兜底                      4.7       81.1%       5,424.0
------------------------------------------------------------------

     规划正确率        端到端成功率       相对 A 的成功率
       95%         90.2%            1.7x
       90%         85.5%            1.6x
       80%         76.0%            1.4x
       70%         66.5%            1.2x
       60%         57.0%            1.1x
```

三个方案说明三件事：

**方案 A 的 54.6% 不是模型不行，是 12 次赌注的数学结果**，而且同时烧掉了 12 倍模型调用和 13,560 token 的输入。

**方案 B 把 12 次赌注变成 1 次**，成功率从 54.6% 抬到 85.3%，token 降到 1,520。但风险换了个位置：从"每步都可能错"变成"规划一次定全局"。第三段敏感性分析就是为诚实面对这点——规划正确率掉到 70% 时方案 B 仍有 66.5%，仍高于方案 A，token 只有九分之一。这正是现实里方案 B 必须配护栏的原因：规划错时要有东西拦下来，而不是让后面 11 步确定性执行把错误放大。

**方案 C 是本节开头那个工单分类系统的正解**，成本和收益都居中。现实里大多数系统落在这条线上，不是两个极端。

## 五、开源实现对照

评估框架时，别问"它有多少功能"，问"它替你解决了什么、你还剩什么"。

| 项目 | 替你解决 | 你仍然要自己解决 |
| --- | --- | --- |
| LangGraph | 状态图、检查点与恢复、循环与分支编排 | 评测、护栏、成本控制、工具契约 |
| PydanticAI | 输入输出的类型契约、依赖注入 | 编排、持久化、护栏 |
| smolagents | 极简动作表示：代码块替代 JSON 工具调用 | 沙箱、持久化、评测 |
| AutoGen | 对话即协作、消息路由 | 状态持久化、评测 |
| OpenAI Agents SDK | 交接、护栏、追踪 | 状态持久化、真正的评测 |

三点观察：

**LangGraph 覆盖了 3.2 节判据表里的"持久化恢复"和"可视化调试"两行**，这两项恰好最难自己写；不需要它们，它就是净负债。

**追踪不等于评测。** OpenAI Agents SDK 提供追踪，LangSmith 提供数据集与评估——两件事。追踪告诉你发生了什么，评测告诉你这样对不对。只上追踪不建评测集，等于装了仪表盘却没有仪表。

**框架的真实成本要算进账**：依赖体积（LangGraph 会拖进一串传递依赖）、抽象层数、调试跳转次数（框架把一次调用拆成多次）、版本升级风险——框架 API 变动比业务代码快。

所以选型顺序是：先算**关键路径上有几次模型决策**（经验值：超过 3 次就有架构理由），再确认是否需要**恢复、人在环、可视化**，然后才挑框架。顺序反了，就是第一节那个 2400 行编排代码换来 2 个百分点。

## 六、坑与检查清单

**可靠性**

- [ ] 数过关键路径上模型决策的次数，超过 3 次就该压缩
- [ ] 确定性步骤（校验、分支、计算）没经过模型
- [ ] 每步的错误类型可区分：失败 / 空 / 成功是三回事
- [ ] 失败被尽早拦住，不是传播到最后变成错误结论

**上下文成本**

- [ ] 统计过一次任务的累计输入 token，不只是一次调用
- [ ] 进上下文的是裁剪后的摘要，原始返回落了盘
- [ ] 不变的背景没有被每轮重发
- [ ] 中间结果存成状态字段，不是每轮重新推导
- [ ] 代码能算的中间结果，没让模型再算一遍

**可测试性**

- [ ] 工具、解析、状态归约是纯函数，有 100% 覆盖的单元测试
- [ ] 决策对象有 schema，护栏的拒绝路径有断言
- [ ] 没有对模型输出做精确字符串断言

**选型（防过度工程化）**

- [ ] 上框架前先量过现状：步数、token、成功率
- [ ] 业务流程的固定分支在代码里，不在图里
- [ ] "专家"是工具不是 Agent，除非真需要不同模型、权限或上下文

## 七、小结与延伸阅读

本章的核心结论三条。

第一，**架构解决的是错误累积，不是模型能力**。可靠性天花板由关键路径上的模型决策次数决定，架构靠缩短路径、混入确定性步骤、提前拦截失败来压低它。

第二，**token 是硬约束，重复推理是最贵的浪费**。一次推理加多次确定性执行，把 12 次赌注变成 1 次，token 降到九分之一。上下文经济学还决定模型能不能稳定记住约束。

第三，**框架是工具不是信仰**。它真正替你解决的只有持久化恢复、人在环、可视化调试三件；都不需要时，手写 300 行的循环在代码量、调试效率和演进速度上更划算。**架构的价值密度在不确定性密集的地方最高，在确定性密集的地方最低**——这句既解释为什么有时必须要架构，也解释为什么那个工单分类系统最终只写了 200 行。

下一卷进入单体 Agent 的核心模式：ReAct、提示增强、反思、规划、工具契约、代码即行动、上下文工程、停止准则——每章都建立在本卷的四回路坐标系之上。
