# 第 28 章 上下文窗口工程：检索、压缩、淘汰与分层

## 一、本章要解决的问题

先看两个真实形状的故障。

**故障一：答案错了。** 一个实施助手接了长期记忆，用户问"现在预算是多少？"，它答了 8 万。上下文里同时躺着两条——三个月前"预算 8 万"和上周"预算能不能提到 12 万"。系统没有失效标记，两条并列，模型挑了先看到的那条。更隐蔽的版本是滚动摘要：旧值留在摘要里，每轮都被当作"当前状态"复述一遍。

**故障二：钱花了。** 同样的功能，某团队把检索结果拼在提示词最前面，每轮都变；另一团队把系统提示、工具定义、长期约束放最前面，检索结果放最后。前者每轮把整段上下文重新计费，后者大部分 token 命中缓存，功能一样，账单差着几倍——差别不在模型，在**前缀的排布**。

这两个故障指向同一个结论：上下文管理不是提示词技巧，是工程问题。它有四种基本操作——检索、压缩、淘汰、分层，每种都有可调的参数和可测的指标，而且互相耦合：压缩策略决定缓存能不能命中，淘汰策略决定检索结果还剩多少。

本章把这四种操作拆开，给出算法、参数与指标，说明它们与 Prompt Caching 的强耦合关系，最后回答：长上下文模型出来之后，这些手段还需要吗。

## 二、原理：机制拆解

### 2.1 分层记忆：三层结构与触发条件

Letta（MemGPT）把记忆分成三层，这个划分至今仍然是最实用的一种：

```
┌─ core    常驻区 ────────────────────────────────┐
│  当前任务必须知道的少量事实: 预算、交付时间、硬约束 │
│  每次必带, 数量以"十几条"为上限, 越少越好         │
├─ recall  近期区 ────────────────────────────────┤
│  对话历史。按当前问题检索命中, 带上原文            │
│  触发条件: 与当前问题相关(且未被压缩掉)           │
├─ archival 归档区 ──────────────────────────────┤
│  长文档、旧方案、历史项目、外部资料                │
│  触发条件: 当前层答不了这个问题, 出现"缺口"        │
└──────────────────────────────────────────────────┘
```

检索顺序是固定的：**core 常驻 → recall 命中 → 缺口检测决定是否下沉 archival**。

关键在第三条。多数实现把"下沉"写成"相似度低于阈值"，这是错的：相似度低只说明词没对上，不代表这一层没有答案。正确的判据是**槽位覆盖检查**——先解析出问句要的量值类型（时长、金额、时间点），再看当前层里有没有对应单位的数值。

这个改动有两个直接效果：下沉变便宜了——recall 层答得完的问题不必再动 archival；而"当前层答不了"变成可测信号——下沉率、下沉后的命中率，都能直接统计。

还有一个容易忽略的点：**core 要有覆盖语义，不能只有追加**。同一主题的新值出现时旧值必须标记失效，否则 core 里会同时躺着两个矛盾的预算。旧值不必删——它在审计和"当初定的是多少"这类问题里还有用——但默认不该出现在当前上下文里。

### 2.2 历史压缩：三种算法与信息损失

对话历史只增不减，很快就会把预算吃光。常见的三种压缩算法，差别全在信息损失的类型上。

**滑窗**：只保留最近 N 轮。实现最简单，成本最低，损失也最粗暴——早期约束直接消失。用户第三轮说过"这个项目不能超过 8 万"，第十轮上下文里已经没有这句话，Agent 报价时完全不知道自己超了。

**滚动摘要**：把历史压成一段话，每轮更新。便宜，但有三种典型损伤：链式累积（前一轮摘要的失真层层叠加）、粘性旧值（摘要里保留了某个数值，事实后来变了没人回头改）、不可逆（原文被覆盖后，否定词、例外条款、具体数字一起没了）。

**抽取式压缩**：不改写，只从历史里挑出含约束信号的句子留下。它最费 token，却保真最高——它没有重写任何东西，也就没有制造新错误。

三种算法对同一段历史的实测结果（配套代码跑出来的，取最后一轮提问"现在预算是多少"时的数据；第一轮提问时数字会不同，因为当时的历史更短）：

| 策略 | tokens | 事实保留 | 问"现在预算是多少" | 问"最初的预算是多少" |
|---|---|---|---|---|
| 滑窗（留最近 2 轮） | 20 | 1/5 | 12 万 ✓ | 12 万 ✗ |
| 滚动摘要 | 20 | 1/5 | 8 万 ✗ | 8 万 ✓ |
| 抽取式 | 50 | 5/5 | 12 万 ✓ | 8 万 ✓ |

这张表比理论说明问题：滑窗答对了当下，答不出历史；摘要恰好反过来，而且它的"现在"答案会随每轮重写漂移；只有抽取式两个都对，代价是 token 数多一倍以上。所以选型不是"哪个更好"，而是"这个场景更怕哪种损失"：单轮问答滑窗够了；要能回溯"当初怎么定的"，就别用摘要。

### 2.3 价值淘汰：在预算里留谁

检索和压缩解决"有什么"，淘汰解决"留什么"。给定一个 token 预算，从候选集合里挑出值得留下的，本质是带约束的排序问题。四个打分维度：

- **相关度**：与当前问题的重合度。
- **新鲜度**：越近的越重要，但用衰减而不是硬截断。
- **未闭合约束**：最关键的一项。一条"预算 12 万"是还在生效的约束，分数应显著高于一句"顺便把最终方案再发一遍"。
- **来源可信度**：用户明说的、工具返回的、模型自己推断的，三者不该等价。

四维加权求和，按分数从高到低装进预算，装不下的淘汰。再加两条规则：

- **被覆盖的旧事实默认不进上下文**，但用户明确追问历史（"最初定的是多少"）时把它请回来。旧版本不是垃圾，是按需调用的档案。
- **不能淘汰被引用的项**。一条结论引用了另一条事实，后者不能单独删掉，否则上下文里会出现悬空引用。工程上要给每条上下文维护依赖关系，淘汰时成组处理。

### 2.4 与 Prompt Caching 的强耦合

多数推理服务提供前缀缓存：请求的 token 序列如果和上一次相同的前缀能复用，就按缓存价计费；**从前缀第一个不同的 token 起，后面全部作废**。顺序即成本。

稳定的组织方式是：

```
[系统提示][工具定义][长期约束][历史(追加式)][检索结果][当前问题]
 └── 稳定前缀：每轮基本不变 ──┘        └── 易变，放最后 ──┘
```

配套代码实测了三种布局的前缀命中率（同一段对话连续两轮）：

| 布局 | 前缀命中率 |
|---|---|
| 检索结果放最前 | 14.5% |
| 检索结果放最后，但历史每轮整体重写 | 49.8% |
| 检索结果放最后，历史只追加 | 74.5% |

结论有两层。第一层很直白：易变内容必须往后放，检索结果、当前问题、时间戳这类每次都变的东西放在前面等于主动放弃缓存。第二层容易被忽略：**压缩策略和缓存策略会互相打架**。滚动摘要每轮整体重写，缓存前缀在历史段就被打断，命中率掉到一半；抽取式压缩只保留句子、前缀稳定，命中率明显更高。"用什么压缩算法"同时决定了你要付多少 token 费。

另外：可缓存前缀有最小长度门槛，太短等于没开缓存；命中率要看"命中 token 数 / 总 token 数"，不是看请求数。

## 三、为什么这样设计：取舍与失效条件

### 3.1 四种操作什么时候不该用

**检索**：不要在没有分层的情况下把所有东西丢进向量库再 top-k。core 层的当前硬约束本来就该常驻，交给相似度检索是自找麻烦。

**压缩**：不要用摘要承载需要逐字保真的内容——错误码、参数名、合同条款、带否定或例外的句子。摘要适合脉络，不适合事实。

**淘汰**：不要把打分权重的默认值当成真理。相关度权重调高，上下文里就只剩当前话题，跨轮约束全丢；未闭合约束权重调高，历史里的话就永远退不出去。权重要按业务调，并配回归用例。

**分层**：不要为一次性任务建三层。任务跑完就结束，三层全是成本。
### 3.2 长上下文模型出现后，这些工程手段还需要吗

需要，但理由变了，而且变得更强。

过去上下文管理是**容量工程**：窗口装不下，必须压缩、淘汰、分层，否则直接失败。长上下文模型把"装不下"基本消解了——窗口从几万 token 变成几十万，原始对话可以整个塞进去。

但换来的不是"不需要管理"，而是三个新问题：

1. **成本与延迟随 token 线性上升**。把十万 token 全塞进去，账单和首字延迟都是实打实的。缓存能缓解，但前提是你按 2.4 的方式排布前缀——不会排布的人，长上下文只会让账单涨得更快。
2. **注意力是有预算的**。上下文越长，模型对中段信息的遵循度越容易下降。真正起作用的可能只有一句约束，它在第 400 个 token 还是第 40000 个 token，可靠性不一样。长上下文把"装得下"变成了"注意力放哪儿"——而注意力分配恰恰需要检索和淘汰。
3. **噪声会稀释信号**。上下文里塞满无关的旧对话，模型更容易被带偏，也更容易在多个版本的事实里挑错。历史越长、版本越多，压缩策略的取舍越关键。

所以结论是反直觉的：**长上下文让上下文管理从"兜底手段"变成"必选项"**。以前不做压缩会报 token 超限，现在不做压缩会付更多钱、更慢、更容易答错。变的只是重心——从"怎么塞进去"转向"怎么让注意力落在该落的地方"，而这正是检索、压缩、淘汰、分层一直在做的事。

### 3.3 可调参数与指标

| 参数 | 含义 | 调它的后果 |
|---|---|---|
| 上下文预算（tokens） | 硬上限 | 调小丢信息，调大成本线性上升 |
| 每层召回 top_k | 每层取几条 | 调大引入噪声，挤占预算 |
| 缺口判定方式 | 何时下沉归档 | 判定太松会频繁下沉，太紧则答不上来 |
| 淘汰权重四维配比 | 留谁 | 决定约束与闲聊谁进上下文 |
| 缓存最小前缀长度 | 能否开缓存 | 低于门槛等于白付全价 |
| 历史重写频率 | 多久重写摘要 | 直接决定前缀命中率 |

要盯的指标：各层命中率与下沉率、压缩后的事实保留率、上下文 token 占用与构成、前缀缓存命中率，以及被淘汰内容的"事后有用率"——最后这个能直接告诉你淘汰策略是不是砍错了。

## 四、动手：最小可实现

下面把四种操作接成一个循环，每轮打印实际指标。依赖只有 Python 3.9+ 标准库，mock 模式内置规则抽取与 mock 回答，不需要 API Key；加 `--live` 用真实模型生成最终回答。完整文件见 `code/ch28-context-windowing/main.py`。

```
python main.py                              # 跑完整语料
python main.py --query "现在预算是多少？"      # 换一个问题
python main.py --live                       # 需要 OPENAI_API_KEY
```

```python
# ---- 分层检索: core 常驻 -> recall 命中 -> 缺口检测下沉 archival ----
def missing_slot(self, query, items):
    """问句要的量值类型, 当前层里有没有出现。"""
    blob = " ".join(it.text for it in items)
    for name, (questions, units) in SLOTS.items():
        if any(q in query for q in questions) and not any(u in blob for u in units):
            return name
    return None

# ---- 压缩三算法 ----
def compress_sliding_window(items, keep_last=2):
    """滑窗: 只留最近 N 轮, 早期约束直接消失。"""
    return list(items[-keep_last:])

def compress_rolling_summary(items, state):
    """滚动摘要: 只保留首次见到的值 —— 粘性旧值就是漂移来源。"""
    first = state.setdefault("first_values", {})
    for it in items:
        vals = budget_values(it.text)
        if vals:
            first.setdefault("预算", vals[0] + "万")
    text = "；".join(f"{k} 是 {v}" for k, v in first.items()) + "。"
    return [Item("recall", text, "model", items[-1].turn)]

def compress_extractive(items):
    """抽取式: 只留带约束信号的子句, 不改写原文, 所以不制造新错误。"""
    keep = re.compile(r"(\d|错误码|必须|不能|要|改成|提到|上线|回滚|额度)")
    return [Item("recall", c, it.source, it.turn)
            for it in items for c in clauses(it.text) if keep.search(c)]

# ---- 价值淘汰: 四维打分 + token 预算 ----
def score(self, it, query):
    relevance = overlap_score(query, it.text)
    recency = 1.0 / (1.0 + max(0, self.current_turn - it.turn))
    obligation = 0.0 if it.stale else (
        1.0 if re.search(r"\d|必须|不能|改成|提到", it.text) else 0.0)
    trust = it.trust * (0.3 if it.stale else 1.0)
    total = (0.35 * relevance + 0.15 * recency
             + 0.35 * obligation + 0.15 * trust)
    return round(total, 4)

# ---- Prompt Caching: 最长公共前缀即命中部分 ----
def observe(self, segs):
    cur = [t for sg in segs for t in (f"<{sg.name}>", *pseudo_tokens(sg.text))]
    if self.prev is None:
        self.prev = cur
        return None, len(cur)
    n = 0
    while n < len(self.prev) and n < len(cur) and self.prev[n] == cur[n]:
        n += 1
    self.prev = cur
    return n / len(cur), len(cur)
```

跑起来是这样：

```
[① 分层检索] core 常驻 -> recall 命中 -> 缺口检测下沉 archival
  core     | 要在 5 月上线
  core     | 预算能不能提到 12 万
  recall   | 预算能不能提到 12 万？
  缺口检测: recall 最高分 0.443 -> 当前层可答, 不触发 archival

[② 历史压缩] 三种算法对同一段历史
  策略                tokens      事实保留   问"现在"          问"最初"
  滑窗(留最近2轮)             20     1/5     现在的预算是 12万。    最初的预算是 12万。
  滚动摘要                  20     1/5     现在的预算是 8万。     最初的预算是 8万。
  抽取式                   50     5/5     现在的预算是 12万。    最初的预算是 8万。

[③ 价值淘汰] 预算 130 tokens
  排除 | recall   | 已被新事实覆盖 | 预算 8 万
  占用 76 tokens

[④ Prompt Caching] 三种布局的前缀命中率
  retrieval_first    本轮命中  14.5%
  retrieval_last     本轮命中  74.5%
  history_rewritten  本轮命中  49.8%

[⑤ 最终回答] 现在的预算是 12万。
```

## 五、开源实现对照

- **Letta（MemGPT）** — https://github.com/letta-ai/letta ：分层与换页的源头。core、recall、archival 三区常驻或按需，换入换出由模型通过工具自主决定。
- **LangGraph** — https://github.com/langchain-ai/langgraph ：把"上下文"变成显式的 state，用检查点（checkpoint）按 thread 持久化，支持回放与从某一步恢复。它解决工作记忆的生命周期问题，与本章分层互补。
- **Mem0** — https://github.com/mem0ai/mem0 ：以语义记忆层为核心，提供抽取、更新与检索接口，可直接当 recall 层的后端。
- **LangMem** — https://github.com/langchain-ai/langmem ：给 LangChain 提供长期记忆工具，并把记忆操作分成前台热路径（hot path）与后台（background）两种模式——后者把写入成本从主链路上挪走。
- **OpenAI Agents SDK** — https://github.com/openai/openai-agents-python ：会话级历史由 session 机制承担，属于 recall 区；跨会话的长期记忆仍要接外部记忆层。
- **CrewAI** — https://github.com/crewAIInc/crewAI ：记忆已统一成一个 `Memory` 类，按 scope 树分层（/company、/project、/agent），召回时把语义相似度、新鲜度与重要度混合打分——和本章的"分层 + 淘汰打分"是一回事。
- **LlamaIndex** — https://github.com/run-llama/llama_index ：以索引与检索为中心，Memory 抽象更接近按预算裁剪的对话历史。
- **LangChain**（https://github.com/langchain-ai/langchain ）、**RAGFlow**（https://github.com/infiniflow/ragflow ）：前者是组合式管线，后者把上下文质量在预处理端解决。

框架层面的分工相当一致：会话历史与状态归框架管，长期事实归记忆层管，检索证据归索引管。上下文预算怎么切、缓存前缀怎么排，由上层应用自己决定——这也是这块最容易出问题的原因，因为它没有默认答案。

## 六、坑与检查清单

**分层**

- [ ] core 是主题槽位而不是文本堆，同主题新值必须覆盖旧值
- [ ] 下沉 archival 的判据是"当前层答不了这个槽位"，不是"相似度低"
- [ ] 每一层都有单独的召回参数和命中率统计
- [ ] 一次性任务不建三层

**压缩**

- [ ] 压缩策略经过"事实保留率"验证，而不是凭感觉
- [ ] 摘要只承载脉络，错误码、参数名、条款、否定句不进摘要
- [ ] 摘要与结构化事实表定期做一致性比对，不一致就告警
- [ ] 摘要永远带原文指针

**淘汰**

- [ ] 打分包含"未闭合约束"这一维，权重不是默认摆设
- [ ] 被新事实覆盖的旧值默认不进上下文，追问历史时要能召回
- [ ] 淘汰时检查引用关系，不制造悬空引用
- [ ] 预算是一个硬上限，不是软目标

**缓存**

- [ ] 系统提示、工具定义、长期约束在最前且每轮不变
- [ ] 检索结果、时间戳、当前问题在最后
- [ ] 历史只追加不重写；必须重写时，把它放到缓存边界之后
- [ ] 监控前缀命中率，把它当成一等指标

## 七、小结与延伸阅读

上下文工程的四个动作——检索、压缩、淘汰、分层——看上去是四件事，其实是同一件事：在一个有限的注意力预算里，决定哪些信息值得被模型看见。长上下文模型没有取消这项工作，只是把预算单位从"能不能装下"换成了"注意力放哪儿"。

最容易被忽略的耦合是压缩与缓存：摘要每轮重写一次，缓存前缀就断一次。这两个设计必须在同一张图上画。
