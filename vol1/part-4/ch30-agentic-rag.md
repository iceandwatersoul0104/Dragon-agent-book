# 第 30 章 Agentic RAG：让检索从预处理变成主动决策

## 一、本章要解决的问题

先看一个客服场景。

用户问："订单 250 元，运费多少？电池续航衰减算保修吗？"一个典型的 RAG 系统检索了三条文档，把它们拼进提示词，模型给出了答案。答案里运费那半句说得含含糊糊，保修那半句直接引用了另一条文档里的一句关于"电池保修 6 个月"的话——可用户问的是续航衰减算不算保修，压根没答。整段回答还顺带加了一句"以上规则同样适用于其他所有场景"，这句话在任何一份文档里都找不到出处。

这不是模型不聪明。问题的根源在架构：朴素 RAG 把检索当成流水线上一个**固定步骤**——用户问一次，系统检一次，把 top-k 塞进上下文，模型照着写。它没有"再查一次"的能力，也没有"检查自己引用的证据到底说了什么"的能力。

Agentic RAG 换掉的就是这一点：**检索不再是预处理，而是 Agent 在运行时做出的决策**。它自己决定要不要分解问题、拆成几路、用什么查询去查、查回来的东西够不够、要不要改写查询再查一遍。

本章讲清这套范式怎么落地：架构上多了哪几个决策点，查询分解与多路检索怎么选，引用校验怎么做才不流于形式，检索质量怎么度量，以及——最实际的——什么情况下应该老老实实退回朴素 RAG。

## 二、原理：机制拆解

### 2.1 架构差异：从流水线到循环

```
朴素 RAG（固定流水线）              Agentic RAG（自主循环）
──────────────────────────         ──────────────────────────────
question                            question
   │                                   │
   ▼                                   ▼
┌─────────┐                        ┌──────────────┐
│ 检索一次 │  ← 固定                 │ 计划/分解     │ ← Agent 决策
└────┬────┘                        └──────┬───────┘
     ▼                                   ▼
┌─────────┐                        ┌──────────────┐
│ top-k   │                        │ 多路检索      │ ← 原查询 + 改写查询
└────┬────┘                        └──────┬───────┘
     ▼                                   ▼
┌─────────┐                        ┌──────────────┐
│ 拼上下文 │                        │ 证据校验      │ ← 每条断言都要有出处
└────┬────┘                        └──────┬───────┘
     ▼                                   │ 校验不通过?
┌─────────┐                            ├──► 改写查询再检索(回到上一框)
│ 生成答案 │                            │ 仍然不通过? 丢弃这条断言
└─────────┘                            ▼
                                  ┌──────────────┐
                                  │ 生成带引用的答案 │
                                  └──────────────┘
```

差别不在于多了一个框，而在于**控制权从流水线交给了 Agent**。三个新的决策点：

1. **要不要分解问题**。一个只问单点的请求，分解是浪费；一个问了两件事的请求，不分解就会漏答。
2. **查什么、查几遍**。首轮检索的查询未必合适；Agent 可以用改写后的查询再查。
3. **查回来的东西够不够**。不够就继续，不够就说明白"没查到"，而不是硬编一句。

### 2.2 查询分解（query decomposition）与多路检索

分解的价值在配套代码里看得很清楚。问题"订单 250 元，运费多少？电池续航衰减算保修吗？"分解成两条子查询（sub-query）——"订单 250 元运费多少"和"电池续航衰减算保修吗"——各自命中不同文档。朴素管线只查一次，拿到的是同一篇文档，第二个问题自然落空。

三种常见的增强手段，取舍不一样：

- **假设性文档嵌入（HyDE）**：先让模型写一段"假设性答案"，用这段答案当查询去检索。原理是答案文本和真实文档的措辞更接近，能跨过"用户用词和文档用词不一样"的沟壑。代价是多一次模型调用，而且假设错了会带偏检索——所以它只能作为**并行的一路**，不能取代原查询。
- **multi-query**：同一个问题生成多个措辞不同的查询，合并结果去重。它的收益是提高召回多样性，代价是查询之间高度相似时几乎是白花钱。
- **并行子查询**：按问题分解出的多个维度同时发起检索。这是解决"多问题只答一半"最直接的办法，因为它天然保证每个维度都有一次独立的检索机会。

工程上三者一起用才完整：每个子查询跑原查询和 HyDE 各一次，合并候选集，再按维度去重。配套代码里就是这么做的，平均每题 3.6 次检索。

### 2.3 引用校验与引用幻觉

引用幻觉有两种形态：

- **凭空引用**：答案里写"依据《XX 政策》第 3 条"，但没有这条文档，或者文档里没这段话。
- **挂错引用**：句子是真的，引用也是真的，但两者对不上——说的是 A 条款，引的是 B 文档。

校验要挡的是这两种。配套代码里的规则只有两条，但两条都必要：

1. **片段必须真实存在于被引用的文档里**。答案句子和它引用的原文片段不是一回事，片段为空就等于凭空写的。这条挡掉的是"顺手加一句"式的收尾语。
2. **片段必须包含这条断言声称的意图维度**。回答"运费"问题却引了一段只讲包邮门槛的话，是挂错引用。

更严格的做法是用自然语言蕴含模型判断"片段是否蕴含断言"，但那多一次模型调用。规则版校验的价值是**便宜且可解释**：失败时能直接告诉你哪条断言没有出处。

校验失败之后怎么办？改写查询再检索一轮：把缺失的维度词补进查询，重新检索。仍然找不到，就**把这条断言从答案里删掉**——宁可少说一句，也不要留一句查无实据的话。

### 2.4 检索质量怎么度量

RAG 的评估最容易被做成"看着还行"。三个可自动计算、互不重复的指标：

- **命中率（hit@k）**：答案里**真正引用了**应引用文档的比例。注意是"用上了"，不是"候选集里出现过"——后者会让检索 top-3 的朴素管线看起来分数很高，但它其实只引用了其中一篇。
- **支撑率（support rate）**：答案中的断言，有多少条能被它的引用片段支撑。没有出处的断言占比越高，支撑率越低。
- **忠实度（faithfulness）**：答案内容有多少来自被引用的片段。实现上可以近似成"答案实词中不在任何引用片段出现的比例"，越低越好。

配套代码里同一批五个问题的实测：

| 方案 | 命中率 | 支撑率 | 忠实度 | 平均检索次数 |
|---|---|---|---|---|
| 朴素 RAG | 0.6 | 0.5 | 0.477 | 1.0 |
| Agentic RAG | 1.0 | 1.0 | 1.0 | 3.6 |

三个质量指标全线上升，代价是检索次数涨了三倍多——这就是这个范式的全部交易。

## 三、为什么这样设计：取舍与失效条件

### 3.1 各种手段什么时候不该用

**查询分解**：单点问题不要分解。"今天天气怎么样"拆成三个子查询是纯浪费。判据是问句里出现了几个互不相干的意图维度。

**HyDE**：术语精确、编号精确的问题不要用。查错误码、查订单号、查具体条款号时，假设性答案反而把精确标识稀释掉了——HyDE 的价值在于跨措辞，不在于猜内容。

**multi-query**：语料小、查询与文档用词高度一致时不要用。它提高的是召回多样性，语料里没有多样性可提的时候，它只是多花几次检索。

**引用校验**：所有面向用户的场景都要做，成本极低。只有纯内部、无人核查的中间产物可以省。

**自主循环**：不要给"检索一定一次就够"的场景上 Agentic 循环。延迟敏感的入口（搜索框补全、实时客服首句）上循环，等于把 P99 延迟乘上循环轮数。

### 3.2 何时退回朴素 RAG

这是最实际的一节。三条判断：

1. **问题复杂度可判定时，按问题分流**。最省事的做法是先用规则或一个轻量分类器判断"这个问题是单点还是多点"：单点走朴素 RAG，多点走 Agentic。配套代码里的意图维度识别就是这种分流器的简化版。
2. **有硬延迟预算时，循环必须有上限**。检索次数上限、轮次上限、token 预算，三个都得设死。超限就带着"未找到依据"作答，而不是继续查下去。
3. **收益不覆盖成本时退回**。如果语料质量高、问题简单，朴素 RAG 的命中率和 Agentic 差不多，那多出来的三次检索就是纯亏。

还要说清 Agentic RAG 不能替代的东西：它解决的是"该查什么、查几遍、证据够不够"，不解决"语料里根本没有答案"。检索质量的上限还是由语料和切块决定的。配套代码里 Q2 的答案虽然引用了正确的文档，但引的是包邮门槛那一句而不是"退货运费谁承担"那一句——Agentic 循环能保证答案有出处、出处相关，但保证不了引用的就是最贴切的那一句。

### 3.3 一份能落地的混合架构

真实系统里两种模式是共存的：

```
             ┌─ 复杂度判断(规则/轻量模型) ─┐
question ────┤                             ├──► 简单: 朴素 RAG(1 次检索)
             └─► 复杂: Agentic 循环 ───────┘        │
                     │                                 │
                     └─► 带引用的答案 ◄────────────────┘
```

两条路都输出同样格式的结果（断言 + 引用），下游的呈现层、审计日志、评估脚本完全共用。评估要**按分流结果分别看指标**——把简单问题和复杂问题混在一起平均，会掩盖两边的真实短板。

## 四、动手：最小可实现

下面把两条管线放进同一份语料里对照。依赖只有 Python 3.9+ 标准库，mock 模式内置规则与 mock 答案，不需要 API Key；加 `--live` 用真实模型生成 HyDE 假设与最终措辞。完整文件见 `code/ch30-agentic-rag/main.py`。

```python
# ---- 查询分解: 按子句识别意图维度, 具体维度覆盖宽泛维度 ----
def decompose(question):
    subs, pending = [], ""
    for clause in re.split(r"[，？?；;。]", question):
        found = [n for n, kws in ASPECTS.items() if any(k in clause for k in kws)]
        if not found:
            pending += clause          # 无维度的前置定语并入后面那个子句
            continue
        specific = [n for n in found if n in SPECIFIC]
        found = specific or [n for n in found if n in GENERAL] or found
        for name in found:
            sub = f"{pending}{clause} {name}"
            pending = ""
            if sub not in subs:
                subs.append(sub)
    return subs or [question]

# ---- 引用校验: 片段必须真实存在, 且必须包含该断言声称的维度 ----
def verify(assertion):
    if not assertion.citation or not assertion.span:
        return False                       # 凭空写的 -> 引用幻觉
    if assertion.aspect and assertion.aspect not in assertion.span:
        return False                       # 挂错引用 -> 答非所问
    return True

# ---- Agentic 循环: 分解 -> 多路检索 -> 校验 -> 必要时改写再检索 ----
def agentic_pipeline(question, retriever, hyde_fn):
    calls = rewrites = rounds = 0
    retrieved, sub_best = {}, []
    for sub in decompose(question):
        aspect = sub.rsplit(" ", 1)[-1]
        local = []
        for q in (sub, hyde_fn(sub)):     # 原查询 + HyDE 假设查询, 并行两路
            calls += 1
            local += retriever.search(q, top_k=2)
        if local:
            sub_best.append((sub, aspect, max(local, key=lambda h: h.score)))

    assertions = []
    for sub, aspect, hit in sub_best:
        span, _ = retriever.best_span(hit.doc_id, sub)
        if any((a.citation, a.aspect) == (hit.doc_id, aspect) for a in assertions):
            continue
        a = Assertion(span, hit.doc_id, span, aspect=aspect)
        a.supported = verify(a)
        assertions.append(a)

    for _ in range(2):                    # 校验不过 -> 补维度词改写查询再查
        bad = [a for a in assertions if not a.supported]
        if not bad:
            break
        for a in bad:
            calls += 1; rewrites += 1
            for h in retriever.search(f"{a.aspect} {a.text}", top_k=3):
                span, _ = retriever.best_span(h.doc_id, f"{a.aspect} {a.text}")
                if a.aspect in span:
                    a.text, a.span, a.citation = span, span, h.doc_id
                    a.supported = verify(a)
                    break
    return Answer(assertions, calls, rewrites)
```

跑起来是这样：

```
问题: 订单 250 元，运费多少？电池续航衰减算保修吗？
  [朴素] 检索 1 次 -> ['d4', 'd2', 'd1']
         答案只覆盖了保修那一半, 并附了一句无出处的收尾语
  [Agentic] 子查询: ['订单 250 元运费多少 运费', '电池续航衰减算保修吗 保修']
         检索 4 次 -> ['d2', 'd1', 'd3', 'd4']
         答案: 单笔订单实付金额满 299 元包邮，未满收取 12 元运费。（来源：d2）
               电池续航衰减属于正常损耗，不属于质量问题，不予保修。（来源：d4）

  方案            命中率       支撑率       忠实度       检索次数
  朴素 RAG        0.6       0.5       0.477     1.0
  Agentic RAG     1.0       1.0       1.0       3.6
```

## 五、开源实现对照

- **LlamaIndex** — https://github.com/run-llama/llama_index ：Agentic RAG 形态最齐全的框架之一，把"要不要再查、怎么查"做成独立的引擎：子问题查询引擎（SubQuestionQueryEngine）把一个问题拆成若干子问题分别检索再合并，HyDE 查询改写器（HyDEQueryTransform）配 TransformQueryEngine 负责生成假设性答案做检索，两者都能挂到同一套索引上。
- **LangChain** — https://github.com/langchain-ai/langchain ：以检索器组合件的方式提供同样的能力：multi-query 检索器一次生成多个查询再合并去重，自查询检索器让模型把自然语言转成结构化过滤条件，HyDE 用提示模板加检索器组成一条链，另有上下文压缩（contextual compression）检索器负责在注入前裁剪。
- **LangGraph** — https://github.com/langchain-ai/langgraph ：把 Agentic RAG 做成显式状态图。检索是一个节点，校验之后用条件边决定是"回到检索节点再查"还是"去生成答案"，轮次上限和预算都写在图里——这正是第 29 章说的"把控制流显式化"。
- **OpenAI Agents SDK** — https://github.com/openai/openai-agents-python ：检索被做成工具，模型自己决定调不调、调用几次、用什么参数；护栏（guardrails）可在输入与输出两侧做校验。
- **CrewAI** — https://github.com/crewAIInc/crewAI ：用角色与任务把"检索者"和"综合者"拆成不同 Agent，检索任务的产出由综合任务合并，是多 Agent 形态的 Agentic RAG。
- **RAGFlow** — https://github.com/infiniflow/ragflow ：两条路都走——先把上下文质量放在预处理端，靠深度文档解析与可追溯引用让检索回来的东西更可靠；同时内置了 Agentic 检索，由模型拆解问题、多轮检索并校验证据。
- **Mem0**（https://github.com/mem0ai/mem0 ）、**Graphiti**（https://github.com/getzep/graphiti ）、**Letta**（https://github.com/letta-ai/letta ）：本身不是 RAG 框架，但它们的记忆层可以作为 Agentic 检索的后端——把"查什么"和"记住什么"打通。

对照下来有一条一致的趋势：**框架把"检索"从固定步骤改成了可编排的节点或工具**，剩下的判断权交给模型或者显式的状态图。

## 六、坑与检查清单

**分解与查询**

- [ ] 只在问题包含多个互不相干的意图维度时才分解
- [ ] 每个子查询独立检索，不要用合并后的候选集去喂所有子查询
- [ ] HyDE 只作为并行的一路，原查询必须保留
- [ ] 查具体编号、错误码、条款号时不用 HyDE
- [ ] 子查询的维度词要带回去，否则改写后跑偏

**引用与校验**

- [ ] 每条断言都带引用，引用指向具体文档与具体片段
- [ ] 校验规则同时挡"凭空引用"和"挂错引用"
- [ ] 校验不通过的断言宁可删掉，不要让它留在答案里
- [ ] 呈现层能把引用回跳到原文，读者自己也能核
- [ ] 校验失败率是被监控的指标，不是日志里没人看的数字

**评估与成本**

- [ ] 命中率按"答案真正引用了"统计，不按"候选集里出现过"
- [ ] 支撑率与忠实度分开看：前者看有没有出处，后者看出处对不对得上
- [ ] 简单问题与复杂问题分开统计指标
- [ ] 检索次数、轮次、token 三条预算都设了硬上限
- [ ] 超限时系统能给出"没查到依据"，而不是继续查或硬编

## 七、小结与延伸阅读

Agentic RAG 的实质不是"多查几次"，而是**把检索的控制权从流水线交回给 Agent**：它自己决定拆不拆、怎么拆、查几遍、够不够、要不要改写。它带来的是质量指标的全线提升（配套代码里命中率 0.6→1.0、支撑率 0.5→1.0），代价是检索次数涨了三倍多。

所以正确的落地姿势不是全量切换，而是**按问题复杂度分流**：简单问题继续走朴素 RAG 把延迟压住，复杂问题才走自主循环，并且把轮次和预算死死钉住。
