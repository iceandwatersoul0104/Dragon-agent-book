# 第 29 章 检查点、回放与多 Agent 共享状态

## 一、本章要解决的问题

先看两个事故。

**事故一：邮件发了两遍。** 一个多 Agent 的采购审批流程跑了二十多步，第十九步进程被 OOM 杀掉。没有检查点，只能从头重跑。结果是订单系统里出现了两条预留记录，邮件发了两封，其中一封还是发给还没批准的那一版方案。问题的根源不是"没有检查点"，而是**重放不安全**——步骤里调了有副作用的工具，而重放会再执行一次。

**事故二：改不动一个参数。** 线上有个 Agent 生成的方案质量不稳定，产品经理问："如果当时检索阈值是 0.6 而不是 0.4，结论会变吗？"没有回放能力，只能把当时的对话、当时的中间结果、当时的模型输出一份份手工捞出来重放，两天后勉强复现出一个"大概是这个结果"的结论。

这两个事故指向同一个东西：**状态持久化**。它不只是"崩溃后能接着跑"，更是恢复、时间旅行（time travel）调试、多 Agent 共享状态三件事的共同载体。

本章讲清五件事：检查点（checkpoint）存什么、什么时候写；事件溯源（event sourcing）和状态快照的差别；怎么从任意历史步重跑并对比分支；多 Agent 共享状态的四种模式各付什么代价；崩溃后重放到底安不安全。

## 二、原理：机制拆解

### 2.1 检查点的数据结构与写入时机

检查点有两种基本形态。**快照**是一次性把整个状态存下来：`{step, state, ts, meta}`。**事件**只记录这一步的变更：`{step, op, path, value, ts}`，`path` 是状态里的路径（比如 `["quotes", "widget"]`），重放时按顺序应用即可还原。

写入时机有三个可选粒度，选哪个等于选了一种恢复语义：

| 粒度 | 一次检查点存什么 | 适合什么 | 代价 |
|---|---|---|---|
| 每步 | 一个业务步骤结束时 | 步骤边界与业务语义对齐的流程 | 工具内部崩溃则整步重来 |
| 每工具 | 每次工具调用前后各记一次 | 工具密集、副作用重的流程 | 写放大明显 |
| 每消息 | 每轮对话 | 对话驱动的助手 | 工具密集时粒度太粗 |

真正要记住的是这条规则：**检查点要写在这一步的所有副作用都完成之后。**

这个位置决定的是"重放"是至多一次还是至少一次。写在副作用之前，崩溃后重放会重复执行副作用（发两封邮件、下两次单）；写在副作用之后，崩溃重放会在"副作用已完成但结果没记下来"时重复触发工具——所以必须配上幂等（idempotency）键。两者都不完美，区别在于：写在之后，错误最多表现为"工具被调用两次"，靠幂等键可以收敛成一次；写在之前，重复副作用可能已经落到不可回滚的外部系统里。

### 2.2 事件溯源 vs 状态快照

两种模式的差别可以列成一张表：

| 维度 | 状态快照 | 事件溯源 |
|---|---|---|
| 恢复速度 | 直接读，快 | 需要重放，慢 |
| 存储成本 | 每步一份完整状态，双重增长 | 只存变化，线性增长 |
| 可重放性 | 只能回到快照点 | 可以回放到任意事件边界 |
| 审计能力 | 只能看到"那一刻的状态" | 能看到状态是怎么一步步变成这样的 |
| 调试价值 | 低 | 高，可以追问"这条是谁改的" |

配套代码里跑了一段 60 步、状态随步数增长的流程：快照模式总字节 105438，事件模式 10713，差 9.8 倍。这就是**状态膨胀**的具体形态——快照总量是"步数 × 状态大小"的乘积。

实际系统两样都要：定期把事件日志压成一个快照（checkpoint = 快照 + 快照之后的事件），平时按快照恢复，调试时按事件重放。只存快照，调试能力上不去；只存事件，长流程恢复会越来越慢。

### 2.3 时间旅行调试

时间旅行做的事很朴素：取第 k 步的状态，改掉某个输入，把剩下的步骤重跑一遍，再对比两个分支的最终状态。配套代码里，原分支是"已批准，合计 3200 元，预算 3500 元"；回到第 1 步之后把 widget 单价从 1200 改成 1800，分支变成"驳回，合计 4400 元"，逐字段差异是三处：单价、合计、审批结论。

做这件事有三个必须遵守的条件：

1. **分支必须隔离**。重跑会再次触发工具调用。生产里时间旅行分支要跑在沙箱里，副作用不落库，否则调试一次就污染一次真实数据。
2. **幂等键必须覆盖全部影响输出的输入**。键里只是物料名的话，改了单价重跑命中的还是旧结果，分支会拿着上一个分支的价格继续算，看起来"重放成功"其实什么都没验证到。
3. **必须有可比性**。两个分支要用同一套模型、同一套工具版本，否则差异分不清是输入引起的还是环境漂移引起的。

### 2.4 多 Agent 共享状态

多个 Agent 要协作，就得有一份共享的状态。四种常见模式，代价完全不同：

| 模式 | 写入方式 | 丢失更新 | 冲突检测 | 往返轮数 | 状态可回放 |
|---|---|---|---|---|---|
| 共享内存 | 直接写同一个 dict | 会，且无声 | 无 | 1 | 否 |
| 共享文档 | 各自写分区，读取时合并 | 不会 | 无 | 2 | 是 |
| 消息传递 | 写变成发消息给下游 | 会（下游只留最后一条） | 无 | 3 | 是 |
| 共享存储 | 带版本号的 KV | 不会 | 有 | 3 | 否 |

这张表是配套代码里四种模式的行为模拟结果，几个要点：

**共享内存最省事，也最危险。** 后写的直接覆盖前写的，没有痕迹：A 写完 B 一写，C 读到 B，A 的写凭空消失。

**共享文档用分区换语义完整性。** 各 Agent 写自己的分区，内容都留着，读时合并。代价是它把"冲突"变成了"合并策略"问题——没有天然的"最后写入者"，上层得自己定义怎么合。

**消息传递把冲突推给了下游。** 写变成发消息，下游按到达顺序处理、只保留最后一条时，上游的更新在下游视角里等于没发生过。好处是消息日志天然可回放，坏处是多一跳延迟。

**共享存储用版本号把冲突显式化。** 写入带上读到的版本，对不上就抛冲突错误而不是覆盖。它牺牲一轮重试，换来"冲突从静默丢数据变成显式失败可重试"——四种模式里唯一不悄悄丢数据的。

## 三、为什么这样设计：取舍与失效条件

### 3.1 什么时候不该做

**不该给无状态流程加检查点。** 一次性的分类、翻译、格式转换，跑完就结束，写检查点纯属浪费。反过来，跨小时的审批流、多轮工具编排、有人工介入的长流程，检查点就是必需品。

**不该为每一步都写细粒度快照。** 状态大的流程里，逐工具快照的存储开销会迅速失控；工具调用少、步骤大的流程，粒度太细也没意义。粒度要跟"一步"的实际时长和副作用密度匹配。

**不该指望检查点解决所有副作用问题。** 检查点能恢复的是**进程内的状态**，恢复不了已经发出去的邮件、已经扣掉的款、已经发给第三方的数据。外部副作用的幂等性必须由幂等键和外部系统共同保证。

**不该在没有可比性的前提下做时间旅行。** 模型版本、工具版本、检索索引都在变的时候，分支差异说明不了任何问题，只能说明环境漂了。

### 3.2 恢复语义：重放安不安全

崩溃后重放是否安全，取决于三件事：

1. **副作用是否幂等**。幂等键必须覆盖决定结果的全部输入，外部系统要认这个键。代码里幂等键是 `reserve:{物料}:{单价}`，崩溃恢复时工具被调用 3 次、真正执行 2 次、命中幂等 1 次——库存预留只发生两次。键里少了单价，改价重跑就会拿旧结果顶掉，分支等于没验证。
2. **检查点写在副作用之后**。这样崩溃重放最多重复触发一次工具，而不是在旧状态上叠加第二次执行。
3. **副作用是否可补偿**。转账、发短信、给外部系统提交单据这类操作天生不可逆，要加补偿事务——失败时发一条反向操作，或者把步骤改成两阶段（先写意向、拿到审批再落地）。不能补偿的步骤，就该单独提交，不要和别的步骤捆在一次重放里。

一句话：重放的安全性不来自检查点，而来自幂等键、写入时机和补偿逻辑三者的配合。

### 3.3 多 Agent 的一致性代价

选共享模式，本质是选一致性等级和延迟的组合：共享内存是弱一致加零延迟，代价是静默丢数据；消息传递是强语义但多一跳；共享存储是可检测的一致加一次重试。要想清楚的是：**跨 Agent 的"谁说了算"是业务问题，不是技术问题**。谁拥有某个键、冲突时听谁的、要不要人工裁决——这些规则写清楚之后，选哪个存储几乎不用犹豫。

## 四、动手：最小可实现

下面把四种能力接进一个三角色流程。依赖只有 Python 3.9+ 标准库，mock 模式内置规则与 mock 答复，不需要 API Key；加 `--live` 用真实模型生成最终答复。完整文件见 `code/ch29-checkpoint-replay/main.py`。

```python
# ---- 检查点: 快照与事件两种模式 ----
class CheckpointStore:
    def __init__(self, mode):
        self.mode = mode          # "snapshot" | "event"
        self.records = []

    def write(self, step, store):
        if self.mode == "snapshot":
            self.records.append({"step": step, "state": store.snapshot()})
        else:
            new = [e for e in store.events if e.step == step]
            self.records.append({"step": step,
                                 "events": [{"op": e.op, "path": e.path, "value": e.value}
                                            for e in new]})

    def state_at(self, step):
        """回放到指定步之后的状态。"""
        if self.mode == "snapshot":
            rec = next(r for r in self.records if r["step"] == step)
            return copy.deepcopy(rec["state"])
        events = []
        for rec in self.records:
            if rec["step"] > step:
                break
            events += [Event(rec["step"], e["op"], e["path"], e["value"])
                       for e in rec["events"]]
        return apply_events(events)     # 事件溯源: 从零重放

# ---- 幂等: 同一幂等键只真正执行一次 ----
class ToolRunner:
    def call(self, name, key, fn):
        self.calls += 1
        if key in self.effects:
            self.hits += 1
            return copy.deepcopy(self.effects[key].result)
        self.real_executions += 1
        result = fn()
        self.effects[key] = Effect(key, copy.deepcopy(result))
        return result

# ---- 恢复: 从最后一份检查点继续, 状态由检查点给出 ----
last = ckpt.last_step()
result = run_flow(tools, ckpt, start_state=ckpt.state_at(last), skip_through=last)

# ---- 共享存储: 带版本号, 冲突显式化 ----
class SharedKV:
    def put(self, key, value, expected=None):
        cur = self.data.get(key)
        version = cur["version"] if cur else 0
        if expected is not None and expected != version:
            raise ConflictError(f"{key}: 读到的版本 {expected}, 当前版本 {version}")
        self.data[key] = {"value": value, "version": version + 1}
```

```
  快照模式总字节: 105438      事件模式总字节: 10713      倍数: 9.8x

时间旅行: 从任意历史步重跑, 并对比分支结果
  原始分支答案: 已批准：widget x2 单价 1200，gadget x1 单价 800，合计 3200 元，预算 3500 元。
  分支答案(回到 step=1 后把 widget 单价 1200 改成 1800): 驳回：...合计 4400 元，超出预算 3500 元。
  分支差异:
    decision.approved: True  ->  False
    decision.total: 3200  ->  4400
    quotes.widget.unit_price: 1200  ->  1800

恢复语义: 崩溃后重放是否安全
  崩溃点: 步骤 3 在工具执行后、写入检查点前中断
  恢复后副作用: 调用 3 次 / 真实执行 2 次 / 幂等命中 1 次
```

## 五、开源实现对照

- **LangGraph** — https://github.com/langchain-ai/langgraph ：显式状态图加检查点器（checkpointer），状态按 thread 隔离持久化；能接内存实现也能接 SQLite / Postgres 这类外部存储；并支持从任意历史检查点重放，是目前 Agent 框架里"时间旅行"最完整的实现之一。
- **OpenAI Agents SDK** — https://github.com/openai/openai-agents-python ：用 session 机制持久化对话历史，session 本身就是一个可恢复的检查点；另有独立的 tracing 组件记录每一步的调用与产出。
- **CrewAI** — https://github.com/crewAIInc/crewAI ：Crews 用角色与任务组织协作，Flows 是事件驱动的流程编排；Flow 内置记忆（`remember()` / `recall()`），状态按 scope 树组织，并支持人工反馈介入。
- **Letta（MemGPT）** — https://github.com/letta-ai/letta ：消息历史与记忆区块由 Agent 自己通过工具改写与落盘，状态边界是"Agent 认为自己写了什么"。
- **Mem0**（https://github.com/mem0ai/mem0 ）、**LangMem**（https://github.com/langchain-ai/langmem ）：重在语义记忆层的抽取与更新，检查点式的状态快照不是主场，但写入同样需要幂等与冲突处理。
- **Temporal** — https://github.com/temporalio/temporal 、**Apache Airflow** — https://github.com/apache/airflow ：不是 Agent 框架，但把工作流引擎的检查点、重放、幂等键、补偿事务做到了工业级。做 Agent 状态持久化时，它们的设计比多数 Agent 框架的文档更值得读。

规律是：**Agent 框架普遍提供状态快照与重放，事件溯源与幂等语义要由应用层自己补**。要把"崩溃后重放安全"做到位，检查点只是起点，幂等键、补偿逻辑和外部系统的配合得自己补。

## 六、坑与检查清单

**检查点**

- [ ] 检查点写在这一步的所有副作用完成之后
- [ ] 粒度与业务步骤对齐，不要机械地每轮对话或每次工具调用都写
- [ ] 记录里带 step、时间戳和元数据（线程、运行 ID、模型版本）
- [ ] 两种模式回放到同一步的状态必须一致，这条要写成断言
- [ ] 有保留期与清理策略，别让检查点日志变成第二个无法治理的存储

**事件溯源**

- [ ] 事件只记录变更，不记录"重新计算出的全量状态"
- [ ] 事件里带上产生它的步骤与来源，否则无法解释"谁改的"
- [ ] 定期把事件压成快照，否则长流程恢复越来越慢
- [ ] 回放要能容忍缺失事件，缺了就报错，不能默默跳过

**幂等与恢复**

- [ ] 每个有副作用的工具都有幂等键，键覆盖全部影响输出的输入
- [ ] 幂等表跨进程持久化，不能只放在内存里
- [ ] 不可逆操作（转账、发信、外部提交）配了补偿动作
- [ ] 崩溃恢复演练过：故意在副作用后崩溃，验证没有重复扣减

**多 Agent 共享**

- [ ] 明确每个键的归属者与冲突裁决规则
- [ ] 共享存储的写入带版本号，冲突是抛错不是覆盖
- [ ] 消息传递模式下，明确下游保留全部消息还是只留最后一条
- [ ] 共享文档模式下，合并策略写在代码里而不是靠人记

## 七、小结与延伸阅读

状态持久化的真正价值不是"崩溃后能接着跑"，而是把黑箱流程变成可观察、可复现、可比较的对象：有了检查点，你能定位到第几步出的问题；有了事件溯源，你能追问这一步为什么这么变；有了时间旅行，你能回答"如果当时那个参数不同会怎样"。

而所有这些能力的安全前提只有一条：**重放必须无副作用**。做不到这一点，检查点写得再密，也只是把重复执行做得更频繁。
