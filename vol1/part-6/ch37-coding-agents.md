# 第 37 章 代码智能体与仓库级自治

## 一、本章要解决的问题

把一个二十万行的 Java 单体仓库交给智能体，让它修一个线上 issue。第一轮它就给出了 diff：改了三处，格式干净，解释也说得通。CI 挂在别的地方——报错来自一个它从没打开过的模块。把日志贴回去，它又改了五处，CI 依然红，因为真正的触发点在一个通过依赖注入装配的类里，而调用它的是 XML 配置文件里的一串字符串，grep 根本搜不到。

这类失败往往不是模型不聪明。模型每一步推理都成立，只是它看不见没被检索到的那部分仓库。在十几个文件的小目录里，同一个智能体表现出色；到了真实仓库，"能不能定位到正确文件"本身就成了主要难点。

再往下拆，改对文件之后还有三道坎：补丁可能因为一个空格的差别应用不上；应用上了，测试可能压根没跑过；跑了，失败日志被截断到只剩第一行，模型就开始自我声明"已经修好了"。

这一章处理三件事：代码智能体有哪几种形态、动作空间和验证回路长什么样；仓库级上下文怎么进到 prompt；小模型配好脚手架、大模型配朴素脚手架，差距落在哪几项工程要素上。

## 二、原理：机制拆解

### 2.1 所有形态共用的骨架

```
   ┌────────────────────────────────────────────────────┐
   │  上下文快照：任务描述 + 仓库地图 + 最近若干轮观察       │
   └───────────────────────┬────────────────────────────┘
                           ▼
   ┌────────────────────────────────────────────────────┐
   │  模型：每轮只输出一个 JSON 动作                       │
   │  {"action":"search","query":"..."} / "apply_patch" … │
   └───────────────────────┬────────────────────────────┘
                           ▼
   ┌────────────────────────────────────────────────────┐
   │  执行器：白名单原子操作，越权直接报错                  │
   └───────────────────────┬────────────────────────────┘
                           ▼
   ┌────────────────────────────────────────────────────┐
   │  观察：结果带行号回灌，不整文件倾倒；失败也是观察      │
   └───────────────────────┬────────────────────────────┘
                           └──► 回到模型
```

形态之间的差别集中在四个旋钮上：**动作空间开多大**、**编辑是精确补丁还是整文件重写**、**验证由谁触发**、**上下文从哪来**。

### 2.2 五种形态

| 形态 | 代表 | 动作空间 | 编辑机制 | 验证回路 | 上下文来源 |
|---|---|---|---|---|---|
| 补丁式 | SWE-agent | 受限命令集：搜索、打开、编辑、提交 | SEARCH/REPLACE 块，失败降级整文件 | 提交前跑测试 | 搜索命中 + 显式打开的文件 |
| 命令式 | OpenHands | 完整 shell、浏览器 | 编辑工具或 shell 重定向 | 自主决定跑什么 | 自己翻目录、自己 grep |
| 编辑器式 | Cline、Roo Code | IDE 工具面 + 终端 | 结构化差异（diff），逐条同意或驳回（approve/reject） | IDE 诊断 + 人来把关 | IDE 索引 + 当前打开的文件 |
| CLI 式 | Claude Code、OpenCode | shell、编辑、任务列表 | 编辑工具 + git 提交 | 自行跑命令验证 | 显式待办清单 + 按需检索 |
| 地图式 | Aider | 文件编辑 + git | diff | 自动提交成原子 commit | 预构建的仓库地图（repo map） |

**补丁式**把模型锁在极小的动作空间里：不能随意执行命令，只能提出结构化的搜索和编辑请求。可预测、可批量重放，但"跑起来才知道对不对"的场景没辙。

**命令式**给模型一个装在 Docker 里的完整 Linux：跑测试、装依赖都行。代价是模型容易发散，一半预算花在探索文件和装依赖上。

**编辑器式**把宿主 IDE 当工具面，每步改动渲染成 diff 等人点头，天然带 git 检查点（checkpoint）。人进了回路：安全，但没人盯着就跑不动。

**CLI 式**是终端里的同事形态。关键是把长任务显式拆成待办清单，让清单承担跨轮次的记忆锚——上下文被压缩后，模型还看得见"我干到哪一步了"。

**地图式**动作空间和 CLI 式接近，差别在上下文是预先算好的：先用语法分析器把仓库抽成"文件 → 符号签名"，再按引用热度裁剪，只放签名不放实现体。

### 2.3 仓库上下文的三种拿法

```
   任务文本
      │
      ├─► ① 仓库地图（预构建、静态）
      │      全仓扫描 → 符号签名 → 引用热度排序 → 裁到预算
      │      优点：一次算好多次复用；缺点：静态，不知道你要什么
      │
      ├─► ② 符号索引（运行时查询）
      │      "谁调用了 X" / "X 定义在哪" → 精确到行
      │      优点：准；缺点：依赖语言服务器，环境重、跨语言质量不齐
      │
      └─► ③ 渐进式披露（多轮展开）
             目录树 → 相关文件的符号摘要 → 完整实现
             优点：省 token；缺点：模型得知道该展开什么
```

工程上三样一起用：地图当默认底座，符号索引做精确追问，渐进式披露控制单次展开量。

### 2.4 搜索策略的四个选项

- **纯 grep / ripgrep**：零成本、精确。搜不到语义相关，也搜不到反射和配置驱动的装配关系。
- **embedding 检索**：能召回"意思相近"的代码块。在代码上常常不如 grep，因为它回答不了"这个符号在哪被调用"这种结构问题。
- **树索引 / LSP**：能回答引用关系。质量取决于语言服务器，跨语言不一致。
- **AST 查询**：语法级取函数体、取调用点。精度最高，代价是每个语言都要写查询规则。

比较省事的组合是：grep 负责召回，引用计数和 LSP 负责排序，AST 负责精确改写。

### 2.5 编辑机制与降级链

补丁应用失败率不低：锚点前后多了空格、缩进用了 tab、行尾是 CRLF、目标片段在文件里出现多次——任何一条都能让精确替换失效。所以降级链是必须的：

```
   精确 SEARCH/REPLACE ──失败──► 读回目标文件的真实内容
        │                               │
        │◄──────── 用真实内容重生成 ─────┘
        │
        └──仍失败──► 整文件重写（最后手段）
```

整文件重写排最后，不是因为它更差，是因为它容易把没读过的部分改坏——要用它，得先真的读过整个文件。

### 2.6 验证回路与闸门

三层，按可信度排：**测试**（最可信，但可能很慢，也可能本身是坏的）、**构建/编译**（能抓 import 错和类型错，比测试快）、**lint / 类型检查**（抓风格和明显的静态问题，最快）。

闸门规则两条：验证没过不允许进入"完成"状态；失败输出必须完整回灌。只给第一行报错，模型看不到失败的断言是什么，等于没回灌。

### 2.7 小模型配好脚手架 vs 大模型配朴素脚手架

脚手架干的事有四件：

1. **把"猜"变成"查"**——把正确的文件送进上下文；
2. **压住动作空间**——不让模型把预算花在无效命令上；
3. **裁剪与排序**——决定有限的 token 装什么；
4. **失败信号保真回灌**——让模型看见此前没看见的东西。

模型越强，这四项的边际收益越小：强模型自己猜中文件的命中率会上升。但只要任务还要求"精确知道文件里到底有什么"，第 1 项和第 4 项就仍然决定成败——再强的模型也看不见没被检索到的内容。

有个方法论上的坑：各家公布的 SWE-bench 成绩里，模型和脚手架是同时变动的，榜单无法把收益归因到某一项。要比较，得固定一个只换另一个。

### 2.8 SWE-bench 上真正起作用的工程要素

SWE-bench 用真实 GitHub issue，判定靠仓库里的测试：待修的测试必须从失败变通过（FAIL_TO_PASS），其余测试不能被弄坏（PASS_TO_PASS）。这约束出几件必须做对的事：

- **定位**：issue 文本 → 候选文件。多路召回（关键词、文件名、符号名、报错栈）比单一路径稳。
- **补丁鲁棒性**：锚点失败要能读回真实内容再重试，否则一步错步步错。
- **本地可复现**：依赖装不上、测试跑不动的样本，模型再强也拿不到分。
- **上下文预算**：真实仓库体积远超窗口，地图与裁剪是前提条件，不是优化项。
- **接得住结构化失败报告**：官方 harness 会把失败输出整理成固定格式喂回来，脚手架要消费这种结构，而不是把原始日志整段塞进去。

## 三、为什么这样设计：取舍与失效条件

### 3.1 按形态列失效条件

**补丁式**在"运行才能确认"的场景失效：依赖注入装配、运行时配置、环境变量分支、反射调用，只有真正跑起来才暴露，而它的动作空间里根本没有"跑一下"这个动作。大范围重构同样失效：跨十几个文件保持一致的改动，锚点补丁会打成一堆互相冲突的碎片。

**命令式**在无人值守和高并发下失效：起一个 Docker 沙箱、按秒计的开销，让它跑批量任务不现实；自由 shell 的安全边界也难收紧；模型在 shell 里特别容易发散——装依赖、翻配置、跑 git log，一半预算花在无关探索上。

**编辑器式**在没有 IDE 的场景失效：服务器上的批处理、CI 里的自动修复。每步 approve/reject 在有人盯着时是优点，无人值守时就是死锁。

**CLI 式**在高风险改动上失效：改生产配置、权限校验、计费逻辑时，逐条审批会让效率崩掉；完全不审批，它又变成一台能执行任意 shell 的自动改代码机器。

**地图式**在仓库小或仓库脏的时候失效：几百行的小项目，建地图的时间比直接把文件贴进上下文还久；符号抽取失败的单文件巨型脚本、模板密集的生成代码会产出残缺地图——残缺地图比没有地图更危险，它让模型误以为自己看全了。

### 3.2 验证回路的失效条件

- 测试太慢（十分钟起步）：模型会绕过验证，直接宣布完成。
- 测试本身是坏的（断言写错、依赖外部服务）：验证退化成随机信号。
- **没有测试的遗留代码**：最危险的一种。此时唯一可用的验证器是"先写一个能复现 bug 的最小脚本，再确认修复后它通过"。没有它，模型没有客观依据说修好了——它只能自证，而自证等于没验证。

### 3.3 检索与上下文的失效条件

- grep 的边界：反射、依赖注入、字符串拼出来的路由、配置驱动的装配——这些调用关系在源码里根本不存在"调用"二字。
- embedding 在代码上常常不如 grep 加符号索引：代码的相似性由标识符和结构决定，不只是语义。
- 上下文裁剪失效：token 预算被 import 和样板代码吃掉；地图热度排序把低引用但核心的文件排到后面裁掉。
- 长任务失效：上下文一压缩模型就忘了目标。写进文件的外部待办清单比"指望模型记住"可靠。

### 3.4 什么活根本不该交给代码智能体

改一行配置、加一个环境变量；写正则、写 SQL 调优；一次性脚本和临时数据处理；生产数据迁移、对账、金额变更这类活；以及代码不能出网的公司环境（模型走云端 API 时，仓库内容会离开你的网络边界，这是合规问题）。

### 3.5 取舍总表

| 形态 | 单次任务开销 | 自主度 | 可控性 | 适合 |
|---|---|---|---|---|
| 补丁式 | 低 | 低 | 高 | 批量修复、基准评测、大范围同构改动 |
| 命令式 | 高（沙箱） | 高 | 中 | 需要跑起来的验证、通用开发任务 |
| 编辑器式 | 中 | 中 | 最高 | 人工主导的高风险改动 |
| CLI 式 | 低 | 中高 | 中 | 日常开发主力形态 |
| 地图式 | 中（建图一次性） | 中 | 中 | 大仓库、上下文常爆的场合 |

## 四、动手：最小可实现

配套实现只有标准库，能在没有 API Key 的情况下跑完"检索 → 定位 → 打补丁 → 跑测试 → 通过才收工"的完整回路，路径 `code/ch37-coding-agents/`。

### 4.1 工具与动作

六个工具：`list_files`、`search`、`read_file`、`read_symbols`、`apply_patch`、`run_tests`，外加一个 `done` 动作表示收工。

### 4.2 动作协议

```json
{"action": "search", "query": "add"}
{"action": "read_file", "path": "calc.py", "start": 1, "end": 120}
{"action": "apply_patch", "path": "calc.py", "patch": "<<<<<<< SEARCH\n...\n=======\n...\n>>>>>>> REPLACE"}
{"action": "run_tests"}
{"action": "done", "summary": "..."}
```

### 4.3 补丁格式的硬要求

```
<<<<<<< SEARCH
    return a + b + 1
=======
    return a + b
>>>>>>> REPLACE
```

缩进要逐字符一致，片段在文件里必须唯一。匹配不到就返回失败原因，让模型读回真实内容再试——这就是 2.5 节的降级链。

### 4.4 主循环

```python
def run_task(index, toolbox, model, task, max_steps=12):
    history = [system_prompt(task), user_msg(task)]
    for step in range(max_steps):
        action = model.next(history)           # 模型只出一个动作
        if action["action"] == "done":
            return finish(action, index)
        result = toolbox.dispatch(action)      # 白名单执行
        history.append(assistant_msg(action))
        history.append(observation(result))   # 失败也是观察
    return {"status": "max_steps_reached"}
```

### 4.5 怎么跑

```bash
cd code/ch37-coding-agents
python main.py                                  # mock 模型 + 内置 demo 仓库
python main.py --show-map                       # 只打印仓库地图，不跑智能体
python main.py --repo /path/to/repo --task "..." # 换自己的仓库（mock 模式还需该目录下的 .code-agent-task.json）
python main.py --repo /path/to/repo --live       # 换成真实模型
```

mock 模式的动作序列由仓库里的 `.code-agent-task.json` 驱动，用来离线验证脚手架通不通：检索命中没有、补丁失败能不能回读重试、测试没过闸门拦不拦得住。`--live` 换成真实模型，脚本、工具、闸门不变。

跑的时候重点看三件事：补丁失败后会不会回读重试；测试失败的断言有没有完整回灌；测试没过时敢不敢收工。

## 五、开源实现对照

| 项目 | 形态 | 上下文策略 | 编辑与验证 | 许可 |
|---|---|---|---|---|
| Claude Code | CLI 式 | 显式待办清单 + 按需检索仓库 | 编辑工具 + shell + git | 专有（Anthropic 商业条款） |
| OpenCode | CLI 式 | 内置全文搜索与文件读取 | 编辑 + 命令执行 | MIT |
| Cline | 编辑器式 | IDE 文件索引与诊断信息 | diff 逐条审批，每步 git checkpoint 可回滚 | Apache-2.0 |
| Aider | 地图式 | tree-sitter 抽符号生成仓库地图 | diff 编辑，每次改动自动 git commit | Apache-2.0 |
| OpenHands | 命令式 | 沙箱内自主探索 | Docker 运行时，可脚本化自主执行 | MIT |
| SWE-agent | 补丁式 | 受限命令集 | SEARCH/REPLACE 补丁 + 提交前验证 | MIT |
| SWE-bench | 基准 | — | 用真实 issue 与仓库测试判定 | MIT |

几条值得注意的差异：

- Aider 和 SWE-agent 都在"上下文"上花大力气：一个建图，一个限制动作空间，两种省 token 思路。
- Cline 把"可回滚"做成了产品功能：每步一个 git 检查点，改错了点一下就回去。命令行形态往往要靠使用者自己先建分支——这一步最容易被漏掉。
- OpenCode 是 Go 写的、模型无关、客户端与服务端分离；OpenHands 更像一个平台，除了编码还能跑别的任务。
- Roo Code 的仓库在本次核实（2026 年 11 月）时已标记为归档，要长期维护优先看 Cline。

## 六、坑与检查清单

- [ ] 检索只有 grep，没有符号索引：反射、依赖注入、配置驱动的调用点全漏。
- [ ] 验证失败只回灌第一行报错，模型看不到失败的断言。
- [ ] 测试没过也允许模型宣布完成，闸门形同虚设。
- [ ] 没有 git checkpoint 或干净分支，改坏了回不去。
- [ ] 上下文塞满完整文件，token 被 import 和样板代码吃掉。
- [ ] 仓库地图不排序，或只按文件大小排序，核心文件被裁掉。
- [ ] 索引混进二进制、生成代码、压缩产物，噪声压过信号。
- [ ] 补丁锚点不做唯一性检查，替换到同名的错误片段。
- [ ] 失败回灌不完整：没有退出码、没有 stderr、没有实际输出。
- [ ] 没设步数上限，模型在一个 bug 上死磕几十轮烧钱。
- [ ] 沙箱里没预装依赖，模型把预算花在装包和联网拉取上。
- [ ] 没有最小复现脚本，遗留代码的修复无法客观验证。
- [ ] 长任务没有外部待办清单，上下文一压缩就重复劳动。
- [ ] 模型能执行任意 shell 且能出网，内部代码泄露到外部。

## 七、小结与延伸阅读

代码智能体的能力上限，往往不由模型决定，而由"能不能在不炸掉上下文的前提下建立仓库心智模型"决定。

五种形态差在四个旋钮：动作空间、编辑机制、验证回路、上下文来源。选型不是选哪个更先进，是选哪个的失效条件跟你这个仓库对得上。

仓库上下文的三件套——地图兜底、符号索引追问、渐进式披露控预算——缺一样就退化成 grep 一把梭，模型再强也会在错误的方向上认真推理。

脚手架四件事里，"把猜变成查"和"失败保真回灌"在模型变强后收益递减，但只要任务还需精确知道文件里有什么，它们就仍决定成败。

最容易踩的坑不是模型不够强，而是没有客观验证器却让它宣布完成。
