# 第 38 章 计算机使用与 GUI Agent

## 一、本章要解决的问题

把一个 IE 内核的老客户端交给智能体：没有 API，界面也不是网页 DOM，只有一张截图。第一步是点右上角那个"×"，关掉一个挡住操作的小窗——模型给出坐标 (1180, 42)，按钮其实在 (1176, 42)。差 4 个像素，点到了旁边的"最小化"。窗口缩进任务栏，智能体看着新截图继续规划下一步，每一步单独看都成立，合起来什么都没做成。

更糟的是不可逆。老系统的"删除草稿"没有撤销键；"确认提交"点下去就进了下游流程。截图既给不了回滚，也给不了内部状态——提交到底成没成功、弹窗还在不在、字段有没有被服务端拒了，模型只能从像素里猜。

还有些界面干脆没有结构：canvas 画出来的报表、远程桌面里的另一套系统、扫描件和影像界面。这种情况下你只能靠像素。

所以 GUI Agent 的本质不是"给模型装上鼠标键盘"，而是在拿不到结构化接口时，用像素去逼近一个本该由 DOM 或可访问性树（accessibility tree，AX 树）提供的接口。这一章拆三件事：怎么看得见（感知通道怎么选）、怎么点得准（grounding 的能力从哪来）、怎么在像素上少犯错（动作空间怎么设计、怎么验证）。

## 二、原理：机制拆解

### 2.1 感知：三条拿到"界面"的路径

| 通道 | 得到什么 | 成本 | 什么时候失效 |
|---|---|---|---|
| DOM | 标签、类名、属性、文本、事件绑定 | 最低 | 只存在于浏览器页面 |
| AX 树 | 角色 + 名称 + 层级 + 状态（焦点、禁用、勾选） | 低 | 自绘控件和 canvas 里画的东西不进树；Electron 常缺；节点上千时冗长 |
| 像素（截图） | 渲染结果，所见即所得 | 最高、最慢 | 丢掉一切语义；小控件缩放后糊掉 |

```
   DOM 解析 ──┐
   AX 树  ────┼──► 统一的"元素 + 角色 + 名称 + 位置" ──► 动作空间
   截图    ──┘            ▲
                    grounding 把像素翻译成元素（OmniParser 这类）
```

选通道是有顺序的：先问"这个界面有没有结构"，有就用结构；结构里找不到目标，再问"这个目标是不是自绘出来的"，是才上视觉；截图最后只用来确认结果。经验上结构通道覆盖了真实工作的绝大部分，剩下的才是视觉的战场。

### 2.2 截图分辨率与视觉 token 成本

图像不是按字符计费，是按面积切成 tile 计费；像素面积翻倍，token 大致也跟着翻倍。模型还有最大图片边长，超出的部分会被缩放。

缩放的直接后果是：12×12 的关闭按钮、8 像素高的文字，缩完就没了。不是模型笨，是输入里根本没有那个信息。

省 token 的另一个办法是裁剪：先在低分辨率全图里定位，再把目标区域裁出来放大单独问一次，确认一次比整张图反复看要省。

实践里的两种做法：低分辨率定位 + 高分辨率复核，或者结构定位、截图只用来确认结果。

截屏时机同样要紧：动画没停就截，模型看到的是中间态。Playwright 那类自动等待机制存在的理由就在这儿。

### 2.3 视觉定位（grounding）：把"点右上角的关闭按钮"变成坐标

它指的就是这个转换：一句自然语言指令 → 一组可执行的坐标。输出形式一般是归一化坐标（0–1000）、元素中心点加包围盒（bounding box），或者直接吐一串动作 token。

能力有三个来源：

1. **专用 grounding 模型或检测器**：UI-TARS 一类视觉动作模型，OmniParser 则把截图解析成带位置的结构化元素；
2. **通用多模态模型直接给坐标**：省事，但坐标精度取决于模型对 UI 的先验；
3. **结构化定位器**：role/name 直接定位到元素——这条根本不需要 grounding 模型。

把定位拆两段更准：先让模型指认区域（"在标题栏右上角"），再在该区域内给坐标；一步到底容易整体偏移。坐标必须归一化：写死像素，换个分辨率或系统缩放比例就全废。

### 2.4 动作空间：从原子到合成

```
  原子动作                 半结构化动作                合成动作
  click_xy(x, y)           click_ref(b5)              open_menu() → scroll() → pick()
  type("A1001")            fill(order_no, "A1001")
  key("Enter")             press("Enter")
  scroll(dy)
  ─────────                ──────────────             ─────────────────────
  最通用，canvas 也能用      更准更快，依赖语义标识          快，但组合爆炸、
                                                       宏内部出错看不见中间态
```

三条取舍：

- **原子动作**不依赖任何语义，代价是步数多：每步一次推理、一次截图，十步就有十次偏的机会，误差逐步累积；
- **半结构化动作**一次命中，代价是元素标识必须稳定——页面重渲染后 ref 就指向别的元素了，这是 DOM 方案被低估的坑；
- **合成动作**把"打开菜单并选中某项"封成一个宏，代价是组合爆炸，而且宏内部出错时你只看到"没成功"。

### 2.5 回合、状态与不可观测

一个回合 = 观察（截图或结构）→ 模型 → 一个动作 → 执行 → 新观察。

截图只给渲染结果，不给内部状态：提交成功了吗？弹窗是不是还开着？字段有没有被服务端拒？这些都看不出来。所以界面层稳定化（等动画结束、等加载完成、等焦点稳定）是前提，不是优化项。

每一回合的成本也很实在：一次截图、一次推理、一次执行。动作拆得越碎，总成本越高——二十步的流程往往比一次 API 调用贵两个数量级，这也是"能合成就别拆"的经济学依据。

### 2.6 失败模式

1. **像素级脆弱**：换主题、换字体、换缩放、窗口尺寸一变，同一套坐标全部失效；差几个像素就点到隔壁控件。
2. **状态不可观测**：只能看到渲染结果，看不到数据层；异步与动画让截图时机变成随机变量。
3. **动作不可逆**：删除、提交、支付没有撤销键。
4. **幻觉控件**：低分辨率纯视觉时，模型会把像素里的噪点当成控件。
5. **视口陷阱**：内容在视口外（虚拟滚动、翻页），模型看不到就断言它不存在。
6. **语义混淆**：同名按钮（一列三个"删除"），坐标对但目标错。
7. **焦点错位**：输入框没拿到焦点，文字进了搜索框；或者弹窗关闭后焦点丢了，后面几轮输入全部无效。

### 2.7 混合策略：结构优先，视觉兜底

```
  DOM selector ──► AX role/name ──► 图像模板匹配 ──► VLM grounding
     （准、快）      （准、需语义）      （死板）        （最通用、最脆）
```

三条原则：能用结构断言结果，就别用截图判断结果——断言"状态字段等于 PROCESSED"比盯着像素看颜色可靠得多；定位失败不要重复点同一个坐标，同样的像素再点一次，错还是同一个错；视觉只用在结构给不出答案的地方。

## 三、为什么这样设计：取舍与失效条件

### 3.1 什么时候根本不该用 GUI Agent

有 API 就用 API：快十倍、稳十倍、便宜十倍，还自带事务和错误码。浏览器页面有 DOM，就用 locator 加自动等待。桌面应用有 AX 树，就用 role/name 定位。只有剩下像素的时候——老旧客户端、canvas 报表、远程桌面、虚拟机里的另一套系统、影像与扫描件——才轮到视觉上场。

### 3.2 视觉兜底什么时候反而更好

AX 树缺失或撒谎的时候：Electron、自绘控件、游戏化界面，结构给了假象，比没有更糟。跨平台同一套交互时，视觉模型在界面之间迁移更平滑；移动端平台差异大，纯视觉反而统一。

代价是每回合一次截图加一次推理，几十步就是几分钟，不适合有 SLA 的实时交互，也不适合高频批量。

反过来，纯视觉在需要精确读数时就不行：核对订单号、金额、账号这类必须逐字符确认的字段，截图不可靠，应该从结构里取值，或者干脆走接口。

### 3.3 结构优先也有失效条件

节点上千且名称不可读（"btn 1"）：结构可查但不可读，模型选不对。虚拟滚动只暴露可见部分：目标不在视口时结构里根本没有。ref 失效：重渲染后旧标识作废，拿旧 ref 硬点会点到别人身上。

### 3.4 混合策略的实践代价

两条路径都要维护：结构路径要写选择器，视觉路径要调 grounding，两套都得有回归测试。降级条件必须写清楚，否则会在两条路径之间来回抖动。最危险的是不可逆动作——能点任意像素，就等于能点"确认付款"。删除、提交、支付这类操作要单独一道闸：显式确认参数、白名单、或者事前快照。

## 四、动手：最小可实现

配套实现是个纯标准库的"伪桌面"：52 列 8 行的字符画面模拟一个订单查询后台，里面有订单号输入框、上下相邻的 Search 与 Reset、标题栏上相邻的 Close 与 Minimize、一个在视口外的 Delete Draft，以及会弹确认框的删除流程。路径 `code/ch38-computer-use/`。

三条感知通道都有：可访问性树（角色、名称、元素引用 ref，只有视口内元素）、字符画面（低分辨率像素）、结构化定位。动作空间是 `observe` / `screenshot` / `click_xy` / `click_ref` / `type` / `key` / `scroll` / `done`。

grounding 用的是最小版本：在字符画面里找标签文本，算出它的中心坐标。`--live` 换成真实模型输出坐标，工具和闸门不变。

验证不看截图，直接查应用状态字段：订单号、状态、草稿数、确认框是否还在。

实现里有两个值得单独说的机关：一是每次点击都回报"实际命中了哪个元素"，模型靠这一行发现意图与实际不符从而换通道；二是工具层校验 ref 的有效性——同一个 ref 在重渲染后可能已经指向别的元素，必须拦下来，否则一次"重试"就会变成误操作。

一次运行会把六个坑全演出来：

1. 模型输出的 y 整体偏一行 → 本要点 Search，点中 Reset，订单号被清空；它从动作效果回报里发现意图与实际不符，改用结构定位；
2. 输入框里只有下划线、没有可见文字 → 这类目标视觉定位无从下手，示例里 mock 直接改用结构定位；
3. Delete Draft 在视口外 → 树里查不到 → 先滚动再定位；
4. 视觉定位偏一行 → 点空，坐标处没有可交互元素；
5. 确认框里 OK 与 Cancel 上下相邻 → 视觉点中 Cancel，删除没生效；状态断言发现草稿还在；
6. 旧 ref 在重渲染后指向别的元素 → 被拦下，不至于误点成 Reset；不可逆动作缺 `confirm=true` 同样被拒。

```bash
cd code/ch38-computer-use
python main.py            # mock 模型跑完整回路
python main.py --render   # 只打印画面与可访问性树
python main.py --live     # 换真实模型
```

## 五、开源实现对照

| 项目 | 感知通道 | 动作空间 | 定位方式 | 许可 |
|---|---|---|---|---|
| Playwright | DOM | 脚本化 API（点击、填写、等待） | 选择器、role/name | Apache-2.0 |
| browser-use | AX 树 | 元素引用点击与输入 | 无障碍树语义 | MIT |
| Stagehand | DOM + 视觉 | act/observe/extract 混搭确定性 Playwright API | 两条路径并存 | MIT |
| Skyvern | 视觉 | 多智能体群分工 | 视觉模型直接看渲染页面 | AGPL-3.0 |
| UI-TARS Desktop | 视觉 | 桌面与浏览器操作 | UI-TARS grounding 模型给坐标 | Apache-2.0 |
| OmniParser | 视觉 → 结构 | 不产生动作，只做翻译 | 截图解析成可交互元素 | CC-BY-4.0 |
| OSWorld | 基准 | — | 真实桌面环境里的开放任务评测 | Apache-2.0 |
| Mind2Web | 基准 | — | 真实网站任务上的网页智能体评测 | MIT |

几条值得注意的差异：

- Playwright 和 browser-use 是结构派，定位靠语义，快而稳；Skyvern、UI-TARS Desktop 是视觉派，什么界面都能上，但脆；Stagehand 是混合派，把确定性 API 和视觉探索摆在一起。
- OmniParser 的位置特殊：它不执行动作，只把像素翻译成带位置的结构化元素，是视觉路线里的翻译层，可以和别的执行器拼在一起。
- 许可要看清：Skyvern 是 AGPL-3.0，要嵌进闭源商业产品得先评估 copyleft 影响；OmniParser 是 CC-BY-4.0，署名要求也得留。
- OSWorld 和 Mind2Web 是评测基准：前者考真实桌面环境的开放任务，后者考真实网站上的网页任务，选型前先看自己的场景像哪个。

## 六、坑与检查清单

- [ ] 每步都截全图进上下文，视觉 token 成本失控。
- [ ] 截图不裁剪、不等稳定就发，模型看到的是动画中间态。
- [ ] 坐标写死像素，换分辨率或系统缩放就全崩。
- [ ] 定位失败后重复点同一个坐标。
- [ ] 用截图判断"操作成功了吗"，而不是查状态字段。
- [ ] 不可逆动作没有显式确认闸门，也没有事前快照。
- [ ] 重试前不确认上一次动作是否已生效，同一个删除执行两次。
- [ ] 只做视觉不做结构，同名控件里选错。
- [ ] 只做结构不做视觉兜底，自绘控件直接卡死。
- [ ] 滚动和翻页没纳入观察范围，模型误判元素不存在。
- [ ] 允许模型自由点击整屏，没有坐标栅格化或白名单约束。
- [ ] 失败只回灌截图不回灌动作效果，模型无法自纠。
- [ ] 没有步数与超时上限，一次卡死烧掉整轮预算。
- [ ] 敏感操作（付款、删生产数据）与普通操作走同一条通道。

## 七、小结与延伸阅读

GUI Agent 是没有结构接口时的兜底，不是默认方案。有 API 用 API，有 DOM 用 DOM，实在只剩像素才上视觉。

技术上就三件事：看得准（选对感知通道）、点得准（grounding 加归一化坐标）、错得起（动作空间粒度、客观验证、不可逆动作单独设闸）。第三件最被低估——它不酷，但它决定了一次误点会不会变成事故。

最大的技术现实是慢、脆、不可观测、不可逆。所以预算要花在验证和确认上，而不是花在更花哨的定位模型上。
