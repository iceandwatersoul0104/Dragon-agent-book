# 第 5 章 提示增强技术：CoT、Few-shot、Self-ask 与 Least-to-Most

## 一、本章要解决的问题

上周评审一个团队的 Agent 方案。抽取任务准确率卡在 60% 上下，负责人试了三版提示："请一步步思考"、"配两个示例"、"先列要点再作答"，最后留下"请一步步思考"，准确率到了 85%。

两个月后，同一套提示换到另一个字段的抽取任务，准确率从 70% 掉到 42%，比什么都不加还低。

这种失败每天都在生产里发生。根子在于提示技巧被当成"咒语"：加一句话涨 25 个点，让人相信"再试一句还能涨 25 个点"——直到某次不涨反跌。

这一章解决三件事：收益从哪来（机制）、失效边界在哪（什么时候会掉）、以及什么时候该继续调提示、什么时候该换架构（判据在第三节）。

## 二、原理：机制拆解

### 2.1 先分类：你在提示里加了什么

按"往提示里加了什么"分成四类，每类都能落到一个具体机制。分类是工程活儿：它决定换模型、换任务、扩上下文时哪些技巧还能用。

| 技巧 | 加了什么 | 收益机制 | 主要代价 |
| --- | --- | --- | --- |
| CoT | "分步思考"或带推理的示例 | 把一次难采样拆成一串易采样 | 输出变长、错误可传播 |
| Few-shot | 若干"输入→输出"样例 | 给出任务形状：标签空间、格式、长度 | 吃上下文预算、易过拟合 |
| Self-ask | 要求先自问子问题并作答 | 把隐式分解显式化，减少漏约束 | 自问发散、答案更长 |
| Least-to-Most | 要求先解简单子问题再解难题 | 用已解出的中间结果搭桥 | 依赖分解质量，分解错则全错 |

### 2.2 CoT 的真实收益来源

CoT（Chain-of-Thought，思维链）不是让模型变聪明，而是**改变计算结构**。直接吐答案，模型是在一步里对"答案 token"做分布采样；让它先生成中间步骤，每一步都条件在自己刚写下的前缀上，复杂问题被拆成一串更简单的问题。人做数学草稿也是这样：不是人变聪明了，是把一个大乘法拆成四次小乘法。

收益边界由此确定：

- **有效**：需要中间计算、需要同时满足多个约束、需要把整体拆成局部步骤。
- **无效甚至有害**：答案能直接从记忆里取出（写十步推理也是编）；步骤依赖模型拿不到的外部事实；输出格式固定且很长（示例和结构化输出更划算）。

代价有三块。**Token 与延迟**：推理链通常让输出长一两个数量级，叠加第 4 章 ReAct 每轮重发全部上下文，是复利式放大。**错误传播**：第一步算错，后面全错，没有回溯机制。**对小模型不稳**：小模型写出的中间步骤正确率本身就低，又没有"发现步骤错了"的能力，于是稳定地错到底——同一提示在强模型上有效、换到小模型上反而不如直接回答，不是提示写得不好，是门槛没到。"小模型上 CoT 不稳"改不了提示，只能换模型或把问题拆得更细（换成架构）。

### 2.3 Few-shot：示例不是答案，是形状

Few-shot（少样本）常被误解成"给模型几个标准答案"。实际上示例真正提供三样东西：**标签空间**（可能有哪些答案）、**输入分布**（什么输入会长什么样）、**整体格式**（输出多长、什么结构）。有研究把示例里的标签随机打乱，准确率几乎不掉——起作用的是这三样，不是示例里的"正确答案"。由此得一条规则：**别把示例内容当事实来源**，示例里的日期、人名、金额都是编的，模型会当真。

三条设计要点：

**示例选择**：跟目标分布贴近，领域、难度、长度都别差太远。分类任务里示例全是长文本而真实输入都是短句，模型就会照长文本的形态作答。

**格式一致性**：示例的标签空间、字段顺序、长度、风格要一致。风格不一致会引发表层形式竞争——同一概念的不同写法在概率上互相抢，模型偏向形式而非语义。对结构化输出尤其致命：示例 A 用 JSON、示例 B 用自然语言，模型就会摇摆。

**顺序效应**：示例顺序会显著影响结果——有研究指出，提示格式、示例选择乃至示例顺序，都能让少样本准确率在接近随机和接近最优之间摆动。最稳的一条：把最容易混、最需要模型注意的示例放最后（离问题最近）。再叠加一条上下文位置的结论：长上下文里放中间的信息最容易被忽略，性能往往在开头和结尾更高。

还有一条常被忽略：**示例会教模型"这是哪类任务"**——给分类任务配了带推理过程的示例，模型就会开始写一大段推理。示例也不是越多越好：示例数 × 示例长度直接吃上下文预算。

### 2.4 Self-ask 与 Least-to-Most：把分解写出来

**Self-ask（自问）** 要求模型回答主问题前，先自己提出并回答若干澄清性子问题（"隐含哪几个约束？""每个约束需要哪个事实？"），再作答。收益机制很朴素：分解从"隐式"变"显式"后，就有了可检查、可补齐、可替换的部件——问题答错常常是漏了一个约束，把约束列出来，漏的就变成看得见的空缺。

**Least-to-Most（由易到难）** 思路不同：把复杂问题拆成有序子问题，先解最简单的，再用已解出的结果解下一个，最后合成。它针对"问题比示例更难"这个失败模式——CoT 在超纲题上栽跟头，是因为默认了"模型见过更难的同类题"这个假设。由易到难把假设变成显式搭桥：即便没见过最难那步，见过并解出前面所有步就够了。

分工是：**Self-ask 管"别漏"，Least-to-Most 管"别卡"**。前者横向补齐约束，后者纵向铺台阶。

两者与第 7 章的关系很清楚：都是**单次调用内的隐式分解**——分解写在生成的文本里，控制流没变，还是"调一次模型、拿一个结果"。Plan-and-Execute、ReWOO 把分解外化成独立规划节点，有显式中间状态、可检查点、可重试、可换模型重跑。**提示里的分解是规划的第一版，架构里的分解是规划的工程版。**

### 2.5 把它们放进同一条流水线

```
                    ┌──────────── 提示装配（纯函数，可单测）────────────┐
任务 + 领域数据 ───► │ select_examples → format_examples → compose_instruction │
                    └────────────────────────┬─────────────────────────────┘
                                             │  一条字符串
                                             ▼
                                      ┌──────────────┐
                                      │  LLM 调用     │  一次
                                      └──────┬───────┘
                                             ▼
                                   解析 + 评分（外部确定性代码）
```

```python
def build_prompt(task, examples, strategy):
    parts = [TASK_TEMPLATE.format(task=task)]
    if strategy in ("fewshot", "cot_fewshot"):
        parts.append(EXEMPLARS_HEADER)          # 顺序即设计，别乱排
        parts.extend(format_examples(examples)) # 格式统一是硬要求
    if strategy in ("cot", "cot_fewshot"):
        parts.append(COT_INSTRUCTION)
    if strategy == "selfask":
        parts.append(SELFASK_INSTRUCTION)       # 先自问子问题，再作答
    if strategy == "ltm":
        parts.append(LTM_INSTRUCTION)           # 先解简单子问题，逐级搭桥
    return "\n\n".join(parts)
```

这段代码里没有模型调用——提示装配是纯函数，可单测、可快照、可 diff。**提示工程该有的工程形态，是一个可测试的函数，而不是一坨手写字符串。**

## 三、为什么这样设计：取舍与失效条件

### 3.1 提示技巧 vs 系统架构：一条判据

提示技巧改**模型这一轮看到什么**；架构改**有几轮、谁决定下一步、状态存在哪、失败了怎么办**。据此得判据：**根源是"模型不知道"，改提示；根源是"模型没法自己决定流程、没法重来、没法并行、没法把状态带下去"，改架构。**

四个典型场景：

1. 分解需要外部事实 → 换架构（第 4、7 章）：加检索或工具。提示里的分解再漂亮，也变不出事实。
2. 需要多次尝试并择优 → 换架构（第 6 章）：加反思与自纠错。提示能让模型一次答好，却不能让它发现答案错了。
3. 需要并行或多来源交叉 → 换架构：提示里写"从三个角度分析"得到的还是一段文本，没有真正并发与独立验证。
4. 需要跨步状态、重放与恢复 → 换架构：检查点、外部存储、幂等（idempotency）重试，提示里写不出来。

反过来有几类问题**上框架是浪费**：单次调用就能答完的抽取分类改写；模型能力足够只是不会按格式输出；生产量小、错了人工看一眼就行的。这几种情况，一条清晰提示 + 一个输出校验就够。

停止调提示的信号有两个：**改了十几次准确率还在原地打转，而你又能说清"模型缺的是什么信息"**——那缺的是信息或流程，不是措辞；**输出 token 涨了但正确率没涨**——说明这段推理没产生信息，只在增加长度。

### 3.2 各技巧的失效边界

- Few-shot 替代不了真实数据：示例能教格式和标签空间，教不了分布里的长尾，要覆盖真实分布应该做检索（第 10 章）。它也会过拟合到示例：评测集里若出现与示例高度相似的输入，正确率是虚高的，所以示例集与评测集必须分开。
- Self-ask / Least-to-Most 依赖分解质量：分解错了后面全错，而且比直接回答更难发现，因为它看起来很有条理。
- 所有技巧都不跨模型迁移：换模型必须重跑评测。

## 四、动手：最小可实现

这一节交付两样东西：一份可运行的提示策略评测器，以及第三节承诺的**对照实验设计**。代码在 `code/ch05-prompting/`，纯标准库、无需 API Key，依赖 Python 3.9+、零第三方包。

**运行**：

```bash
cd code/ch05-prompting
python main.py
```

默认跑 6 策略 × 2 任务的对照矩阵，输出正确率、平均输出字符、格式合规率、平均延迟四列。两个任务故意挑得不同：一个需要中间计算的几何题（长方形周长 22、长 8，求面积），一个是纯事实题（爱因斯坦出生年份），正好能看出 CoT 类技巧在两类任务上的差别。

**mock 说明**（重要）：内置的"模型"不是真的推理，它**按提示里的特征标记模拟行为**——看到"step by step"就产出带步骤且算对的回答，零样本时模拟"不守输出格式"这一常见现象。这样做只为让评测流水线能离线跑通并可回归，**不代表真实模型表现**，结论要用 `--live` 跑。

**真实模型**：

```bash
export LLM_API_KEY=sk-xxx
export LLM_BASE_URL=https://api.openai.com/v1
export LLM_MODEL=gpt-4o-mini
python main.py --live --repeat 3
```

`--repeat` 是关键：温度大于 0 时单次比较没有意义，必须多次采样看均值和方差。

### 4.1 对照实验设计：怎么判断一个提示技巧真的有效

这是本章最该被抄走的一段。提示技巧最大的陷阱是**在噪声上做决策**——同一提示跑两次结果不同，团队很容易把随机波动当成"技巧生效"。

最小可用版本，五条：

1. **固定任务集**：20～30 条有标准答案的任务，覆盖典型样本和易混样本。少于 10 条，统计上基本什么都看不出来。
2. **只变一个变量**：模型、温度、解码参数、上下文全部固定，只换提示策略。改两个变量就分不清是谁的功劳。
3. **多次采样**：温度大于 0 时每个任务跑 k 次（3～5 次起步），报均值和方差，不报单次结果。
4. **配对比较**：同一条任务同时跑 A、B 两种策略，用配对差值而不是两组独立均值——任务难度差异被消掉了。
5. **留出集**：调提示用的例子和评测集必须分开，防止把提示过拟合成"背答案"。

指标至少四个：正确率、平均输出 token（或字符数代理）、平均延迟、解析失败率。**只看正确率是另一个陷阱**：CoT 可能把正确率从六成提到八成多（比如从 60% 提到 85%），但输出长度翻十倍，端到端成本可能反而更差。

判定标准一句话：**差异必须大于采样噪声才算有效。** 连跑 3 次、两次结果差 30 个点的提示，不值得上生产。

## 五、开源实现对照

- **LangChain**（MIT，https://github.com/langchain-ai/langchain）：把提示拆成模板片段再拼装，示例与指令是结构化对象而不是手写字符串，正好对应"提示装配是纯函数"这条主张。代价是抽象层多，调试要看好几层才知道最终发出去的是什么。
- **DSPy**（MIT，https://github.com/stanfordnlp/dspy）：提示在这里不是手写常量，而是**被优化出来的产物**——用声明式签名描述任务，再自动优化指令与示例。它回答的正是"怎么判断技巧有效"：把示例选择与提示结构当成待优化参数，用评测集驱动。这条路线的前提是有评测集，和 4.1 节是同一件事。
- **PydanticAI**（MIT，https://github.com/pydantic/pydantic-ai）：把输出契约从提示里拿出来变成类型定义。对应"格式一致性"那条：与其用示例暗示格式，不如用类型强制格式。
- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python）：指令、护栏、追踪分层，提示只是其中一层；追踪正好用来做 4.1 节的对照实验。

## 六、坑与检查清单

- [ ] 每次实验只改一个变量。
- [ ] 示例集与评测集分离，防止示例过拟合。
- [ ] 示例的标签空间、字段顺序、长度、风格统一。
- [ ] 最易混的示例放最后（离问题最近）。
- [ ] 不要把示例里的内容当事实来源。
- [ ] 示例数量 × 示例长度受上下文预算约束，收益递减。
- [ ] 每条提示记录输出 token 与延迟，CoT 的成本要进预算。
- [ ] 温度大于 0 时用多次采样均值判定，不看单次结果。
- [ ] 同时报正确率、成本、延迟、解析失败率四个指标。
- [ ] 提示模板文件化、可 diff、可回滚，别散落在代码里。
- [ ] 自问/分解类技巧要设子问题数量上限，防止无限自问。
- [ ] 换模型后重跑整套评测，提示技巧不跨模型迁移。
- [ ] 小模型上 CoT 不稳时，先怀疑机制门槛而不是继续改措辞。

## 七、小结与延伸阅读

提示技巧是在**固定控制流里改输入**：CoT 改推理链的形状，Few-shot 改模型对"任务长什么样"的先验，Self-ask 与 Least-to-Most 改分解的显式程度。它们有明确的收益机制，也有明确的失效边界：需要外部事实、需要多次尝试、需要并行、需要跨步状态的问题，提示解决不了，那属于架构（第 4、6、7、10 章）。而判断技巧是否有效的唯一办法，是**固定其他变量、多次采样、配对比较、留出评测集**——没有评测集的提示调整，本质是玄学。
