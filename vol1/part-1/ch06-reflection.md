# 第 6 章 反思与自纠错：Reflexion、Self-Refine 与独立评审者

## 一、本章要解决的问题

让模型写一个判断回文的函数。它交上来：

```python
def is_palindrome(s):
    return s == s[::-1]
```

测试跑不过：`is_palindrome("A man, a plan, a canal: Panama")` 返回了 False。

于是最自然的念头来了——把结果再喂回模型，让它自己检查一下。模型的回答是："代码逻辑清晰，使用切片操作实现反转比较，思路简洁，建议保留。"

错误原封不动留在了那里，而且现在还多了一段自信的背书。

这不是模型偶尔失手，而是结构性的：**模型评审自己的时候，几乎复用了它写答案时的那套判断**，评审环节没有引入任何新信息。反思（reflection）不是把错误擦掉的橡皮擦，它是把一段新文本写进上下文——写错了，反思本身就成了错误的二次传播源。

于是问题变成三个：让 Agent 检查自己有哪几种形态，机制差别在哪？反思信号从哪来、什么信号才真能纠错？反思要多花 2～6 倍 token，这笔账怎么算，什么时候根本不该开反思。

## 二、原理：机制拆解

### 2.1 三种形态：差别在信息流向

| 形态 | 机制 | 反思落在哪 | 典型场景 |
| --- | --- | --- | --- |
| Reflexion（带记忆重试） | 跑一轮拿反馈，把反思写进外部记忆，下一轮重新生成 | 跨轮保留的 episodic memory | 长任务、要试错的编码与决策 |
| Self-Refine（多轮改写） | 同一上下文里"生成→反馈→改写"迭代，反馈只作用于当前产物 | 当前产物的下一版 | 文案、报告、翻译这类"改一版更好"的任务 |
| 独立评审者（Judge/Critic） | 生成与评审由不同角色承担（常常不同模型、不同提示），评审有否决权 | 判定结果，决定收不收 | 需要质量门禁的交付物 |

三者的差别不在"有没有批评"，而在批评的信息流向哪里：

- Reflexion 改的是**下一次尝试的起点**（把经验存进记忆），所以它对"需要试错"的场景有效；
- Self-Refine 改的是**当前产物的下一版**（就地修订），所以它对"已经接近对、只差一点"的任务有效；
- 独立评审者改的是**收不收的判定**（否决权），所以它对"质量必须有门槛"的场景有效。

```
Reflexion（带记忆重试）          Self-Refine（多轮改写）         独立评审者（Judge）
┌────────┐   ┌──────┐            ┌────────┐   ┌──────┐           ┌────────┐   ┌──────┐
│ 生成 v1 │──►│ 评审  │            │ 生成 v1 │──►│ 反馈  │           │ 生成   │──►│ 评审者│
└────┬───┘   └──┬───┘            └────┬───┘   └──┬───┘           └───┬────┘   └──┬───┘
     │ 反思      │ 写进 memory          ▲ 改写 v1  │                   │ 通过？   │ 否决
     ▼           ▼                     └────┬─────┘                   ▼ 是       ▼ 否
┌────────┐  ┌────────────┐                ▲ 再反馈                  收尾      └─► 回到生成
│ 生成 v2 │  │ memory:    │                └────────────────────────┘
│ 带经验  │  │ "上次忘了   │
└────────┘  │  过滤标点"  │
            └────────────┘
```

Self-Refine 的箭头是"就地回环"，没有跨轮记忆；Reflexion 的箭头是"经由记忆回到起点"。这个差别决定了同样的反思文本在两种形态下作用完全不同。

### 2.2 反思信号从哪来：可靠性排序

反思的价值完全取决于信号质量。同一个"评审者"，换个信号源，结果天差地别：

| 信号源 | 可靠性 | 覆盖范围 | 代价 |
| --- | --- | --- | --- |
| 规则校验（编译、类型、schema） | 最高：确定性、可复现 | 只能查编码进去的规则 | 几乎为零 |
| 测试用例 | 高：能复现真错 | 只覆盖写了的用例 | 写用例的成本 |
| 检索证据 | 中：取决于召回 | 事实类问题 | 一次检索 |
| 独立 LLM 评审 | 最低：弱验证器 | 语义、规范、风格 | 一次模型调用 |

排序背后的逻辑是：**信号必须独立于被评审的产物**。编译器不知道作者怎么想的，测试用例是作者之外写死的断言，检索证据来自外部语料——只有 LLM 评审和作者共享同一套先验，所以它最容易重复作者的错误。

还有个反向证据：训练验证器（verifier）去挑候选答案，效果显著好于让模型直接答——因为验证器的任务被约束成"打分"，比"生成"窄得多。同一道理，评审任务给模型越窄的检查清单，它的判断越可靠。

### 2.3 自我强化错误：为什么自己审自己只是确认偏见

三个原因叠在一起：

1. **共享先验**：生成和评审用的是同一套"什么算好"的判断，作者的盲区在评审里原样复现。
2. **角色与位置惯性**：LLM-as-a-Judge 的研究明确列出了位置偏差、冗长偏好和自我偏好（self-enhancement bias）——模型倾向于认可看起来更完整、更长、更像自己写的答案。
3. **反思的二次传播**：最隐蔽的一条。第一轮评审写下的理由会被当成既定事实带进下一轮——如果第一轮说"这段代码没有空指针风险"，后面几轮就在这句话上继续推理，把一个错误结论越滚越结实。

工程上有效的对策：

- **换角色**：评审者用不同的系统提示，明确它只负责找错、不负责表扬；
- **换证据源**：给评审者外部证据（测试输出、检索片段），别让它凭空判断；
- **换上下文**：评审者只看产物和规格，不看作者的推理过程——作者的叙事会污染评审；
- **换模型**：成本允许时用不同模型评审，比同模型自评可靠得多；
- **先出检查清单**：让评审者先列出"这类任务该查什么"，再逐项判定，而不是直接下结论。

### 2.4 反思文本的三种类型

反思不是一段话就完了，内容类型决定它能不能驱动下一轮：

- **结论型**："这段代码有问题。"——只说有问题，没说错在哪、怎么改。下一轮拿它没法行动，等于白跑一轮。
- **诊断型**："错在比较前没有归一化，直接比了原串和它的反转。"——指出了错因，能直接推导下一步怎么写。
- **指导型**："先把非字母字符过滤掉并统一大小写，再比较正反两个字符串。"——可以直接当成下一轮的约束条件。

工程上要的就是后两种。所以评审提示里要明确要求输出格式：**"指出具体哪一行、哪个判断不对，并给出应该改成什么"**，而不是"评价一下这个方案好不好"。可核验的缺陷清单是反思能被用起来的前提。

### 2.5 反思循环的熔断：四道闸

反思循环最常见的死法不是报错，是转圈。四道闸必须都有：

1. **最大轮次**：最粗的一道，通常 2～3 轮。超过就说明反思没带来信息。
2. **无进展（no progress）检测**：产物的哈希不变、评测分数不动，就判定没有进展，直接停。
3. **反思内容去重**：把每轮反思规范化（压空白、去标点、忽略大小写）后判重。同一句"建议补充边界条件"连着出现三次，不该再烧三轮 token。
4. **成本闸**：给整条循环一个 token 预算上限，超了降级——转人工，或走一条不依赖模型的兜底路径。

熔断之后要有明确出路，不是直接抛错：把当前产物和已收集的失败证据交给人，或者走确定性兜底路径。

### 2.6 成本账

一轮反思的成本结构是：初版生成 + 评审 + 改写，而下一轮的上下文比上一轮更长——所以第 2 轮大约是第 1 轮的 2 倍，第 3 轮约 3 倍（上下文累积）。跑满 3 轮，总 token 大约是"只生成一次"的 4～6 倍；只跑一轮到一轮半的方案，那才是 2～3 倍。

收益侧的收益来自"把一次失败的信息再利用一次"，它成立需要三个前提同时满足：

1. 初版错误率不低——否则没有可挖的信息；
2. 错误能被某个信号捕获——否则反思只是重写措辞；
3. 一次成功重写的概率显著高于一次初版——否则多轮反思不如多采样几次再选。

**缺任何一个前提，反思就是纯成本。** 最常见的缺法是第 2 条：错误根本捕获不到（"这段文案哪里不好"没有客观信号），那每一轮都在做没有反馈的自我说服。

## 三、为什么这样设计：取舍与失效条件

**什么时候不该开反思：**

1. **错误能被规则捕获** → 直接加校验和测试，不要用 LLM 评审去检查编译器能查的东西。规则校验是毫秒级、零 token 的。
2. **任务没有可验证的正确性信号** → 反思只能优化"看起来更像好答案"。这种场景要在人，不在轮次。
3. **高频低延迟场景** → 2～6 倍的 token 与延迟要能在延迟预算里算得过来。
4. **有不可逆副作用的任务** → 反思发生在动作之后，撤销不了已发出的邮件、已删除的文件。让 Agent 先在只读模式自查，再执行。
5. **上下文已经吃紧** → 反思文本本身要占上下文（第 10 章）。长任务里反思记忆可能比任务本身还长。

**三种形态怎么选：**

- 成本敏感、错误可测 → 规则 + 测试，别用 LLM 评审；
- 语义质量、评审面窄（合规、风格、可读性） → 独立评审者，并且评审者要有否决权；
- 长任务、要试错、要复用经验 → Reflexion 的记忆机制。

**独立评审者还有额外风险：过度否决。** 评审标准写得含糊时，评审者可能反复挑刺，把本来合格的产物打回。做法是给评审者明确的验收清单（checklist），要求它对每一条给出"通过/不通过 + 依据"，而不是笼统评价。

## 四、动手：最小可实现

代码在 `code/ch06-reflection/`，纯标准库、无需 API Key。

**依赖**：Python 3.9+，零第三方包。

**运行**：

```bash
cd code/ch06-reflection
python main.py
```

默认场景：让 Agent 实现"忽略大小写和非字母字符的回文判断"。初版有 bug，然后由不同的评审信号来纠：

```bash
python main.py --form judge --critic rule       # 独立评审者 + 测试用例信号
python main.py --form judge --critic llm        # 同一个模型自评（确认偏见演示）
python main.py --form judge --critic judge      # 独立评审者 + 语义评审信号
python main.py --form reflexion --critic rule   # 带记忆重试
python main.py --form self_refine --critic rule # 多轮改写
```

输出是逐轮轨迹和终局状态：

| form | critic | 终局 | 说明 |
| --- | --- | --- | --- |
| judge | rule | solved | 测试信号直接指出失败用例 |
| judge | judge | solved | 独立评审定位到"未做归一化" |
| judge | llm | not_solved | 自评给不出具体缺陷 → 产物无变化 → 熔断 |
| reflexion | rule | solved | 反思写进记忆，下一轮重写时用上 |
| self_refine | rule | solved | 反馈就地改写当前产物 |

**mock 说明**：内置的"模型"按提示特征模拟行为，不是真推理；但**规则评审是真的**——它真的在受限命名空间里执行候选代码并跑断言。真实结论用 `--live` 跑。

**真实模型**：

```bash
export LLM_API_KEY=sk-xxx
export LLM_BASE_URL=https://api.openai.com/v1
export LLM_MODEL=gpt-4o-mini
python main.py --live --critic rule --max-rounds 3
```

## 五、开源实现对照

- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：把"生成→评审→重写"画成状态图，条件边天然表达"评审通过就收尾、否则回到生成"，检查点还能在第三轮断电后续跑。反思循环最需要的就是这种显式循环。
- **LangChain**（MIT，https://github.com/langchain-ai/langchain）：把生成与评审做成两条可替换的链，组合灵活，但循环与熔断要自己写。
- **CrewAI**（MIT，https://github.com/crewAIInc/crewAI）：用角色分工表达"作者"与"评审者"，天然就是独立评审者的形态。
- **Letta (MemGPT)**（Apache-2.0，https://github.com/letta-ai/letta）：把记忆当一等问题，Reflexion 的"带记忆重试"在这里是原生能力而不是外挂。
- **DSPy**（MIT，https://github.com/stanfordnlp/dspy）：把"生成 + 批评 + 修订"做成可优化模块，用评测集驱动哪套提示更有效。
- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python）：护栏（guardrail）在评审之前拦截，算是"反思"的前置版本。

## 六、坑与检查清单

- [ ] 评审者与生成者尽量不是同一套提示、同一个模型。
- [ ] 有规则能查的先用规则，不用 LLM 评审。
- [ ] 评审者不读作者的推理过程，只看产物与规格。
- [ ] 评审输出必须是可核验的缺陷清单，不是"看起来不错"。
- [ ] 评审者有明确的验收 checklist 与"通过/不通过 + 依据"格式。
- [ ] 四道熔断闸全开：最大轮次、无进展、反思去重、成本预算。
- [ ] 反思内容规范化后判重，不要用字符串完全相等判重。
- [ ] 熔断后有明确降级路径（转人工或兜底方案），不是直接抛错。
- [ ] 反思要在副作用动作之前做，已执行的操作不可撤销。
- [ ] 用评测集验证"是否真的有效"，不要凭一两个案例下结论。
- [ ] 记录每轮 token 与耗时，反思成本要进预算表。
- [ ] 防止过度否决：给出验收清单，而不是让评审者自由发挥。

## 七、小结与延伸阅读

三种"让 Agent 检查自己"的形态，差别在信息流向：Reflexion 把经验写进记忆，改变下一次尝试的起点；Self-Refine 就地改写当前产物；独立评审者握有收不收的否决权。反思的有效性不来自"模型变聪明"，而来自**信号独立于被评审的产物**——规则和测试比 LLM 自评可靠，因为前者不共享作者的那套盲区。真正决定成败的是熔断和成本账：反思的收益只在"初版错误率不低、错误可被信号捕获、重写比重抽更可能成功"三条同时成立时才为正，否则它就是 4～6 倍 token 的自我说服。
