# 第 7 章 规划范式：Plan-and-Execute、ReWOO 与搜索型推理

## 一、本章要解决的问题

一个六步的运营流程 Agent。计划事先写好了：读 CSV → 汇总 → 写日报 → 发邮件。跑到第四步，邮件接口返回"收件人不在通讯录"。

两种常见处理都难看：

- **硬跑**：把失败当噪音跳过，最后交付一份根本没发出去的日报，还标成"完成"；
- **一遇错就从头规划**：前面三步的成果全部作废，重跑一遍读取和汇总——可收件人这个问题跟前三步毫无关系。

问题在于：计划不是写完就永远对的工件。**计划过时（stale plan）**——计划写完到执行完之间环境变了，使原计划的部分步骤不再成立或不再最优——是所有规划系统都要面对的核心问题，比"怎么生成计划"更难。

所以本章要拆三件事：计划**什么时候**生成（先规划后执行、边规划边执行、先搜索再执行）、计划**怎么用**（可编辑工件），以及计划过时了**怎么办**。

## 二、原理：机制拆解

### 2.1 分类轴：时机与粒度

| 范式 | 计划何时产生 | 执行期模型是否在线 | 典型优势 | 典型代价 |
| --- | --- | --- | --- | --- |
| Plan-and-Execute | 开工前一次性生成 | 在线（每步都要模型定参数） | 计划可读、可编辑、可人工改 | 计划漂移；LLM 调用次数多 |
| ReWOO | 开工前一次性生成 | 离线（执行期是确定性解释器） | 调用次数少、上下文省 | 计划必须一次写对；执行期没有反馈通道 |
| 搜索型推理（ToT/GoT） | 搜索过程中不断生成候选 | 在线 | 能回溯、能看几步之后 | 成本高，收益完全依赖评估函数 |

### 2.2 ReWOO：把变量引用预解耦

ReWOO 的核心机制是**把推理和观察解耦**（decoupling reasoning from observations）。计划长这样：

```
Step 1: read_csv(path="data.csv")            -> #E1
Step 2: aggregate(rows="#E1")                -> #E2
Step 3: write_report(path="report.md", content="#E2") -> #E3
Step 4: send_email(to="boss@example.com", body="#E3")
```

`#E1` 是**变量引用**，不是真实数据。执行时由解释器把第 1 步的返回值填进第 2 步的参数——全程不需要再调模型。注意引用表达的是**数据来源**，不是提前求值：写计划时不知道 `#E1` 的值，但知道它会从哪来。

这省掉了什么？省掉了"每执行一步就把全部历史重新喂给模型"。ReWOO 论文在 HotpotQA 上报告了 5 倍的 token 效率提升——这是多跳问答上的数字，别当成普适倍数，但方向是对的：**如果一个任务的步骤序列事先能定下来，执行期就不该有模型。**

代价也清楚：模型不在执行期，就看不到执行期的事实。汇总出来是什么样、收件人存不存在，解释器知道，模型不知道。计划的前提一旦错了（字段名变了、文件不存在、地址不在通讯录），ReWOO 没有"发现并修正"的能力，只能重规划——这就是计划过时在 ReWOO 上更尖锐的原因。

### 2.3 Plan-and-Execute：计划是可编辑工件

先规划后执行这一类做法（Plan-and-Solve 提示、LLM+P、早期自主任务循环都是它的变体）的价值在于：**计划是数据，不是提示词里的一段字**。它能被打印出来给人看、被改、被存、被审批、被复用。

```
plan = planner(task)              # 一次 LLM 调用，产出结构化计划
for step in plan:
    args = llm_resolve(step)      # 执行期模型在线：把 #E 引用填成实参
    result = tool(step.tool, args)
```

好处有三个：人可以在执行前改计划（把"顺便把发票也发了"删掉）；计划可以复用（同一套对账流程每周跑一次）；失败可以定位（日志里明确说"第 3 步失败"，而不是"模型思考了一会儿然后说做完了"）。

代价是**计划漂移（plan drift）**：计划写的时候和执行的时候，环境已经不一样了。典型三种：

- **假设漂移**：计划假设文件里有某列，执行时那列不存在；
- **顺序漂移**：本可并行的两步排成了串行，白等一倍时间；
- **目标漂移**：执行到一半发现用户真正要的是另一个指标，但没人改计划。

### 2.4 搜索型推理：把"一步向前"变成"一层层试"

搜索型推理不在一条路径上走到底，而是把当前状态扩成一组候选，逐个评估（evaluate），留下好的继续展开。

Tree of Thoughts（ToT）把它做成树：节点是思路片段，边是生成动作，叶子上用打分函数（自评估或外部验证器）选出答案。Graph of Thoughts（GoT）把结构从树放宽成图——节点可以合并、可以回路，思考之间能互相借鉴。

搜索的成本是明确的：**每展开一个节点多一次生成，每评估一个叶子多一次判断。** 所以搜索只在两个条件同时成立时才划算：

1. **搜索空间大到单条路径容易走死**（下棋、组合优化、谜题）；
2. **有可用的评估函数**（能打分、能验证），否则既不知道往哪边走，也不知道什么时候停。

典型的失败案例是"没有评估函数的搜索"：让模型自己给候选打分，它打的分和最终选出的答案质量常常不相关——搜索退化成"多生成几个答案，挑一个看起来最顺眼的"。

### 2.5 计划过时：三种处理方式

这是本章的核心。计划过时指：计划写完到执行完之间环境或目标变了，使原计划的部分步骤不再成立或不再最优。

**第一类，重规划触发条件。** 问题是"什么时候停下来问模型重新规划"。三个典型触发信号：步骤失败（工具返回错误）；观察与假设矛盾（工具成功了，但返回值与计划的前提对不上）；成本或风险越界（剩余步骤预计花费超预算，或某一步不可逆）。

**第二类，局部修补（local repair）。** 只改出错的那一步及其下游依赖，其余保留。适用于**错误是局部的**：参数写错、地址变了、这一步该换个工具。这是最省成本的方案，也是最容易被滥用的方案——如果错误是"整体思路错了"（用户要季度数据，计划做的是月度），局部修补只会把错误加工得更精致。

**第三类，全量重规划（full replan）。** 丢掉原计划，带着"已完成到哪一步、拿到了什么结果"重新生成计划。适用于**假设层面的错误**。代价是已完成的工作可能作废，所以正确做法是重规划时把已有结果作为事实喂回去，让新计划复用它们，而不是从零再跑。

选择标准可以压成一句话：**错误在参数层就局部修补，在假设层就全量重规划；拿不准时看"改动是否影响已完成步骤的产物"。**

### 2.6 任务分解质量怎么评估

一个计划好不好，不看它读起来顺不顺，而看子任务是否满足两个性质：

- **可执行（executable）**：这一步有明确的输入来源和确定的动作。不合格的例子："分析数据"（没说做什么）、"必要时联系客户"（没给工具和触发条件）。
- **可验证（verifiable）**：做完能明确判断成没成。不合格的例子："写一份高质量的报告"——没有验收条件就无法验证，也就没法触发重规划。

五条实用自查项，不需要额外训练一个评估模型，人工也能用：

1. 每一步是不是都指向一个具体工具或确定动作？
2. 每一步的输入是不是都来自任务描述或前面某一步的输出？
3. 每一步能不能写出验收条件？"发出去了"是验收条件，"报告写得好"不是。
4. 子任务粒度是否一致？一步塞三个动作，出问题时不知道是哪部分坏了。
5. 计划里有没有"必要时""酌情""尽量"这类词？有，就说明这一步没想清楚。

## 三、为什么这样设计：取舍与失效条件

**什么时候不该做规划：**

1. **路径唯一且很短**：一次调用就够的任务，规划只是多花一次模型调用。
2. **步骤可由代码直接推导**：格式转换、字段抽取这种，写代码比让模型规划更快更稳。
3. **实时环境不可预测且代价高**：需要不可撤销的操作时，先做只读探查比先规划更安全。

**三种范式怎么选：**

- 步骤事先能定、且要省调用 → ReWOO；
- 步骤需要人确认或会被中途改 → Plan-and-Execute，计划是可编辑工件，天然能被人接管；
- 路径不确定且有评估函数 → 搜索型推理。

**规划系统的三个常见过度设计：**

- 给一个 3 步任务加状态机、持久化、回滚——省下的调用成本抵不上维护成本；
- 把所有工具调用都塞进一条大计划，执行期一口气走到底——长计划的后半段几乎必然过时；
- 把"规划"和"反思"两套系统叠加，但反思信号还是模型自评（第 6 章的确认偏见），等于把偏见乘以二。

**搜索型推理的边界**：ToT、GoT 在需要探索与回溯的任务上有效，但成本随展开节点数增长。ToT 论文在"24 点"上对比过链式思考：GPT-4 用链式思考只解出 4% 的题，ToT 达到 74%。这类结果不要外推到日常业务——那里往往没有"对错分明"的评估函数。

## 四、动手：最小可实现

代码在 `code/ch07-planning/`，纯标准库、无需 API Key。

**依赖**：Python 3.9+，零第三方包。

**运行**：

```bash
cd code/ch07-planning
python main.py
```

默认跑三个对照：

```bash
python main.py --form plan_execute --policy patch    # 先规划后执行 + 局部修补
python main.py --form plan_execute --policy replan   # 先规划后执行 + 全量重规划
python main.py --form rewoo                         # 执行期无模型的 ReWOO
python main.py --demo search                        # 搜索型推理 vs 贪心
```

场景：把 CSV 汇总成日报并发出去，第四步发送邮件失败——收件人不在通讯录。这是一个**局部的**计划过时：前三步的结果照旧可用。

| form | policy | LLM 调用 | 工具调用 | 结果 |
| --- | --- | --- | --- | --- |
| plan_execute | patch | 6 | 5 | solved |
| plan_execute | replan | 10 | 8 | solved |
| rewoo | patch | 1 | 5 | solved |

三个数字说明两件事。ReWOO 只用 1 次模型调用就跑完全程，另外两种分别用了 6 次和 10 次——省下来的正是"执行期每步都要模型在线"那部分。而全量重规划比局部修补多花 4 次模型调用、多跑 3 次工具：前三步的成果被作废重做，这就是"重规划不便宜"的具体数字。搜索型推理的对照给出另一组数：贪心路径评估 2 次没找到可行解，树搜索评估 13 次找到了最优解（上海＋成都，客户数 5）。

**mock 说明**：内置的"模型"按提示特征返回预设的计划文本，不做真实推理；工具环境（读 CSV、汇总、写文件、发邮件）是本地模拟，其中"收件人不在通讯录"这个失败是确定性的。真实结论用 `--live` 跑。

**真实模型**：

```bash
export LLM_API_KEY=sk-xxx
export LLM_BASE_URL=https://api.openai.com/v1
export LLM_MODEL=gpt-4o-mini
python main.py --live --form rewoo
```

live 模式下模型要按固定格式产出计划（一行一步，`tool(arg=value)`），解析器会忽略不合法的行。

### 4.1 计划的表示与修补

计划要能被编辑，先得是数据：

```python
@dataclass
class Step:
    tool: str
    args: Dict[str, str]      # 值可以是 "#E1" 这种变量引用
    label: str = ""

@dataclass
class Plan:
    steps: List[Step]

    def patch(self, index: int, **kw) -> "Plan":   # 局部修补：只改这一步
        new = Plan([copy.deepcopy(s) for s in self.steps])
        new.steps[index].args.update(kw)
        return new
```

局部修补和全量重规划在数据结构上的差别只有一句：前者改的是 `plan.steps[i]`，后者是 `plan = planner(task, history)`。

## 五、开源实现对照

- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：规划节点、执行节点、条件边（"失败就回到规划"）与检查点，是把"计划过时"显式化的最直接方式——重规划就是走另一条边。
- **LangChain**（MIT，https://github.com/langchain-ai/langchain）：提供 plan-and-execute 类 Agent 的组合方式，灵活，但循环与重规划要自己写。
- **LLM+P**（https://github.com/Cranial-XIX/llm-pddl）：把自然语言翻译成 PDDL，交给经典规划器求解，再翻回自然语言。用的是"规划算法"而不是"模型即规划器"，在有明确领域定义的任务上更可靠。
- **Plan-and-Solve Prompting**（https://github.com/AGI-Edgerunners/Plan-and-Solve-Prompting）：同一思路的提示层版本——先列子问题再逐个作答，用来解决链式推理的"缺步骤"错误。
- **Tree of Thoughts**（https://github.com/princeton-nlp/tree-of-thought-llm）：搜索型推理的参考实现，提示与打分函数都在里面。
- **DSPy**（MIT，https://github.com/stanfordnlp/dspy）：把"规划步骤"这类结构化输出做成可优化模块，用评测集驱动提示迭代。

## 六、坑与检查清单

- [ ] 计划是结构化对象，能打印、能人工改、能存版本。
- [ ] 步骤粒度一致，一步一个动作。
- [ ] 每步都有验收条件（可验证）。
- [ ] 变量引用只表达数据来源，不要在计划期提前求值。
- [ ] 明确区分"参数错了"（局部修补）和"思路错了"（全量重规划）。
- [ ] 重规划时把已完成结果作为事实带回去，不要从零重跑。
- [ ] 定义清楚重规划的触发信号：失败、观察与假设矛盾、预算越界。
- [ ] 不可逆操作前必须有只读探查或人工确认。
- [ ] 长计划要设分段检查点，别指望一条计划走到底。
- [ ] 搜索型推理必须有独立于模型的评估函数，否则只是在多生成几个答案。
- [ ] 给搜索设展开预算（最大节点数），别让它无限展开。
- [ ] 记录 LLM 调用次数与工具调用次数——两种范式的差别全在这个数上。
- [ ] 反思信号不要用模型自评（第 6 章的确认偏见）。

## 七、小结与延伸阅读

规划范式的差别可以压成三句话：Plan-and-Execute 把计划当成**可编辑工件**，人能在执行前改它，代价是模型一直在执行期在线、计划容易过时；ReWOO 把计划的变量引用**预解耦**，执行期是确定性解释器，调用次数少得多，代价是计划必须一次写对；搜索型推理用**分层展开加评估函数**换取"能回溯"，但只有在有评估函数且搜索空间真的大的时候才划算。三者共同的真问题是**计划过时**：参数层错误就局部修补，假设层错误就全量重规划；而判断分解质量的唯一可靠办法，是检查每个子任务是否既可执行又可验证。
