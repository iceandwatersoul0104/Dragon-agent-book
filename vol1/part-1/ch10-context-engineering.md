# 第 10 章 上下文工程：把上下文当作稀缺资源预算

## 一、本章要解决的问题

给 Agent 接上代码仓库、监控面板、工单系统和十几个内部 API。第一天跑得好好的，第三天开始出问题：

- 上下文涨到十万 token，每轮都在为同样的系统提示和十二个工具定义重复付费；
- 模型开始"忘事"——十分钟前刚说过"不要动数据库 schema"，隔了几轮它建议改表结构；
- 检索回来的文档有四十篇，其中三十五篇跟当前任务无关，但每一篇都占了位置；
- 上下文窗口还剩三成，而真正重要的那条约束刚好埋在中间。

于是有人说了那句经典的话："把上下文窗口做大就行了。" 窗口确实能做很大，但变大不解决注意力被稀释的问题。

本章换一个角度：**上下文不是提示词的一段字符串，是一个要被分配、检索、压缩、淘汰的预算**。当预算有上限，"放什么、放在哪、扔掉什么"就是工程问题，不是措辞问题。

## 二、原理：机制拆解

### 2.1 先算账：预算怎么分

一次调用的上下文由五块拼成，每块都吃 token：

| 层 | 内容 | 变化频率 | 处置 |
| --- | --- | --- | --- |
| 系统提示 | 角色、规则、输出契约 | 几乎不变 | 常驻，放最前 |
| 工具定义 | 工具名、描述、schema | 偶尔变 | 常驻或按需加载 |
| 任务 | 目标、硬约束、验收条件 | 每任务变 | 常驻，位置敏感 |
| 历史 | 之前的轮次与观察 | 每轮变 | 滚动、压缩、淘汰 |
| 检索结果 | 文档片段、数据库行 | 每轮变 | 排序、截断、选位置 |

分配的经验账（具体比例是每个团队自己的账，但量级有共性）：系统提示与工具定义构成常驻部分，量不大，却决定模型"会什么"；任务与硬约束小而硬，必须完整保留；历史最容易膨胀，也是最该被管理的；检索结果最容易失控——召回五十条就吃掉一半预算，而真正相关的可能只有两条。

一条原则：**预算先分给不能丢的，再分给可以用更便宜方式表达的。** 硬约束和当前任务第一优先；历史可以用摘要换；检索结果可以用排序换。

### 2.2 四种手段

**分层（常驻与按需）。** 常驻的是每轮都用得上的：系统提示、当前任务、少数几个核心工具。按需的是"这一步才用得上"的：几十个工具定义、几十份参考文档、按领域加载的规则集。第 8 章讲过工具定义每次都要发给模型，工具一多，光它们就能吃掉几千 token。按需加载有两种做法：先让模型选工具、再加载那一批定义（两段式）；或者把工具按领域打包，只加载当前领域那一包。

**检索。** 不是把历史全塞进去，而是把需要的东西找回来。检索对象有三类：文档片段（最常见的 RAG）、历史里的关键事实（从旧对话里检索相关轮次）、结构化数据（数据库或 API 的实时查询）。检索要同时解决召回与排序——只优化召回不优化排序，召回二十条相关的全塞进去，等于没筛。

**压缩（摘要 / 结构化提取）。** 历史太长时不要直接砍，先压。三种压法：摘要（把旧轮次压成一段话，便宜但丢细节，还可能编）、结构化提取（只留工具调用记录、关键参数、结论、待办项，丢掉过程叙述）、差分与引用（保留原文指针，需要时回查）。选择标准是：**Agent 下一步需要的是状态还是理由？** 要状态用结构化提取；要写复盘、要解释决策，就留摘要。

**淘汰（按价值与新鲜度）。** 价值是"这条信息对当前任务还有用吗"，新鲜度是"它是不是已经过期"。淘汰顺序：先淘汰最旧且已被摘要覆盖的中间过程，再淘汰与当前任务无关的，最后才动还没被摘要的近期内容。**永远保留最近一两轮原文**——模型需要精确措辞来衔接。

### 2.3 上下文腐化（context rot）：长上下文里中间的信息会被忽略

现象：在长上下文任务上，模型表现随输入变长而变差，即使相关信息确实在上下文里。两条证据链：

- **位置效应**：Lost in the Middle 的实验显示，同一条信息放在上下文开头或结尾时，模型答对的概率明显高于放在中间；而且这个效应在长上下文模型上依然存在。
- **注意力竞争**：更新的研究给出了更细的解释——在检索类任务上，真正伤害准确率的不完全是长度，而是**同上下文里出现了竞争信息**（同格式的干扰项、给出竞争答案的陈述）。填满无害的噪声影响有限，但放一条"竞争陈述"能把准确率打下去一个量级；注意力质量比长度更能解释这种下降。

四条可操作的结论：

1. **重要信息别放中间。** 放开头或结尾（紧邻问题）。这一条几乎零成本。
2. **减少同格式的竞争内容。** 检索结果别一股脑堆同类文档；换格式、换顺序、标清来源都有帮助。
3. **压缩峰值长度。** 上下文管理手段本质上是测试时扩展——把模型从"信息过多导致的不确定放弃"推回"继续探索"。有研究系统比较了七种上下文管理方法，结论是它们通过降低峰值上下文长度来改善长程任务。
4. **周期性提醒。** 长对话里定期重申关键约束（"再说一遍：不改 schema"），比只在开头说一次有效。

### 2.4 与 Prompt Caching 的联动

提示缓存（prompt caching）的机制是：请求的前缀如果与上次相同，命中缓存的部分不计费也不重算。于是上下文的**排布**不只影响质量，还直接影响钱。

三条布局规则：

1. **稳定在前，变动在后。** 系统提示、工具定义、长期不变的规则放最前，构成可缓存前缀；历史与检索结果放后面。多数缓存实现按前缀匹配，前缀一变，后面全部失效。
2. **别把变动的东西插进稳定区。** 每轮变化的时间戳、请求 ID、随机数放进系统提示，会让整段前缀缓存失效——这是最常见也最贵的失误。
3. **给缓存前缀留出稳定长度。** 有的缓存按固定块命中，前缀太短或频繁变动都吃亏；稳定的块越多，命中率越高。

所以布局和预算是一回事：组装器既决定"留什么"，也决定"按什么顺序拼"。

### 2.5 上下文组装器：把上面四件事变成一个函数

接口应该很简单：

```python
prompt, report = assembler.assemble(
    task=task, history=history, retrieval=candidates, tools=tool_specs)
```

内部四步：分层（每层一个优先级和预算）→ 超预算的层按各自策略处理（压缩 / 淘汰 / 排序 / 按需加载）→ 按缓存友好顺序拼接 → 输出一份预算报告（每层原 token、保留 token、采取的动作、总占用、关键事实落在哪个位置）。

**报告是组装器最有价值的部分。** 上下文问题的排查难度远高于代码 bug：没有报告，你根本不知道模型这轮看到的是什么、扔掉了什么。

## 三、为什么这样设计：取舍与失效条件

- **摘要的代价**：摘要会丢信息，也会编。摘要一旦编了，后续轮次会当成事实。所以摘要要**可追溯**——保留被摘要掉的原文指针，必要时回查。
- **结构化提取的代价**：它只保留状态，会丢掉"为什么"。下游要写复盘、要解释决策时，结构化摘要不够用。
- **检索的代价**：检索本身要花一次调用和延迟；召回质量不稳时，检索是把噪声送进上下文，比不检索更糟。先有评测集，再上检索。
- **淘汰的代价**：被淘汰的信息后面可能又需要，所以要留指针。
- **什么时候不该做上下文工程**：任务短、上下文天然装得下时，多加一层组装器只是增加延迟和维护成本。先测，看上下文到底是不是瓶颈。
- **一个反直觉的结论**：上下文变大有时比变小更危险。窗口三十二万不代表该放三十二万；把五万 token 的无关历史留着，会稀释注意力、推高成本，还会掩盖真正的约束。**窗口之外还要有工作集（working set）的概念**——每轮只放这一轮用得上的东西。

## 四、动手：最小可实现

代码在 `code/ch10-context-engineering/`，纯标准库、无需 API Key。

**依赖**：Python 3.9+，零第三方包。

**运行**：

```bash
cd code/ch10-context-engineering
python main.py
```

演示三件事：

1. **朴素拼装**：系统提示 + 十二个工具定义 + 二十轮历史 + 三十条检索结果直接拼接 → 超出预算，关键约束"不改数据库 schema"落在中段；
2. **组装器**：分层 → 历史压缩成结构化摘要并淘汰中段 → 检索按相关度排序截断 → 工具按需加载 → 按缓存友好顺序拼接 → 落在预算内，关键约束被前置到任务层；
3. **预算报告**：每层原 token、保留 token、采取的动作、缓存前缀长度。

```bash
python main.py --budget 4000      # 收紧预算，看降级动作
python main.py --budget 100000    # 放宽预算，看检索排序的影响
python main.py --layout naive     # 只跑朴素拼装做对照
python main.py --trace            # 打印组装后的完整上下文
```

输出形如：

```

         关键约束位置：中段（20%～80%）
         模型回答：否……（没有找到关于生产库结构的硬约束，无法确认依据。）

上下文组装器
layer          before    after  action
system             52       52  keep
tools             425      110  按需加载：保留 2 / 12 个工具
task              147      147  keep
retrieval        2507     1933  按相关度排序后截断：保留 23 / 30 条
history          3072      428  压缩 18 轮为结构化摘要 + 淘汰中段，保留最近 2 轮

```

两排输出的差别不在 token 数，而在**关键约束的位置**：它被从历史中结构化提取出来，前置到任务层，于是从"模型够不着的中段"变成"模型一定看得见的头部"。这就是第 2.3 节说的四条缓解手段里最便宜的一条——不压缩任何东西，只换个位置。

**mock 说明**：内置"模型"用**窗口模型**模拟长上下文里的信息可及性——它只可靠地读取上下文开头 20% 和结尾 20%。这只是对"注意力被稀释"现象的近似模拟，不代表任何真实模型的表现，真实行为必须用 `--live` 测。

**真实模型**：


### 4.1 组装器的骨架

```python
LAYERS = [
    Layer("system",   priority=0, budget=800,  strategy="keep"),
    Layer("tools",    priority=1, budget=1200, strategy="load_on_demand"),
    Layer("task",     priority=2, budget=600,  strategy="keep"),
    Layer("history",  priority=3, budget=3000, strategy="compress_then_evict"),
    Layer("retrieval",priority=4, budget=2000, strategy="rank_then_truncate"),
]

def assemble(self, task, history, retrieval, tools):
    blocks = {l.name: [] for l in self.layers}
    ...  # 填充各层
    for layer in self.layers:                  # 按优先级处理超预算的层
        if tokens(layer) <= layer.budget:
            continue
        if layer.strategy == "compress_then_evict":
            layer.blocks = compress(layer.blocks) + keep_recent(layer.blocks, 2)
        elif layer.strategy == "rank_then_truncate":
            layer.blocks = rank(layer.blocks)[:layer.budget]
        ...
    return join_in_cache_friendly_order(blocks), report
```

四种策略与三个动作之间能互相替换：历史太长可以压缩，也可以直接淘汰老轮次；检索太长可以排序截断，也可以只留 top-1。**组装器要做的不是选唯一正确的策略，而是按优先级把预算花在刀刃上，并如实报告花在了哪。**

## 五、开源实现对照

- **Letta (MemGPT)**（Apache-2.0，https://github.com/letta-ai/letta）：把"上下文不够用"当成一类要管理的问题——记忆分层，按需换入换出。
- **Mem0**（https://github.com/mem0ai/mem0）与 **Graphiti**（https://github.com/getzep/graphiti）：记忆层的抽取与检索，是第 2 节"检索"手段的工程实现。
- **LangMem**（MIT，https://github.com/langchain-ai/langmem）：给 LangChain 提供自主写入与检索长期记忆的工具。
- **RAGFlow**（https://github.com/infiniflow/ragflow）：把"上下文里放什么"做成有解析、有引用、有裁剪的流水线。
- **DSPy**（MIT，https://github.com/stanfordnlp/dspy）：从另一头解决同一问题——不手工拼上下文，而是优化模块与示例。
- **LangSmith SDK**（MIT，https://github.com/langchain-ai/langsmith-python）：追踪每次调用的实际提示，是验证预算与压缩策略是否奏效的唯一依据。
- **LangChain**（MIT，https://github.com/langchain-ai/langchain）：提示模板与消息化的历史管理。

## 六、坑与检查清单

- [ ] 每轮有明确的 token 预算，以及各层的分配。
- [ ] 硬约束与当前任务不可压缩、不可淘汰。
- [ ] 历史先压缩再淘汰，永远保留最近一两轮原文。
- [ ] 压缩后的摘要带原文指针，可回查。
- [ ] 检索结果先排序再截断，不要按召回顺序塞。
- [ ] 重要信息放开头或结尾，不放中段。
- [ ] 控制同类竞争信息，别把同格式干扰项堆在一起。
- [ ] 系统提示与工具定义放最前，构成稳定缓存前缀。
- [ ] 变动信息（时间戳、请求 ID）不要插进稳定前缀。
- [ ] 工具多时按需加载，别一次性全塞。
- [ ] 每轮输出预算报告：各层占用、丢弃了什么、关键事实在哪。
- [ ] 用评测集验证上下文策略，别凭感觉调。
- [ ] 上下文窗口再大，也要有工作集上限。

## 七、小结与延伸阅读

上下文工程的本质是分配：把有限的 token 分给不能丢的硬约束与当前任务，把可以重新获取的信息变成指针，把只能一次说清的内容压成结构化状态，把无关的东西淘汰掉。四种手段（分层、检索、压缩、淘汰）不是四选一，而是按优先级依次动用。上下文腐化提醒我们两件事：重要信息别放中间，同格式的竞争信息要少放。提示缓存则让"怎么排"直接变成"花多少钱"。最后，每个组装器都应该输出一份预算报告——没有报告的上下文优化，等于在盲调。
