# 序言：为什么这本书现在才写

## 一、先说两次事故

先讲一个我亲眼见过的场景。一个团队做了个运维问答 Agent，三个 Agent 协作：一个负责检索内部文档和监控面板，一个负责写结论，一个负责审校。链路跑得很顺，提示词改过七八轮，文档里明明白白写着"逐条引用原文，不得推断"。

出事那天给出的结论是"上周服务调用量正常回落"。这句话错得很具体：查询语句本身没问题，是监控面板在扩容期间数据采集停过，窗口里只剩成功请求。检索 Agent 把"没有失败记录"读成了"没有失败"，撰写 Agent 把它当成既成事实写进结论，审校 Agent 读的正是同一份被污染的素材，逻辑自洽，挑不出毛病。这条结论进了对外的周报。

复盘时大家的第一反应是"提示词不够强"。于是把检索 Agent 的提示词又加严了一轮，加了"若数据存在缺失或异常必须显式声明"——下一周同一个坑又踩了一次。因为"必须声明"是对模型的建议，不是系统的约束：模型在该开口的地方沉默了，你没有别的办法让它开口。

第二件事更让人窝火。一个四 Agent 的系统里，某次改动被自动推上线，三个月后有人问"这个限流是谁加的"，四个 Agent 互相说不清。不是它们推卸责任——日志里只有自然语言，没有结构化的决策记录，决策、观测、原始返回全挤在上下文里，上下文一滚动就不可追溯。

## 二、这本书的立场

这两件事都不是提示词写得好不好的问题。所以这本书从头到尾只主张一件事：**Agent 的难点不在提示词技巧，在控制流设计。**

展开一点。一个 Agent 系统里，应该有且只有一个地方决定"接下来干什么"——这是第 2 章讲的规划回路。而观测、工具返回这类数据流是可以批处理的：一次规划多个动作、并行调多个工具、合并多个观测，都不破坏语义。把这两者塞进同一段提示词，等于把调度规则塞进了数据，代价是没法并行、没法插人工确认、没法做检查点、没法在出错时退回第几步。

架构的价值也不在于让模型更准。模型的不确定性是给定的，抹不掉。架构能做的是**把不确定性收敛到可测试的边界内**：工具参数先过 schema 校验再执行；工具失败和空结果用不同类型表示，不共用一个空字符串；步数、token、金额都有上限；每一次决策都落盘，可以回放。第 3 章用一个可靠性算式说明，为什么单步成功率乘以步数会塌陷。

同样重要的是这本书不做什么。它不做框架复读机，不写"最佳实践"合集。每个结论都尽量带上适用条件和失效边界。第 3 章专门算过一次边际收益：什么时候手写 300 行的循环比用框架更划算。第 19 章的十个反模式里，一半在讲什么时候别用框架——书里那句话说得直接：绝大多数项目停在"手写循环 + 几个工具"这一级就够了。

## 三、怎么读

全书 40 章，分七卷。读法很简单：先读导论的三章建立坐标系，再按眼下的问题跳着读。

第 1 章到第 3 章值得读完，它们不长，但后面每一章都要用里面的术语——尤其是第 2 章的四回路和四个横切面。读完直接进你那一卷，不必从头顺读。

配套代码是另一条入口。全书 33 个可运行示例，默认 mock 模式、离线可跑，不需要 API Key：

```powershell
python code/run_all.py                  # 批量跑通全部示例
python code/ch04-react/main.py          # 只跑某章
python code/ch04-react/main.py --live   # 切到真实 API（需自行配置环境变量）
```

每章第四节还嵌了一份可以直接抄进自己项目的最小实现。

## 四、关于事实

书里出现的仓库 URL 与许可证都经过核实，可以自己去点开对照：每章末尾的"延伸阅读"里标着 URL 和许可证，附录 D 的项目索引可以按仓库名反查相关章节。许可证这类信息最容易写错，也最容易被下游忽略——比如 AutoGen 的代码是 MIT，仓库根目录的 LICENSE 却是 CC-BY-4.0，这种差异不写清楚会误导人。

具体数字上，本书的态度是：能溯源到论文或官方文档的才写；只出现在示例脚本实跑输出里的数字保留，因为它们和脚本对得上；核实不了的，写"未核实"，不猜、不删。

开源项目迭代很快。读到具体 API 名称和版本号时，请以官方仓库为准。

## 五、三条起点

**第一次接触 Agent**：第 1、2、4、8、10、11 章。顺序是"是什么 → 怎么拆 → 怎么转 → 怎么调工具 → 上下文怎么花 → 什么时候停"。业务涉及检索再加第 30 章，要选框架加第 19 章。

**已经写过 ReAct，想推上线**：第 2、3、6、8、9、10、11、12、28、29、33、34、35、36 章。重点从"能不能跑"转到"能不能测、能不能查、能不能控成本"。第 33 章的 Trace 是这一步的门槛：没有 Trace，后面所有问题都只能靠猜。

**负责把 Agent 推上生产的架构师**：第 2、3、12、19、23、24、25、29、31、32、33、34、35、36、39、40 章。编排、协议、拓扑、隔离、评测、成本、生产化清单，再到协议生态和自举这条前沿线。第 36 章的上线清单可以当验收表用。

另外三份材料：附录 A 是主流框架的架构对比，附录 C 是术语表（全书用词以它为准），附录 D 是全书索引。书前的《阅读路线图》按问题做了索引，遇到具体症状可以直接查章。

就从第 2 章开始吧。那四回路划清楚，后面三十八章都会省事。
