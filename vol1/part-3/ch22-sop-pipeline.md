# 第 22 章 SOP 流水线：MetaGPT、ChatDev 与 AgentVerse 的软件公司隐喻

## 一、本章要解决的问题

上一个需求我们把评审做成了三个 Agent 的对话会：产品经理提需求，架构师出方案，测试工程师挑毛病，来回吵了十一轮。结论很好，方案也落地了。

复盘的时候出了岔子。有人问"架构师当时为什么否掉那个方案"，没人答得上来——那些话在聊天记录里，聊天记录没有版本、没有结构、也没有索引，等你想找的时候，得从头把十几轮消息读一遍才拼得出来。

更糟的是第二周来了个新需求，团队说"照上次那样做一遍"。上次是三个 Agent 开了十一轮会，中间那些来回没有一句能直接搬过来。

于是我们把做法换成流水线：产品经理写需求文档，架构师写接口定义，工程师写实现，测试工程师写用例，每个阶段只读上游的文档、不读上游的过程。文档留档、可比对、可回放；改需求只改需求文档，下游按依赖关系重跑。

**把人类软件公司的流程编码成 Agent 流水线，关键设计不是"有几个人"，而是"用什么当共享状态"。** 答案不是聊天记录，是标准文档。

## 二、原理：机制拆解

### 2.1 MetaGPT 的 SOP 与标准文档

MetaGPT 的思路朴素得近乎刻板：把软件公司的标准作业流程（standard operating procedure，SOP）直接写成 Agent 流水线。角色固定、顺序固定、产物固定。

```
【需求】
   │
   ▼ 产品经理
【PRD】 需求文档：背景 / 目标 / 验收标准 / 非目标
   │
   ▼ 架构师
【接口定义】 方法与路径 / 入参出参 / 错误码 / 数据模型
   │
   ▼ 工程师
【任务清单】【实现代码】
   │
   ▼ 测试工程师
【测试用例】
   │
   ▼ 评审
【评审报告】 ──打回──► 回到指定阶段（返工次数有上限）
```

关键不在流程长什么样，在**接口定义是事实来源（single source of truth）**：工程师不读架构师的推理过程，只读那份接口定义；测试工程师不读工程师的思考，只读接口定义和代码。

这一条决定了两件事。

**第一，上下文是收敛的。** 架构师的推理可能有上万字，接口定义只有几百字。下游读的是后者，于是每个阶段的输入规模可控，不会随流程推进而膨胀。

**第二，格式稳定才能缓存与审计。** 文档有固定结构，就能做版本号、能做差异对比、能判断"这份文档变没变"——这是第 2.4 节要讲的全部好处的前提。

### 2.2 ChatDev 的 ChatChain

ChatDev 把这套东西组织成"链"（chain）：链上串起若干阶段，每个阶段有自己的角色与输入输出；阶段内部允许对话，阶段之间必须落到文档。

它比 MetaGPT 更细的地方有两个。

一是**角色更贴近真实分工**：CEO 提需求、CTO 出技术方案、程序员写代码、测试工程师验收。每一步的产物也很具体——设计文档、任务列表、代码文件。

二是**评审回路是显式的一环**。评审阶段读上游产物，如果发现不达标，不是打个"已读"就往下走，而是写明问题、打回到指定阶段重做，并且有次数上限。

这一点是流水线能不能用的分水岭。没有回路的流水线只会把错误一路推到底，最后在最后一步炸掉；有回路的流水线能在中途截住。但要注意，评审回路天然有"橡皮章"化的倾向——评审角色每轮都说通过，这个回路就白设了。

### 2.3 AgentVerse 的场景与求解器

AgentVerse 的抽象层次又往上提了一层：它不写死一条流水线，而是准备一批**场景**（scenario）。每个场景是一组角色、各自的画像、以及它们之间的互动规则；再配上一组**求解器**（solver），负责"给定一个任务 → 挑一个合适的场景 → 跑起来 → 交出结果"。

三者的谱系很清楚：

| | 组织方式 | SOP 是写死的还是可替换的 |
| --- | --- | --- |
| MetaGPT | 一条软件公司流水线 | 写死在框架里 |
| ChatDev | 阶段组成的链，阶段内可对话 | 写死在链的定义里 |
| AgentVerse | 场景库 + 任务求解器 | 场景可替换、可扩展 |

对自建系统来说，这个抽象的价值在于：**SOP 从"一段代码"变成"一份配置"。** 换一个任务族，换一套场景定义就行，引擎不动。

### 2.4 共享文档作为状态载体

把状态放在文档里，好处和坏处都很具体。

**可审计。** 每份文档记录了：谁产出、读了哪些输入的哪个版本、第几轮产出。配套脚本的审计日志长这样：

```
阶段        读                      写                token      结论
产品经理    —                       prd@v1            455        —
架构师      prd@v1                  api@v1            640        —
工程师      api@v1                  tasks@v1、code@v1 769        —
测试工程师  api@v1、code@v1         tests@v1          735        —
评审        prd@v1、api@v1、tests@v1 review@v1        915        rework
工程师      api@v1                  tasks@v2、code@v2 769        —
测试工程师  api@v1、code@v2         tests@v2          735        —
评审        prd@v1、api@v1、tests@v2 review@v2        880        approve
```

**可缓存。** 文档有稳定版本号，上游没变，下游就不用重算——这是流水线相对对话最实在的一笔省钱。

**可回放。** 历史版本全在，任何一次运行都能还原：拿旧版本的接口定义配上旧版本的代码，能复现当时的产物。

坏处同样有三条，而且每条都会真咬人。

**腐化（corruption）。** 上游改了，下游没跟着改，于是陈旧内容混在新流程里继续往下传。修法是给每份文档记下"输入的版本号"，上游版本一变，下游立刻能判定自己失效——而且要算传递闭包：需求文档改了，接口定义脏，接口定义脏了，实现和测试跟着脏。

**格式耦合。** 下游对上游文档的格式有隐式依赖。接口定义里加个字段没事，把"错误码从列表改成对象"就可能让整条链崩。修法是给文档定 schema，格式变更要过契约测试。

**语义漂移。** 字段对得上不等于意思对得上。"金额单位是分"这种约定写在文档里，工程师理解成"元"，schema 检查一点问题都发现不了。这只能靠评审回路兜，而评审回路又容易退化成橡皮章。

### 2.5 成本账

流水线的成本优势不在模型，在契约。每个阶段只读声明的输入，输入规模就是可控的。

配套脚本里，同一条流水线、同一份产物，改成"每个阶段都读全部文档"之后：

```
契约式输入（只读声明的输入）   8 次       输入 4255        总 token 5898
全量共享输入（每阶段都读全部文档） 8 次       输入 7166        总 token 8809
```

多花 1.5 倍。文档越多、阶段越往后，这个倍数越大——因为"全读"那份是平方级增长，"契约"那份是线性的。

增量重跑是第二笔账。改了需求文档之后，失效的文档是接口定义、实现、任务清单、测试用例、评审报告五份；只重跑受影响的四个阶段，花了 3,052 token，而全量重跑要 5,898。

**所以流水线的成本公式不是"阶段数 × 每阶段成本"，而是"脏掉的部分 × 重跑成本"。** 前提是失效判定得准。

## 三、为什么这样设计：取舍与失效条件

先把什么时候**不该**上流水线说清楚：

1. **需求本身还不确定。** 流水线会把当前的错误固化成标准文档，越跑越正式，改起来越贵。探索期该用对话（第 21 章）。
2. **阶段产出没法用文档表达。** "用户访谈得到的感受"写不成结构化文档，硬写就变成了空话。
3. **任务短到不值得走流程。** 为一个十分钟的活铺五个阶段文档，是拿工程量换仪式感。
4. **需要人临场判断。** 流程中间插人工审核点没问题，但每次插点都要付一次"打断—等待—恢复"的成本。
5. **阶段会频繁重排。** 真实业务里阶段经常重叠甚至并行，写死顺序的流水线会天天返工。

再讲 SOP 固有的脆弱性：

- **语义损失。** 文档是压缩过的表达。上游那 5000 字里的权衡、取舍、妥协，到了下游只剩 500 字的事实描述。压缩率越高，损失越大。
- **返工放大。** 返工点越靠前，重跑越贵。评审在最后一道，返工要重跑整条链；评审在第一道，后面全白做。所以评审环节要尽量前移。
- **伪确定性。** 格式统一了不等于内容没退化。模型这次产出的接口定义可能比上次少了一条错误码，而格式检查发现不了。流水线的"整齐"会掩盖质量的漂移。
- **橡皮章评审。** 评审角色每轮都通过，等于没有评审。至少要抽查评审记录，看它打回的比例是否合理——一直 100% 通过的评审，本身就是一个 bug。

最后是迁移到非软件任务。这件事是可行的，因为 SOP 的本质是"阶段契约 + 文档交接"，与领域无关。脚本里换了一套契约，引擎一行没改：

```
阶段        读            写             结论
调研员      —             brief@v1       —
方案师      brief@v1      proposal@v1    —
风控评审    proposal@v1   review2@v1     approve
```

三个角色、三份文档、951 token，评审回路同样生效。会员系统选型这种任务，完全可以走流水线。

但有四个陷阱：

1. **照抄角色名。** 把 CEO、CTO、程序员原样搬到"选一套会员系统"上，角色会空转，产出格式正确但内容正确的废话。
2. **照抄文档结构。** PRD 的章节结构是给软件需求用的，硬套到别的领域，写出来的章节没有信息量。
3. **把阶段顺序当铁律。** 调研和访谈常常该并行，评审也可能要插在中间。
4. **阶段越多，腐化传播越快。** 五个阶段以上，失效判定的复杂度会超过收益。

## 四、动手：最小可实现

代码在 `code/ch22-sop-pipeline/`，纯标准库、无需 API Key。

**依赖**：Python 3.9+，零第三方包。

**运行**：

```bash
cd code/ch22-sop-pipeline
python main.py                  # A~E 五段演示
python main.py --trace          # 打印每一步的完整提示
python main.py --live           # 切真实模型
```

一次跑清五件事：阶段契约、标准文档的版本与审计、评审回路与返工上限、契约式输入与全量共享输入的成本差、上游变更后的失效判定与增量重跑，以及同一引擎在非软件任务上的运行。

典型输出（节选）：

```
终止原因 completed｜返工 1 次｜模型调用 8 次｜总 token 5898

契约式输入（只读声明的输入）   8 次   输入 4255   总 token 5898
全量共享输入（每阶段都读全部文档） 8 次   输入 7166   总 token 8809

改了 PRD 之后，失效的文档：api、code、review、tasks、tests
增量重跑执行了：架构师、工程师、测试工程师、评审｜本次花费 3052 token
可回放：prd 一共有 2 个历史版本，随时能取回任意一版对比。
```

### 4.1 关键实现片段

阶段契约就是一份声明，写清楚读什么、写什么：

```python
Stage(
    name="架构师", role="架构师",
    reads=["prd"], writes=["api"],
    instruction="依据 PRD 写出接口定义：方法与路径、入参出参、错误码、数据模型。"
                "金额一律注明单位。不要写实现代码。",
),
Stage(
    name="评审", role="评审",
    reads=["prd", "api", "tests"], writes=["review"],
    instruction="对照 PRD 的验收标准评审接口定义与测试用例。",
    format_spec=OUTPUT_FORMAT + ' 额外字段：{"verdict": "approve|rework", ...}',
    is_review=True, rework_to="工程师",
),
```

失效判定是流水线的关键机制——它要算传递闭包：

```python
def stale_set(self):
    stale = set()
    changed = True
    while changed:                      # 迭代到不动点，因为失效会往下传
        changed = False
        for name, art in self.current.items():
            if name in stale:
                continue
            for dep, ver in art.inputs.items():
                cur = self.current.get(dep)
                if cur is None or cur.version != ver or dep in stale:
                    stale.add(name)     # 输入版本对不上，或输入本身已脏
                    changed = True
                    break
    return stale
```

两个提醒：

**版本号要记在产物上，不能只记在文档库里。** 产物里存的是"我读的是 prd 的第几版"，这样失效判定才有依据。只存当前版本号的话，判定不出"这份实现是基于旧接口生成的"。

**返工上限是硬闸门。** `max_rework` 到了就停，不要无限循环。评审说"打回"时先回头看需求文档有没有歧义——需求本身没写清楚，再跑一百遍流水线也没用。

## 五、开源实现对照

- **MetaGPT**（MIT，https://github.com/geekan/MetaGPT）：把软件公司的 SOP 直接编码成 Agent 流水线，PRD、接口定义、任务清单作为阶段产物交接。它是"标准文档作为共享状态"最完整的样本。
- **ChatDev**（Apache-2.0，https://github.com/OpenBMB/ChatDev）：ChatChain 形态，阶段内可对话、阶段间落文档，评审阶段可打回。角色分工比 MetaGPT 更细，值得对照两者的阶段切分粒度。
- **AgentVerse**（Apache-2.0，https://github.com/OpenBMB/AgentVerse）：多角色场景 + 任务求解器，SOP 是可替换的场景而不是写死的链，抽象层次最高。
- **OpenAgents**（Apache-2.0，https://github.com/xlang-ai/OpenAgents）：沿 AgentVerse 路线继续做的开放平台，把角色、工具与流程放到一起配置。
- **Qwen-Agent**（Apache-2.0，https://github.com/QwenLM/Qwen-Agent）：把函数调用、MCP、代码解释器与 RAG 收在单 Agent 内，正好作为对照——阶段内部需要的工具能力，不必拆成多个 Agent。
- **CrewAI**（MIT，https://github.com/crewAIInc/crewAI）：角色—任务—流程的另一种抽象，流程（Process）只有 sequential 与 hierarchical 两个取值，默认 sequential；与 SOP 流水线同构但表达更轻。
- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：显式状态图与检查点。把 SOP 写成状态图，阶段边界、回退边、持久化都由代码控制，适合长流程与断点续跑（见第 23 章）。
- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python）：Agent、工具、交接与护栏，工作流是组合出来的，适合把流水线拆成可复用的小块。
- **AutoGen**（MIT，代码部分为 LICENSE-CODE，仓库根目录 LICENSE 为 CC-BY-4.0，https://github.com/microsoft/autogen）：GroupChat 路线，正好与本章形成对照——对话式协作与 SOP 流水线的分野就在这里。
- **AgentScope**（Apache-2.0，https://github.com/agentscope-ai/agentscope）：可视化调试与追踪，流水线出问题时，能看到每个阶段读了什么、写了什么。

许可证之外的具体 API 与版本，请以官方仓库为准。

## 六、坑与检查清单

上流水线之前，逐条打勾：

- [ ] 每个阶段都显式声明了"读哪些文档、写哪些文档"。
- [ ] 下游只读上游的文档，不读上游的推理过程。
- [ ] 文档有版本号，产物里记录了输入的版本号。
- [ ] 有失效判定，且能算传递闭包（上游脏了，下游跟着脏）。
- [ ] 增量重跑只重跑脏掉的阶段，不是整条链重来。
- [ ] 文档有 schema，格式变更有契约测试兜底。
- [ ] 评审环节有返工次数上限，不允许无限打回。
- [ ] 我抽查过评审记录：打回比例合理，不是每次都通过。
- [ ] 每个阶段的产物有可验证的验收条件，不只是"看起来对"。
- [ ] 返工点尽量靠前，我算过"在这里打回要重跑多少"。
- [ ] 我实测过契约式输入与全量共享输入的 token 差。
- [ ] 需求还不确定的时候，我没有上流水线。
- [ ] 迁移到新领域时，阶段是重新定义的，不是照抄软件公司的角色名和文档模板。
- [ ] 阶段数量控制在五个以内，腐化传播不至于失控。

## 七、小结与延伸阅读

把软件公司的流程编码成 Agent 流水线，真正要设计的是共享状态。MetaGPT 用 SOP 加标准文档，ChatDev 把它做成阶段链并留下评审回路，AgentVerse 再抽象成可替换的场景库——三代演进的方向是一致的：流程要能被配置、被审计、被回放，而不是被写死在对话里。

共享文档的三个好处——可审计、可缓存、可回放——是流水线的真正收益：改一处需求文档，只重跑脏掉的那几段，3,052 token 而不是 5,898。它的三个坏处——腐化、格式耦合、语义漂移——也都要在设计阶段就防住：产物记版本号、文档定 schema、评审兜语义。

迁移到非软件任务是可行的，脚本里 951 token 就跑完了一个会员系统选型的完整流程。陷阱不在技术，在偷懒——照抄角色名和文档模板，一定产出格式正确、内容正确的废话。
