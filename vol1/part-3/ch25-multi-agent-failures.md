# 第 25 章 多 Agent 失效模式与成本治理

## 一、本章要解决的问题

去年我们上线了一个四 Agent 的运营分析小组：检索员、分析员、撰写员、审核员，一句话交活，前两周跑得挺好。

第三周的周一早上出了事。日报第一行写着"Q3 获客成本环比**暴涨** 38%，退款率**飙至** 6.7%，创**历史最差**"。而 38% 这个数字，检索员给的是一条中性陈述："获客成本环比 +38%"。

接下来三步是这样的：分析员把它写成"暴涨 38%，飙到 6.7%，历史最差"；撰写员写成"创下历史最差，必须立刻全面整改"；审核员说"审核通过"。一个普通的波动，经过三轮转述，被改写成了一场灾难——而系统的状态是**成功**。

复盘时我们才意识到更麻烦的一点：**单 Agent 出错，你看得见**——一条轨迹，扫一眼就知道哪一步偏了。多 Agent 出错，你看到的是一份言之凿凿的结论和一堆没人细看的日志。

于是问题变成了三句话：多 Agent 有哪些典型死法？怎么在它死之前把它按下来？以及最根本的——**多 Agent 到底值不值**，怎么用数据回答而不是靠感觉。

## 二、原理：机制拆解

### 2.1 失效清单：六个典型死法

| 失效 | 现象 | 机制 | 后果 |
| --- | --- | --- | --- |
| 无限循环（infinite loop） | 两个角色来回打转 | A 要 B 的结论，B 要 A 的输入 | token 与时间双涨，无产出 |
| 角色塌缩（role collapse） | 所有角色说同一句话 | 共享历史里前面的发言成为模板 | 差异化归零，像一个人自言自语 |
| 共识幻觉（consensus hallucination） | 宣称"已达成共识" | 没有可验证内容，靠措辞制造共识 | 决策建立在空气上 |
| 错误放大（error amplification） | 下游把上游数字说得更夸张 | 错误结论进入上下文后被当作事实 | 一轮比一轮离谱，还带着推理过程 |
| 委派死锁（delegation deadlock） | 互相等待，谁也不推进 | 依赖成环 | 流程挂起，靠超时兜底 |
| 上下文污染（context contamination） | Agent 执行了工具返回里的指令 | 工具内容与指令混在同一层 | 外部数据劫持内部流程 |

这六个不是并列的。塌缩和共识幻觉是**内容层**的问题（说的话本身坏了），无限循环和委派死锁是**控制层**的问题（流程本身卡住了），错误放大和上下文污染是**信任层**的问题（进来的东西被当成了可信的）。分类的意义在于：检测手段完全不同。

### 2.2 检测信号：五个可计算的量

多 Agent 的监控不能只靠"感觉有点不对"。能被算出来的信号才敢写进熔断条件。

**重复率（duplicate ratio）**：相邻发言之间的相似度均值。实现上用字符 3-gram 的 Jaccard 相似度——不需要模型，也不需要语义理解。实测：正常场景 0.03，塌缩场景 1.00。

**消息长度趋势**：每步发言长度的线性斜率。持续为负说明发言在缩水，是塌缩的早期征兆。

**角色熵（role entropy）**：发言者分布的归一化熵。它抓的是"少数角色垄断了对话"——比如三个角色轮流出场，第四个再也没说过话。

**token 斜率**：每步 token 用量的线性趋势。持续为正说明上下文在滚雪球，每一轮都要把历史重读一遍。

**步数增长曲线**：步数本身不一定是坏事，但"步数增长而结论没变"是明确的浪费。

这里有一条实测出来才想得到的结论，值得单独说：**塌缩的时候，角色熵是满的（实测 1.00）**。因为四个角色各说一遍同样的话，分布依然均匀。角色熵抓不到内容塌缩——它只抓分布塌缩。真正抓住塌缩的是重复率。指标要一起看，单看一个会被骗。

除了这五个统计量，还需要三个语义信号，它们没法纯靠统计得到：

- **无进展**：连续几条发言都在"等/待/依赖"，没有任何实际推进。
- **断言放大**：下游把上游的数字换成了"暴涨/历史最差/立刻整改"这类强化措辞。做法是提取消息里的数字，看下游是不是在复述上游的数字、同时用了强化词。
- **注入回声**：工具返回里被引号框起来的"照着输出"的内容，原样出现在 Agent 的输出里。这一条是上下文污染的直接证据。

### 2.3 熔断与降级：三层阶梯

熔断条件要硬一点，写在代码里，不靠人盯：

| 熔断条件 | 触发阈值 | 拦的是什么 |
| --- | --- | --- |
| 步数上限 | max_steps | 无限循环 |
| 总时长上限 | max_seconds | 慢而不止 |
| token 预算上限 | max_tokens | 成本失控 |
| 重复率超阈值 | 0.75（示例值） | 角色塌缩 |
| 连续无进展 | 连续 3 步 | 委派死锁 |
| 断言放大 | 命中即停 | 错误放大 |
| 注入回声 | 命中即停 | 上下文污染 |

熔断之后不能直接报错退出，那是最糟的处理——前面已经产出的有效信息全丢了。正确的做法是走**降级阶梯**：

```
熔断触发
   │
   ├─ 第一级：强制收敛（force convergence）
   │    换一条"停止讨论、只输出结论"的指令，限制在一轮内
   │    ↓ 还是空
   ├─ 第二级：单 Agent 回退（single-agent fallback）
   │    换一个不带他人历史的 Agent，基于最后一份素材直接给结论
   │    ↓ 还是空
   └─ 第三级：中止
        返回部分结果：已确认的事实、卡在哪一步、下一步该谁做
```

**三个要点。** 第一，降级结果要标"降级完成"，让下游知道这份结论没有经过完整讨论。第二，单 Agent 回退的价值在于丢掉历史包袱——带着一堆互相污染的历史去总结，只会总结出污染。第三，第三级虽然叫中止，但必须返回**可用的部分结果**，而不是空响应或者一句"失败了"。

另外每一步调用都要有重试上限。重试是给瞬时故障用的，不是给逻辑错误用的；无上限重试在多 Agent 里会变成指数级的浪费。

### 2.4 成本可视化：一次任务的总账与归因

成本不能只看到一个总数。一次多 Agent 运行的总账应该是四行：调用次数、输入 token、输出 token、墙钟时长。

更关键的是**归因**：把 token 按角色摊开。实测正常场景：

```
按角色归因：审核员 177 token（39%）；撰写员 139 token（30%）；
             分析员 92 token（20%）；检索员 49 token（11%）
```

一眼看出谁最贵：审核员。原因是它最后出场，要读完前面所有人的产出。归因的作用就是——**分清是调度在烧钱，还是执行在烧钱**。如果是调度（反复派单、反复总结），该改拓扑；如果是执行（产出本身太长），该改提示词。两种病因，两种药。

美元金额按单价表算，单价从配置读，不要写死。这里用的是示例单价（$0.001/$0.002 每千 token），只为演示计算方式，不代表任何厂商的真实价格。

### 2.5 用评测而不是直觉判断值不值

判断多 Agent 是否值得，要看两套任务集、两个数字：正确率和成本倍数。配套脚本里的判据是：**正确率提升 ≥ 0.2 且成本倍数 ≤ 3，才算值得。**

跑出来两个相反的结论：

| 任务集 | 单 Agent 正确率 | 多 Agent 正确率 | 提升 | 成本倍数 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 需要检索的任务 | 75% | 100% | +25% | 2.6× | 值得上多 Agent |
| 格式固定的任务 | 100% | 100% | +0% | 3.1× | 不值得，别上 |

同一个问题，两套任务集给出相反的答案。这就说明"多 Agent 更好"是个没有信息量的说法：**它对你那套任务集成立不成立，只能自己测。**

而且测的时候两个指标必须一起看。只看正确率，会在收益小的地方上多 Agent；只看成本，会在收益大的地方省掉多 Agent。

## 三、为什么这样设计：取舍与失效条件

每个检测信号都有误报代价，阈值是调出来的，不是拍的：

- **重复率**阈值太低，"是，对""同意"这类正常短回复会被当成塌缩误杀。阈值要靠标注样本扫出来。
- **无进展检测**会误伤异步场景——工具返回"处理中"、人在等外部审批，这类本来就该等。所以要留一条"我在等待"的白名单，和心跳标记（第 11 章那套思路）。
- **角色熵**只看分布不看内容，塌缩时它反而是满的（见 2.2）。
- **token 斜率**受任务长度影响，短任务天生斜率低，不能跨任务直接比。

熔断本身也有代价：太早熔断会误杀好任务，太晚会烧钱。所以应该分级——先告警观察，再熔断；对高价值任务，宁可多花一次调用确认也不要急着降级。

降级的代价也要承认：强制收敛的结论质量不如完整讨论；单 Agent 回退丢掉了多方视角；中止则意味着这次任务没完成。**所以降级不是免费的保险，它是一个需要标注的业务事实。**

回到更根本的一层：什么时候压根不该上多 Agent。任务单一、没有对抗、结果可验证——这种任务上多 Agent 只会把成本翻倍，把可观测性做差（第 20 章的判断题）。

最后一条自我提醒：**上面这六个失效模式不是全集。** 清单永远只能覆盖已经见过的坑。新失效模式只能靠线上 trace 和告警发现，所以指标和评测这两套基础设施，比清单本身更重要。

### 4.1 关键实现片段

重复率是检测器里最该先写的，因为它不需要模型：

```python
def similarity(a: str, b: str) -> float:
    """字符 3-gram 的 Jaccard 相似度，用来判断两条发言是不是在复读。"""
    ga, gb = ngrams(a), ngrams(b)
    if not ga or not gb:
        return 0.0
    return len(ga & gb) / float(len(ga | gb))
```

断言放大要同时看"数字"和"措辞"：

```python
INTENSIFIERS = ["暴涨", "飙升", "历史最差", "极其严重", "全面整改", "立刻"]
for i, s in enumerate(msgs):
    nums = set(extract_numbers(s.text))
    if not nums or not any(w in s.text for w in INTENSIFIERS):
        continue
    upstream = any(set(extract_numbers(p.text)) & nums for p in msgs[:i])
    if upstream:
        return "第 %d 步把上游的数字 %s 换成了强化表述" % (i + 1, "/".join(sorted(nums)))
```

降级阶梯的实现，三级依次尝试：

```python
def _converge(self, report, history):
    # 第一级：强制收敛——同一个 Agent，不给新信息，只要求出结论
    out = self.llm.chat("审核员", CONVERGE_PROMPT, "\n".join(history))
    report.steps.append(Step(..., kind="converge"))
    if out.strip():
        report.degradation = "强制收敛：复用最后一位发言者，限定只出结论"
        return out
    # 第二级：单 Agent 回退——新 Agent 不带他人历史
    out2 = self.llm.chat("兜底分析员", FALLBACK_PROMPT, "素材：%s" % (history[-1] if history else ""))
    report.steps.append(Step(..., kind="fallback"))
    if out2.strip():
        report.degradation = "单 Agent 回退：新 Agent 不带他人历史，直接给结论"
        return out2
    return ""      # 第三级：中止，由调用方返回部分结果
```

三个提醒：

**信号要分级，不要一把梭。** 现在脚本里是"命中即熔断"，生产上建议先只告警、积累几天标注数据，再把阈值调到该熔断的水平。阈值拍出来的熔断器，第一天就会误杀。

**降级路径也要被测试。** 脚本里降级路径用 mock 固定返回，但真实情况下"强制收敛"这一轮仍可能失败——所以要单独造一批"强制收敛也拿不到结论"的 case，验证第二级、第三级能接住。

**注入回声检测是事后检测，不是防御。** 它能发现 Agent 已经被劫持，但更好的做法是在工具返回进入上下文之前就把指令部分剥离或隔离（第 32 章）。两件事都要做。

## 五、开源实现对照

- **AutoGen**（MIT，代码部分为 LICENSE-CODE，仓库根目录 LICENSE 为 CC-BY-4.0，https://github.com/microsoft/autogen）：GroupChat 的最大轮数与终止条件是最基本的熔断配置（老接口参数名 `max_round`，新版 AgentChat 里叫 `max_turns`），对照上面的熔断条件表看它默认给了哪些。
- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：递归上限与检查点。检查点让中断后可恢复，是熔断之外另一种"别把已做的工作丢掉"的手段（见第 29 章）。
- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python）：运行器最大轮次、护栏与追踪。护栏是熔断的前置版本——在越界之前拦住，而不是事后检测。
- **CrewAI**（MIT，https://github.com/crewAIInc/crewAI）：流程与任务上限，适合看"用配置而不是代码"来限制步数。
- **AgentScope**（Apache-2.0，https://github.com/agentscope-ai/agentscope）：Studio 可视化调试与追踪，上面这套检测信号要落地成看板，这里是现成的参考。
- **CAMEL**（Apache-2.0，https://github.com/camel-ai/camel）：角色扮演范式的出处，也是"角色漂移"这个问题的原始观察地——角色设定写得越极端，越容易出现塌缩。
- **Microsoft Agent Framework**（MIT，https://github.com/microsoft/agent-framework）：把 Agent、工作流与部署统一起来，治理能力（预算、护栏、追踪）在同一处收口。
- **OpenLLMetry**（Apache-2.0，https://github.com/traceloop/openllmetry）：基于 OpenTelemetry 语义的 LLM 追踪，把每一步的调用、token、耗时变成可聚合的 span，这些指标可以基于它落库。
- **AgentOps**（MIT，https://github.com/AgentOps-AI/agentops）：面向 Agent 运行的追踪与成本看板，适合对照"把成本按角色归因"怎么做。

许可证之外的具体 API 与版本，请以官方仓库为准。

## 七、小结与延伸阅读

多 Agent 的问题不是设计不出来，是出了问题看不见。六个典型死法分属三个层次：内容层（塌缩、共识幻觉）、控制层（无限循环、委派死锁）、信任层（错误放大、上下文污染）。每一类都有对应的可计算信号——重复率、角色熵、token 斜率、无进展、断言放大、注入回声。

熔断之后要走降级阶梯，而不是直接失败：强制收敛 → 单 Agent 回退 → 中止并返回可用的部分结果。三级里任何一级成功，任务就不算白做。

但最该记住的其实是最后那个评测结果：同一套多 Agent 方案，在"需要检索的任务"上把正确率从 75% 提到 100%、成本 2.6 倍，值得；在"格式固定的任务"上正确率一点没涨、成本 3.1 倍，不值得。**多 Agent 不是一个技术选型，是一个要按任务集分别算账的决策。** 算账的方式只有一个：跑你自己的评测集。
