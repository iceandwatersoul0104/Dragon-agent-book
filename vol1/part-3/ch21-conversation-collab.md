# 第 21 章 对话式协作：GroupChat 与 CAMEL 角色扮演

## 一、本章要解决的问题

去年做客服工单核对报表，我第一次认真用上了"多角色讨论"。需求分析师、架构师、测试工程师三个 Agent，按角色扮演的提示开会，目标是让它们自己吵出需求边界和验收口径。

第一次运行就有三个问题。

**一是停不下来。** 三个角色互相追问，从字段口径吵到索引重建策略，谁都不肯先收尾。设计里写了终止词，但模型经常忘记说；等到第 9 轮测试工程师才打断，第 11 轮架构师才说出 `[DONE]`。在真实业务里，这就是一个会烧钱的循环。

**二是输入越来越贵。** 我把每轮的 prompt 打出来，增长得很直白：

| 轮次 | 1 | 3 | 5 | 7 | 9 | 11 |
| --- | --- | --- | --- | --- | --- | --- |
| prompt token | 356 | 551 | 732 | 911 | 1096 | 1286 |

同样这 11 段发言，共享全量历史要 9,047 token 输入；换成"只带摘要 + 最近两条"是 7,096，只省下两成。差距要到长对话才拉开——60 次发言时，同样两种策略是 45,660 对 170,049，差 3.7 倍（见 2.5 节）。

**三是"谁说话"本身就是个决策。** 换成让模型自动挑下一个发言的人之后，12 段发言花了 23 次模型调用——每说一句话之前，还得先开一次会决定谁说。

于是问题就清楚了：**对话式协作不是"让几个 Agent 聊聊"，而是三个必须单独设计的机制——谁发言（调度）、说什么（角色提示）、什么时候停（协议）。** 这三件事分开设计，代码才不会长成一坨互相嵌套的 if。

## 二、原理：机制拆解

### 2.1 GroupChat 的轮次控制

GroupChat 的骨架只有三张表加一个循环：参与者表、消息表、调度器。

```
┌──────────────┐   ①选人     ┌──────────────────┐
│   调度器      │───────────►│  角色 A          │
│ (scheduler)  │            │ (inception prompt)│
└──────┬───────┘            └──────────────────┘
       │ ②发言+可见历史  ◄──────┘
       ▼
┌────────────────────────────────────────────────┐
│ 消息表：#1 需求分析师 / #2 架构师 / #3 测试工程师 │
└────────────────────────────────────────────────┘
       │ ③渲染可见历史（shared / partitioned / summary）
       └──────────────► 下一位发言者
```

核心循环短到可以一眼看完：

```python
while len(messages) < max_turns:
    speaker = select_speaker(messages)      # 调度：谁说
    system = inception_prompt(speaker)      # 角色：说什么
    user = render_history(speaker, mode)    # 上下文：看到什么
    msg = llm.chat(speaker.name, system, user)
    messages.append(msg)
    if "[DONE]" in msg:                      # 协议：怎么停
        break
    if "[INTERRUPT:X]" in msg:
        next_speaker = X
```

说话人选择（speaker selection）怎么实现，直接决定账单。AutoGen 老接口的 `GroupChat` 把它做成了一个配置项 `speaker_selection_method`，取四个字符串值，再加一个自定义函数：

| 策略 | 谁决定下一个发言者 | 模型调用 | 适合什么 |
| --- | --- | --- | --- |
| 轮转（round_robin） | 固定顺序 | 每次发言 1 次 | 流程稳定、要复现、要压测 |
| 随机（random） | 随机 | 每次发言 1 次 | 压测，避免固定顺序带来的位置偏好 |
| 自动（auto，AutoGen 的默认值） | 模型自己选 | 每次发言 2 次 | 需要临场判断谁该接话 |
| 手动（manual） | 人来点 | 每次发言 1 次 | 高风险决策、要留人工审计 |
| 代码规则（callable） | 你的函数 | 每次发言 1 次 | 有明确业务规则，如"报错就让架构师说" |

配套脚本实现了其中四种（round_robin / auto / manual / callable），没做 random——它和 round_robin 一样只花 1 次调用，没什么可演示的。

自动选人最像"智能"，也最贵——它让每次发言的调用数翻倍。更隐蔽的代价是：选人调用本身也要读历史，历史越长，选人越慢越贵。

新版 AutoGen 把这件事拆成了几个专门的组队类：轮转对应 RoundRobinGroupChat，模型选人对应 SelectorGroupChat，Agent 之间直接交接对应 Swarm。选哪种，比在提示词里写规则更可靠。

### 2.2 CAMEL 的角色扮演提示范式

CAMEL（https://github.com/camel-ai/camel）的核心贡献之一是 **inception prompt（角色扮演提示）**：把一个抽象任务改写成一个具体角色的一段开场白。它有固定四段：

```
【任务】为客服团队做一套退款与赔付工单的自动核对报表……
【你的角色】你是架构师。负责技术方案与容量估算，讨厌没有回滚路径的设计。
           你的风格：先讲约束，再讲方案，最后讲代价。你的目标：……
【对话对象】需求分析师（负责把用户场景和验收口径讲清楚，讨厌模糊需求）、测试工程师（……）
【输出格式】每次只输出你自己的一段发言，100-150 字，不要替对方说话；
           需要对方回应时结尾写 [ASK:<对方名字>]；认为讨论已经收敛时结尾写 [DONE]；……
```

为什么这四段有效：

1. **把"任务"翻译成"角色"。** 角色自带立场与拒绝的理由。"你是一个资深工程师"只是标签，"你讨厌没有回滚路径的设计"才是能让模型挑剔起来的约束。
2. **写"反对什么"比写"要什么"有效。** "目标是给出可运维的方案"太虚，"讨厌没有回滚路径的设计"能直接改变取舍。
3. **把对话对象写进提示。** 模型不用你再解释一遍"现在跟谁说话"，语气和详略自然对齐对象。
4. **输出格式前置。** 格式写在提示里，就不用事后解析自然语言——这是后面所有控制信号的前提。

CAMEL 原始设定是两方一问一答，GroupChat 是多方。把"对方"从一段提示升级成参与者表，其余四段不变——这是把 CAMEL 范式用到多角色场景上最省事的路径。

### 2.3 对话协议设计

对话式协作里，控制信号必须写成**结构化标记**，不能指望模型用自然语言表达"我同意"。可用的标记不多，四个够用：

| 标记 | 谁发出 | 语义 | 谁处理 |
| --- | --- | --- | --- |
| `[ASK:名字]` | 任意角色 | 需要对方回应 | 调度器可据此插队或加权 |
| `[DONE]` | 任意角色 | 讨论收敛 | 调度器终止会话 |
| `[INTERRUPT:名字]` | 任意角色 | 让出发言权 | 调度器跳过当前策略，直接点名 |
| 无标记 | 任意角色 | 普通发言 | 正常推进 |

三条设计要点：

**打断优先级最高。** `[INTERRUPT:名字]` 要绕过轮转、自动、手动所有策略，直接点名下一位。否则"打断"只是一个建议，模型可以无视。

**终止判定在代码里，终止词由模型产出。** 模型说 `[DONE]` 只是一个候选信号，真正的终止要三层兜底：协议终止词 → 轮次上限 → 预算上限（预算守卫见第 11 章）。只靠模型自觉，实测必然漏。

**仲裁要单独算账。** "谁说了算"这件事如果不是确定性规则（比如轮转、代码规则），就必然要一次模型调用。这笔开销要单列，不要混进发言成本里。

### 2.4 上下文膨胀：共享 vs 分区

三个角色各自持有一段上下文，可见范围有三种设计：

```
shared 全量共享            partitioned 分区              summary 摘要
┌─────────────────┐       ┌─────────────────┐         ┌─────────────────┐
│ A: 1,2,3,4,5…   │       │ A: 只看自己 1,3 │         │ A: 摘要+最近 2 条 │
│ B: 1,2,3,4,5…   │       │ B: 只看自己 2,4 │         │ B: 摘要+最近 2 条 │
│ C: 1,2,3,4,5…   │       │ C: 只看自己 +   │         │ C: 摘要+最近 2 条 │
│                 │       │   最近一条他人 │         │                 │
└─────────────────┘       └─────────────────┘         └─────────────────┘
 一致性高、输入二次方      一致性低、输入线性降          折中，输入基本恒定
```

三种选择各自的代价：

- **共享全量历史**：任何角色都能引用所有人的发言，一致性最好。代价是每个角色都要把全部历史重读一遍，输入随轮次二次方增长；而且后面的人看得到前面的人怎么说的，容易附和（sycophancy）——第 9 轮之后的发言质量明显下降。
- **分区历史**：每个角色只带自己的发言，成本最低。代价是角色之间互相看不见，架构师不知道测试工程师已经提过幂等键，结论会打架。
- **摘要（黑板，blackboard）**：共享一份滚动摘要加最近两条原文。中间方案：一致性够用，输入基本恒定。代价是摘要会丢信息，而且需要一个真的会压缩的摘要器——这一环最容易做成"截断"，一旦变成粗暴截断，就等于分区历史。

### 2.5 成本核算：token 放大系数

设 B 为基础提示长度（角色提示 + 任务 + 格式约定），s 为平均每次发言长度，T 为发言总次数：

```
共享全量：总输入 ≈ T·B + s·T(T−1)/2      ← 二次方
分区：    总输入 ≈ T·B + s·T(T−1)/(2N)    ← N 是参与者数
摘要：    总输入 ≈ T·(B + 摘要长度)         ← 恒定
```

放大系数（amplification factor）A 定义为：总花费 ÷ 内容下界，其中内容下界 = 产出同样内容的输出 token + 一次基础提示。A=1 表示每个 token 都花在了内容上，没有任何重复。

下面是配套脚本的实测（3 个角色、60 次发言、同一套发言内容，mock 模式）：

| 方案 | 总 token | 内容下界 | 放大系数 A |
| --- | --- | --- | --- |
| 3 人 · 共享全量历史 | 170,049 | 4,736 | 35.9× |
| 3 人 · 分区历史 | 78,910 | 4,736 | 16.7× |
| 3 人 · 共享摘要 | 45,660 | 4,736 | 9.6× |
| 单 Agent 顺序扮演（摘要上下文） | 42,138 | 4,736 | 8.9× |

两行值得反复看：**共享全量比共享摘要贵 3.7 倍；一个人带摘要比三个人共享全量历史省 4 倍。** 也就是说，在对话式协作里，贵的不是参与者数量，是共享了多少历史。

再补两笔账：自动选人让 12 次发言花了 23 次调用，调用数翻倍；轮次是唯一能二次方放大成本的旋钮——所以轮次上限是最重要的成本闸门，不是 token 预算。

## 三、为什么这样设计：取舍与失效条件

对话式协作有它明确的适用边界。先说什么时候**不该**用它：

1. **流程是固定的。** 需求评审有固定阶段、每阶段产出固定文档，那就该用流水线（第 22 章）。对话的灵活性在这里是浪费。
2. **要的产物是结构化数据。** 对话产出的是散文，最后一定要有一道确定性的加工把它变成表、代码或 JSON——这道加工存在，就说明大部分工作不需要开会。
3. **角色之间其实不需要交流。** 各查各的数据库、各写各的模块，直接并行更省（第 23 章）。
4. **任务一次性、低价值。** 为一次几十块的活开一场几十块的会，是纯亏。
5. **需要精确复现。** 对话有随机性，同一 case 跑两次结论不同，就没法做回归测试。

再说对话式协作特有的几个失效模式：

- **塌缩（collapse）**：共享全量历史下，后面的角色开始重复并附和前面的角色，表现为发言越来越短、越来越像。征兆是连续几轮出现高度雷同的内容——这跟第 11 章的"观察不变"是同一个检测思路。
- **乒乓（ping-pong）**：A 问 B，B 又问 A，没人推进也没有终止词。必须由代码侧的轮次上限兜底。
- **仲裁失控**：自动选人时，模型可能反复挑同一个角色，也可能挑不出人来。选人要有兜底顺序，不能只有一个出口。
- **打断滥用**：任何角色都能打断，抢话会取代讨论。打断应当是稀缺资源：限制连续打断次数。
- **角色污染（persona contamination）**：角色越极端，输出的事实性越差。角色提示要约束的是取舍方式，不是立场强度。
- **协议漏标**：模型一定会漏掉终止标记。终止判定必须有三层兜底。

最后一条经验，来自那次失败：**如果你的角色之间没有真实的分歧点，角色扮演就是给同一个答案套三个名字，还多花了三倍 token。** 判断标准很简单——你能不能说出"A 一定会反对 B 的哪一点"。说不出，就别开会。

### 4.1 关键实现片段

角色提示的拼装，四段固定：

```python
def inception_prompt(role, others, task, format_spec):
    counterpart = "、".join("%s（%s）" % (r.name, r.persona) for r in others) or "无"
    return (
        "你正在参与一场多角色讨论。\n\n"
        "【任务】%s\n\n"
        "【你的角色】你是%s。%s。你的风格：%s。你的目标：%s。\n\n"
        "【对话对象】%s\n\n"
        "【输出格式】%s\n\n"
        "【讨论规则】\n"
        "1. 只输出你自己的一段发言，不要替对方说话；\n"
        "2. 不要重复别人已经说过的内容，要接着往下推进；\n"
        "3. 与你有分歧时直接说出来，不要附和；\n"
        "4. 严格使用上面的输出格式标记。"
        % (task, role.name, role.persona, role.style, role.goal, counterpart, format_spec)
    )
```

可见历史的三种渲染方式，是控制成本的主要开关：

```python
def _render_history(self, role_name):
    if self.history_mode == "shared":          # 全员共享全量历史
        return "\n".join("[%d] %s：%s" % (i + 1, m.speaker, m.content)
                         for i, m in enumerate(self.messages))
    if self.history_mode == "partitioned":     # 各自只看自己的 + 最近一条他人发言
        own = [m for m in self.messages if m.speaker == role_name]
        others = [m for m in self.messages if m.speaker != role_name]
        lines = ["[我说的] %s：%s" % (m.speaker, m.content) for m in own]
        if others:
            lines.append("[最近一条他人发言] %s：%s" % (others[-1].speaker, others[-1].content))
        return "\n".join(lines)
    # summary：共享滚动摘要 + 最近两条原文
    lines = ["[会议摘要] %s" % self._rollup()]
    lines += ["[最近] %s：%s" % (m.speaker, m.content) for m in self.messages[-2:]]
    return "\n".join(lines)
```

三个提醒：

**mock 与真实的差别在数字，不在结构。** 脚本的 token 是估算值，真实模型以服务端 `usage` 为准；但"共享全量历史是二次方增长"这个结构在任何模型上都成立。

**摘要器是最容易糊弄的一环。** 脚本里的 `_rollup()` 是截断近似。真上生产要用模型做压缩，并给它一条硬规则：**结论必须进摘要，讨论过程可以丢。**

## 五、开源实现对照

- **AutoGen**（MIT，代码部分为 LICENSE-CODE，仓库根目录 LICENSE 为 CC-BY-4.0，https://github.com/microsoft/autogen）：GroupChat 与 GroupChatManager 是"消息表 + 说话人选择"这套骨架最标准的实现。老接口的 `speaker_selection_method`、终止条件与轮数上限（`max_round`）都是框架级配置，新版 AgentChat 把它们拆进 RoundRobinGroupChat、SelectorGroupChat、Swarm 等组队类，轮数上限参数叫 `max_turns`。
- **CAMEL**（Apache-2.0，https://github.com/camel-ai/camel）：inception prompt 范式的出处，值得读它怎么把角色扮演拆成可复用的提示结构，以及两方设定里怎么控制轮次与成本。
- **ChatDev**（Apache-2.0，https://github.com/OpenBMB/ChatDev）：把软件公司搬进对话。它用"CEO、CTO、程序员、测试"这类强角色分工，但阶段之间靠标准文档交接而不是聊天记录——这是它比纯对话省钱的根本原因（见第 22 章）。
- **AgentVerse**（Apache-2.0，https://github.com/OpenBMB/AgentVerse）：把"解法生成—执行—评估"做成对话式流程，适合对照讨论与执行的边界怎么划。
- **MetaGPT**（MIT，https://github.com/geekan/MetaGPT）：SOP 式流水线与角色协作的对比样本，用标准化的中间产物替代聊天记录。
- **CrewAI**（MIT，https://github.com/crewAIInc/crewAI）：角色—任务—流程的另一种抽象，流程默认串行，对照着看"角色多"与"要开会"并不是一回事。
- **OpenAI Agents SDK**（MIT，https://github.com/openai/openai-agents-python）：交接（handoff）语义是"把控制权交出去"，而不是"大家一起讨论"，正适合和 GroupChat 做对照。
- **AgentScope**（Apache-2.0，https://github.com/agentscope-ai/agentscope）：多 Agent 对话流程配可视化调试与追踪，塌缩和乒乓这类问题在 trace 里比在日志里好查。
- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：把对话轮次显式写成状态图与检查点，控制流是代码而不是提示词，适合需要可恢复的长对话（见第 23 章）。

许可证之外的具体 API 与版本，请以官方仓库为准。

## 六、坑与检查清单

开对话式协作之前，逐条打勾：

- [ ] 我先跑通了单 Agent 版本，再决定要不要"开会"。
- [ ] 每个角色的 inception prompt 里有任务、角色、对话对象、输出格式四段。
- [ ] 角色设定写了"这个角色反对什么"，不只是"要什么"。
- [ ] 发言格式用结构化标记，不靠自然语言约定。
- [ ] 终止条件有三层：协议终止词、轮次上限、预算上限。
- [ ] 终止词由模型产出，终止判定写在代码里。
- [ ] 轮次上限按"发言次数"算，不是按"轮"算——一轮可能有多次发言。
- [ ] 自动选人的仲裁调用单独记账，没有混进发言成本。
- [ ] 我实测过共享全量 / 分区 / 摘要三种策略的 token 差异。
- [ ] 默认的上下文策略不是共享全量历史。
- [ ] 摘要器有长度上限，且明确要求"结论进摘要、过程可丢"。
- [ ] 打断有最高优先级，同时限制了连续打断次数。
- [ ] 我检查过角色之间是否存在真实分歧点。
- [ ] 对话产物到最终交付物之间还有一道确定性加工（抽取、校验、落库）。
- [ ] 我在 trace 里看过有没有塌缩（连续几轮高度雷同）与乒乓（两个角色来回问答）。

## 七、小结与延伸阅读

对话式协作的三个机制要分开设计：谁发言是调度问题，轮转最便宜、自动最贵、代码规则最可控；说什么是角色提示问题，inception prompt 的四段结构里最有用的是"你反对什么"；什么时候停是协议问题，模型产出的终止词只能当候选信号，真正的终止要靠轮次上限和预算上限兜底。

成本上最反直觉的一条是：**贵的不是参与者数量，是共享了多少历史。** 三个角色共享全量历史，放大系数 35.9×；同样三个角色共享摘要，降到 9.6×；一个人带摘要顺序扮演，是 8.9×。共享全量历史最贵，也最容易塌缩——多花的钱和多听的话，最后都变成了附和。
