# 第 23 章 协作拓扑与调度：Supervisor、层级、网状、辩论与黑板

## 一、本章要解决的问题

同一组四个角色——检索员、分析员、撰写员、审核员——我们用五种接法跑同一个任务，总花费从 809 token 到 2,977 token，差了 3.7 倍。

更麻烦的不是钱，是失败。注入一次故障（分析员调用失败）之后：

- 一种接法里，调度层当场抓住、重试一次、然后中止，任务返回"部分结果"；
- 一种接法里，故障被吞掉，其余角色照常跑完，流程以**成功**收尾，而结论里少了一块——没人知道少了什么；
- 还有一种，任务确实没完成，但系统自己知道，因为有一张表在检查"该有的字段是不是都齐了"。

于是结论很直接：**拓扑不是实现细节，它是决定成本、上下文范围和失败语义的设计决策。** 换拓扑就是换语义，不是换个写法。

## 二、原理：机制拆解

### 2.1 拓扑坐标系

一个协作拓扑由三件事决定：谁跟谁通信、谁决定下一步、谁能看到什么。五种主流拓扑摆在一起是这样：

```
【Supervisor 集中调度】
        S
     派单│
    ┌───┼───┐
   W1  W2  W3        中心决定下一步；执行者只拿到中心压缩后的一段
    └───┴───┘
      汇总↑

【层级 Hierarchical】
        R                根管组，组管人
     派单│
   ┌────┴────┐
  G1         G2        G1 只看得到本组产出
 ┌┴┐       ┌┴┐
 W1 W2     W3 W4

【网状 Mesh】                【辩论 Debate】            【黑板 Blackboard】
   W1 ←→ W2                    正方 ⇄ 反方                  ┌────────┐
    ↕     ↕                      ↘  ↙                       │ facts  │
   W3 ←→ W4                       裁判                      │ issues │
                                                           │ draft  │
  没有中心，信息靠转发            交叉反驳后裁决             │ checked│
                                                           └────────┘
                                                             ↑ ↑ ↑ ↑
                                                           W1 W2 W3 W4
```

配上共享范围与失败语义，坐标系才完整：

| 拓扑 | 控制流 | 共享范围 | 失败语义 |
| --- | --- | --- | --- |
| Supervisor | 中心决定下一步 | 中心看全部，执行者看一小段 | 中心或执行者失败都被拦截，返回部分结果 |
| 层级 | 根 → 组 → 人 | 组内可见，组间只见结论 | 组调度器拦截，失败止于本组 |
| 网状 | 消息直达 | 只看寄给自己的消息 | 无人拦截，失败被吞，流程可能假成功 |
| 辩论 | 正反论证 + 裁决 | 辩手看对方，裁判看全部 | 缺方时仍会裁决，依据不完整 |
| 黑板 | 轮流入场读写 | 所有人看整块板 | 缺栏能被完备性检查发现 |

### 2.2 Supervisor：集中调度与去中心化

Supervisor 模式的核心不是"有个中心节点"，而是**中心持有全局视图，并且负责把上下文压缩后下发**。执行者拿到的是中心写的一段交接，而不是一堆原始材料。

这带来两个具体收益。一是上下文可控：中心看到全部（约 600 token 的他人内容），执行者每人只看到一小段。二是失败有拦截点：中心知道每个执行者的状态，失败时能重试、能换人、能中止。

集中调度的代价也实在：中心是瓶颈（所有派单都要过它）、中心是单点（中心挂了整链停）、中心本身要花调用（实测 9 次调用里有 5 次是中心在派单）。

它真正的对立面不是"分布式"，而是**去中心化网状**：Agent 之间直接投递消息，没有谁持有全局视图。网状的好处是没有单点、天然并行；坏处是信息靠转发扩散——一条消息能不能传到对的人手里，取决于拓扑的连接方式，而不是取决于谁需要它。更要紧的是，网状没有拦截点，某个节点挂了，流程照样往下走。

所以集中与去中心化的真正差别是两句话：**谁有全局视图**，以及**失败在哪里被看见。**

### 2.3 层级：深度与扇出如何决定成本

层级把调度树展开：根调度器管组调度器，组调度器管执行者。完全展开时，最坏情况的调用数是个等比数列：

```
calls(d, f) = 1 + f + f² + ... + f^d
```

| 深度 d | 扇出 f=2 | 扇出 f=3 |
| --- | --- | --- |
| 1 | 3 次 | 4 次 |
| 2 | 7 次 | 13 次 |
| 3 | 15 次 | 40 次 |

同样 9 个叶子任务：扁平结构（1 个调度器 + 9 个执行者）10 次调用；两层（1 + 3 组 + 9 执行者）13 次；三层（1 + 3 + 9 + 27）40 次。

**深度每加一层，调用数按扇出倍数放大。** 实测的两层层级比扁平多花 29% 的 token，换来的是上下文隔离：资料组的中间产物，成稿组看不到。

这笔交易划不划算，要看你买到了什么。层级真正买到的是三样东西：组内的局部自治（组调度器能自己决定先做谁）、组间的上下文隔离（省 token）、以及局部失败不扩散到全链。买不到其中任何一样，就别加这一层——那只是在放大调度开销。

### 2.4 辩论与黑板：什么时候真的有用

**辩论（debate）** 的成立条件很窄：结论需要被挑错，而且存在真实的对立解释。判据是那句"你能不能说出一个会改变结论的反方论点"。说不出，辩论就是两个人对着空气各说各的，token 花两倍，结论不变。

辩论适合的是方案取舍、原因归因、风险评估这类"没有 ground truth、但有多个合理解释"的问题；不适合查一个数、做一件有确定答案的事。实测辩论用了 5 次调用、1,380 token，其中 499 token 是"他人内容"——交叉反驳让输入翻倍，这是它的固有成本。

还要防一件事：裁判退化成橡皮章。双方说得再有道理，裁判每轮都判"正方胜"，这个辩论就白设了。至少要抽查裁决理由是否真的针对了反方论点。

**黑板（blackboard）** 换了个思路：Agent 不互相说话，都去读写同一块共享工作区。它成立的条件是**工作区有明确的完成判据**——比如"事实、问题、结论草稿、审核结论"四个字段都齐了才算完成。

实测黑板用 4 次调用、971 token，比 Supervisor 少一半多。但它有一个致命前提：**必须有完备性检查。** 一个角色挂了，黑板上就缺一栏，如果没人检查缺栏，流程会拿着残缺的黑板宣布成功。黑板拓扑的价值一半在共享空间，一半在这张检查表。

另外，黑板必须定 schema。字段名固定、每个字段有明确的写入者与格式要求，否则几个人往同一块板上写，最后谁也说不清哪句话是谁的。

### 2.5 失败传播：拓扑决定的语义

把分析员打挂，五种拓扑的反应完全不同（实测）：

| 拓扑 | 失败传播路径 | 系统是否察觉 |
| --- | --- | --- |
| Supervisor | 调度层捕获 → 重试 1 次 → 中止，已产出部分保留 | 察觉，返回部分结果 |
| 层级 | 组调度器捕获 → 本组中止 → 整链中止 | 察觉，返回部分结果 |
| 网状 | 失败被吞 → 其余节点照常跑 → 结论缺一块 | **不察觉，流程标记为成功** |
| 辩论 | 一方缺阵时裁判仍会裁决 | 察觉不到，依据不完整 |
| 黑板 | 缺栏 → 完备性检查不通过 → 达到轮次上限 | 察觉，返回部分结果 |

**网状那一行最该记住。** 一个失败的节点，被吞掉之后流程以成功收尾，交付物少了一块内容，监控上看不出任何异常。这不是实现 bug，这是去中心化拓扑的语义：你用"没有单点"换来的代价，就是"没有拦截点"。

所以选去中心化之前要先回答一个问题：某个环节挂了怎么办？要么你自己补一张完备性检查表，要么明确接受静默降级。两者都不选，就是把一个失败藏进生产环境。

## 三、为什么这样设计：取舍与失效条件

选拓扑看三个维度：任务可分解度、对抗性需求、可验证性。

| 任务特征 | 可分解度 | 对抗性 | 可验证性 | 推荐拓扑 |
| --- | --- | --- | --- | --- |
| 流水线式产出（文档/代码） | 高 | 低 | 高 | Supervisor 或层级 |
| 独立子任务（各查各的库） | 高 | 低 | 低 | 扁平并行，不必多 Agent |
| 方案需要被挑错 | 中 | 高 | 低 | 辩论 |
| 多角色共享一份工作区 | 中 | 低 | 高 | 黑板 |
| 无中心可自治推进 | 低 | 中 | 低 | 网状 |
| 全流程固定且要审计 | 高 | 低 | 高 | SOP 流水线（第 22 章） |

三个维度的用法：可分解度低，说明任务本身需要全局视角，别拆；对抗性高，才值得上辩论，没有对立解释时辩论纯属浪费；可验证性低（结果难以客观判定对错）时，多 Agent 的收益最可疑——因为你既验不了，也观测不了。

各拓扑的失效条件：

- **Supervisor**：中心提示写得不好会陷入派单循环；中心上下文被撑爆后决策质量下降；中心本身是单点，挂了要有人接管——这是特性不是缺陷，但要有预案。
- **层级**：深度超过三层，隔离收益盖不住调用倍数；扇出太大时，一次中心决策要在太多候选里挑，错误率上升。
- **网状**：信息靠转发扩散，关键信息传不到对的人手里；没有拦截点；真实系统里还要处理重复消息与环路。
- **辩论**：没有真实分歧就是空转；裁判橡皮章化；裁判上下文要装下双方全部论证，辩手一多就撑不住。
- **黑板**：没有 schema 就无法判定谁写坏了一条；没有完备性检查就会假成功；并发写同一栏会互相覆盖。

最后一条反直觉的经验：**同一组 Agent，换个拓扑成本差 3.7 倍，失败语义完全不同。** 所以拓扑应该在写代码之前画出来，而不是等代码写完再"顺便"决定谁给谁发消息。

## 四、动手：最小可实现

代码在 `code/ch23-topology/`，纯标准库、无需 API Key。

**依赖**：Python 3.9+，零第三方包。

**运行**：

```bash
cd code/ch23-topology
python main.py                    # 四段演示
python main.py --fail 撰写员      # 换一个角色注入失败
python main.py --fail ""          # 关掉注入，只看健康基线
python main.py --live             # 切真实模型
```

一次跑清四件事：五种拓扑在同一任务上的调用数与 token 差异、上下文共享范围、失效注入下的五种失败传播路径、以及层级深度与扇出的成本模型。

典型输出（节选）：

```
拓扑                   调用    输入token   总token    他人内容    结果
Supervisor（集中调度） 9       1946        2305       601         成功
层级（Hierarchical）   13      2509        2977       721         成功
网状（Mesh，去中心化） 4       621         809        160         成功
辩论（Debate）         5       1046        1380       499         成功
黑板（Blackboard）     4       783         971        301         成功

[网状（Mesh，去中心化）] 成功
    失败角色：分析员
    传播路径：失败被吞 → 其余节点照常跑 → 结论缺一块，无人察觉
```

### 4.1 关键实现片段

五种拓扑共用一个骨架：调用、计量、失败注入都收敛到一处，所以对比才公平。

```python
class Topology:
    def __init__(self, llm, fail_agent="", max_retry=1):
        self.llm = llm
        self.fail_agent = fail_agent
        self.max_retry = max_retry

    def _call(self, role, foreign, instruction=""):
        """返回 (产出, 其中他人内容的 token 数)。失败按 AgentFailure 抛出。"""
        if self.fail_agent == role:
            raise AgentFailure("%s 调用失败（注入）" % role)
        user = "任务：%s\n素材：%s" % (TASK, BRIEF)
        if foreign:
            user += "\n\n他处传来的内容：\n%s" % foreign
        text = self.llm.chat(role, instruction, user)
        return text, approx_tokens(foreign)
```

调度节点与执行节点的差别，就是"输出的是下一个人的名字，还是最终产物"：

```python
# 调度节点：看全部已有产出，输出下一个该谁做
raw, f_tokens = self._call("监督者", "\n".join(accumulated),
                            '输出 JSON：{"next": "<角色名>", "handoff": "<交接>", "done": false}；'
                            '全部做完后输出 {"done": true, "final": "<结论>"}。')
payload = json.loads(raw)
if payload.get("done"):
    break
out, f_tokens = self._call(payload["next"], payload["handoff"])
```

黑板的完备性检查，是这个拓扑唯一不能省的东西：

```python
REQUIRED = ["facts", "issues", "draft", "checked"]
missing = [k for k in REQUIRED if k not in board]
if missing:
    res.ok = False
    res.failure_path = "黑板缺栏 %s → 未凑齐" % "、".join(missing)
```

两个提醒：

**"他人内容"这一列比总 token 更值得看。** 总 token 受产出长度影响很大，"他人内容"直接反映了共享范围：实测网状 160、黑板 301、Supervisor 601。同一个任务，五种拓扑下 Agent 看到的彼此信息量从 160 到 601，差了近四倍。

**失败注入要能开关。** `--fail ""` 是健康基线，`--fail 分析员` 是故障演练，两者对照着看，才知道某个拓扑的"成功"是真的成功还是侥幸成功。

## 五、开源实现对照

- **AutoGen**（MIT，代码部分为 LICENSE-CODE，仓库根目录 LICENSE 为 CC-BY-4.0，https://github.com/microsoft/autogen）：GroupChatManager 就是 Supervisor 角色的教科书实现——它持有会话状态、挑选下一个发言者，是最值得对照的中心节点样板。更有意思的是老接口的 `allowed_or_disallowed_speaker_transitions`：限定"谁说完之后允许谁接话"，同一个群聊就能被约束成层级化或扁平化的拓扑。
- **LangGraph**（MIT，https://github.com/langchain-ai/langgraph）：把拓扑表达成显式状态图。节点是角色，边是交接，条件边就是路由规则。拓扑在这里是代码而不是约定，适合需要回放、断点续跑与人工介入的流程（见第 29 章）。
- **CrewAI**（MIT，https://github.com/crewAIInc/crewAI）：流程（Process）只有 sequential 与 hierarchical 两个取值，默认 sequential；层级模式内部还有委派与委派上下文，是"层级拓扑"最简明的对照物。
- **Microsoft Agent Framework**（MIT，https://github.com/microsoft/agent-framework）：融合 AutoGen 与 Semantic Kernel，把工作流编排与部署统一起来，适合看拓扑怎么变成配置。
- **AgentScope**（Apache-2.0，https://github.com/agentscope-ai/agentscope）：多 Agent 协作框架配 Studio 可视化调试与追踪，拓扑的"实际跑成什么样"在可视化里一眼能看出来。
- **CAMEL**（Apache-2.0，https://github.com/camel-ai/camel）：角色扮演范式的出处，辩论拓扑的思想原型——让两个角色分别持一个立场再互相质证。
- **Google ADK**（Apache-2.0，https://github.com/google/adk-python）：给多 Agent 提供了顺序、并行、循环等拓扑预设，最适合用来对照"预置拓扑"和"自己写拓扑"两种做法。
- **AG2**（Apache-2.0，https://github.com/ag2ai/ag2）：AutoGen 的社区分支，GroupChat 与嵌套对话等实验性拓扑可以在这里对照着看。
- **OpenAI Swarm**（MIT，https://github.com/openai/swarm）：用交接（handoff）把控制权从一个 Agent 交给另一个，是网状拓扑的轻量版——没有中心，但路由规则仍然写在代码里。

许可证之外的具体 API 与版本，请以官方仓库为准。

## 六、坑与检查清单

选拓扑之前，逐条打勾：

- [ ] 我在写代码之前画了控制流图。
- [ ] 我说得出这个拓扑的失败传播路径。
- [ ] 我知道每个 Agent 能看见什么（共享范围）。
- [ ] 深度不超过 3，扇出不超过 4。
- [ ] 层级带来的隔离收益我能量化，说得出省了多少 token、挡了什么错。
- [ ] 黑板有 schema，也有完备性检查表。
- [ ] 辩论的双方有真实分歧，裁判不是橡皮章。
- [ ] 我明确接受或修补了去中心化拓扑"失败被吞"的后果。
- [ ] 调度节点有调用上限，不会无限派单。
- [ ] 汇总节点能给出"结论 + 已知缺口"，而不是只给结论。
- [ ] 我验证过失败路径，不只验证过 happy path。
- [ ] 我测过同一任务在不同拓扑下的 token 差，选型有数据支撑。
- [ ] 任务本身可分解度低时，我没有硬拆。

## 七、小结与延伸阅读

拓扑是三件事的组合：谁跟谁通信、谁决定下一步、谁能看到什么。五种主流拓扑的差别，集中起来就是"全局视图在谁手上"和"失败在哪里被看见"。

Supervisor 用调用换可控，实测 9 次调用换来明确的失败拦截；层级用深度换隔离，深度每加一层调用数按扇出倍数放大（9 个叶子：10 → 13 → 40）；网状用单点风险换自治，代价是失败会被吞、流程可能假成功；辩论用双倍输入换挑错，前提是存在真实对立解释；黑板用共享空间换低成本，前提是字段有 schema、完成有判据。

最实用的一条：**别拿总 token 选拓扑，拿"他人内容 token"和"失败路径"选。** 前者告诉你 Agent 们彼此看见了什么，后者告诉你出事的时候谁会喊停。这两个指标算清楚了，拓扑自然就定了。
