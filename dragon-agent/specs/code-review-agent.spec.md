# 代码审查 Agent 规格说明

> 规格版本：v1.2 ｜ 状态：已评审 ｜ 负责人：后端平台组 ｜ 最后更新：2026-11-08
>
> 本文件是 `dragon-agent` 工程里 `reviewer` 这个 Agent 的需求规格。
> 配套检查器：`python specs/check_spec.py specs/code-review-agent.spec.md`

## 任务定义

- 服务对象：后端仓库的 code owner 与提交变更的开发者。
- 要解决的问题：人工审查一次改动平均要花 40 分钟，其中约三分之一的时间花在
  "把改动逐个文件读一遍、对着规则清单核对"这类可重复的机械劳动上。
  本 Agent 负责读改动、套规则、产出结构化审查意见；**判断"这个意见提不提"由模型做，
  "这个意见对不对"由确定性检查器做**。
- 触发方式：CI 流水线在 PR 打开时触发，或开发者在命令行传入一个 diff 文件路径。
- 完成的定义（业务层面）：产出一份结构化审查意见，其中每条 high 级别发现都带
  文件路径与行号，行号落在本次改动的行范围内；同时明确列出**没有**被审查到的文件。

## 输入输出契约

输入：

```json
{
  "target": {"kind": "diff_path", "value": "changes.patch"},
  "rules": "backend",
  "focus": ["sql", "auth"]
}
```

- `target.kind`：只接受 `diff_path` 或 `pr_ref` 两种取值。
- `target.value`：diff 文件路径，或 PR 编号加仓库标识。
- `rules`：规则包名称，取值必须在白名单内；白名单外直接判失败，不允许模型猜。
- `focus`：可选关键词列表，用于让模型优先审查某些主题；为空表示不偏好。

输出：

```json
{
  "summary": "一句话结论",
  "findings": [
    {
      "id": "F1",
      "severity": "high",
      "file": "src/app.py",
      "line": 42,
      "rule": "SEC-001",
      "message": "问题描述",
      "suggestion": "修改建议"
    }
  ],
  "unreviewed": [],
  "status": "completed"
}
```

字段约束：

- `severity`：只允许 `high`、`medium`、`low` 三个取值。
- `file`：必须是本次改动里真实存在的文件路径。
- `line`：正整数，且必须落在该文件的改动行集合内；无法定位行号时填 `null`，不允许编造。
- `unreviewed`：没有审查到的文件列表。**即使一条发现都没有，这个字段也必须存在且为空数组**，
  不能省略——"我什么都没查"和"我没查完"是两种不同的失败，调用方要能区分。
- `status`：取值必须与 `AgentResult.status` 一致，见"失败定义与退出状态"。

## 可用工具清单

| 工具名 | 作用 | 关键参数 | 副作用 | 失败时行为 |
| --- | --- | --- | --- | --- |
| `list_changed_files` | 列出本次改动的文件与改动行区间 | `diff_path` | 只读 | 返回错误文本，模型自行判断是否换目标 |
| `read_file_slice` | 读文件指定行区间 | `path`、`start`、`end` | 只读 | 越界或不存在时返回错误文本 |
| `load_rule_pack` | 加载审查规则包 | `name` | 只读 | 名称不在白名单时直接失败，不回退到默认规则 |
| `search_in_repo` | 在仓库内按关键词检索 | `pattern`、`path` | 只读 | 无命中返回空列表 |
| `post_review_comment` | 把审查意见发布到 PR 评论 | `body`、`pr_ref` | 不可逆写 | 未获人工确认时被护栏拦截并返回确认请求 |

`post_review_comment` 是唯一的写操作，且**不可逆**：评论一旦发到 PR 就撤不回来，
只会再发一条补充说明。因此它必须带幂等键，且在人工确认前不得执行。

## 决策边界

| 步骤 | 决策方 | 说明 |
| --- | --- | --- |
| 决定优先审查哪些文件 | LLM | 按改动行数与规则命中度排序 |
| 判断一条规则命中是否值得报告 | LLM | 需要语义判断，误报和漏报都在这里产生 |
| 写每条发现的描述与修改建议 | LLM | 这是 Agent 的主要产出 |
| 校验文件路径是否在仓库工作区内 | 代码 | 越权路径直接拒绝，不交给模型判断 |
| 限制单文件读取行数与总读取量 | 代码 | 防止上下文被一个大文件打爆 |
| 校验规则包名称在白名单内 | 代码 | 白名单外的名称直接失败并回灌错误 |
| 校验每条发现的行号是否落在改动行集合内 | 代码 | 落不在就丢掉这条发现，不让模型"差不多"蒙混过关 |
| 执行 `post_review_comment` | 代码 | 模型只负责准备正文，真正调用必须由代码在人工确认后发起 |

## 成功判据

- **C1**：每条 `severity` 为 `high` 的发现都带 `file` 与 `line`，且 `line` 落在该文件的改动行集合内
  - 验证方式：评测任务集断言每条 high 发现的 `line` 命中 diff 改动行集合
- **C2**：不存在指向未改动行的发现（误报约束）
  - 验证方式：任务集断言全部 `findings[].line` 均命中改动行集合
- **C3**：输出同时包含 `summary` 与 `unreviewed`，无发现时 `findings` 为空数组而不是缺失
  - 验证方式：对输出做 JSON Schema 校验，断言 `findings`、`unreviewed` 两个键必存在
- **C4**：未经人工确认不得调用 `post_review_comment`
  - 验证方式：护栏测试断言该工具调用被拦截，返回 `require_confirm` 且工具未真正执行
- **C5**：单次任务步数不超过 12、单次成本不超过 0.5 美元
  - 验证方式：断言 `AgentResult.total_cost` 不超上限、步数索引不超过 `max_steps`
- **C6**：规则包缺失时以 `error` 状态退出，并在 `summary` 里说明缺了哪个规则包，不得凭印象编规则
  - 验证方式：构造缺失规则包的任务，断言 `status` 为 `error` 且 `summary` 含规则包名称
- **C7**：改动超过 50 个文件时必须在 `unreviewed` 里列出未审查文件，不得只报已看的那部分
  - 验证方式：构造超大 diff 任务，断言 `unreviewed` 非空

## 失败定义与退出状态

| 退出状态 | 触发条件 | 调用方动作 |
| --- | --- | --- |
| `completed` | 走完流程并产出 `findings` 与 `unreviewed` | 把意见交给人工确认 |
| `stopped_budget` | token 预算或成本预算到顶 | 提示人工放宽预算或缩小审查范围 |
| `stopped_no_progress` | 连续多步观察内容没有变化 | 记录断点并转人工 |
| `max_steps` | 达到 12 步上限 | 保留已产生的部分发现，缺失部分进 `unreviewed` |
| `error` | 规则包缺失、仓库不可读、输入参数非法 | 原样报错，最多重试 1 次后转人工 |

## 明确不做的事

- 不修改任何代码、不提交 commit、不建分支、不改 CI 配置。
- 不决定 PR 是否合并，也不给"通过"或"不通过"的结论——审查意见是给人看的，不是裁决。
- 不执行依赖安装、构建与测试，因此不联网；构建类问题不在本 Agent 的覆盖范围内。
- 不做安全渗透测试，不验证漏洞是否可利用，只按规则报告可疑模式。
- 不把源码片段发到仓库之外的任何服务。
- 不在人工确认前发布任何评论：`post_review_comment` 只在确认后由代码发起。
- 不审查非本次改动引入的问题，历史遗留问题一律不报。

## 评测与观测

- 任务集：20 个历史 PR，其中 5 个是"没有任何问题的干净 PR"，用来测误报。
  按难度分三层：单文件小改、多文件关联改动、跨模块影响。
- 指标：任务成功率、工具错误率、无进展率、每次成功成本。
  这四个指标与 `observability.py` 里 `Tracer.sli()` 的字段一一对应。
- 判定方式：确定性断言优先——JSON Schema 校验 + 关键字匹配 + 改动行集合比对，
  **不使用 LLM 判定**，保证离线可跑、结果可复现。
- 基线：与人工审查对比的是"漏报率"而不是"总时长"：人工审查本来就会漏，
  Agent 的价值必须体现在"机器看过的部分比人多"，而不是"比人快"。
  上线前的人工基线：20 个 PR 的人工平均耗时与人工标出的问题集合。
