# 第 13 章 评测与回归：让改动有依据

## 一、本章要解决的问题

周三下午，你改了一句工具的描述——把 `read_budget` 的 description 从"读取预算表"改成"读取指定财年的预算表，返回各科目金额与总额"。改动只有一句话。

上线前你手测了三个问题，都对。周五上午，用户投诉说"预算总额变成了 50 万"。

问题来了：**你怎么知道是这一句话导致的？** 你手上没有任何东西能回答它。上周你改过上下文装配策略，上上周你动过预算工具的取数字段，两周前换过一次模型提示词。这四类改动都可能在同一个位置留下痕迹，但没有任何一条记录能把它们分开。

更糟的是第二件事：**你不知道还有多少用例坏了**。你手测的三个问题覆盖了"能读对数字"，但没覆盖"拒绝把转账金额改成负数"，没覆盖"输出必须是 JSON 才能下单"，也没覆盖"不知道的时候要说我不知道"。这三件事里，说不定有两件已经在上周那次改动里坏了，只是没人跑过。

于是评测要解决的就是这两件事：

1. **改动前后能比**——不是比一个总分，是比**哪几条用例从通过变成了不通过**；
2. **没跑到的地方要看得见**——任务集要有覆盖矩阵，缺口要显式暴露，而不是靠"我觉得测过了"。

而这一切必须在**不调模型**的前提下成立：评测要能离线跑、能进 CI、能当基线存下来。判据一旦依赖模型采样，同一条用例两次判定就可能不同，基线也就失去了意义。

## 二、原理：机制拆解

### 2.1 任务集：覆盖矩阵 × 难度分层

任务集不是一列 prompt，是一张**矩阵**。两条轴：

- **能力维度**（标签）：这条用例考察什么——`lookup`（查得准不准）、`format`（格式对不对）、`tool_use`（工具调对没）、`refusal`（该拒的拒没）；
- **难度分层**：`easy`（单步、无歧义）、`medium`（多步或需要一点推理）、`hard`（对抗性、有陷阱）。

矩阵的价值在于**缺口是可见的**。代码里 `coverage_gaps()` 把没被任何用例覆盖的格子列出来：

```python
def coverage_gaps(cases: list[EvalCase], tags: list[str], difficulties: list[str]) -> list[str]:
    """覆盖矩阵里的空格——"标签 × 难度"没被覆盖到的组合。"""
    return coverage_report(cases, (tags, difficulties)).gaps
```

这个函数在 `examples/evaluation_demo.py` 里跑出来的结果是 `覆盖缺口：无`——矩阵里 `lookup` 与 `format` 两行、`easy/medium/hard` 三列全部有货。假设哪次你漏写了 `format/easy` 这一格，缺口会直接写成 `format/easy` 出现在输出里。**"我没测到"从一句自觉变成了一个可以进断言的字符串。**

那么**最小规模**是多少？按矩阵算，2 个维度 × 3 档难度 = 6 格，每格至少 1 条，就是 **6 条起步**。但"起步"不等于"够用"——6 条只是让矩阵不空。真正的下限取决于你要拦的是什么：

- **只想拦住"改坏了"**：每个维度 2~3 条就够，重点放在**该维度最典型的失败方式**上（查不准、格式错、该拒没拒）；
- **想拦住"改偏了"**：每格至少 3 条，因为一条用例只能对应一种失败方式；
- **想拿通过率做趋势**：至少 20 条。低于这个数，百分比就是噪声——第 2.4 节讲过噪声地板是怎么算的。

本章的示例用了 **7 条**：2 个维度 × 3 档难度 = 6 格，其中 `format/hard` 有 2 条（拒答和幻觉各一条）。7 条够演示所有机制，但**不足以当趋势基线**——示例里 `budget-total` 和 `budget-breakdown` 都栽在同一类错误（金额算错），说明这两条用例的失败模式其实是重合的，真要拦"改坏了"，它们得拆开。

难度分层的意义不是好看。它决定**抽样回归怎么抽**：`sample_cases()` 按难度轮流取，用例少的时候不至于把难例全丢掉：

```python
def sample_cases(cases: list[EvalCase], k: int, seed: int = 0) -> list[EvalCase]:
    """分层抽样：按难度轮流取，保持难度配比。

    抽样必须**可复现**：同一个 seed 选出来的必须是同一批用例。
    所以这里不用 ``random``，而是用 ``seed + 用例 id`` 的哈希排序——
    跨进程、跨机器、跨 Python 版本都一致。
    """
```

注意它不用 `random.Random`——那个在不同 Python 版本、不同平台上给出的序列未必一致。这里用 `seed + 用例 id` 的 SHA-256 排序：**同一个 seed 必须选出同一批用例**，否则 CI 每次跑的是不同题目，回归根本无从谈起。

### 2.2 黄金答案与可接受答案

一条用例要写两样东西：**黄金答案**和**可接受答案**。

黄金答案是"必须逐字出现的事实"。比如问上季度预算，黄金答案是 `"90万"`。可接受答案是"同一件事的别的合法说法"——`"九十万"` 也是对的。如果只允许逐字匹配，一条本来正确的用例会因为模型说了"九十万"而被判失败，然后你会花半小时去调一个根本没坏的用例。

所以 `EvalCase` 把这两者分开：`expect` 是黄金答案的硬事实，`accept` 是同义表述的分组，每组命中任意一个即通过：

```python
    #: 可接受答案：每组是一组同义表述，命中任意一个即视为该组通过。
    accept: list[list[str]] = field(default_factory=list)
```

判定时的规则是：`expect` 每条都得在，`forbid` 每条都不能在，`accept` 每组命中一个就算过。`forbid` 同样重要——"我不知道"这条用例，期望答案里要有"不知道"，同时禁止出现"3000万"，防的是模型编一个数出来。

### 2.3 判定器：三种类型，三种偏差

判定器决定"什么算对"。它有三种类型，各自的偏差完全不同：

| 类型 | 判什么 | 偏差在哪 | 能不能进 CI |
| --- | --- | --- | --- |
| **确定性断言** | 关键字、正则是否出现 | 判据写得不对就整片误判；改判据等于改基线 | 能，结论可复现 |
| **结构化校验** | 答案是不是合法 JSON、字段类型对不对 | 只管形状不管内容；形状对了内容可能是错的 | 能 |
| **LLM 判定** | 语义上"答得好不好" | 位置偏好、长度偏好、自偏好；同一答案两次判可能不同 | **默认不能** |

**确定性断言**是主力。`AssertionJudge` 的判定过程全是子串和正则匹配，同一输入永远同一结论：

```python
    def judge(self, case: EvalCase, answer: str) -> CheckResult:
        checks = (
            list(case.expect)
            + list(case.expect_pattern)
            + list(case.forbid)
            + list(case.forbid_pattern)
            + [g for g in case.accept if g]
        )
        if not checks:
            return CheckResult(passed=False, reason="用例没有任何断言", applied=False)
```

注意最后那句 `applied=False`：**一条没有断言的用例不会被默认判过**。判定器"不适用"和"通过"是两回事——这个区分在 `Evaluator._judge()` 里靠 `applied` 标志传递。如果不给这个标志，一条写空的用例会静悄悄地算通过，然后某天你发现基线通过率 100% 是因为其中三条用例根本没判。

**结构化校验**管的是"输出格式是契约的一部分"的场景。下单要 JSON，那答案就必须是 JSON，字段和类型都不能错：

```python
    def judge(self, case: EvalCase, answer: str) -> CheckResult:
        schema = case.json_schema
        if schema is None:
            return CheckResult(True, "用例没有结构要求", applied=False)

        payload = extract_json(answer or "")
        if payload is None:
            return CheckResult(False, "答案里找不到合法 JSON")
```

它比 LLM 裁判便宜一个数量级，而且不飘。注意 `extract_json()` 有三条路径：整段解析 → ```` ```json ```` 代码块 → 文本里抠出第一段 `{...}`。模型很少只输出裸 JSON，抠不出来就判失败。

**LLM 判定**在本工程里是个**显式 opt-in** 的适配器，不是默认路径。判官函数由调用方注入，模块本身不 import 任何模型客户端：

```python
class LLMJudge:
    """用模型当裁判——**必须显式注入判官函数**，且默认不参与门禁。

    为什么不放在默认判定器里：模型裁判有采样偏差、位置偏差、长度偏好，
    同一个答案两次判可能不同。它的结论适合"参考"，不适合"卡流水线"。

    用了它产出的报告会带 ``nondeterministic=True``，CI 门禁默认拒绝这种报告
    （除非显式 ``require_deterministic=False``）。
    """
```

关键在最后一句：**用了模型裁判的报告会被打上 `nondeterministic` 标记，而 CI 门禁默认拒绝这种报告**。这就是"确定性断言优先"这条纪律的落地方式——不是写在文档里劝你别用，而是代码层面让它用不了：你想用，得同时改两处配置，并且这个决定会留在报告里，谁都能看见。

### 2.4 基线对比：噪声地板与逐条翻转

有了基线报告和当前报告，怎么比？

先说一个容易踩的坑：**小任务集上的通过率百分比不稳定**。7 条用例的集合，1 条用例就占 14.3 个百分点。改动前后通过率从 100% 掉到 57.1%，看着是暴跌，但如果这轮跑的时候模型采样本来就有波动，你分不清是改动导致的还是采样导致的。

所以 `diff_reports()` 同时给出两样东西：百分比差，和**噪声地板**（一条用例的权重）：

```python
    baseline_rate = baseline.pass_rate
    current_rate = current.pass_rate
    delta = current_rate - baseline_rate
    floor = (1.0 / current.total) if current.total else 0.0

    significant = bool(newly_failing) or abs(delta) > floor
```

`significant` 的判据是"**有具体用例翻转了，或者百分比变化超过了噪声地板**"。注意这是"或"：一条用例翻转，哪怕百分比只动了 1%，也是信号——因为确定性断言下用例不会自己飘，它翻转了就是行为真的变了。反过来，百分比动了但没到噪声地板、也没有用例翻转，那就只是波动。

真正稳定的信号永远是**逐条**：哪几条从通过变成了不通过。`compare_reports()` 的产出就是这个：

```python
def compare_reports(current: EvalReport, baseline: EvalReport) -> EvalReport:
    """把当前报告和基线报告合并：填上 ``regression_vs_baseline``。

    回归 = **基线里通过、现在不通过**的用例。注意只有两边都跑过的用例
    才算回归；新加的用例（基线里没有）不算回归，它只是新增覆盖。
    """
```

最后那句限定很要紧：**新加的用例不算回归**。你今天加了三条新用例，其中一条没通过——那不是回归，是你昨天没测到它。把新增当成回归，会让人对评测集失去信任，然后就不敢加用例了。

### 2.5 CI 门禁与失败样本归档

门禁的判据按"稳定性"排序，从硬到软：

```python
def gate(current: EvalReport, baseline: EvalReport | None = None,
         config: GateConfig | None = None) -> GateResult:
    """判断这一轮能不能放行。

    门禁的判据按"稳定性"排序：

    1. **新增回归条数**——最硬的信号，一条就是一条；
    2. **不可复现的报告**——含模型裁判的报告默认不放行；
    3. **通过率下限**——粗粒度的兜底；
    4. **成本增量**——防止"跑得更久更贵也算改进"。
    """
```

新增回归条数排第一，是因为它是唯一"一条就是一条"的判据。通过率下限排第三，是因为它是粗粒度兜底——用例少的时候它几乎给不出额外信息。成本增量排最后但不能没有：不然"多绕三圈把答案说全了"会被算成改进。

失败样本自动归档是门禁的**后半程**。CI 红了的时候，最值钱的东西不是"红"这个事实，而是**到底哪里坏了**。`archive_failures()` 把每条失败用例落成一个 JSON 文件：

```python
def archive_failures(report: EvalReport, cases: list[EvalCase], out_dir: str | Path) -> list[Path]:
    """把失败样本归档成 JSON 文件，一条用例一个文件。

    失败的样本是**最值钱的产物**——它告诉你这次改动到底哪里坏了。
    自动归档的意义是：CI 红了的时候，样本已经在产物目录里躺着了，
    不用再手动去捞、去复现。
    """
```

每个文件里记了用例 id、失败原因、完整用例定义，以及**它是不是一条回归**。注意归档的输入是 `merged`（合并了基线对比的）报告，不是裸的当前报告——否则归档出来的文件会丢失"这是回归"这个标记，而那恰恰是最该被看见的信息。

### 2.6 CI 的三层节奏

评测跑一次要花钱、要时间，塞进每一次提交是不现实的。合理的做法是**分层**，让快的东西拦快的门：

| 层级 | 跑什么 | 跑多快 | 拦什么 |
| --- | --- | --- | --- |
| **提交级** | 纯断言自检：任务集格式合法、覆盖矩阵无缺口、判定器自身的行为 | 秒级，不调模型 | 提交烂掉的用例、判据写错 |
| **发版前** | 分层抽样回归：按难度抽 N 条，和基线比 | 分钟级 | **新增回归** |
| **nightly** | 全量任务集 + 真实模型 | 小时级 | 长尾退化、模型抖动 |

三层用的是**同一套任务集、同一套判据**，区别只在跑多少条。抽样那一层用 `sample_cases(cases, k, seed)`——`seed` 固定，所以每次抽的是同一批题；`k` 可以调，任务集大了以后可以把提交级也带上抽样。

这个分层的价值在于**失败信号和排查成本匹配**：提交级失败，一分钟就能看出是不是用例写坏了；nightly 失败，说明有东西在漫长的过程中漂了——那通常是模型侧或者数据侧的事，不是你这次改动的事。**把这两类失败混在一个门禁里，你会花半天去查一个昨天就存在的问题。**

## 三、为什么这样设计：取舍与失效条件

评测很贵：写用例要时间，跑一遍要钱，尤其是接了真实模型之后。这一节讲清楚**什么时候不该做这些**。

### 3.1 什么时候不该建评测集

- **原型阶段（还没想清楚要什么）**：评测集是"你要做成什么样"的具象化。功能每天都在变的时候，写评测集是在给一个还在移动的目标画靶子。**先把功能跑通，接口稳定了再补评测**。
- **一次性脚本**：如果这件事只跑一次，写评测集是浪费——直接跑，看结果，比划不划算。
- **失败成本极低的场景**：模型答错一次，大不了用户重问一次。为这种场景建一套 CI 门禁，投入产出比很差。

### 3.2 什么时候不该用 LLM 判定

**能用确定性断言的，绝不用 LLM 判定。**这条纪律的失效条件是：

- **答案本质上没有可断言的关键词**：开放式写作、创意生成、"这个方案好不好"。这类任务的语义质量确实只能靠人或者模型判断。但注意代价——**这类任务不适合当 CI 门禁**，只适合做发版前的抽样人工评审。
- **但即使是开放任务，也应该先试结构化校验**：把"要点 JSON"变成硬要求之后，格式问题就退化成确定性断言了，只剩下内容质量需要人看。

一个具体的**反例**：有人拿 LLM 判定当 CI 门禁，理由是"我们的任务就是开放问答"。结果是流水线每天随机红一次，两周后大家开始无脑点重跑——门禁一旦被习惯性绕过，就等于没有。**不可复现的门禁比没有门禁更糟**，因为它训练团队忽略红灯。

### 3.3 什么时候不该信通过率

- **任务集只有几条用例的时候**：7 条用例的通过率，粒度是 14%。这时候该看的是逐条结果，不是百分比。**低于 20 条的任务集，通过率只能当参考。**
- **两次跑的不是同一批用例时**：比如这次抽了 5 条、上次跑了 20 条，百分比之间没有可比性。`diff_reports()` 里 `added` / `removed` 两个字段就是暴露这件事的。
- **基线本身是脏的时候**：基线如果是某次手忙脚乱时存下来的，通过率再高也没有参考价值。基线要在**已知是好状态**的时刻存。

### 3.4 什么时候不该加门禁

- **改动还在剧烈迭代期**：每天改十几次的时候，门禁的噪声会淹没信号。**先把判据调稳，再挂门禁。**
- **用例里混进了模型裁判**：门禁拒绝不可复现的报告是设计意图，不是 bug。别绕过它——要么换确定性判据，要么让这一层不进 CI。

### 3.5 这套东西的失效条件

最后说清楚边界。本章的实现有几处**明确的局限**：

- **判据写得对不对，评测答不了**。`expect=["100万"]` 前提是你的黄金答案本身是对的。判据错了，评测会忠实地报告"全绿"，而实际行为是错的。**评测集也需要被评测**——上线后拿真实失败案例反查判据，是维护评测集的主要工作。
- **任务集永远追不上真实分布**。用户问的问题永远比你写的用例野。评测集防的是**已知的坏**，不是未知的坏。
- **纯离线判定测不出真实模型的抖动**。mock 模式下本模块的 75 条单元测试全过，只说明控制流没坏；换成真实模型，采样波动会带出新的失败模式。**离线评测是 CI 的第一道闸，不是最后一道。**
- **没有防过拟合**。任务集一旦被用来调提示词，它就变成了训练集，不再是测试集。留一份不参与调优的隐藏集，是有必要的。

## 四、动手：最小可实现

本章的代码在 `dragon_agent/evaluation.py`，纯标准库，不需要 API Key 就能跑通完整回路。

**一条用例怎么写**——判据、黄金答案、可接受答案、元信息分四组：

```python
@dataclass
class EvalCase:
    """一条评测用例。

    字段分三组：

    - **判据**（``expect`` / ``forbid`` / ``expect_pattern`` / ``forbid_pattern`` /
      ``json_schema``）：答案必须满足什么。
    - **可接受答案**（``accept``）：同一事实的多种合法表述，每组命中任一即通过。
      黄金答案是 ``expect`` 里的字面事实，可接受答案是它的同义改写集合。
    - **元信息**（``difficulty`` / ``tags`` / ``answer``）：用来做覆盖矩阵与
      分层抽样；``answer`` 只在**自检模式**下使用（没有 runner 时拿它当被测答案）。

    ``expect`` 与 ``forbid`` 是契约里定死的两个字段，其余都是可选扩展。
    """
```

**评测器怎么构造**——`Evaluator(config)` 或 `Evaluator(config, runner)`。不注入 runner 走**自检模式**（拿用例自带的 `answer` 当被测答案，适合写纯断言的单测）；注入 runner 就是真的跑一遍被测对象：

```python
    def __init__(self, config: Any = None, runner: Any = None,
                 judges: list[Any] | None = None) -> None:
        self.config = config
        self.runner = runner
        self.judges: list[Any] = list(judges) if judges is not None else [
            AssertionJudge(),
            StructuredJudge(),
        ]
        self._last_report: EvalReport | None = None
```

默认判定器只有两个，**都是确定性的**。要加模型裁判就显式传 `judges=[...]`，代价是报告带上不可复现标记、门禁默认拦下。

**跑一轮**——`run()` 不抛异常，一条用例炸了只算这条失败：

```python
    def run(self, cases: list[EvalCase]) -> EvalReport:
        """跑一轮评测。**不抛异常**：单条用例出错只算这条失败。"""
        report = EvalReport()
        for case in cases:
            try:
                answer, tokens, cost = self._answer_for(case)
            except Exception as exc:
                report.case_results[case.id] = False
                report.details[case.id] = f"取答案时异常：{type(exc).__name__}: {exc}"
                report.failures.append(case.id)
                continue
```

**判一条**——所有适用的判定器依次判，没有一个适用就算失败：

```python
    def _judge(self, case: EvalCase, answer: str) -> tuple[bool, str, bool]:
        """让所有适用的判定器依次判定。

        返回 ``(是否通过, 原因, 是否用过模型裁判)``。没有判定器适用时判失败——
        一条没有断言的用例不该算通过。
        """
```

**比基线**——`compare()` 返回的报告里 `regression_vs_baseline` 就是那条用例 id 列表：

```python
    def compare(self, baseline: EvalReport) -> EvalReport:
        """把最近一次结果和基线比，返回带 ``regression_vs_baseline`` 的报告。"""
        current = self._last_report
        if current is None:
            current = EvalReport()
        return compare_reports(current, baseline)
```

**完整回路**在 `examples/evaluation_demo.py`。它用 `MockLLM` 当被测模型，`BEFORE` 与 `AFTER` 两套剧本分别代表改动前后——改动让预算金额被除以二、把"不知道"换成了编造的数：

```python
#: 改动后的剧本：改了"预算"这个词的解读方式，金额被除以二，
#: "不知道"被替换成了编造的数——两条用例因此从通过变成不通过。
AFTER: dict[str, list[LLMResponse]] = {
    "budget-total": [_say("2026 年预算总额是 50万。")],
```

跑完你会看到七段输出：覆盖矩阵、基线、当前、和基线比、CI 门禁、失败样本归档、自检。实测结果是基线 7/7 通过，改动后 4/7 通过，**3 条用例被判为新增回归**，门禁拦下，失败样本落成三个 JSON 文件。

## 五、开源实现对照

自建的这套东西不是凭空发明的，它对应几个成熟开源项目里的不同侧面。

| 项目 | 许可证 | 定位 | 与本章的关系 |
| --- | --- | --- | --- |
| [promptfoo](https://github.com/promptfoo/promptfoo) | MIT | 面向提示词与链路的声明式评测框架 | 它的"断言 + 多模型对比"思路对应本章的判定器与基线对比 |
| [OpenAI Evals](https://github.com/openai/evals) | MIT | 以"注册评测 + 跑模型"为核心的评测框架 | 它的评测注册表思路对应本章的任务集组织方式 |
| [DeepEval](https://github.com/confident-ai/deepeval) | Apache-2.0 | 面向 LLM 输出的测试框架，指标与断言较全 | 它的指标体系比本章广，但同样强调断言式判定 |
| [Inspect AI](https://github.com/UKGovernmentBEIS/inspect_ai) | MIT | 面向大模型安全评测的框架 | 它的"solver + scorer + 策略"分层与本章的 runner / judge 分层同构 |
| [pytest](https://github.com/pytest-dev/pytest) | MIT | Python 测试框架，插件生态庞大 | 断言式测试与参数化的习惯可以直接迁移到评测集上 |
| [Ragas](https://github.com/vibrantlabsai/ragas) | Apache-2.0 | 面向 RAG 的评测指标集 | 提醒一件事：**指标口径必须先定义死**，否则不同人算出来的数不可比 |

再往上一层是**公开基准**——它们测的是"能力"而不是"你的系统"：

- [SWE-bench](https://github.com/SWE-bench/SWE-bench)（MIT）：真实 GitHub issue 的修复成功率；
- [tau-bench](https://github.com/sierra-research/tau-bench)（MIT）：模拟用户与领域规则下的多轮任务。

**公开基准不能替代自建任务集**，原因很实在：它们的题目、工具、数据全都不是你的系统遇到的东西。它们能告诉你"这个模型大概什么水平"，但不能告诉你"你这次改动是不是变坏了"。**前者是选型依据，后者是回归依据——两件事。**

本章的实现和这些框架的差别，主要在**依赖**：本章的 `evaluation.py` 纯标准库，不装任何第三方包，判定不调模型，报告能直接存成 JSON 当基线。它不是功能更全的替代品，而是**一个能被完整读懂、能按自己的判据改、能离线进 CI 的最小内核**。真要上规模，评估框架的开销是值得付的。

## 六、坑与检查清单

开跑之前，逐条对一遍：

- [ ] **每条用例都有断言**——没有断言的用例不算通过，本实现会判它失败；别靠"我觉得它对"过关。
- [ ] **黄金答案写的是关键事实，不是全文**——`expect` 里放"100万"这种事实，不要放整段标准答案。
- [ ] **给每条容易换个说法的用例配 `accept` 组**——否则你会花时间调没坏的用例。
- [ ] **`forbid` 要写上最怕出现的东西**——尤其是"我不知道"这类用例，要禁止模型编数字。
- [ ] **覆盖矩阵每格都有货**——跑 `coverage_gaps()`，有缺口就补用例，别指望"下次再说"。
- [ ] **难度标签认真填**——`sample_cases()` 靠它保配比，全填 `easy` 等于没分层。
- [ ] **基线在已知是好状态时存**——脏基线比没基线更糟。
- [ ] **基线和当前跑的是同一批用例**——否则百分比不可比；先看 `added` / `removed`。
- [ ] **门禁卡"新增回归条数"，不是"通过率百分比"**——任务集小于 20 条时百分比是噪声。
- [ ] **失败样本自动归档**——CI 红了的时候，样本得已经在产物目录里躺着。
- [ ] **不用模型裁判当 CI 门禁**——不可复现的门禁会被习惯性绕过，比没有门禁更糟。
- [ ] **留一份不参与调优的隐藏集**——任务集一旦被用来调提示词，它就不是测试集了。
- [ ] **把评测集当代码管**——版本化、有单测、有人负责。评测失效最常见的原因不是没人跑，是跑不动了。

## 七、小结与延伸阅读

评测与回归解决的是一个很朴素的问题：**凭什么说这次改动是变好了，而不是变坏了？**

答案分三层。**任务集**给出覆盖面——覆盖矩阵让"我没测到"变成一个可断言的字符串，黄金答案与可接受答案让判据既严格又不苛刻。**判定器**给出确定性——能用正则和状态断言的绝不用模型裁判，模型裁判只做参考，且用它的报告会被门禁拒绝。**基线与门禁**给出可比性——逐条翻转是硬信号，百分比是小样本上的噪声，CI 卡的是"新增回归几条"，失败样本自动归档成产物。

最该记住的一条纪律：**评测集本身也是需要被评测的资产**。判据写错的时候，评测会忠实地报告全绿。所以上线后拿真实失败案例反查判据，是维护评测集的主要工作——不是一次性把用例写完就完事。
