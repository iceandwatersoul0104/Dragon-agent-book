# 第 13 章 · 评测与回归：让改动有依据

本卷第十三章解决的是一个很朴素的问题：**凭什么说这次改动是变好了，而不是变坏了？**

答案是三层：**任务集**给出覆盖面（覆盖矩阵让缺口可见，黄金答案 + 可接受答案让判据既严格又不苛刻），**判定器**给出确定性（能用正则和状态断言的绝不用模型裁判），**基线与门禁**给出可比性（逐条翻转是硬信号，百分比是小样本上的噪声，CI 卡"新增回归几条"，失败样本自动归档）。

- 正文：[`evaluation.md`](evaluation.md)
- 配套工程产物：`dragon-agent/` 下的三个文件（见下）

## 本章给了什么

1. **`dragon_agent/evaluation.py`（847 行）**——任务集、判定器、基线对比、CI 门禁，纯标准库：
   - **任务集**：`EvalCase` 把判据（`expect` / `forbid` / 正则 / JSON schema）、可接受答案（`accept` 同义表述组）、元信息（`difficulty` / `tags`）分成三组；`coverage_report()` / `coverage_gaps()` 算「标签 × 难度」覆盖矩阵，缺口是**可断言的字符串**；
   - **三种判定器**：`AssertionJudge`（子串 + 正则，默认）、`StructuredJudge`（JSON + schema）、`LLMJudge`（**必须显式注入判官函数**，默认不参与门禁，用它的报告会被打上 `nondeterministic` 标记并被 CI 拒绝）；
   - **自检模式 vs 真实模式**：`Evaluator(config)` 拿用例自带的 `answer` 当被测答案（纯断言单测）；`Evaluator(config, runner)` 真的跑一遍被测对象；
   - **基线对比**：`diff_reports()` 给出逐条翻转 + **噪声地板**（一条用例在通过率里的权重），`significant` 的判据是「有具体用例翻转了，**或**百分比变化超过噪声地板」；
   - **CI 门禁**：`gate()` 按稳定性排序四条判据——新增回归条数 → 不可复现报告 → 通过率下限 → 成本增量；
   - **失败样本归档**：`archive_failures()` 一条用例一个 JSON，带「是不是回归」的标记；`sample_cases()` 分层抽样，同 seed 必选同一批题。
2. **`examples/evaluation_demo.py`（283 行）**——`MockLLM` 当被测模型，`BEFORE` / `AFTER` 两套剧本代表改动前后，七段输出：覆盖矩阵 → 基线 → 当前 → 和基线比 → CI 门禁 → 失败样本归档 → 自检。
3. **`tests/test_evaluation.py`（681 行）**——75 条契约断言，全部离线。

**本章没有改动 `dragon_agent/` 下的其它任何模块**——判定器不调模型，评测层对被测对象只依赖「能不能交回一个答案」这一个接口。

## 核心约定

> **判定器不用 LLM**：本模块不 import 任何模型客户端，判定只用规则与关键字，保证确定性与可离线运行。
> **能用确定性断言的，绝不用 LLM 判定**：模型裁判是**显式 opt-in** 的适配器，用它的报告会被标记为 `nondeterministic`，CI 门禁默认拒绝——这是代码层面的强制，不是文档里的劝告。
> **回归以逐条为准**：门禁卡的是「新增回归几条」，不是「通过率掉了百分之几」——小任务集上 1 条用例就等于好几个百分点。
> **新加的用例不算回归**：它只是新增覆盖。

## 怎么跑

```powershell
cd dragon-agent

# 1) 演示：MockLLM 跑完整回路，退出码 0
python examples/evaluation_demo.py

# 2) 本章的契约测试：75 个用例
python -m unittest tests.test_evaluation

# 3) 全量测试：确认没有打破其它模块
python -m unittest discover
```

不需要 API Key，不联网，不装任何第三方包，也不写用户目录。中文输出在 GBK 控制台上可能显示为乱码，加 `python -X utf8` 即可。

演示里的关键输出：

- 覆盖矩阵 `lookup` / `format` 两行 × `easy/medium/hard` 三列，**覆盖缺口：无**；
- 基线（改动前）**7/7 通过**，通过率 100.0%；
- 当前（改动后）**4/7 通过**，通过率 57.1%，失败 `budget-total` / `budget-breakdown` / `no-hallucination`；
- 通过率变化 **-42.9%**，噪声地板 **14.3%**（1 条用例的权重），**新增回归 3 条**；
- CI 门禁**拦下**：`新增回归 3 条，超过允许的 0 条`；
- 失败样本落成三个 JSON，每个都带 `回归=True`。

## 局限（这一章不等于可以上线）

这一章交付的是**评测闭环的最小内核**，不是一套完备的评测平台。上线前，下面每一条都要自己补：

- **判据的正确性没人能替你保证**。`expect=["100万"]` 前提是黄金答案本身是对的；判据错了，评测会忠实地报告「全绿」而实际行为是错的。**评测集本身也需要被评测**——拿线上真实失败案例反查判据，是维护评测集的主要工作。
- **没有防过拟合机制**。任务集一旦被用来调提示词，它就变成了训练集。留一份不参与调优的隐藏集，得自己安排。
- **纯离线判定测不出真实模型的抖动**。mock 模式下全绿只说明控制流没坏；换成真实模型，采样波动会带出新的失败模式。**离线评测是 CI 的第一道闸，不是最后一道。**
- **没有分布漂移检测**。任务集覆盖的是你写下来的场景，用户实际问的问题永远更野。评测集防的是**已知的坏**，不是未知的坏。
- **没有并发与超时控制**。评测层是顺序跑的，用例多了会线性变慢；接了真实模型之后，一条卡住的用例会拖住整轮。`run()` 保证不抛异常，但不保证不卡。
- **门禁只有阈值，没有豁免机制**。已知失败（比如某个依赖暂时不可用）没有「临时放行」的通道，硬扛着改判据会污染基线。
- **LLM 判定是适配器，不是实现**。`LLMJudge` 只提供调用与标记，判官函数由调用方注入，偏差、位置偏好、长度偏好一样都不会少——它只是让「用了模型裁判」这件事**在报告里看得见**，不是让它变准。
