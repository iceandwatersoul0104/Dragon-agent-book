# 第 7 章 状态与检查点：让任务可回放、可恢复

## 一、本章要解决的问题

一个 Agent 任务跑了 9 步，在第 9 步挂了。值班的人面对的是这样一个现场：

- **日志**里有模型的调用记录，但没有模型的**完整响应**——工具调用的参数被截断了；
- **内存**里的状态全在进程里，进程一重启，什么都不剩；
- 想复现？做不到，因为模型输出本身不可复现（温度、供应商侧变化、并发）；
- 想从第 5 步接着跑？也做不到，只能从头再来，前 8 步的 3 美元白花了；
- 最糟的是：任务里有一个扣款动作，挂在扣款之后。重启重试，**扣款被执行了第二次**。

四条问题，前三条是"看不见"，第四条是"看不见的代价"。

根子是一样的：Agent 的状态是**隐式**的——散在主循环的局部变量里、模型客户端的缓存里、工具注册表的字典里。代码跑着的时候它们都在，一停就全没了。

这一章要把状态显式化，变成两样东西：**能存下来的快照**（现在是什么）和**能重跑的日志**（怎么变成这样的）。

## 二、原理：机制拆解

### 2.1 三类状态：进状态、只在内存、必须落盘

不是所有东西都该进状态。分错类的代价是：状态膨胀、序列化变慢、恢复时一堆用不上的东西被塞回去。

| 东西 | 放哪 | 为什么 |
| --- | --- | --- |
| 任务状态、每一步的记录 | 进 `TaskState` | 恢复后要接着用 |
| 对话历史 | 不进状态，是主循环的局部列表 | `TaskState` 没有 history 字段；能恢复的是 steps 里的 thought/observation，恢复后得靠它重建 history |
| 已执行动作登记 | 单独一个对象，自己落盘 | 它是独立类，不进 `TaskState`；恢复后要防止副作用重演 |
| 模型客户端 | 只在内存 | 重连一个就行，没必要序列化 |
| 工具注册表的幂等缓存 | 只在内存 | 跨进程靠"已执行动作登记"，不靠它 |
| 上下文装配器 | 只在内存 | 它是纯函数，没有状态 |

关键一条：**工具注册表自己的幂等键缓存是进程内的**。第 4 章那个"幂等键用过就拒绝重复执行"的保护，在进程存活时有效，进程一崩就失效。跨进程的保护得另做一份——这就是"已执行动作登记"（第 2.5 节）。

### 2.2 检查点时机：每步、每工具、每消息

检查点不是免费的：每写一次就要版本号加一、状态深拷贝一次。

| 时机 | 成本 | 适用 |
| --- | --- | --- |
| 每条消息 | 最便宜，但**最没用**——每一步本来就有几条消息，检查点密度和"每步"没差 | 几乎不用 |
| 每工具调用 | 比每步细一档 | 一步里调多个工具、且工具之间可能崩的场景 |
| **每一步** | 一次深拷贝 | **默认选择** |

本章选每步。理由很实际：Agent 的主循环以"步"为天然单位——第 6 章的每一步都以一个模型响应结束，步与步之间的状态是自洽的。在步内部再切检查点，收益只在"工具执行到一半崩溃"时才出现，而那种场景的恢复粒度通常也不需要更细。

```python
    def checkpoint(self) -> Checkpoint:
        """写一次检查点：版本号 +1，返回可以恢复的快照。

        每一步结束都该调一次——这是"崩溃后从哪儿接着跑"的依据。
        """
        self._state.version += 1
        return Checkpoint(
            task_id=self._state.task_id,
            version=self._state.version,
            snapshot=self._state.to_dict(),
            created_at=time.time(),
        )
```

### 2.3 快照与事件：不是二选一，各管一段

```
        一次运行
           │
     ┌─────┴─────┐
     ▼           ▼
   快照         事件
  "现在是什么"  "怎么变成这样的"
     │           │
     ▼           ▼
  恢复/续跑    回放/复现/审计
```

| | 快照（Snapshot） | 事件（Event） |
| --- | --- | --- |
| 回答的问题 | 现在任务进行到哪一步 | 这一步为什么发生 |
| 形态 | 一份完整状态 | 一串追加的记录 |
| 成本 | 每次一份深拷贝 | 每条一次追加 |
| 适合 | 崩溃恢复、界面展示当前进度 | 复现问题、审计、对比两次运行 |

只有快照没有事件，你知道现在是什么，但**不知道为什么**——上次那步为什么调了这个工具，查不出来。只有事件没有快照，你得从头重放一遍才知道现在是什么。

所以本章两个都做：`StateStore` 同时维护 `TaskState`（快照）和事件列表。

### 2.4 回放：录 → 重放 → 对比

回放是这一章的核心，也是最容易被误解的地方。

**回放不是"再跑一次看看会不会一样"。** 模型输出不可复现，再跑一次必然不一样，那样比的是模型的随机性，比不出任何东西。

回放真正要做的是：**把模型当时的响应录下来，用录下来的响应重跑一遍。** 于是模型这一环被"冻结"了，重跑验证的是**控制流、工具与上下文**这三样是否稳定。

```python
class RecordingLLM:
    """包在模型客户端外面，把每次返回的响应录下来。

    这是回放的**唯一前提**：模型响应不可复现（温度、供应商侧变化、并发），
    所以必须先录。录下来之后，回放才有可能做到"同样的输入 → 同样的结果"。
    """

    def __init__(self, inner: Any) -> None:
        self.inner = inner
        self.responses: list[LLMResponse] = []

    def complete(self, messages: list[dict[str, Any]],
                 tools: list[dict[str, Any]] | None = None,
                 **kwargs: Any) -> LLMResponse:
        response = self.inner.complete(messages, tools=tools, **kwargs)
        self.responses.append(response)
        return response
```

有了录制件，回放就是"用录下来的响应重跑 + 逐步对比"：

```python
def replay(build_agent: Callable[[Any], Any], record: RunRecord,
           build_client: Callable[[list[LLMResponse]], Any]) -> ReplayResult:
    """用录下的响应重跑一遍，并逐步对比。

    回放**不重新调模型**：响应是录下来的，重放的是控制流。
    这正是它能定位问题的原因——结果不一致，只可能是控制流、工具或上下文变了。

    ``build_client`` 接收响应列表，返回一个按剧本返回它们的模型客户端。
    """
```

对比要**逐步**做，指出"第几步的哪个字段不一样"：

```python
def compare_steps(original: list[dict[str, Any]],
                  replayed: list[dict[str, Any]]) -> list[str]:
    """逐步对比两次运行，返回差异描述列表。空列表表示完全一致。"""
```

这个差异列表是回放的**产出物**。它可以进 CI（"回放结果与基线不一致 → 红灯"），也可以进事故报告（"第 1 步的 observation 不同：'total: 1000000' != 'total: 999999'"——一眼看出是工具的行为变了，不是模型变了）。

要说清楚回放**能证明什么、不能证明什么**：

- 能证明：控制流是确定的；工具行为没变；上下文装配没变。
- 不能证明：模型在真实 API 上会给出同样的响应（那是另一个问题，要靠录制真实响应来对比）。

### 2.5 崩溃恢复与副作用去重

恢复有两半：**状态恢复**（`restore`）和**副作用去重**。前者容易，后者才是真问题。

第 4 章的幂等键机制管的是"同一次执行里别重复调"，但它的缓存是进程内的。崩溃重启之后，缓存空了，扣款动作会被执行第二次。

解法是**已执行动作登记**：把"哪些副作用已经发生过、结果是什么"单独记下来，跨进程保存，重启后装回工具层。

```python
class ExecutedActions:
    """已执行动作登记：记住哪些副作用**已经发生过**。

    工具层自己的幂等键缓存是**进程内**的——进程一崩就没了。
    崩溃恢复要跨进程，就要把这份登记落到状态层，重启后再装回工具层。
    """
```

装回去的动作：

```python
def restore_executed_actions(registry: Any, executed: ExecutedActions) -> int:
    """把已执行动作登记装回工具注册表，返回装了几条。

    工具层没有公开的注入接口（``_seen_keys`` 是私有的），这里直接写它。
    这是刻意的取舍：跨进程恢复副作用去重，比等工具层加接口更急——
    装回去之后，``replayable=False`` 的工具见到用过的幂等键会**拒绝执行**，
    可重放的工具会直接返回上次的结果。
    """
```

装回去之后，重启后的进程再碰到同一个幂等键，工具层会按第 4 章的规则拒绝执行——**副作用不会重演**。

注意这里有个刻意的取舍：工具层没有公开的注入接口，这里直接写了它的私有属性 `_seen_keys`。这在工程上不优雅，但比"等工具层加接口再恢复"更实际。代价是：如果工具层改了内部结构，这段会失效——所以它必须有测试守着。

## 三、为什么这样设计：取舍与失效条件

### 3.1 什么时候**不需要**检查点与回放

- **任务只有一两步。** 崩了就重跑，成本可以忽略。
- **纯离线、纯玩具、只给自己看。** 没有"线上事故"要复现。
- **完全确定的工作流。** 没有模型参与，重跑结果本来就一样，回放验证不了任何东西。
- **没有副作用。** 崩了重跑最坏就是多花点钱，不需要副作用去重。

但只要任务**会跑很久、会改外部世界、或者出过事故需要复现**，这三样就都值得做。

### 3.2 状态与回放的四种失效方式

| 失效方式 | 症状 | 后果 |
| --- | --- | --- |
| 状态没进快照 | 恢复后上下文是空的 | 从第 1 步重来 |
| 录了响应但没对比 | 回放"跑过了"就当没事 | 行为变了没人知道 |
| 幂等键没跨进程 | 重启后副作用重演 | 重复扣款 |
| 快照越写越大 | 每步深拷贝整个历史 | 吞吐掉下来 |

第一种靠"状态对象显式化"挡住——状态不是散在局部变量里，而是集中在 `TaskState` 里。第二种是纪律问题，本章用"对比结果必须能列出差异"来兜。

第三种是本章专门加"已执行动作登记"的原因。第四种要注意：**快照是全量深拷贝**，历史长了以后每步一次拷贝会越来越贵。真到了这个规模，要换成增量（只存增量 + 定期全量快照），或者把历史挪到专门的存储里。

### 3.3 一个诚实的边界

本章的回放是**进程内**的：录制件在内存里，落盘靠 `RunRecord.to_dict()` 自己写文件。它没有做跨机器的分布式回放，也没有做多 worker 的协调。

要跨机器，得引入外部存储和一套并发写入协议——那是 Temporal、LangGraph checkpointer 那种东西的活（第五节会对照）。本章做的是**最小可用**：让"同一次运行可以被复现"这件事在一个进程里成立。

**这不等于可以上线。** 真正上线还要处理：快照的存储位置与加密、并发写同一任务的锁、登记表的过期策略（一条动作登记要留多久？）。

### 4.2 状态层的三块

状态对象本身是第 6 章就定好的：

```python
@dataclass
class TaskState:
    """一次任务的当前状态。"""

    task_id: str
    status: str = "running"
    data: dict = field(default_factory=dict)
    steps: list[dict] = field(default_factory=list)
    version: int = 0
```

`snapshot()` 返回**副本**——这是"唯一真相源"能成立的前提：

```python
    def snapshot(self) -> TaskState:
        """当前状态的**副本**。改它不会改到真相源。"""
```

`restore()` 是恢复的另一半：

```python
    def restore(self, cp: Checkpoint) -> TaskState:
        """从检查点恢复状态，返回恢复后的副本。"""
```

### 4.3 录与放

录一次运行：

```python
def record_run(build_agent: Callable[[Any], Any], task: str, llm: Any) -> RunRecord:
    """跑一次任务，把模型的每次响应和每一步都录下来。

    ``build_agent`` 接收一个模型客户端，返回一个 Agent——这样录制和回放
    走的是**同一套装配代码**，对比才有意义。
    """
```

`build_agent` 这个参数是关键：录制和回放走的是同一套装配代码，所以对比出来的差异只可能来自模型响应、工具行为或上下文装配——**不会是"我换了个写法组装"这种噪声**。

### 4.4 实跑

```powershell
cd dragon-agent
python examples/state_replay_demo.py
```

```text
1) 录下来：一次运行的模型响应与每一步
  录到 2 条模型响应，2 个步骤
    第 1 步：read_budget → read_budget: {"year": "2026", "total": 1
    第 2 步：（无动作） →
  最终状态：completed，停止原因：模型给出了最终答案

2) 回放：用录下来的响应重跑一遍
  回放状态：completed
  与原运行一致：True
  差异：（没有差异）

3) 对比：把工具的行为改掉，回放立刻报出差异
  与原运行一致：False
    · 第 1 步的 observation 不同：'read_budget: {"year": "2026", "total": 1000000}' != 'read_budget: {"year": "2026", "total": 999999}'

4) 恢复：崩溃重启后，副作用动作不会被执行第二次
  第一次执行：ok=True  output={'charged': 100}
  登记里有 1 条已执行动作
  重启后装回登记：1 条
  重启后再执行：ok=False  error=charge 不可重放，幂等键 order-42 已用过，拒绝重复执行
  扣款函数实际被调用：0 次（第一次那次是在重启前的进程里）
```

第 3 段是回放真正的用处：**工具行为变了，回放立刻指到第 1 步**。第 4 段是恢复真正的用处：**重启之后扣款函数一次都没被调用**。

### 4.5 测试

回放与恢复的测试要覆盖三件事：录得对不对、重放一致不一致、副作用挡没挡住。

```python
    def test_restored_actions_block_repeated_side_effects(self):
        """崩溃重启后装回登记，不可逆的工具不会被执行第二次。"""
        executed = ExecutedActions()
        first_registry = RecordingRegistry(make_tools(), executed)
        first = first_registry.invoke("charge", {"amount": 100}, idempotency_key="order-42")
        self.assertTrue(first.ok)

        # 模拟进程重启：工具层的进程内缓存没了，登记还在
        restarted = make_tools()
        restored = restore_executed_actions(restarted, executed)
        self.assertEqual(restored, 1)
        second = restarted.invoke("charge", {"amount": 100}, idempotency_key="order-42")
        self.assertFalse(second.ok)
        self.assertIn("不可重放", second.error or "")
        self.assertEqual(restarted.calls["charge"], 0, "扣款函数不该被再执行一次")
```

最后那行断言是关键：不能只断言"返回了错误"，要断言**函数真的没被调用**。否则"拒绝"可能只是返回了一个错误对象而副作用照样发生了。

```powershell

```

## 五、开源实现对照

### LangGraph checkpointer

- 仓库：<https://github.com/langchain-ai/langgraph>
- 许可证：MIT

LangGraph 的检查点机制：把每个超级步（super-step）的状态存下来，支持从任意检查点恢复、时间旅行（拿旧检查点开新分支）。**差异**：它是**服务端持久化**——检查点进数据库，跨进程、跨机器都能用。本章的实现是**进程内**的：快照在内存里，落盘靠调用方自己写文件。差别在规模，不在原理。

### Temporal

- 仓库：<https://github.com/temporalio/temporal>
- 许可证：MIT

持久化执行（Durable Execution）平台：工作流的状态由平台自动持久化，失败后从断点自动重放，开发者不用自己写恢复逻辑。**差异**：Temporal 把"事件溯源"做成了平台级能力——事件日志是它的一等公民，工作流代码本身写成确定性的函数，重放时靠日志重算出同样的结果。本章的思路一致（事件 + 快照），但重放的粒度是"一次模型响应"，而不是"一段工作流代码"。

### SQLite

- 官网：<https://www.sqlite.org/>
- 许可：公有领域（public domain）

嵌入式关系型数据库，一个文件就是一个库。**差异**：本章的状态是**内存里的 Python 对象**，用 `copy.deepcopy` 快照。真要落盘，TaskState 这种带嵌套 dict 和 list 的结构，存进 SQLite 要么序列化成 JSON，要么建表拆字段。SQLite 的价值在于：它是"文件级持久化"这件事最省事的答案——没有服务、没有配置，写文件就是存状态。

### Pydantic

- 仓库：<https://github.com/pydantic/pydantic>
- 许可证：MIT

用类型注解声明数据模型，自动校验与序列化。**差异**：本章的状态对象是手写的 dataclass，没有运行时校验。代价是：`TaskState` 的字段写错了，运行时才发现。Pydantic 能把这类错误提前到构造那一刻——但它要引第三方依赖，本工程的契约是纯标准库。手写 dataclass 加几条断言，是这个约束下的合理折中。

## 六、坑与检查清单

### 状态分类

- [ ] 任务状态、步骤进了 `TaskState`；对话历史没混进去——它是主循环的局部列表，不是状态的一部分
- [ ] 模型客户端、装配器、工具的进程内缓存**没有**进状态
- [ ] 已执行动作登记单独存，因为它要跨进程
- [ ] `snapshot()` 返回副本，不是内部对象

### 检查点

- [ ] 每步结束写一次检查点
- [ ] 检查点带版本号，能判断"这是第几次"
- [ ] 快照是全量深拷贝——历史长了要改增量
- [ ] 恢复后状态版本号、步骤数与检查点一致

### 回放

- [ ] 录的是**模型响应**，不是"重跑模型"
- [ ] 录制与回放走同一套装配代码
- [ ] 对比是**逐步**的，能指出"第几步的哪个字段"
- [ ] 差异列表能进 CI，也能进事故报告
- [ ] 明确知道回放证明不了什么（模型本身的随机性）

### 恢复与副作用

- [ ] 幂等键跨进程有效——靠已执行动作登记，不靠工具层的内存缓存
- [ ] 登记能落盘、能读回
- [ ] 装回登记后，不可逆工具**真的没被再次执行**（断言函数调用次数，不只看返回值）
- [ ] 登记有过期策略（一条登记留多久）

### 常见坑

- [ ] **把状态留在局部变量里**：进程一停，什么都不剩
- [ ] **回放时重新调模型**：比的是随机性，比不出问题
- [ ] **只重放不对比**：行为变了没人知道
- [ ] **只记成功不记失败**：失败的副作用也要登记
- [ ] **快照忘了深拷贝**：调用方改一下就把真相源改了
- [ ] **登记无上限地长**：跑久了内存和磁盘都撑不住

## 七、小结与延伸阅读

这一章把 Agent 的状态从"跑着的时候才有"变成了"随时能拿出来看、能重跑、能接着跑"。要点回顾：

1. **状态要显式，而且要分类。** 进状态的、只在内存的、必须落盘的，三类分开。
2. **检查点每步一次**，版本号 +1，全量深拷贝——历史长了要改增量。
3. **快照与事件各管一段**：快照管"现在是什么"，事件管"怎么变成这样的"，不是二选一。
4. **回放录的是模型响应**，不是重跑模型；对比要逐步，能指出"第几步的哪个字段"。
5. **跨进程的副作用去重靠已执行动作登记**，不靠工具层的内存缓存。

下一章 `p08-memory` 做记忆：什么时候该把一条经验写进长期记忆，写进去的又该带什么来源标记。
