# 第 1 章 立项：把想法变成一份可执行的需求

## 一、本章要解决的问题

需求评审会上，产品经理说："我们要做一个能自动审查代码的 Agent。"

研发问："审查什么级别的代码？" 产品答："所有代码。"

研发又问："那什么算做对了？" 产品答："审查得准。"

会议纪要上就写了这一句。代码写了，提示词调了两周，上线第一周就被同事找上门：这个 Agent 报的问题里有一半是历史遗留的老代码，跟这次改动没关系；另一半它标成"高危"的问题其实根本不严重。

复盘会上大家一致认为"需求没说清楚"。这结论对了一半。真正的问题不是"没说清楚"，而是**说得清楚也没用**——"审查得准"就算写进需求文档也没法验收：没人能指出它什么时候做到了、什么时候没做到。改完提示词之后它变好了还是变差了？没人答得上来。

于是这个需求掉进了工程师最熟悉的陷阱：**它变成了一份永远在改、永远改不完、也没人签字的东西。**

本章要解决的：在写第一行代码之前，把"我想做个 Agent"变成一份**别人拿着能独立实现、而且能判断做没做到**的规格（Specification）。这份规格回答五个问题——为谁解决什么问题、吃什么吐什么、能用哪些工具、哪些步骤交给模型决策哪些必须由确定性代码把持、什么叫成功什么叫失败以及**明确不做什么**。加粗的那半句，是整份规格最省钱的部分。

## 二、原理：机制拆解

### 2.1 规格在整个工程里的位置

第二卷动手的第一件事不是写 `agent.py`，是产出一份规格。规格不是文档，是**流水线的上游工位**——它往下游流的东西，在 `dragon-agent` 里都有对应落点：

```
        想法（一句话）
            │
            ▼
   ┌────────────────────┐
   │  需求规格 spec.md   │   ← 本章的产物
   └────────────────────┘
        │      │      │
        │      │      └──────────────────────────┐
        ▼      ▼                                 ▼
   工具清单  成功判据                        明确不做的事
        │      │                                 │
        ▼      ▼                                 ▼
  tools.py   evaluation.py                  forbid 列表
  ToolSpec   EvalCase.expect/forbid        （越界就拒）
        │      │
        └──────┴──────────────┐
                             ▼
                       agent.py 的主循环
                             │
                    ┌────────┴────────┐
                    ▼                 ▼
             退出状态 status      trace / 成本账
                    │                 │
                    ▼                 ▼
              调用方要做的动作     observability.py
```

这张图的意思是：**规格里的每句话都该在代码里有地方接。** 写不出落点的话，多半是废话。

### 2.2 把"智能"翻译成可观测的成功判据

规格写得软，最常见的表现是成功判据里塞满了形容词。可验收的判据有固定形状：**主体 + 可观测的动作 + 可判定的条件**。翻译不靠语感，靠对照表：

| 软的说法 | 为什么没法验收 | 改成可判定的写法 |
| --- | --- | --- |
| 审查得准 | "准"没有参照物 | 每条 high 级发现都带 `file:line`，且 `line` 落在改动行集合内 |
| 别乱花钱 | 花了多少算乱 | 单次成本不超过 0.5 美元，超出即以 `stopped_budget` 退出 |
| 回答要靠谱 | 靠谱是主观评价 | 答案里每个事实断言都必须能在工具输出里找到来源 |
| 要快 | 慢多少算快 | P95 延迟不超过 30 秒 |
| 别胡编 | 胡编没法列举 | 找不到来源的事实断言数量必须为 0 |

改完之后都能写成一个断言。写不出断言的判据描述的是期待，不是行为。第 13 章会把这些判据接成回归测试（Regression Test）：一条判据一个断言，改完跑一遍就知道有没有变差。

### 2.3 划边界：谁来决定什么

这是整份规格里最影响可靠性的一节。判断依据只有一条：**这件事出错的时候，谁来承担后果。**

- 出错的代价是"再跑一次" → 交给模型决策。
- 出错的代价是"给出错误的结论" → 由确定性代码校验。
- 出错的代价是"不可撤销" → 谁都不能自动执行，必须有人确认。

按这条分界线，一个 Agent 的决策边界（Decision Boundary）通常长这样：

```
   任务描述
      │
      ▼
┌─────────────────────────────────────────────┐
│  LLM 决策区                                  │
│  · 决定先看哪个文件                           │
│  · 判断一个模式命中是否值得报告                │
│  · 写每条发现的描述与建议                      │
│  —— 需要语义判断、无法用规则枚举的部分         │
└─────────────────────────────────────────────┘
      │  产出待校验的中间结果
      ▼
┌─────────────────────────────────────────────┐
│  确定性代码区                                 │
│  · 路径白名单、行数上限、总量上限              │
│  · schema 校验、枚举校验、权限校验             │
│  · 幂等键去重（幂等键，Idempotency Key）       │
│  —— 需要准确、每一步都必须成立的部分           │
└─────────────────────────────────────────────┘
      │  放行
      ▼
┌─────────────────────────────────────────────┐
│  人工确认区                                   │
│  · 不可逆的外部动作（发评论、扣款、发版）       │
│  —— 需要责任的部分，不交给任何自动环节          │
└─────────────────────────────────────────────┘
```

三条经验规则：

1. **只读、可逆、可重试的步骤，多交给模型。** 它们的价值就在"不用为每种情况写分支"。
2. **凡是要写进结论里的数字、ID、路径，必须由代码校验。** 模型说"这个文件第 42 行有问题"，代码要确认第 42 行确实在这次改动里；不在就丢掉这条发现，而不是让模型"差不多蒙混过关"。
3. **把不可逆的写操作从 Agent 的动作空间里拿走，比给 Agent 加十道护栏更有效。** 第一卷第 1 章给过这个结论：护栏是运行时的一道门，动作空间是设计时的一道墙。墙比门结实。

### 2.4 失败也是契约

只定义成功不定义失败的规格等于没定义失败，因为 Agent 一定会失败。

`dragon-agent` 的接口契约里，`AgentResult.status` 已经把失败方式定死了：

| status | 什么时候发生 | 调用方该做什么 |
| --- | --- | --- |
| `completed` | 正常产出结果 | 消费结果 |
| `stopped_budget` | token 预算或成本预算到顶 | 放宽预算，或缩小任务范围 |
| `stopped_no_progress` | 连续多步没有进展 | 保留检查点，转人工 |
| `max_steps` | 步数上限到顶 | 消费已完成的部分，剩下的记为未完成 |
| `error` | 输入非法、依赖缺失、工具异常 | 原样报错，不重试超过一次 |

规格里必须把这五个值**逐个写出来并说明触发条件和调用方动作**。少写一个，调用方遇到那个状态就只能靠猜，而猜错的代价通常比 Agent 出错还大。

### 2.5 明确不做的事

"不做的事"不是免责声明，是**范围管理工具**。它回答的是每次评审都会冒出来的问题：能不能顺便支持 PDF？能不能加个写文档的功能？有清单时，答案不再是"这个不好做"，而是"这在不做清单里，需要重新评估"——前者是技术判断，容易吵；后者是范围判断，有依据。

写"不做的事"有两条讲究：

- 写**现在**不做，和**永远**不做，要分开。"暂不支持 PDF"是"以后要做"，属于待办列表；"不做多模态输入，因为审查场景里没有截图"才是真的边界。
- 每一条要能被检查。本章的检查器会强制：规格里出现的**不可逆写工具**，要么被写进"明确不做的事"，要么在"决策边界"里由确定性代码把持——不受控的不可逆操作是最大的事故来源。

## 三、为什么这样设计：取舍与失效条件

### 3.1 什么时候**不该**写规格

规格的成本是真实的一两天工时，收益是少返工几天的工时。下面三种情况，**先别写规格**：

1. **你还没想清楚要做什么。** 这是探索期，不是立项期。先手工做三五个样本，看共同规律，再从规律里反推规格。探索期写出来的规格，通常在第三个样本时就作废了。
2. **需求一个月变三次。** 变的是"内部实现"，写规格的收益仍然成立；变的是"到底做什么"，就先固定输入输出契约，暂缓细节。
3. **活儿是一次性的，而且不到半小时。** 直接写。给一次性脚本写规格是过度工程化（Over-engineering）——第一卷第 3 章讲过，这是在不需要的地方引入抽象带来的净负担。

反过来，**只要这个 Agent 会长期存在、会被别人用、或者失败代价高，规格就是必需品。** 三个月后你还要回来改它、却不记得当初为什么这么定，那就该写。

### 3.2 规格怎么腐坏

规格最大的风险不是写得不好，是**写着写着就和实现脱节了**。一份和实现脱节的规格比没有规格更危险：它让人误以为有验收依据，实际上是在自欺欺人。常见的四种腐坏：

| 腐坏形态 | 表现 | 后果 |
| --- | --- | --- |
| 判据过软 | "审查得准"这类句子留在成品规格里 | 测不出退化，改动全靠感觉 |
| 判据过严 | 判据变成"模型输出必须包含这句话" | 模型被优化成刷分，真实质量下降（评估污染，Evaluation Contamination） |
| 不做的事没写 | 每来一个需求就加一项 | 范围只涨不跌，没人说得清这个 Agent 干什么 |
| 规格沦为注释 | 代码写完了，规格是照着代码补的 | 顺序反了，规格失去约束力 |

对策只有一个：**让规格参与构建**。不靠自觉，靠机器检查——这正是本章工程产物的用意。判据写成断言后，改动一提交就跑一遍，人不看文档也能被拦下。

### 3.3 识别伪需求：哪些活儿不值得上 Agent

很多"我想做个 Agent"的需求，本质上是**工作流（Workflow）**或者**链式调用（Chain）**。用 Agent 的代价是：多一层不确定性、更多 token、更难复现、更多失效模式（第一卷第 20、25 章展开讲多 Agent 的协调开销与失效模式）。

三个问题问完，才有资格继续：

1. **流程能画成状态图且不需要回头吗？** 顺序和条件都能提前写死，那是工作流——在延迟、成本、稳定性上全面胜出。
2. **结果能自动判定对错吗？** 判据只能靠人读一遍才知道好不好，那自动化不了，Agent 只是在批量生产需要人返工的产物。
3. **出错代价可控吗？** 不可逆、需要审计、延迟敏感（第一卷第 1 章列出的四种场景），就老老实实用工作流。

**三个都是"否"才值得考虑 Agent。** 只要有一个是"是"，先用工作流往往更划算。

| 需求 | 真相 | 更好的做法 |
| --- | --- | --- |
| "自动生成周报" | 步骤固定：取数 → 算指标 → 套模板 → 发送 | 工作流 + 一次模型调用润色措辞 |
| "查数据库" | 查询是核心难点，不是"下一步做什么" | 受控查询工具 + 单次模型调用生成 SQL（第一卷第 8 章《工具调用契约》） |
| "分析日志" | 判断主观，判据不客观 | 先做检索与聚合，模型只负责写成人话 |
| "帮新人答疑" | 问题域固定，答案有标准来源 | 检索增强（RAG）够用，不需要自主决策 |

最后提醒一句：**"我觉得模型自己判断更聪明"不是理由。** 模型确实更聪明，但它每次判断都会花 token、都可能出错、都不能复现。流程确定的活儿给模型自由发挥空间，换来的不是更好的结果，是不可预测的结果。

### 3.4 取舍与代价

写一条成功判据并写成一个能跑的断言，大致是**从读懂到写出、再到跑通，一小时上下**——前提是判据本身写得好。一份 5 到 8 条判据的规格，加上工具清单和决策边界，一个工作日内可以完成。

而一次口径不对导致的返工——模型写完了、跑起来了、发现"准"的定义不是团队理解的那个"准"——通常以天计。这个交换比在多数团队里划算，但**判据超过 12 条以后维护成本就会超过收益**：没人愿意维护一份二十条的判据表，它会慢慢腐烂成装饰品。5 到 8 条，覆盖主要失败模式，就够了。

## 四、动手：最小可实现

### 4.1 本章的工程产物

`dragon-agent/specs/` 目录下三个文件：

| 文件 | 作用 |
| --- | --- |
| `SPEC_TEMPLATE.md` | 可填写的需求规格模板，九个章节，占位符用 `TODO` 标记 |
| `code-review-agent.spec.md` | 一份填好的完整范例：自建代码审查 Agent |
| `check_spec.py` | 规格检查器，纯标准库，把"规格可验收"变成一条退出码 |

为什么放在 `specs/` 而不是 `dragon_agent/` 包里？因为它**不是运行时代码**：不进 import 路径，不被任何模块依赖。它是上游工位——这和第一卷"下层不知道上层的存在"是同一条纪律：依赖方向不可逆，规格不该被下游 import。

### 4.2 模板长什么样

模板的九个章节与第二节一一对应。以"决策边界"为例，每一行都标注决策方，并且两类都必须有：

```markdown
### 决策边界

> 这一节决定 Agent 的可靠性上限。**判断"下一步做什么"可以交给 LLM，**
> **"能不能做""做得对不对"必须留给确定性代码。**
>
> 两类都必须有。全交给 LLM 是最常见的错误。

| 步骤 | 决策方 | 说明 |
| --- | --- | --- |
| TODO | LLM | TODO |
| TODO | 代码 | TODO |
```

成功判据则强制要求"验证方式"：

```markdown
### 成功判据

> 每条判据必须**可观测、可复现、能写成断言**。
> "审查得准确"不是判据，"每条高危发现都带 `文件路径:行号` 且行号落在实际改动行内"才是。
> 每条都要写清**怎么验证**，后面第 13 章会把它们接成回归测试。

- **C1**：TODO
  - 验证方式：TODO
```

这两处约束不是格式问题：**"每条判据都带验证方式"**直接决定了这份规格能不能在第 13 章变成回归测试——没有验证方式的判据接不成断言，只能靠人肉读。

### 4.3 检查器怎么工作

`check_spec.py` 是纯标准库实现，不联网、不依赖第三方包，clone 下来就能跑，把九项规则编成九道检查：

```python
#: 规格必须有的章节。顺序就是填写顺序。
REQUIRED_SECTIONS: tuple[str, ...] = (
    "任务定义",
    "输入输出契约",
    "可用工具清单",
    "决策边界",
    "成功判据",
    "失败定义与退出状态",
    "明确不做的事",
    "评测与观测",
    "预算与约束",
)

#: 退出状态取值必须与 dragon_agent/agent.py 的 AgentResult.status 完全一致。
CONTRACT_STATUSES: tuple[str, ...] = (
    "completed",
    "stopped_budget",
    "stopped_no_progress",
    "max_steps",
    "error",
)

#: 副作用三档：只读 / 可逆写 / 不可逆写。
SIDE_EFFECT_TIERS: tuple[str, ...] = ("只读", "可逆写", "不可逆写")
```

判据可验证性这条，是收集每条 `- **C<n>**` 开头的判据，看它后面有没有"验证方式："：

```python
CRITERION_RE = re.compile(r"^\s*[-*]\s+\*\*(C\d+)\*\*")
VERIFY_MARKER = "验证方式："
```

```python
    def check_criteria(self) -> CheckResult:
        res = CheckResult("S3", "成功判据可验证", "")
        lines = self.body("成功判据")
        criteria: list[tuple[str, bool, int]] = []
        current: tuple[str, int, list[str]] | None = None

        for idx, line in enumerate(lines):
            m = CRITERION_RE.match(line)
            if m:
                if current is not None:
                    criteria.append(self._finish_criterion(current))
                current = (m.group(1), idx, [line])
            elif current is not None:
                current[2].append(line)
        if current is not None:
            criteria.append(self._finish_criterion(current))
```

最后一道也最有价值：**不可逆写工具必须受控**。它把工具清单里的"不可逆写"一栏，和"明确不做的事"、"决策边界"两节交叉比对：

```python
        for name in irreversible:
            if name in nogo_text or name in code_guarded:
                continue
            res.findings.append(
                Finding("S6", "content", "error",
                        f"不可逆写工具「{name}」既没有写进「明确不做的事」，也没有在「决策边界」里由代码把持")
            )
```

命令行入口支持两种模式和机器可读输出：

```python
    parser.add_argument(
        "--mode",
        choices=("spec", "template"),
        default="spec",
        help="spec=检查成品规格（默认）；template=只检查模板结构",
    )
    parser.add_argument("--json", action="store_true", help="输出机器可读的 JSON")
```

退出码是它的接口契约：**0 = 通过，1 = 有错误，2 = 用法或读写错误**，可以直接挂到 CI 上当门禁。

对着一份故意写坏的规格跑，九道规则里有八道亮红灯并指出行号：

```text
  ❌ S1 章节齐全：8/9 个必需章节
       - [error] 缺少必需章节「评测与观测」
  ❌ S3 成功判据可验证：2 条判据，其中 0 条带验证方式

  ❌ S4 决策边界标注完整：LLM 2 行，确定性代码 0 行
       - [error] 决策边界里没有任何一行由 代码 决定——两类都必须有
  ❌ S5 工具清单规整：3 个工具，其中不可逆写 1 个

  ❌ S7 退出状态覆盖契约全集：4/5 个退出状态

  ❌ S8 明确不做的事非空：0 条不做的事
       - [error] 「明确不做的事」是空的——不写不做什么，后面所有加功能的争论都没有依据
```

退出码 1。

对着**模板本身**跑 `spec` 模式，会报出 41 个错误，其中 39 个是占位符残留；换成 `--mode template` 只查结构，结论变成"结构完整，可以开始填写"。模板本来就该是空的，用成品标准要求它是误用。

### 4.5 规格怎么被上下游调用

一份规格不是写完就完事的，它要在后面每一章里被兑现：

| 规格里的东西 | 落到哪个模块 | 兑现方式 |
| --- | --- | --- |
| 可用工具清单 | `tools.py` | 每行对应一个 `ToolSpec`，"副作用"决定 `side_effect` 与 `replayable` |
| 工具描述 | `tools.py` | 工具描述即提示词（Tool Description as Prompt），写坏了模型就调不对 |
| 成功判据 | `evaluation.py` | 变成 `EvalCase.expect`（必须出现）与 `forbid`（不得出现） |
| 明确不做的事 | `evaluation.py` | 变成 `forbid` 列表，越界输出判失败 |
| 失败定义 | `agent.py` | 就是 `AgentResult.status` 的五个取值 |
| 决策边界里的"代码"行 | `guardrails.py` | `before_tool` 收紧权限，模型绕不过去 |
| 预算与约束 | `config.py` | `max_steps` / `token_budget` / `cost_budget` / `timeout_s` |

对照 4.4 节跑出来的结果：这份规格有 7 条判据、5 个工具、决策边界里 LLM 决策 3 行、确定性代码 5 行、5 个退出状态、7 条"不做的事"。**这六个数字，就是后面第 2 章到第 13 章逐个要兑现的清单。**

## 五、开源实现对照

把"想要什么"写成可执行的规格，这件事别人也做过。下面几个是真实的开源项目，各有侧重。

### GitHub Spec Kit

- 仓库：<https://github.com/github/spec-kit>
- 许可证：MIT

它把规格驱动开发（Spec-Driven Development，SDD）做成了工具包：先写项目原则，再产出需求规格，然后出设计、拆任务、落地。**差异**：Spec Kit 管的是**一次开发流程的阶段产物**，产物是给人读、给 Agent 读的 Markdown；本章的模板管的是**单个 Agent 的能力边界与验收判据**，产物要被机器检查——判据能不能写成断言、不可逆写操作有没有被控住。它"先原则、再规格"的阶段划分也值得借鉴。

### OpenAI Evals

- 仓库：<https://github.com/openai/evals>
- 许可证：`LICENSE.md` 正文是 MIT，后面附了数据集使用条款（限制把评测数据用于竞品对比），因此 GitHub 把许可证识别为 Other 而不是 MIT。引用前请以仓库内该文件为准。

它把评测做成"注册表 + 可执行样例"。**差异**：Evals 从**评测**这一端出发，先有任务和打分器；本章从**需求**这一端出发，先有判据，再把它变成评测。没有判据的评测集，测出来的只是一个数字。

### promptfoo

- 仓库：<https://github.com/promptfoo/promptfoo>
- 许可证：MIT

用声明式 YAML 描述测试：给什么输入、期望输出包含什么、禁止出现什么、阈值多少，一条命令跑完整批。**差异**：promptfoo 的 YAML 是**测试用例**的形态——围绕 prompt 和模型写的；本章的模板是**需求**的形态——围绕 Agent 写，覆盖能力边界、工具清单、决策边界、失败定义。两者是接力关系：需求规格里的判据，就是 Evals 里那些断言的来源。

### Inspect AI

- 仓库：<https://github.com/UKGovernmentBEIS/inspect_ai>
- 许可证：MIT

把评测拆成任务、求解器、评分器、日志四层。**差异**："任务 + 评分器"的分离值得借鉴——对应本模板里"成功判据"和"验证方式"必须分开写的设计。判据是**要什么**，验证方式是**怎么测**，混着写，测试就会跟着判据漂。

### SWE-bench

- 仓库：<https://github.com/SWE-bench/SWE-bench>
- 许可证：MIT

用真实 GitHub issue 加上改动前后的代码库状态当任务集，成败由测试是否通过决定。**差异**：它示范了一件关键的事——**任务集必须包含"本来就该失败"的样本**，比如 4.4 节那份范例里放了 5 个"没有任何问题的干净 PR"用来测误报。没有这类样本，Agent 报什么都像是对的。

### DSPy

- 仓库：<https://github.com/stanfordnlp/dspy>
- 许可证：MIT

用声明式签名（Signature）描述输入输出字段，再自动优化提示与示例。**差异**：它证明了"把'要什么'写成结构化字段声明"比写散文提示词有效。本章的输入输出契约与工具清单就是更严格版本的签名声明——多出来的成功判据、失败定义、不做的事，是 DSPy 不管却决定 Agent 能否进生产的东西。

## 六、坑与检查清单

写规格，坑基本都集中在"写软了"和"漏了失败"上。下面这份清单可以直接拿去用。

### 立项前

- [ ] 一句话说清"为谁、解决什么问题"，说不清就先做三个样本再回来
- [ ] 问过三个问题：流程能画成状态图且不用回头吗？结果能自动判定对错吗？出错代价可控吗？三个都是"否"才继续

### 规格内容

- [ ] 输入有类型和必填项，输出给了结构化样例，而不是"返回一段文本"
- [ ] 每个工具都标了三档副作用：只读 / 可逆写 / 不可逆写
- [ ] 不可逆写工具，要么写进"明确不做的事"，要么在"决策边界"里由确定性代码把持并留人工确认
- [ ] 决策边界里 LLM 与确定性代码两类都存在，每一行都标了归属
- [ ] 每条成功判据都带"验证方式"，且不依赖 LLM 判定
- [ ] 判据总数控制在 5 到 8 条，不是 2 条也不是 20 条
- [ ] 失败定义覆盖全部五个退出状态，每个都写了触发条件和调用方动作
- [ ] "明确不做的事"非空，且区分了"现在不做"和"永远不做"
- [ ] 预算写明了 `max_steps`、`token_budget`、`cost_budget`

### 常见坑

- [ ] **把功能清单当规格**：写了"要支持 A、B、C 功能"，却没一条能判断做没做到
- [ ] **判据里混进 LLM 判定**：判据要能被确定性断言接住，否则回归测试没法离线跑
- [ ] **只写成功不写失败**：Agent 一定会失败，不定义失败就是把失败留给调用方猜
- [ ] **"暂不支持"当成"不做"**：前者是待办，后者才是边界
- [ ] **规格写在代码之后**：顺序反了，规格就变成注释，不再有约束力

### 收尾

- [ ] `python specs/check_spec.py specs/<你的规格>.spec.md` 退出码为 0
- [ ] 规格已提交进版本库，和代码在同一次提交或紧邻的提交里

## 七、小结与延伸阅读

这一章没有写任何 Agent 代码，它产出的东西是后面十三章的验收依据。要点回顾：

1. **规格的价值在于可验收。** "审查得准"不是判据，"每条 high 发现带 file:line 且行号落在改动行集合内"才是。写不出断言的判据描述的是期待。
2. **决策边界是可靠性的来源。** 要判断力的给模型，要准确性的给代码，要责任的不给任何自动环节。不可逆的写操作，能移出动作空间就别留在里面。
3. **失败必须提前定义。** 五个退出状态与 `AgentResult.status` 一一对应，少一个调用方就要靠猜。
4. **"不做的事"是范围管理工具。** 它把"能不能顺便做"从技术争论变成范围判断。
5. **规格会腐坏，所以要让机器来查。** `check_spec.py` 把九项规则变成九道检查，退出码即契约，可直接挂 CI。

下一章开始搭工程骨架：`p02-skeleton` 讲分层约定、配置管理、错误分类和日志规范。本章的规格文件会在那里变成第一批真实的模块。
